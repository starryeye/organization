# 운영

> 기준 커밋: 44147b3 (ops-readiness, main 에 머지됨). 코드가 바뀌면 이 문서도 함께 고친다.
> 읽기 전에: [개요](01-개요.md), [용어집](02-용어집.md), [아키텍처](03-아키텍처.md)

두 앱을 띄우고 지켜보는 데 필요한 것을 모았다. 설정, 시작할 때 일어나는 일, 지표와 경보, 헬스 체크, 한 번의 비용, 로그와 추적, 여러 대 띄우기의 전제, 로컬 실행이다. 장애가 났을 때 무엇을 하는지는 [12 장애와 복구](12-장애와-복구.md), 개발과 시험은 [14 개발 가이드](14-개발-가이드.md)에 있다.

> **운영에 넣기 전에 알아 둘 것.** 이 저장소의 `application.yml` 은 로컬 개발용 값이다. 운영 프로필(`prod`)은 그 위에 얹혀 로그와 운영 보호 값을 바꾼다 — 테이블·장부를 만들지 않고, 테이블의 삭제 보호·PITR 을 요구하고, LDAP 바인드 비밀번호를 환경 변수로 받고 `ldaps://` 를 요구한다([2.5](#25-prod-프로필)). **설정 실수는 기동 때 멈춘다**([2.1](#21-순서와-실패)). `prod` 가 덮지 않는 DynamoDB 주소와 OpenFGA·LDAP 의 주소·계정은 로컬 값 그대로라 운영에 맞게 따로 덮어써야 한다([1.8](#18-운영-배포-전에-바꿀-값)). 인증이 없다는 점은 [09 관리 API](09-관리-API.md#10-인증이-없다)와 [13 한계와 알려진 문제](13-한계와-알려진-문제.md)에 있다.

## 1. 설정

### 1.1 읽는 법

설정은 스프링 부트 속성이다. 앱마다 `src/main/resources/application.yml` 이 있고(`app-ldap`, `app-scim`), `prod` 프로필은 `application-prod.yml` 을 더한다. 시험은 `application-test.yml`(시험 클래스패스에만 있다)이 값을 되돌린다.

- 덮어쓰는 법은 부트의 보통 방법이다 — 환경 변수(`SYNC_CRON`, `DYNAMODB_TABLE_NAME` 처럼 대문자·밑줄), 명령줄 `--sync.cron=…`, 프로필 파일.
- 값을 읽는 클래스는 다섯이다. `DynamoDbProperties`(`dynamodb.*`, storage-dynamodb), `OpenFgaProperties`(`openfga.*`, authz-openfga), `LdapProperties`(`ldap.*`, connector-ldap), `SyncProperties`(`sync.*`, app-ldap), `ScimSyncProperties`(`sync.*`, app-scim). 두 `sync.*` 클래스는 접두사만 같고 앱마다 따로다.
- 아래 표의 **기본값**은 셋까지 나란히 적는다. "클래스" 는 속성 클래스에 적힌 값, "yml" 은 앱의 `application.yml` 값, "prod" 는 `application-prod.yml` 값이다. 하나만 적었으면 모두 같거나 yml 에 없다. 다른 곳은 굵게 표시했다.
- 앱이 읽지 않는 키는 무시된다. 예를 들어 app-scim 에 `ldap.*` 나 `sync.deletion-guard.*` 를 적어도 아무 일이 없다.
- `Duration` 은 `30m`, `10s`, `150s`, `2m` 처럼 적는다. cron 은 스프링의 여섯 칸(초 분 시 일 월 요일)이다. **값을 `-` 로 주면 그 스케줄이 꺼진다.**
- cron 은 JVM 기본 시간대로 해석한다(코드가 `zone` 을 주지 않는다). 컨테이너의 시간대가 UTC 가 아니면 하루 창 "03~08시" 는 UTC 03~08시가 아니다. 하루 1회 표지의 날짜만 UTC 로 센다([하루 1회 표지](02-용어집.md#하루-1회-표지)) — 그래서 하루 창이 UTC 자정을 넘지 않아야 한다([1.5](#15-sync)).

| `dynamodb.create-table-on-startup` | 클래스 `false` / yml **`true`** / prod `false` | 시작할 때 테이블이 없으면 만든다. 꺼져 있는데 없으면 기동을 멈춘다. 켜든 끄든 테이블은 늘 확인한다([2.2](#22-테이블)) | 운영은 `false` 다 — 이름 오타가 빈 테이블을 새로 만들어 신원이 갈라지지 않게. 처음 설치라면 `true` 로 한 번 띄우거나 미리 만든다 |

| `dynamodb.api-call-attempt-timeout` | `10s` (yml 없음) | AWS SDK 의 시도 한 번 한도. 매달린 연결을 끊는다 | 규모 시험의 DynamoDB Local 이 부하 아래에서 느려 넉넉히 잡았다 |
| `dynamodb.api-call-timeout` | `60s` (yml 없음) | SDK 재시도를 포함한 호출 하나의 한도. 스로틀이 이어져도 호출 하나가 이보다 오래 매달리지 않는다. 재시도 정책 자체는 SDK 기본값이다 | 스냅샷 묶음(약 350KB)을 써야 해서 넉넉히 잡았다 |
| `dynamodb.snapshot-retention-days` | `7` | 튜플 스냅샷 보관 일수. 지나면 하루 1회 정리가 지운다. 최신은 지우지 않는다 | 늘리면 스냅샷이 쌓인다 — 10만 명 규모에서 한 벌이 압축 약 6MB 다([5절](#5-한-회차의-비용)) |
| `dynamodb.syncrun-retention-days` | `30` | 실행 기록 보관 일수(테이블 TTL). 읽기는 이번 달과 지난달만 한다 | 30일보다 늘려도 이전 달 기록은 관리 API 로 찾히지 않는다([04](04-데이터-모델.md#5-ttl)) |
| `dynamodb.audit-retention-days` | `30` | 감사 이력 보관 일수(테이블 TTL) | 늘리려면 `syncrun-retention-days` 도 함께 늘린다 — 이력의 원인 회차가 먼저 사라지면 거슬러 갈 곳이 없다 |
| `dynamodb.lock-ttl` | `30s` (yml 없음) | 변경 락 리스 길이 | SCIM 쓰기 p99 보다 한참 길어야 한다. 짧으면 일하는 중에 만료된다. 서버 시계 차이의 허용 폭도 이 값으로 정해진다([7절](#7-여러-대-띄우기의-전제)) |
| `dynamodb.lock-acquire-timeout` | `3s` (yml 없음) | **SCIM 쓰기만.** 락을 잡으려 기다리는 한도(서버 안 줄 + 다른 서버와 겨루기). 넘으면 503. 획득 시도 하나는 `min(남은 한도, 1초)`(하한 200ms)에서 끊는다 — 스로틀로 매달린 시도 하나가 한도를 다 먹지 않게([08](08-동시성과-작업.md#43-다른-서버와-겨루기)) | 재적재·동기화는 보지 않는다(기다리지 않고 409) |
| `dynamodb.lock-renew-interval` | `10s` (yml 없음) | 락을 쥔 동안 리스를 갱신하는 주기. SCIM 쓰기·재적재·동기화 모두 | `lock-ttl` 보다 충분히 짧게. 마지막 성공에서 주기 두 번 안에 못 하면 멈춘다 |

`dynamodb.lock-*` 셋과 `dynamodb.api-call-*` 둘은 yml 에 없다. 클래스 기본값이 그대로 쓰인다. 락 동작은 [08 동시성과 작업](08-동시성과-작업.md)에 있다.

### 1.5 `sync.*`

cron·기한의 기본값은 **속성 클래스에만 있다.** 스케줄러가 `@Scheduled(cron = "#{@syncProperties.cron}")` 처럼 SpEL 로 속성 빈을 읽는다(빈 이름 `syncProperties`·`scimSyncProperties` — `UseCaseConfig`·`ScimUseCaseConfig` 가 올린다). 그래서 두 앱의 yml 에는 cron·기한 키가 없고, 키가 없어도 뜬다. yml 은 덮어쓸 때만 쓴다. `-` 를 주면 그 작업이 꺼진다.

**app-ldap** (`SyncProperties`)

| 키 | 기본값 | 뜻 | 바꿀 때 |
|---|---|---|---|
| `sync.cron` | `0 0 * * * *` (yml 없음) | 정기 [동기화](02-용어집.md#동기화) 주기. 매시 정각 | 회수 목표는 "다음 정각 + 회차 시간" 이다. 더 빠르게 하면 매 회차의 읽기 비용이 그만큼 자주 든다([5절](#5-한-회차의-비용)). `-` 는 끈다 |
| `sync.purge-cron` | `0 0 4-8 * * *` (yml 없음) | 만료 스냅샷 정리(하루 1회 표지 `ldap-purge`). 하루 창(04~08시) 안에서 매시 시도하고, 성공한 뒤의 시도는 표지를 보고 건너뛴다 | 끄면 스냅샷이 끝없이 쌓인다(테이블 TTL 을 쓰지 않는다). 창 규칙은 아래 |
| `sync.job-timeout` | `30m` (yml 없음) | 동기화·재적재 한 번의 전체 [기한](02-용어집.md#기한). 넘으면 `FAILED`("기한 초과 — 30분"). 하루 1회 표지의 임대(잡은 때 + 이 값 + 5분)에도 쓴다 | 10만 명 재적재를 수 분으로 추정해 넉넉히 잡았다. LDAP 재시도 창(최대 약 6분)과 읽기 대기도 이 안에 든다 |
| `sync.deletion-guard.enabled` | `true` | [삭제 가드](02-용어집.md#삭제-가드) 사용 | 끄면 디렉터리의 큰 부분이 빠진 그림이 장부를 그대로 지운다(사람 소속이 하나도 없는 그림은 가드와 상관없이 데이터 오류로 멈춘다 — [05](05-LDAP-동기화.md)) |
| `sync.deletion-guard.threshold-ratio` | `0.3` | 지울 수 ÷ [기준 수](02-용어집.md#기준-수) 가 이 값을 **넘으면** 걸린다 | 큰 개편이 잦으면 올린다. 대신 사람 확인(`force`)이 줄어든다 |
| `sync.deletion-guard.min-baseline` | `10` | 기준 수가 이 값 미만이면 가드를 보지 않는다 | 작은 조직도 시험용 |

`sync.deletion-guard.*` 셋은 yml 에도 같은 값으로 적혀 있다.

**app-scim** (`ScimSyncProperties`)

| 키 | 기본값 | 뜻 | 바꿀 때 |
|---|---|---|---|
| `sync.archive-cron` | `0 0 3-8 * * *` (yml 없음) | 하루 1회 [아카이빙](02-용어집.md#아카이빙)(하루 1회 표지 `scim-archive`). 하루 창(03~08시) 안에서 매시 시도한다. `SUCCEEDED` 가 아니면(`FAILED`, 재적재 중이라 `ABORTED`) 다음 정각에 다시 돌고, 성공한 뒤의 시도는 건너뛴다 | 끄면 드리프트 게이지가 갱신되지 않고 [남은 회수](02-용어집.md#남은-회수)가 지워지지 않는다. 경보 식의 창(32시간)이 이 창과 기한에서 셈한 값이다 — 바꾸면 다시 센다([3.6](#36-경보-예)) |
| `sync.purge-cron` | `0 0 4-8 * * *` (yml 없음) | 만료 스냅샷 정리(`scim-purge`). 창 규칙은 위와 같다 | 끄면 스냅샷이 쌓인다 |
| `sync.job-timeout` | `30m` (yml 없음) | 재적재·아카이빙 한 번의 기한. 넘으면 `FAILED`("기한 초과 — 30분"). 하루 1회 표지의 임대에도 쓴다 | |

**하루 창의 규칙.** 하루 1회 작업(app-ldap 정리, app-scim 아카이빙·정리)은 그날 표지가 `DONE` 이 될 때까지 창 안에서 매시 시도한다. 정리는 오류 없이 끝나면, 아카이빙은 `SUCCEEDED` 여야 성공이다([08 — 하루 1회 표지](08-동시성과-작업.md#6-하루-1회-표지)).

- **창은 UTC 자정을 넘지 않아야 한다.** 표지의 날짜가 UTC 라 그래야 한 창이 한 날로 묶인다. cron 은 서버 시간대로 돈다. 기본 창은 서버가 UTC 든 KST 든 이 조건을 지킨다(KST 03~08시는 전날 UTC 18~23시). 다른 시간대에서 창을 바꿀 때 지킨다. 어겨도 정확성은 깨지지 않는다 — 창이 두 날로 갈려 하루에 두 번 돌 수 있을 뿐이다(정리는 멱등이고, 아카이빙은 스냅샷 하나와 `BatchCheck` 를 더 쓴다).
- **아카이빙에는 기한이 있다**(`sync.job-timeout`). 정리에는 기한이 없다.

### 1.9 시험 프로필이 되돌리는 값

`application-test.yml`(`app-ldap/src/test/resources`, `app-scim/src/test/resources`)은 시험에서만 쓰인다. 운영과 다른 값을 알아 두면 시험 로그와 설정을 읽을 때 헷갈리지 않는다.

| 키 | 시험 값 | 까닭 |
|---|---|---|

## 2. 시작

### 2.1 순서와 실패

앱이 뜨면서 일어나는 일이다. 일은 모두 스프링 컨텍스트가 빈을 만드는 중에 한다. **설정 실수는 여기서 멈춘다** — 엉뚱한 테이블·장부에 조용히 붙거나 틀린 비밀번호로 바인드하지 않는다.

| 순서 | 무엇이 | 하는 일 | 실패하면 |
|---|---|---|---|
| 1 | `DynamoDbAsyncClient` | 리전과 시간 한도(시도 10초·호출 60초). `dynamodb.endpoint` 가 있으면 그 주소와 가짜 자격 증명(`local`/`local`), 없으면 SDK 기본 자격 증명 제공자 | 자격 증명 문제는 첫 호출에서 드러난다 |
| 2 | `TableInitializer.afterPropertiesSet` | 테이블 이름이 비었는지 보고, 테이블을 **늘** 확인한다([2.2](#22-테이블)) | 이름이 비었거나, 없는데 생성이 꺼져 있거나, 모양이 다르거나, 보호가 꺼져 있으면 **앱이 뜨지 않는다**(`block()`) |
| 3 | `StoreBootstrapper` 생성자 | `openfga.store-name` 이 비었는지 본다 | 비었으면 앱이 뜨지 않는다 |
| 4 | `OpenFgaStoreInitializer.afterPropertiesSet` | store 를 이름으로 찾고(생성이 켜져 있으면 없을 때 만든다), 인가 모델을 맞춘다([2.3](#23-장부)) | store 가 없고 생성이 꺼져 있으면(`StoreNotFoundException`) **앱이 뜨지 않는다**. OpenFGA 에 닿지 못한 것 등 그 밖의 실패는 경고만 남기고 **계속 뜬다** |
| 5 | `LdapConfig`(app-ldap) | `ldapContextSource`·`ldapMappingStrategy` 빈을 만들며 전략 이름·바인드 비밀번호·TLS 를 검사한다([1.4](#14-app-ldap--ldap)) | 앱이 뜨지 않는다 |
| 6 | 스케줄러·`LastSuccessGauge` | `@Scheduled` 등록. `LastSuccessGauge`(app-ldap)는 시작 직후 한 번 돌고 1분마다 돈다 | — |

- 2~5 사이의 순서는 스프링이 빈 의존으로 정한다. 어느 것이든 멈추면 앱이 뜨지 않는다.
- 정기 작업(동기화, 아카이빙, 정리)은 기동 직후에 돌지 않는다. 다음 cron 시각에 처음 돈다. 새 테이블의 첫 LDAP 회차는 기준선이 없어 [장부 맞추기](02-용어집.md#장부-맞추기)를 한다([기준선 상태](02-용어집.md#기준선-상태)) — 이때 장부에 목표 밖의 줄이 있었다면 삭제 가드가 걸릴 수 있다. 확인한 뒤 `POST /admin/sync/full?force=true` 로 넘긴다([09](09-관리-API.md#92-app-ldap)).
- 같은 앱을 여러 대 처음 띄울 때는 한 대가 테이블을 만들고 뜬 뒤에 나머지를 띄운다. `TableInitializer` 는 `DescribeTable` 의 `ResourceNotFoundException` 만 "없음" 으로 읽어 만들기로 넘어가므로, 동시에 만들려는 경쟁은 처리하지 않는다. 남이 만드는 중(ACTIVE 가 아님)인 테이블은 ACTIVE 를 기다린 뒤 검사하지만, 만든 대는 ACTIVE 를 본 뒤에야 TTL·PITR 을 켜므로 그보다 먼저 깨어난 대는 모양(TTL)·보호 검사에서 멈출 수 있다 — 그때는 테이블을 지우지 말고 만든 대가 뜬 뒤 다시 띄운다(코드로 읽은 것이며 실제 AWS 로 실행해 보지는 않았다).

### 2.2 테이블

`TableInitializer.ensureTable`(storage-dynamodb)이 한다. `create-table-on-startup` 과 상관없이 늘 이 순서다.

1. `DescribeTable`.
2. **없으면**
   - 생성이 꺼져 있으면 기동을 멈춘다: `DynamoDB 테이블 <name> 이 없다 — 처음 설치라면 dynamodb.create-table-on-startup=true 로 한 번 띄우거나 미리 만든다`.
   - 켜져 있으면 만든다. 키 `PK`/`SK`, `PAY_PER_REQUEST`, GSI1·GSI2·GSI3. 테이블이 ACTIVE 가 되기를 기다리고 `expiresAt` 에 TTL 을 켠다.
   - `require-protection` 이면 삭제 보호를 켠 채 만들고, 그 뒤 PITR 을 켠다. 실제 AWS 는 막 만든 테이블의 PITR 요청을 한동안 `ContinuousBackupsUnavailableException` 으로 거절한다고 알려져 있어(확인하지 못했다) 그 예외만 5초마다 2분 안에서 다시 시도한다. 그래도 못 켜면 `테이블은 만들었으나 PITR 을 켜지 못했다 — 콘솔·CLI 로 켠 뒤 다시 띄운다` 로 멈춘다. 그 밖의 PITR 실패(권한 없음 등)도 같은 문구로 멈추고 원인은 예외에 남는다. 테이블은 남으므로, 다음 기동은 아래 보호 확인에서 같은 처방을 다시 보인다.
3. **있으면** 만들지 않고 확인한다. 상태가 ACTIVE 가 아니면(함께 뜬 다른 대나 배포 직전의 IaC 가 막 만드는 중) 먼저 INFO `DynamoDB 테이블 '<name>' 이 <상태> 이다 — ACTIVE 가 되기를 기다린 뒤 확인한다` 를 남기고, 만들기와 같은 대기로 ACTIVE 를 기다린 뒤 다시 읽은 설명으로 확인한다 — 만드는 중인 테이블은 TTL 이 꺼짐으로 보여 모양 검사가 막 만든 테이블에 "다시 만들어야 한다" 로 멈추기 때문이다. "없음" 은 첫 `DescribeTable` 에만 해당한다.
   - **모양.** GSI1·GSI2·GSI3 이 있고 키가 맞는지, GSI2 프로젝션이 `INCLUDE` 이고 비키 속성이 `userName`·`displayName`·`active`·`externalId` 인지, TTL 이 `expiresAt` 에 `ENABLED`(켜는 중인 `ENABLING` 포함)인지 본다(`DescribeTimeToLive`). 다르면 다른 점을 모두 적어 `테이블 '<name>' 의 모양이 이 버전과 다르다 — <다른 점> — 테이블을 다시 만들어야 한다` 로 멈춘다. 운영 배포 전이라 옛 모양의 테이블은 이관하지 않는다.
   - **보호.** `require-protection` 이면 삭제 보호(`DescribeTable`)와 PITR(`DescribeContinuousBackups`)이 둘 다 켜져 있어야 한다. 아니면 꺼진 것을 적어 `테이블 '<name>' 의 보호가 꺼져 있다: 삭제 보호, PITR — 콘솔·CLI 로 켠 뒤 다시 띄운다` 로 멈춘다. 있는 테이블의 보호는 앱이 켜 주지 않는다.
   - **복원본.** PITR 로 복원한 테이블(설명에 `restoreSummary` 가 있다)이면 WARN 을 한 번 남기고 뜬다: `PITR 로 복원한 테이블이다 — 장부보다 낡은 기준선일 수 있어 재적재를 권한다(SCIM 은 mode=tuples)`. 자동으로 재적재하지는 않는다([12 — PITR 로 복원했다](12-장애와-복구.md#37-pitr-로-복원했다)).

손으로 미리 만드는 테이블은 위 모양을 갖춰야 한다 — GSI1(`ALL`), GSI2(`INCLUDE` — 위 네 속성), GSI3(`KEYS_ONLY`), `expiresAt` TTL([04](04-데이터-모델.md#3-dynamodb-단일-테이블)). 멈췄을 때의 처방은 [12 — 기동이 멈췄다](12-장애와-복구.md#36-기동이-멈췄다--테이블이-없거나-모양보호가-다르다)에 있다.

### 2.3 장부

`StoreBootstrapper.resolveStore` 가 한다([04](04-데이터-모델.md#장부를-찾고-만드는-법)). 쓰기·`Check`·장부 훑기가 모두 이것을 거친다.

1. `openfga.store-name` 으로 store 를 모든 페이지에서 찾는다.
2. 같은 이름이 둘 이상이면 멈춘다. 사람이 정리해야 한다.
3. 없으면, `openfga.create-store` 가 켜져 있을 때만 만든다. 동시에 처음 뜬 인스턴스끼리는 가장 먼저 만든 것으로 모이고, 늦게 만든 쪽은 자기 것을 지운다. 꺼져 있으면 `StoreNotFoundException` 이다: `OpenFGA store <name> 이 없다 — 처음 설치라면 openfga.create-store=true 로 한 번 띄운다`.
4. 인가 모델을 맞춘다. 최신 모델(`ReadLatestAuthorizationModel`)을 읽어 `schema_version`·`type_definitions`·`conditions` 를 견주고, 같으면 쓰지 않는다(INFO `OpenFGA 인가 모델이 최신과 같아 쓰지 않았다`). 모델이 없거나, 다르거나, 읽기가 실패하면 쓴다 — 견주지 못하면 쓰는 쪽이 안전하다. 그래서 기동마다 같은 모델 버전이 쌓이지 않는다. 성공하면 그 프로세스는 store 번호를 기억한다.

- **시작 때 store 가 없다고 판명되면**(목록 조회는 성공했는데 그 이름이 없고 생성이 꺼져 있으면) 앱이 뜨지 않는다.
- **시작 때 OpenFGA 에 닿지 못하면** 경고만 남기고 뜬다. 실패는 기억하지 않으므로 이후의 쓰기·`Check` 가 다시 시도한다. 그 사이 헬스의 `openFga` 항목이 DOWN 이다. 나중에 닿아서 store 가 없다고 판명되면 같은 문구의 `StoreNotFoundException` 이 그 요청·회차를 실패시킨다 — 일시 장애가 아니라 설정 오류라 SCIM 은 503 이 아니라 500 이다.

### 2.4 종료

앱이 내려갈 때 도는 [회차](02-용어집.md#회차)는 `FAILED`("서버 종료로 중단")로 기록되고 락을 반납한다. 최대 10초 기다린다. 그 안에 못 마치면 기록이 `RUNNING` 으로 남았다가 [죽은 기록 닫기](02-용어집.md#죽은-기록-닫기)가 닫는다 — 다음에 락을 잡는 회차가 나이와 상관없이, 또는 동기화·재적재·아카이빙 어느 것이든 시작할 때 기한 + 10분이 지난 것을([08](08-동시성과-작업.md#56-죽은-기록-닫기)). 그래서 app-scim 도 다음 하루 창의 아카이빙이 닫는다.

### 2.5 `prod` 프로필

`SPRING_PROFILES_ACTIVE=prod`(또는 `--spring.profiles.active=prod`)로 켠다. `application-prod.yml` 은 로컬 `application.yml` **위에 얹힌다** — 덮지 않는 값은 로컬 값 그대로다.

| 키 | 기본 프로필 | `prod` | 앱 |
|---|---|---|---|
| `logging.structured.format.console` | 없음 — 평문 | `ecs` — JSON 한 줄(Elastic Common Schema, 스프링 부트 3.4 부터 내장) | 둘 다 |
| `logging.level.dev.starryeye.organization` | `DEBUG` | `INFO` | 둘 다 |
| `dynamodb.create-table-on-startup` | `true` | `false` — 없으면 멈춘다 | 둘 다 |
| `dynamodb.require-protection` | `false` | `true` — 삭제 보호·PITR 이 꺼져 있으면 멈춘다 | 둘 다 |
| `openfga.create-store` | `true` | `false` — 없으면 멈춘다 | 둘 다 |
| `ldap.bind-password` | `adminpassword` | `${LDAP_BIND_PASSWORD}` — 기본값 없이 환경 변수 | app-ldap |
| `ldap.require-tls` | `false`(클래스) | `true` — `ldaps://` 가 아니면 멈춘다 | app-ldap |

`prod` 가 덮지 않는 값 — `dynamodb.endpoint`(`http://localhost:8000`), `openfga.api-url`, `ldap.url`·`base-dn`·`bind-dn` 등 — 은 로컬 값 그대로라 환경마다 적는다. 특히 `dynamodb.endpoint` 를 비우지 않으면 그 주소에 가짜 자격 증명으로 붙는다. app-ldap 은 `ldap.url` 을 `ldaps://` 운영 주소로 덮어야 뜬다(로컬 값 `ldap://localhost:1389` 로는 `require-tls` 에 멈춘다). 헬스 세부(`when-authorized`)와 노출 엔드포인트는 로컬 yml 부터 운영 값이다. 수집 백엔드가 정해지면 `gelf`·`logstash` 로 바꿀 수 있다고 yml 주석이 적는다.

### 2.6 IAM 권한

앱이 부르는 DynamoDB API 다. GSI 를 Query 하므로 리소스에 테이블과 그 인덱스(`table/<이름>/index/*`)를 함께 준다([루트 README.md](../../README.md#운영-배포)).

| 언제 | 권한 |
|---|---|
| 늘 — 읽기·쓰기 | `GetItem`·`PutItem`·`UpdateItem`·`DeleteItem`·`Query`·`BatchGetItem`·`BatchWriteItem` |
| 늘 — 기동 검사·헬스 | `DescribeTable`·`DescribeTimeToLive` |
| `require-protection` 일 때 | `DescribeContinuousBackups` |
| 처음 생성할 때만(`create-table-on-startup=true`) | `CreateTable`·`UpdateTimeToLive`, `require-protection` 이면 `UpdateContinuousBackups` 도 |

## 3. 지표

### 3.1 노출과 이름

- 노출: `GET /actuator/prometheus`(Prometheus), `GET /actuator/metrics`. 두 앱 모두 `management.endpoints.web.exposure.include: health,info,metrics,prometheus` 다. 인증은 없다.
- 이름: Micrometer 이름의 점을 밑줄로 바꾼 것이 Prometheus 이름이다. 카운터는 `_total` 이 붙고 타이머는 `_seconds_count`·`_seconds_sum`·`_seconds_max`, 게이지는 그대로다. 루트 README.md 의 경보 식이 `sync_last_success{source="LDAP"}`, `scim_archive_drift{kind}`, `scim_archive_drift_observed`, `scim_revocations_total{kind}` 를 쓴다. 나머지는 이 규칙에서 따른 이름이며 실제 출력을 보지는 못했다.
- `sync.*`, `scim.*`(게이지와 `scim.revocations` 제외), `audit.write.failures` 는 **처음 올라갈 때 만들어진다**(`registry.counter(...).increment()` 호출 시). 한 번도 일어나지 않은 일의 계열은 아예 없다. 경보 식이 계열이 없는 경우를 따로 다루는 이유다. 게이지(`sync.last.success`, `scim.archive.drift*`)와 `authz_*` 카운터 넷은 시작할 때 등록된다(`authz_*` 는 0 으로 보인다).
- `scim.revocations` 의 계열 넷(`kind` 마다)은 **기동 때 0 으로 만들어 둔다**(`ScimSyncMetrics` 생성자). Prometheus `increase()` 는 새 계열의 첫 값을 증가로 세지 않으므로, 첫 회수 때 만들면 기동 직후의 첫 대량 회수가 증가량 0 으로 보이기 때문이다.

### 3.2 app-ldap

`SyncMetrics.record`(app-ldap)가 [회차](02-용어집.md#회차)가 끝날 때 부른다. 정기 동기화는 스케줄러가, 수동 동기화·재적재는 컨트롤러가 부른다. `finishedAt` 이 없는 기록은 무시한다.

| 지표 | 종류 | 태그 | 뜻 |
|---|---|---|---|
| `sync.duration` | Timer | `source`, `trigger`, `status` | 회차 하나의 소요 시간(시작~끝). `status` 는 `SUCCEEDED`·`PARTIAL`·`ABORTED`·`FAILED` |
| `sync.tuples.written` | Counter | `source` | 쓴 튜플 수의 합 |
| `sync.tuples.deleted` | Counter | `source` | 지운 튜플 수의 합 |
| `sync.tuples.failed` | Counter | `source` | 실패한 튜플 수의 합. 영구히 거절되는 줄이 있으면 매 회차 오른다 |
| `sync.guard.aborted` | Counter | 없음 | `ABORTED` 로 끝난 회차 수. app-ldap 에서 `ABORTED` 는 [삭제 가드](02-용어집.md#삭제-가드)가 걸린 회차(비활성 회수만 반영한 회차 포함)다 |
| `sync.last.success` | Gauge | `source=LDAP` | 반영까지 마친 마지막 LDAP 회차의 끝난 시각(epoch 초). 아래 |

`LastSuccessGauge`(app-ldap)는 `sync.last.success` 를 낸다.

- **`SUCCEEDED` 와 `PARTIAL` 만 센다.** 영구히 거절되는 줄 하나 때문에 매 회차가 `PARTIAL` 이어도 회수는 계속 나간다. 그것을 멈춤으로 울리면 경보가 늘 울린다. `ABORTED` 와 `FAILED` 는 세지 않는다 — 그 동안이 경보가 울려야 하는 때다.
- 값은 DynamoDB 의 실행 기록에서 1분마다 읽는다. 어느 인스턴스를 보든·재시작을 넘어서도 같다. 최신 기록부터 읽다 처음 만나는 `SUCCEEDED`·`PARTIAL` 에서 멈춘다.
- **값이 없으면 `NaN`** 이다. 성공·부분 회차가 기록에 없을 때(처음 뜬 직후, 보관 기간을 지났을 때)와 기록을 읽지 못했을 때다. 읽지 못했는데 지난 값을 쥐고 있으면 "방금 성공" 으로 보이기 때문에 비운다. 읽기 실패는 WARN 한 줄이다.
- 이 읽기는 인스턴스마다 1분에 한 번 이번 달 파티션의 첫 쪽(최대 1MB)을 읽는다. 읽기 비용이 문제가 되면 이 읽기와 실행 기록 하나를 찾는 `findById` 부터 본다(`DynamoDbSyncRunRepository` 주석).

app-ldap 은 락 지표를 내지 않는다(`LockObserver.NOOP`).

### 3.3 app-scim

`ScimSyncMetrics`(app-scim)가 콜백 다섯을 구현한다 — core 의 `DriftObserver`·`ArchiveDriftObserver`·`LockObserver`·`RevocationObserver` 넷과 connector-scim 의 `IgnoredAttributeObserver` 하나다.

| 지표 | 종류 | 태그 | 뜻 |
|---|---|---|---|
| `scim.drift.detected` | Counter | `kind=extra`\|`missing` | SCIM 쓰기가 [Check 기준선](02-용어집.md#check-기준선)과 현재상태가 요구하는 튜플을 견주다 본 [드리프트](02-용어집.md#드리프트)의 줄 수. `extra` 는 있어선 안 될 튜플(예: 퇴사자의 남은 권한), `missing` 은 있어야 하는데 빠진 튜플. 요청이 건드린 범위만 본다. 아카이빙의 남은 회수 복구는 이 카운터를 올리지 않는다 |
| `scim.lock.wait` | Timer | 없음 | 변경 락을 잡거나 포기하기까지 기다린 시간(서버 안 줄에서 기다린 시간 포함). 꼬리가 길어지면 `dynamodb.lock-acquire-timeout` 을 다시 본다 |
| `scim.lock.contended` | Counter | 없음 | 한 번이라도 다른 쪽에 밀린 획득. 꾸준히 오르면 변경 락 하나로 직렬화하는 비용이 실제로 든다는 뜻이다 |
| `scim.lock.lease_lost` | Counter | 없음 | 쥐고 있어야 할 [리스](02-용어집.md#리스)를 잃었다([리스 상실](02-용어집.md#리스-상실)). 응답에 흔적이 없거나(반납 실패) 503 뿐이라 이 카운터가 없으면 로그를 읽을 때까지 모른다. 0 이 아니면 락이 TTL 만큼 묶였거나 두 인스턴스가 겹쳤을 수 있다 |
| `scim.patch.ignored` | Counter | `attribute` | 직원 PATCH 가 받아서 버린 RFC 속성. 태그는 RFC 정규 이름이나 `other` 뿐이다(요청 문자열이 태그가 되지 않는다). 꾸준히 오르는 이름이 있으면 IdP 매핑에서 빼도 된다는 신호다 |
| `scim.archive.drift` | Gauge | `kind=extra`\|`missing` | 마지막 [아카이빙](02-용어집.md#아카이빙)이 현재상태 전체와 `Check` 결과를 비교해 센 드리프트 줄 수. **쌓는 값이 아니라 마지막 비교의 값**이다. 시작 값은 0. 복구 전 비교 시점의 수라서, 한 번 보인 `extra` 는 대개 이미 지웠고 다음 아카이빙에서 0 으로 내려온다 |
| `scim.archive.drift.observed` | Gauge | 없음 | 이 인스턴스가 아카이빙을 마지막으로 비교한 시각(epoch 초). 관찰한 적이 없으면 `NaN` |
| `scim.revocations` | Counter | `kind=deactivate`\|`delete_user`\|`remove_member`\|`delete_group` | SCIM 쓰기가 **커밋한** [회수](02-용어집.md#회수). 아래 |

- **아카이빙 게이지는 인스턴스마다 따로다.** 하루 1회 아카이빙은 클러스터에서 한 인스턴스만 돌리므로(하루 1회 표지) 나머지 인스턴스의 게이지는 낡은 값을 쥔다. 그래서 `observed` 가 있다. 경보는 `observed` 가 최근 32시간 안인 계열만 본다([3.6](#36-경보-예)).
- 게이지는 `Check` 비교 **직후**, 스냅샷 저장과 남은 회수 지우기 전에 갱신된다. 그래서 저장이 실패해도 갱신된다. 아카이빙이 건너뛰어지거나(재적재 중) 비교 전에 실패하면(현재상태 읽기·`Check` 실패, 비교 전의 기한 초과) 게이지도 `observed` 도 그대로다. 멈춘 아카이빙을 `observed` 가 낡아지는 것으로 잡는 이유다.
- `kind=missing` 은 아카이빙이 고치지 않는다. 비교에 쓴 현재상태가 락 밖에서 읽은 낡은 값일 수 있어, 그대로 쓰면 지운 직원이 되살아나기 때문이다. 사람이 풀어야 한다.
- **`scim.revocations` 는 막지 않고 보이게만 한다.** IdP 의 잘못된 매핑이나 대량 퇴사를 시간 창으로 막으면 정당한 회수가 늦어진다. 상태 쓰기가 성공한 뒤 이력에 더하는 자리에서 세므로, 장애 중 IdP 의 재시도는 남은 것만 센다(`RevocationObserver`, core).

  | `kind` | 언제 | 한 번에 |
  |---|---|---|
  | `deactivate` | `active` 가 true → false 로 저장됐다(직원 삭제가 일부 실패해 비활성으로 남긴 경우 포함) | 1 |
  | `delete_user` | 직원 레코드를 지웠다 — 그때 활성이던 직원만 | 1 |
  | `remove_member` | 조직에서 직원 멤버를 뺀 것이 커밋됐다(PATCH remove, PUT·replace 로 빠짐) | 뺀 직원 멤버 수 |
  | `delete_group` | 조직 삭제가 커밋됐다 | 지운 직원 멤버 수 |

  세는 단위가 직원 수와 꼭 같지는 않다. 직원 하나를 두 번 세지 않는 것은 `deactivate` 와 `delete_user` 사이뿐이다(비활성으로 남긴 뒤 DELETE 재시도가 레코드를 지우면 `delete_user` 로 세지 않는다). `remove_member`·`delete_group` 은 빠진 직원 멤버 줄을 세므로 이미 비활성인 직원도 들고, 비활성화된 직원이 뒤에 조직에서 빠지면 두 `kind` 에 함께 든다. 하위 조직 멤버와, 직원을 지우며 함께 빠지는 소속은 세지 않는다.
- app-scim 은 `sync.*` 를 내지 않는다. SCIM 재적재·아카이빙의 성공·실패는 실행 기록(`GET /admin/sync/runs`)으로 본다.

### 3.5 스프링이 기본으로 내는 것

JVM·프로세스·시스템 지표와 HTTP 서버 요청 지표 같은 스프링 부트·Micrometer 기본 지표는 그대로 나온다. 이 저장소는 그것을 설정하지 않았다. 스케줄러는 `sync.ldap.full`·`sync.ldap.purge`(app-ldap), `sync.scim.archive`·`sync.scim.purge`(app-scim) 이름의 관측(Observation)을 열어 traceId 를 만든다([6절](#6-로그와-추적)). 이것이 지표로도 나오는지는 실행해 확인하지 못했다.

설계 문서(2026-08-14 §12.2)에 있던 `scim.request` 타이머는 구현되지 않았다. 코드에 없다.

### 3.6 경보 예

루트 README.md 의 식 일곱과, 이 문서가 덧붙인 예(표시한다)다. 모든 식은 `for` 와 함께 쓴다. 임계와 `for` 는 매시 정각(LDAP)·하루 창 03~08시(SCIM 아카이빙) 주기를 전제로 정했다.

**LDAP — 신선도.** 마지막 성공 회차가 낡았다.

```promql
# 마지막 성공이 2.5시간보다 낡았다 — 매시 정각 주기라 한 번 거른 것은 넘기고 두 번 연달아 거르면 울린다(경보 규칙의 for: 5m)
# 모든 인스턴스가 같은 값을 내므로 max 로 하나로 모은다
time() - max(sync_last_success{source="LDAP"}) > 2.5 * 3600

# 값이 없다(NaN 이거나 계열이 사라짐) — 90분 넘게 이어질 때 울린다(경보 규칙의 for: 90m)
absent(max(sync_last_success{source="LDAP"}) > 0)
```

- 첫 식은 퇴사자 회수가 멈췄다는 신호다. 임계가 2시간이 아니라 2.5시간인 까닭: 한 번 거른 뒤의 성공 회차는 앞 성공보다 늦게 끝날 수 있다(변경이 있는 회차, LDAP 재시도 최대 약 6분, 작업 기한 30분). 2.5시간은 작업 기한까지 늦어진 한 회차를 넘긴다.
- 둘째 식은 첫 식의 빈자리를 막는다. `NaN` 과의 비교는 늘 거짓이라 첫 식은 값이 없을 때 조용해진다. `> 0` 이 `NaN` 을 걸러 벡터가 비면 `absent` 가 1 이 된다. `for` 는 새로 뜬 인스턴스가 첫 정각 동기화를 치르기 전에 울리지 않을 만큼 길게 둔다.
- 울리면 `GET /admin/sync/runs` 에서 최근 기록이 `FAILED`(LDAP 읽기 실패, 기한 초과 등)인지 `ABORTED`(삭제 가드)인지 본다.

**SCIM — 아카이빙이 본 드리프트.**

```promql
# 아카이빙이 본 남은 회수가 이틀 연달아 보인다 — 32시간 안에 비교한 인스턴스의 계열만 모아 가장 큰 값을 본다(경보 규칙의 for: 36h)
max(
  scim_archive_drift{kind="extra"}
    and on(instance) ((time() - scim_archive_drift_observed) < 32 * 3600)
) > 0

# 현재상태가 요구하는데 장부에 없는 줄이 이틀 연달아 보인다 — 위와 같은 모양, 같은 창(경보 규칙의 for: 36h)
max(
  scim_archive_drift{kind="missing"}
    and on(instance) ((time() - scim_archive_drift_observed) < 32 * 3600)
) > 0

# 어느 인스턴스도 32시간 안에 비교한 적이 없다 — 아카이빙이 멈췄다(경보 규칙의 for: 1h). 창은 위 셈과 같다
time() - max(scim_archive_drift_observed) > 32 * 3600

# 값이 없다(NaN 이거나 계열이 사라짐) — 비교한 적이 한 번도 없다. 재시작 뒤 첫 비교(다음 하루 창, 늦으면 약 29.5시간 뒤)까지는 NaN 이므로 길게 둔다(경보 규칙의 for: 36h)
absent(max(scim_archive_drift_observed) > 0)
```

- **창(32시간)의 셈 — 설정을 바꾸면 다시 한다.** `observed` 는 아카이빙이 비교를 마친 시각이다. 아카이빙은 하루 창(`sync.archive-cron` 기본 `0 0 3-8 * * *`)에서 성공할 때까지 매시 시도하고, 한 번은 기한(`sync.job-timeout` 30분) 안에 끝난다. 그래서 하루의 비교는 03:00~08:30 사이에 있다. 이웃한 두 날의 비교 간격은 가장 짧으면 18.5시간(08:30 → 다음 날 03:00), **가장 길면 29.5시간**이다 — 앞날은 03:00 첫 시도에서 성공하고, 다음 날은 03~07시 시도가 모두 비교 전에 실패하거나 재적재로 건너뛰어 08:00 마지막 시도가 08:30 직전에 비교한 경우다. 서버 시간대에 일광 절약 시간이 있으면 한 시간 더(30.5시간)다. 32시간은 이 최대를 넘고, 남은 1.5시간은 스크레이프 간격과 인스턴스 사이 시계 어긋남 몫이다. 창은 이 최대보다 길고 `for`(36시간)보다 짧아야 한다.
- **extra**: 끝나지 않은 회수다. 하루 보인 `extra` 는 그날 아카이빙이 지우므로 길어야 32시간만 참이라 울리지 않는다. 이틀 연달아 보이면 두 관찰의 간격(18.5~29.5시간)이 창보다 짧아 참이 끊기지 않고 36시간 뒤 울린다. 창을 `for` 보다 짧게 두는 것이 핵심이다 — 창이 `for` 이상이면 이미 지운 남은 줄에도 울리고, 창이 간격의 최대보다 짧으면 이틀 연달아 보여도 참이 끊겨 울리지 않을 수 있다. 복구가 지우지 못하는 `extra` 도 있다(조직 연결 줄 `child`, 직원 레코드가 이미 없는 `direct_member`). 처방은 `POST /admin/sync/rebuild?mode=tuples`.
- **missing**: 현재상태가 요구하는데 장부에 없는 줄이다. 아카이빙이 고치지 않으므로 사람이 풀어야 한다. 빠진 줄이 지운 직원 것이 아닌지 확인한 뒤 `mode=tuples` 로 다시 쓴다. 예컨대 재활성화의 OpenFGA 쓰기가 실패하면 현재상태는 이미 활성인데 줄이 빠진 채로 남는다.
- **not-running** (셋째 식): 아카이빙이 멈췄다. 하루 창의 시도가 모두 실패한 날이 이어진 것이다. `trigger=ARCHIVE` 인 실행 기록을 보고, `FAILED` 면 사유를, `ABORTED` 면 재적재가 창 내내 돌았는지 본다.
- 넷째 식은 셋째 식의 빈자리를 막는다. `observed` 에는 `kind` 라벨이 없어 `on(instance)` 로만 맞춘다.

**SCIM — 대량 회수.**

```promql
# 예 — 지난 1시간의 회수가 지난 7일 시간당 평균의 5배를 넘고 100건 이상이다. 배수·바닥은 배포의 평소 값에 맞춘다
sum(increase(scim_revocations_total[1h])) > 5 * sum(increase(scim_revocations_total[7d])) / (7 * 24)
  and
sum(increase(scim_revocations_total[1h])) > 100
```

- 인스턴스마다 따로 세므로 `sum` 으로 모은다. 계열 넷이 기동 때부터 0 으로 있어 기동 직후의 첫 대량 회수도 `increase()` 에 잡힌다.
- 울리면 IdP 프로비저닝 로그와 직원·조직의 변경 이력(`GET /admin/employees/{employeeId}/history`)으로 의도한 회수인지 본다. 막는 장치는 없다 — LDAP 의 삭제 가드 같은 것이 SCIM 에는 없다.

**덧붙인 예** (루트 README.md 에 없다. 시험하지 않았다):

```promql
# LDAP 삭제 가드가 걸린 회차가 있다 — 사람 확인(force)을 기다리는 상태. 매시 되풀이되므로 두 번째 회차부터 잡힌다
increase(sync_guard_aborted_total[2h]) > 0

# 감사 이력을 못 쓴 줄이 있다 — 변경은 일어났지만 이력에서 빠졌다
increase(audit_write_failures_total[1h]) > 0

# SCIM 변경 락 리스를 잃었다 — 두 인스턴스가 겹쳤을 수 있다
increase(scim_lock_lease_lost_total[1h]) > 0

# 관리 API 조회의 Check 실패율 — OpenFGA 에 닿지 못하는 상태
increase(authz_check_failed_total[15m]) / increase(authz_checks_total[15m]) > 0.1
```

- 가드 식: `sync.guard.aborted` 는 첫 `ABORTED` 에서야 계열이 생긴다. 첫 1회는 `increase` 에 잡히지 않을 수 있다. 가드가 걸린 동안은 `sync.last.success` 도 낡아져 신선도 경보가 뒤따라 울린다(가드 회차는 성공으로 세지 않는다). 가드는 멈춘 원인을 알려 주는 쪽이다.
- `authz_check_failed` 는 누가 관리 API 를 부를 때만 오른다. 상시 신호가 아니다.

## 4. 헬스

`GET /actuator/health` 는 DynamoDB 와 OpenFGA 연결을 본다. app-ldap 은 LDAP 도 본다 — 이 앱의 파이프라인이 거기서 시작하기 때문이다. 하나라도 DOWN 이면 전체가 DOWN(HTTP 503)이다.

세 인디케이터 모두 프로브 상한이 2초다. 넘으면 DOWN 이다. 매달린 프로브는 죽은 것보다 나쁘다 — 오케스트레이터는 DOWN 을 보면 재시작하지만 답이 없으면 판단조차 못 한다.

| 항목(헬스 이름) | 앱 | 무엇을 하나 | UP 의 세부 |
|---|---|---|---|
| `dynamoDb` | 둘 다 | `DescribeTable` 한 번 | `table`, `itemCount` |
| `openFga` | 둘 다 | `StoreBootstrapper.findExistingStore` — 이미 해석한 store 번호가 있으면 `GetStore` 로 **실제로 묻고**, 없으면 이름으로 목록을 찾는다. 어느 쪽도 store 를 만들거나 모델을 쓰지 않는다 | `storeName`, `apiUrl`. store 가 없으면(404 — 지워졌거나 아직 만들지 않았다) DOWN 과 `reason`(`store 가 없다(지워졌거나 아직 만들지 않았다)`). OpenFGA 에 닿지 않으면 그 오류로 DOWN |
| `ldap` | app-ldap | `LdapContextSource.getReadOnlyContext()` — 연결과 **바인드**만 하고 검색은 하지 않는다. `boundedElastic` 에서 돈다 | `url`, `baseDn`, `strategy` |

- `dynamoDb` 의 `itemCount` 는 DynamoDB 가 테이블 설명에 주는 값이다. 대략값이고 갱신이 늦다(DynamoDB 의 설명에 따르면 약 6시간마다) — 이 저장소가 확인한 것이 아니라 DynamoDB 의 성질이다.
- `openFga`: 캐시한 번호를 묻지 않고 돌려주면 OpenFGA 가 죽거나 store 가 지워진 뒤에도 UP 이므로 늘 묻는다. `GetStore` 의 404 만 "store 가 없다" 로 읽고, 닿지 않는 것을 "없다" 로 읽지 않는다. `GetStore` 는 이 프로젝트가 제한하는 튜플 Read 가 아니다([장부 훑기](02-용어집.md#장부-훑기)는 재적재와 기준선을 믿을 수 없는 LDAP 회차에서만 쓴다).
- `ldap`: 인증 실패(`AuthenticationException`)를 받으면 **30분 동안 바인드하지 않고** 기억한 오류로 DOWN 을 답한다(`다음 확인` 과 `이유` 세부가 붙는다). 틀린 비밀번호로 프로브가 몇 초마다 바인드하면 AD 의 잠금 기준에 닿아 서비스 계정이 잠기고 동기화까지 멈추기 때문이다. 30분이 지나면 한 번 다시 바인드하므로 비밀번호를 고치면 재시작 없이 UP 으로 돌아온다. 인증이 아닌 실패(연결 끊김 등)는 매번 다시 확인한다. 정기·수동 동기화는 이 쉼과 무관하게 그때마다 한 번 바인드한다.
- 빈 이름이 `ldapHealthIndicator` 인 것은 부트의 기본 LDAP 인디케이터가 물러나게 하려는 것이다. 헬스 이름은 `ldap` 이다.
- 헬스 체크는 store 를 만들지 않는다. 오타난 `openfga.store-name` 으로 프로브가 빈 store 를 만들면 안 되기 때문이다.

### 세부 노출

두 앱 모두 `management.endpoint.health.show-details: when-authorized` 다. 인증이 없는 지금은 항목과 세부가 보이지 않고 전체 상태(`UP`/`DOWN`)만 나온다(부트 기본 동작 — 실행해 보지는 않았다). 관리 API·SCIM 엔드포인트와 같은 포트이고 인증이 없어, `always` 로 두면 `openfga.api-url`, `dynamodb.table-name`, `ldap.url`·`base-dn`, `Health.down(error)` 의 예외 메시지가 그대로 공개되기 때문이다(두 앱 yml 의 주석). 시험 프로필(두 앱)은 컴포넌트별 상태를 보려고 `always` 로 되돌린다.

### 프로브(liveness·readiness)

두 앱 모두 `management.endpoint.health.probes.enabled: true` 다. `/actuator/health/liveness`·`/actuator/health/readiness` 가 열린다.

- 두 그룹은 부트 기본 구성 그대로라 **외부 의존(OpenFGA·DynamoDB·LDAP)을 보지 않는다.** 외부 장애로 인스턴스가 재시작되지 않게 하려는 것이다. 외부 의존은 `/actuator/health` 본 그룹이 본다.
- 그래서 오케스트레이터의 liveness·readiness 는 이 두 경로에 건다. `/actuator/health` 에 걸면 LDAP 이나 DynamoDB 장애가 곧 DOWN(503)이라 재시작으로 번질 수 있다.
- OpenFGA 장애의 실제 신호는 헬스의 `openFga` DOWN 과 함께 회차의 `FAILED`/`PARTIAL`, `sync.tuples.failed`, SCIM 쓰기의 503, 관리 API 의 `openFgaCheck: null`(`authz_check_failed`)이다([12 장애와 복구](12-장애와-복구.md)).

## 5. 한 회차의 비용

app-ldap 의 정기 동기화는 매시 정각이라 비용이 "한 번" 이 아니라 "하루 24번" 이다. 아래는 루트 README.md 와 코드를 읽어 센 것이다. **10만 명 전체 읽기 시간은 재지 않았다.** 숫자(압축 약 6MB, 묶음 18개, 약 1,100번)는 루트 README.md·주석의 10만 명 규모 추정이다.

### 5.1 평소 회차 (기준선 있음, 비교 경로)

모든 회차가 공통으로 한다.

| 무엇 | 얼마 |
|---|---|
| 변경 락 | 잡기 PutItem 1, 갱신 UpdateItem `lock-renew-interval`(10초)마다, 반납 DeleteItem 1 |
| 죽은 기록 닫기 | 이번 달·지난달 실행 기록 파티션 Query(`status = RUNNING` 거름식). 거름식은 읽은 뒤에 걸러 읽기 용량은 두 파티션 전체만큼이다 — 매시 회차면 약 1,500건(`DynamoDbSyncRunRepository.findRunning` 주석의 어림). 아이템이 작아 읽기 용량은 수십 단위다 |
| 실행 기록 | PutItem 2(열기·닫기) |
| LDAP | 디렉터리 전체. `page-size` 500 이면 10만 명에 직원 검색 약 200 요청(계산) + 그룹 검색. 실패하면 **처음부터 다시** 읽는다(최대 5번) |
| 직전 스냅샷 | 압축 묶음을 읽는다(10만 명 규모 약 6MB, 묶음 18개). 포인터 1 |
| 현재상태 읽기 | 현재상태 교체가 비교하려고 읽는 모든 직원·조직 META(GSI1 의 고정 파티션 둘, `ALL` 프로젝션) + 조직마다 멤버 줄 Query |

**변경이 없는 회차**는 여기서 끝난다. 델타가 비면 "변경 없음. OpenFGA 를 호출하지 않는다" 를 남기고 현재상태 교체(저장본과 같으면 쓰지 않는다)만 한 뒤 `변경 없음` 으로 끝난다. OpenFGA 호출 0번, 스냅샷 쓰기 0번, 현재상태 쓰기 0번이다(실행 기록과 락 쓰기만 남는다).

**변경이 있는 회차**는 위에 더해 든다.

- 바뀐 줄의 OpenFGA 쓰기·지우기와 바뀐 직원·조직의 현재상태 쓰기.
- **튜플 스냅샷 한 벌을 통째로 새로 저장한다.** 한 줄만 바뀌어도 같은 크기다(압축 약 6MB, 묶음 18개). 보관 7일(`dynamodb.snapshot-retention-days`)에 매시 변경이 있으면 최대 약 168벌, 약 1GB 가 쌓인다(루트 README.md).
- 락을 반납한 뒤 감사 이력을 쓴다. 변경이 있는 직원·조직 줄만 쓴다.

### 5.2 장부 맞추기 회차

기준선이 없거나(첫 회차, 새 테이블) 지난 회차가 기록 전에 멈춘 경우(기록 중 표시)다. 평소 비용에 더해, 있어야 할 줄 전체를 다시 쓰고(10만 명 규모 쓰기 약 1,100 배치) 장부를 처음부터 훑는다(약 1,100 호출). 삭제 가드가 이 회차를 통째로 막으면 스냅샷이 남지 않아 **다음 회차도 같은 길을 탄다.** 사람이 `force=true` 로 넘기기 전까지 매시 반복이다 — 하루 한 번이던 때의 24배다(루트 README.md). 기준선이 있는 비교 경로에서 가드가 막으면 쓰기 없이 델타를 구하는 데까지만 든다.

### 5.3 그 밖에 상시 드는 것

- `LastSuccessGauge`: 인스턴스마다 1분에 한 번 이번 달 실행 기록 파티션의 첫 쪽을 읽는다.
- `DynamoDbHealthIndicator`: 프로브마다 `DescribeTable` 1번.
- `ldap-purge`: 하루 창(04~08시)의 정각마다 표지를 잡아 보고, 그날 처음 성공할 때까지 만료 스냅샷을 지운다. 표지를 못 잡은 인스턴스와 성공한 뒤의 시도는 건너뛴다 — 건너뛰는 시도도 표지 잡기(조건부 PutItem) 한 번은 든다.

### 5.4 SCIM 의 하루 1회

app-scim 의 아카이빙은 현재상태 전체를 읽고(직원 id 를 GSI1 로 열거해 100명씩 BatchGet, 조직은 조직마다 파티션), 나올 수 있는 튜플 전체를 `BatchCheck`(50건씩, 후보가 약 11만 줄인 10만 명 규모에서 약 2,200번 — 후보 수 ÷ 50 으로 셈한 어림)하고, 실제 있는 튜플을 스냅샷으로 저장한다(압축 약 6MB 규모). 남은 회수가 있으면 직원마다 락을 잡고 지운다. 기한은 `sync.job-timeout`(30분)이다. 실패하면 하루 창 안의 다음 정각에 이 비용을 다시 치른다. 시작할 때 죽은 기록 닫기가 실행 기록 두 달 치를 한 번 읽는다(5.1). 한 회차의 시간은 `sync.duration` 이 없는 app-scim 에서는 실행 기록의 `startedAt`~`finishedAt` 으로 본다.

## 6. 로그와 추적

### 6.1 로그

- 로깅 구현은 스프링 부트 기본(Logback)이다. 로그 설정 파일(`logback-spring.xml`)은 없다. 설정은 `application*.yml` 의 `logging.*` 둘뿐이다([2.5](#25-prod-프로필)).
- 기본 프로필은 평문 한 줄이다. 줄의 상관관계 자리에 `[traceId-spanId]` 가 나온다(앱 yml 주석. 스프링 부트의 기본 상관관계 형식이 `traceId(32),spanId(16)` 이다). `prod` 는 ECS JSON 이다 — `traceId`·`spanId` 는 MDC 항목이므로 최상위 필드로 나온다(앱 yml 주석과, 부트의 ECS 포맷터가 MDC 맵을 싣는 것으로 확인했다. 실제 출력을 실행해 보지는 못했다).
- 수준: `dev.starryeye.organization` 이 기본 `DEBUG`, `prod` 에서 `INFO` 다. 그 밖의 로거는 부트 기본(`INFO`)이다. `DEBUG` 로그는 드물다(OpenFGA `Check` 실패 한 줄, SCIM 이 버린 PATCH 속성 등).
- 로그 문구는 한국어다. 문구로 `grep` 하면 만드는 자리가 바로 나온다([03 — 한국어 식별자](03-아키텍처.md#8-한국어-식별자)).
- 회차 로그에는 `[runId]` 가 앞에 붙는다(`SyncJobs`). 실행 기록의 `runId` 로 그 회차의 로그를 모은다.

볼 만한 줄이다.

| 수준 | 문구(일부) | 뜻 |
|---|---|---|
| ERROR | `[{runId}] 작업 실패: {사유}` | 회차가 `FAILED` 로 끝났다 |
| ERROR | `실행 기록을 열지 못했다`, `[{runId}] 작업 결과를 기록하지 못했다 — 기록이 RUNNING 으로 남는다` | 실행 기록 저장 실패. 기록이 사실과 달라질 수 있다(`RUNNING` 으로 남는 등) |
| ERROR | `{사유} — 락 리스를 갱신하지 못했다. 하던 일을 멈춘다` | [리스 상실](02-용어집.md#리스-상실) |
| ERROR | `감사 기록 {N}줄을 쓰지 못했다 — 원인 {source}/{kind}/{id}`, `감사 기록 묶음 하나({N}줄)를 쓰지 못했다` | 이력이 빠졌다(`audit.write.failures`) |
| ERROR | `스케줄 동기화를 걸지 못했다`, `만료 스냅샷 정리에 실패했다`, `스냅샷 아카이빙이 예기치 않게 실패했다` | 스케줄러가 작업을 걸지 못했다 |

| ERROR | `스냅샷 저장 실패 — 남은 회수 지우기는 이어서 한다` | 아카이빙의 스냅샷 저장 실패. 기록은 `FAILED` 이고 남은 회수는 지운다 |
| ERROR | `서버 종료: {대기} 안에 작업 기록을 마치지 못했다 — 기록이 RUNNING 으로 남을 수 있다` | 종료 대기 초과 |

| WARN | `삭제 가드 발동: …` | 가드가 회차를 멈췄다 |

| WARN | `튜플 변환 경고: …` | 건너뛴 엔트리, 순환으로 보류한 연결 등 |

| WARN | `PITR 로 복원한 테이블이다 — 장부보다 낡은 기준선일 수 있어 재적재를 권한다(SCIM 은 mode=tuples)` | 기동 때 본 테이블이 PITR 복원본이다([12](12-장애와-복구.md#37-pitr-로-복원했다)) |
| WARN | `결과를 모르는 획득 시도의 토큰으로 반납하지 못했다 …` | SCIM 쓰기의 락 획득을 포기하며 보낸 반납이 실패했다 — 서버에서 잡혔다면 TTL(30초)이 푼다 |
| WARN | `변경 락 리스를 잃었다`(app-scim) | `scim.lock.lease_lost` |
| WARN | `아카이빙 중 OpenFGA 어긋남 발견: …`, `OpenFGA 어긋남 발견: …`(쓰기 경로) | 드리프트(로그 문구는 "어긋남") |
| WARN | `재적재 중이라 오늘 아카이빙을 건너뛴다` | 이번 시도의 아카이빙이 `ABORTED`. 표지를 풀어 다음 정각에 다시 본다 |
| WARN | `시작 시점에 OpenFGA store 를 준비하지 못했다. 앱은 계속 기동하며 …` | 시작 때 OpenFGA 에 닿지 못했다 |
| WARN | `마지막 성공 시각을 실행 이력에서 읽지 못해 sync.last.success 를 비운다` | `sync.last.success` 가 `NaN` |
| INFO | `다른 인스턴스가 동기화·재적재 중이라 이번 스케줄을 건너뛴다`, `오늘({날짜}) {작업} 은 다른 인스턴스가 이미 했거나 하고 있다 — 건너뛴다` | 정상이다(여러 대일 때, 또는 그날 이미 성공한 뒤의 시도) |
| INFO | `{작업}({날짜}) 이 {까닭} — 표지를 풀어 다음 시도(창이 끝났으면 다음 날)가 다시 잡는다` | 하루 1회 작업이 성공하지 못했다. 까닭은 `실패했다`·`성공이 아니다`·`결과 없이 끝났다`·`취소됐다` |
| INFO | `OpenFGA 인가 모델이 최신과 같아 쓰지 않았다` | 기동 때 모델을 견주고 쓰지 않았다(정상) |
| INFO | `스케줄 동기화 완료: status=… written=… deleted=… failed=…` | 정기 동기화 결과 한 줄 |

### 6.2 traceId 와 추적

traceId 는 **로그를 묶으려고** 만든다. 추적 라이브러리(`micrometer-tracing-bridge-otel`)는 두 앱에 있지만 내보내는 쪽(exporter)은 넣지 않았다 — `management.tracing.sampling.probability: 1.0` 이어서 모든 요청과 작업이 span 을 만들고(그래야 모든 로그 줄에 traceId 가 붙는다), 어디로도 보내지는 않는다.

| 경로 | traceId 는 어디서 오나 |
|---|---|
| HTTP 요청(관리 API, SCIM) | 들어오는 요청이 trace 를 시작한다. 요청 헤더의 W3C `traceparent` 를 이어받는지는 부트 기본 동작이고 이 저장소가 설정하지 않았다(확인하지 못했다) |
| 예약 작업(정기 동기화, 아카이빙, 정리) | 시작해 줄 요청이 없으므로 스케줄러가 관측을 직접 연다(`SyncScheduler.관측하며실행`, `ArchiveScheduler.관측하며실행`). 이름은 `sync.ldap.full`·`sync.ldap.purge`·`sync.scim.archive`·`sync.scim.purge` |
| 요청과 떼어 도는 작업(`SyncJobs`, SCIM 쓰기) | 요청의 Reactor Context 를 이어받는다. 그래서 요청과 같은 traceId 로 묶인다 |

- **`spring.reactor.context-propagation: auto` 가 있어야 한다.** traceId 는 Reactor Context 를 타고 흐르지만 Logback 은 MDC(ThreadLocal)를 읽는다. 둘을 잇는 다리를 늘 건너게 하는 설정이다. 기본값(`limited`)이면 이 앱의 체인에서 traceId 가 한 줄도 안 찍힌다(앱 yml 의 실측 주석). 이 값은 JVM 전역 스위치(`Hooks.enableAutomaticContextPropagation()`)로 모든 Reactor 연산자에 걸리며, 비용을 감수하고 켠다. 지우면 컴파일도 시험도 다 통과하는데 traceId 만 조용히 빈칸이 된다 — `TraceCorrelationTest`(두 앱)가 이것을 지킨다.
- SCIM 쓰기의 [감사 이력](02-용어집.md#원인) 원인 id 는 이 traceId 다(`TraceIds`). 이력의 `cause.id` 를 로그의 traceId 로 검색하면 그 요청의 로그를 찾는다. traceId 를 읽지 못하면 원인 id 는 임의 UUID 가 되고 WARN 한 줄이 남는다.
- `@Scheduled` 메서드는 구독만 걸고 바로 돌아오므로 로그는 모두 관측이 걸린 체인 안에서 남긴다. 그 밖에서 찍으면 traceId 가 비어 있다.

## 7. 여러 대 띄우기의 전제

두 앱 모두 여러 대를 띄울 수 있다. 일은 [변경 락](02-용어집.md#변경-락) 하나로 한 번에 하나, 하루 한 번 작업은 [하루 1회 표지](02-용어집.md#하루-1회-표지)를 잡은 인스턴스만 돈다(성공할 때까지 하루 창 안에서 매시 다시 잡는다). 동작은 [08 동시성과 작업](08-동시성과-작업.md). 운영자가 맞춰야 할 것은 다음이다.

- **서버 시계를 NTP 로 맞춘다.** 리스 만료를 각 서버의 벽시계로 판단한다. 서버 사이 시계 차이는 `lock-ttl − 2 × lock-renew-interval`(기본 `30s − 2×10s = 10초`)보다 작아야 한다. 크면 쥐고 있는 락을 다른 서버가 가져갈 수 있다.
- **같은 배포의 인스턴스는 같은 설정을 쓴다.** 같은 `dynamodb.table-name`·`openfga.store-name`·`sync.*`·`ldap.*`. 다른 배포(LDAP/SCIM)는 서로 다른 테이블·장부를 쓴다.
- **같은 배포의 인스턴스는 같은 시간대로 띄운다.** 하루 창은 서버 시간대의 cron 이고 표지의 날짜는 UTC 다. 시간대가 다르면 인스턴스마다 창이 어긋나 하루에 두 번 돌 수 있다(정확성은 깨지지 않는다).
- **정각에 모든 대가 깨어나지만 한 대만 돈다.** 나머지는 락을 못 잡아 기록 없이 INFO 한 줄(`다른 인스턴스가 … 건너뛴다`)을 남긴다. 오류가 아니다. 관리 API 는 곧바로 409 다.
- **지표 수집은 모든 인스턴스를 긁는다.** `sync.last.success` 는 실행 기록에서 읽으므로 어느 인스턴스를 봐도 같은 값이다. 반면 `sync.duration`·`sync.tuples.*`·`sync.guard.aborted` 는 그 회차를 돌린 인스턴스에만 오르므로 합치려면 모든 인스턴스를 긁어 더한다. 아카이빙 게이지는 인스턴스마다 값이 다르다. 경보 식이 `max(...)` 로 모으고 `on(instance)` 로 창을 맞추는 이유다.
- **처리량은 늘지 않는다.** SCIM 쓰기는 변경 락 하나로 직렬화하므로 서버 수와 상관없이 락을 쥐는 시간의 역수가 상한이다. 서버를 늘리는 것은 가용성을 위한 것이다.
- **인스턴스 식별자(`holder`)는 부팅마다 새 UUID 다.** 로그용이고 배제 판단에는 쓰지 않는다.
- **롤링 배포.** 내려가는 인스턴스는 도는 회차를 `FAILED`("서버 종료로 중단")로 닫고 락을 반납한다(최대 10초). 재적재 중에는 SCIM 변경 요청이 503(`Retry-After: 60`)이다. IdP 가 다시 보낸다.

## 8. 로컬 실행

개발 환경 전체는 [14 개발 가이드](14-개발-가이드.md)에 있다. 운영과 관계되는 부분만 적는다.

```bash
docker compose up -d
./gradlew :app-ldap:bootRun
```

`docker-compose.yml` 의 서비스 셋이다.

| 서비스 | 이미지 | 포트 | 메모 |
|---|---|---|---|
| OpenFGA | `openfga/openfga:v1.10.2` | 8080(API), 3000(플레이그라운드) | 저장소가 `memory` 라 컨테이너를 내리면 장부가 사라진다. 서버 v1.10.0 이상이 필요하다 |
| DynamoDB Local | `amazon/dynamodb-local:2.5.3` | 8000 | `-inMemory -sharedDb` — 컨테이너를 내리면 테이블이 사라진다 |
| OpenLDAP | `bitnamilegacy/openldap:2.6.10-debian-12-r4` | 1389 | 수동 검증 전용(자동 시험은 임베디드 UnboundID LDAP 서버를 쓴다). 루트 `dc=example,dc=com`, 관리 계정 `cn=admin,dc=example,dc=com`. 이미지는 보안 패치가 더 나오지 않는 마지막 무료 빌드다 |

앱의 기본값(`localhost:8000`·`8080`·`1389`)이 이 포트에 맞춰져 있어 설정 없이 뜬다. 앱은 app-ldap 8081, app-scim 8082 다. 컨테이너를 내리면 DynamoDB 와 OpenFGA 가 함께 비워지므로 둘을 같이 올리고 내린다. 한쪽만 비우면 어긋난다. DynamoDB 만 비우면 다음 LDAP 회차가 "기준선 없음" 으로 장부를 맞춘다. OpenFGA 만 비우면 기준선(스냅샷)은 남고 장부가 비어, 변경 없는 회차가 장부를 채우지 않는다 — 평소 회차가 장부를 읽지 않는 설계에서 따른 결론이며, 이때는 재적재(`POST /admin/sync/rebuild`)를 건다.

시드는 두 갈래다.

- **LDAP**: `LDAP_SEED_DIR` 환경 변수로 OpenLDAP 이 먹을 LDIF 디렉터리를 고른다. 기본 `docker/ldap/small`(손으로 훑기 좋은 소규모 시드 — groupOfNames 트리에 직원 셋·그룹 둘, DIT 트리에 `ou=company` 아래 OU 둘과 직원 한 명)은 저장소에 있다. 규모 시드 `docker/ldap/scale-groupofnames`(5천여 명), `docker/ldap/scale-dit`(`ldap.strategy=dit` 와 함께 쓴다)는 생성물이라 저장소에 없고 `./gradlew :connector-ldap:generateScaleSeed` 로 만든다.
- **SCIM**: app-scim 은 받는 쪽이라 밖에서 IdP 역할로 쏴야 한다. `./gradlew :connector-scim:generateScimSeed` 가 `docker/scim/initial-sync.ndjson` 을 만들고, 앱을 띄운 뒤 `python3 docker/scim/replay.py [주소]` 로 순서대로 보낸다(기본 `http://localhost:8082`). 서버가 id 를 발급하므로 스크립트가 응답의 id 로 뒤 요청의 경로와 멤버 값을 바꿔 보낸다.

생성기는 이 문서를 쓰는 중에 돌리지 않았다. 위는 빌드 파일과 스크립트 머리말에서 읽은 것이다.

## 확인하지 못한 것

- 10만 명 규모의 실제 회차 시간과 DynamoDB 읽기 용량. 위의 규모 숫자는 루트 README.md·주석의 추정이다.
- `ecs` 로그 포맷의 실제 출력, 평문 로그의 정확한 상관관계 자리 문구, `traceparent` 헤더 수용.
- `prometheus` 출력의 실제 이름(카운터 `_total` 등은 Micrometer 규칙에서 따랐다), 관측(Observation)이 만드는 추가 지표.
- `health.show-details=when-authorized` 가 인증이 없을 때 세부를 숨기는 것(부트 기본 동작).
- 실제 AWS 가 막 만든 테이블의 PITR 요청을 한동안 거절하는지(2분 재시도의 근거), 실제 `ldaps://` 연결과 트러스트스토어(시험은 설정 검증만 본다).
- `openfga.write-batch-size` 와 서버 한도의 관계. (OpenFGA SDK 0.9.11 의 기본 시간 제한·재시도 — 요청·연결 10초, 재시도 3번, 최소 대기 100ms — 는 SDK 의 `FgaConstants` 로 확인했다.)
