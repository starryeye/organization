# 한계와 알려진 문제

> 기준 커밋: 5675b3c (ops-readiness, main 에 머지됨). 코드가 바뀌면 이 문서도 함께 고친다.
> 읽기 전에: [개요](01-개요.md), [용어집](02-용어집.md), [12 장애와 복구](12-장애와-복구.md)

이 서버가 하지 못하는 것, 알고 남겨 둔 것, 확인하지 못한 것을 숨기지 않고 모았다. 항목마다 네 가지를 적는다.

- **무엇** — 한계가 무엇인가.
- **영향** — 그래서 무슨 일이 생기나.
- **우회** — 지금 할 수 있는 것. 없으면 "없음".
- **상태** — 아래 다섯 가운데 하나.

| 상태 | 뜻 |
|---|---|
| 계획 | 맡을 슬라이드가 정해져 있다(예: 인증 슬라이드) |
| 남김 | 설계 문서가 범위 밖으로 둔 것. 맡을 슬라이드는 아직 없다 |
| 받아들임 | 대가를 알고 고른 결정이다 |
| 확인하지 못함 | 코드는 있지만 실제 환경(실제 AD, 실제 AWS, 실제 IdP)이나 규모로 보지 못했다 |
| 확인함 | 이 묶음을 쓰며 코드를 읽어 확인한 동작 문제다. 설계 문서에 판단이 없다. 코드 수정은 이 문서 묶음 밖이다 — 맡을 슬라이드가 정해지면 "계획" 으로 바꾼다 |

고친 항목은 이 문서에서 뺐다. 이 묶음의 앞 판이 적었던 번호는 [6절](#6-관찰과-운영)과 [7절](#7-코드를-읽어-확인한-문제) 머리의 표에 "고침(커밋)" 으로 남겼다 — 옛 링크를 따라온 독자가 어디로 갔는지 알 수 있게.

출처는 [루트 README.md](../../README.md), 각 설계 문서의 "말할 수 없는 것·범위 밖" 절, 외부 리뷰 종합(`docs/superpowers/specs/2026-10-19-outsider-review/0-종합.md`, 이하 "리뷰")이다. 리뷰의 항목 번호(N1~N11)를 [점검 번호](02-용어집.md#점검-번호)처럼 함께 적는다. 코드를 읽다 이 문서에서 처음 적는 것은 "코드로 확인" 이라고 밝혔고, 그런 것 가운데 동작이 놀라운 것은 [7절](#7-코드를-읽어-확인한-문제)에 모았다.

## 1. 인증과 노출

### 1.1 인증이 어디에도 없다

- **무엇.** 다음 넷 모두 인증이 없다.
  - SCIM 엔드포인트 `/scim/v2/**`
  - [관리 API](02-용어집.md#관리-api) `/admin/**` — 동기화·재적재·초기화를 거는 쪽까지
  - actuator — `health,info,metrics,prometheus` 를 노출한다(두 앱 `application.yml`)
  - OpenFGA 호출 — 클라이언트에 `apiUrl` 과 store 번호만 준다(`StoreBootstrapper.newClient`). 자격 증명이 없어 장부(store) 쓰기 권한을 이 서버로만 좁힐 수 없다
- **영향.** 리뷰 넷이 모두 이것을 막는 이유로 꼽았다.
  - 누구나 `mode=wipe` 를 걸 수 있다. 확인값은 테이블명 하나이고 비밀이 아니다. 헬스 세부는 두 앱 모두 `when-authorized` 라 인증이 없는 지금은 드러나지 않는다.
  - 누구나 `force=true` 로 [삭제 가드](02-용어집.md#삭제-가드)를 넘길 수 있다.
  - 조직도·이름·이메일과 [감사 이력](02-용어집.md#감사-이력)의 이전 값이 열려 있다.
  - 익명 요청으로 비용을 키울 수 있다 — SCIM 목록의 COUNT 와 건너뛰기, 경로마다 Check 하는 직원 상세(리뷰는 한 번에 200번을 예로 들었다).
  - 이 서버를 거치지 않고 OpenFGA 에 직접 쓸 수 있다. 그렇게 생긴 줄은 재적재가 지운다.
- **우회.** 앞단(게이트웨이·네트워크 정책)에서 막는다. 루트 README.md 도 "실제 운영에 투입하기 전에 반드시 앞단에서 보호해야 한다" 고 적는다.
- **상태.** 계획 — 인증 슬라이드(리뷰 §5). 남은 슬라이드 가운데 마지막이다.

### 1.2 감사 이력에 행위자가 없고, 바꿀 수 없는 저장소가 아니다

- **무엇.**
  - [원인](02-용어집.md#원인)은 `AuditCause(source, kind, id)` 뿐이다. 누가 걸었는지 적는 칸이 없다.
  - 감사 이력은 같은 DynamoDB 테이블에 산다. 테이블 TTL 이 `dynamodb.audit-retention-days`(기본 30일) 뒤 지운다. 위변조 방지(서명·해시 사슬)도 외부 내보내기(SIEM)도 없다.
  - 최선을 다해 쓴다. 쓰기가 실패해도 회차·요청은 실패하지 않는다. 대신 ERROR 로그, `audit.write.failures`, 회차 메시지 앞의 "감사 기록 N건 실패" 가 남는다. 서버가 회차 도중 죽으면 그때까지 모은 변경이 남지 않는다([10 감사 이력](10-감사-이력.md)).
  - `force=true` 를 걸었다는 사실은 실행 기록의 트리거로 남는다 — 동기화는 `FORCED`, LDAP 재적재는 `FORCED_REBUILD`. 누가 걸었는지는 남지 않는다.
- **영향.** 누가 `wipe`·`force` 를 걸었는지 사후에 알 수 없다. 기록을 지우거나 고친 흔적도 남지 않는다.
- **우회.** 앞단 게이트웨이의 접근 로그로 누가 불렀는지 남긴다.
- **상태.** 행위자는 계획 — 인증 슬라이드(리뷰 §5). 위변조 방지·외부 내보내기는 남김(감사 이력 설계 2026-10-10 §13).

### 1.3 로그인한 사용자를 employeeId 로 바꾸는 정확한 조회가 없다

- **무엇.** [권한을 묻는 앱](02-용어집.md#권한을-묻는-앱)은 관리 API `GET /admin/employees?userName=…` 이나 `?externalId=…` 로 [employeeId](02-용어집.md#employeeid)를 찾는다. 인증된 정확 일치 API 는 없다. LDAP 의 [userName](02-용어집.md#username)은 유일하지 않다 — 로그인 속성의 원본 값을 그대로 쓰고 겹침을 막지 않는다.
- **영향.** 조회 결과가 0건이거나 2건 이상일 때의 계약이 없다(리뷰 N10). `userName` 은 접두사 검색이라 다른 직원이 섞여 나올 수 있다.
- **우회.** `externalId`(LDAP 은 DN)로 찾는다. 결과가 정확히 하나인지 앱이 확인한다. 그 값은 직원 검색·상세 응답의 `externalId` 칸에 있다 — 이 서버가 다시 쓴 표기 그대로라 한 번 받아 저장해 두면 정확히 맞는다([09 — LDAP 에서 externalId 를 쓸 때](09-관리-API.md#ldap-에서-externalid-를-쓸-때)).
- **상태.** 계획 — 인증 슬라이드(리뷰 §5, 설계 2026-10-20 §14).

### 1.4 운영 프로필은 주소를 덮지 않는다

- **무엇.** `application-prod.yml` 은 로컬 `application.yml` 위에 얹힌다. 운영 보호 값(테이블·store 생성 끔, 삭제 보호·PITR 요구, 바인드 비밀번호 환경 변수, `ldap.require-tls`)은 덮지만, 주소와 계정은 덮지 않는다 — `dynamodb.endpoint`(`http://localhost:8000`), `openfga.api-url`, `ldap.url`·`base-dn`·`bind-dn` 이 로컬 값 그대로다([11 — prod 프로필](11-운영.md#25-prod-프로필)).
- **영향.** 덮어쓰지 않으면 DynamoDB 는 로컬 주소에 가짜 자격 증명으로 붙으려 하고, app-ldap 은 `ldap://` 주소 때문에 `require-tls` 에 멈춘다. 엉뚱한 곳에 조용히 붙지는 않는다 — 실제 AWS 테이블이 아니면 기동 검사가 멈추거나 호출이 실패한다.
- **우회.** 배포 설정에서 덮어쓴다(예 `--dynamodb.endpoint=`). 목록은 [루트 README.md 의 "운영 배포"](../../README.md#운영-배포).
- **상태.** 받아들임 — 주소는 환경마다 달라 배포의 몫이다. 헬스 세부(`when-authorized`), 평문 LDAP(`require-tls`), DynamoDB 시간 한도, 생성 스위치는 운영 준비 슬라이드가 고쳤다(리뷰 N9).

## 2. SCIM 배포

### 2.1 SCIM id 의 내구성

- **무엇.** SCIM 배포에서 직원·조직 id 는 이 서버가 POST 마다 발급하는 UUID 다. DynamoDB 가 그 id 의 유일한 발급처이자 조직도의 유일한 사본이다. 운영(`prod`)은 테이블을 만들지 않고(이름 오타로 빈 테이블을 만들지 않는다), 삭제 보호와 PITR 이 켜져 있어야 뜬다([11 — 테이블](11-운영.md#22-테이블)). 남은 것은 셋이다.
  - IaC 가 없다. 테이블은 손으로 미리 만들거나 `create-table-on-startup=true` 로 한 번 띄워 만든다.
  - 테이블을 PITR 로 복원하면 복원 시점 뒤에 발급한 id 는 테이블에 없다. 기동 때 WARN 만 남기고 자동으로 재적재하지 않는다([12 — PITR 로 복원했다](12-장애와-복구.md#37-pitr-로-복원했다)).
  - 문서화된 마지막 복구(`mode=wipe` 뒤 IdP 재프로비저닝)를 하면 모든 직원·조직 id 가 바뀐다.
- **영향.**(리뷰 N4)
  - 테이블을 잃거나 복원하면 그만큼 신원이 갈라진다. 권한을 묻는 앱이 저장한 employeeId·orgCode 가 낡는다.
  - 장부의 옛 id 튜플은 지울 주체 없이 남는다([12 장애와 복구 3.4](12-장애와-복구.md#34-테이블을-다시-만들었거나-이름이-틀렸다--store-에는-줄이-있는-채로)).
  - OpenFGA store 번호는 영구 고정인 것과 비대칭이다.
- **우회.** PITR 의 보관 기간 안에서 복원하고, 복원 시점 뒤의 변경을 IdP 가 다시 보내게 한 뒤 `mode=tuples` 를 건다(12 3.7).
- **상태.** 생성·보호는 운영 준비 슬라이드가 고쳤다(운영 준비 설계 §3 — IaC 전용은 버린 길이다). 복구 뒤 id 를 보존하는 방법은 남김.

### 2.2 SCIM 배포의 조직 계층을 어디서 받는지 정해지지 않았다

- **무엇.** [child](02-용어집.md#child) 튜플은 SCIM 조직의 멤버 가운데 GROUP 타입에서만 나온다. 리뷰어의 지식으로는 Entra·Okta 가 중첩 그룹을 SCIM 으로 보내지 않는다.
- **영향.**(리뷰 N5) 그렇다면 SCIM 배포에서는 [롤업](02-용어집.md#롤업)이 생기지 않는다. 상위 조직의 `member` Check 가 하위 조직 직원에게 거짓이다.
- **우회.** 없음. 롤업이 필요하면 지금은 LDAP 배포다.
- **상태.** 확인하지 못함(벤더 동작). 원천(enterprise 속성, 조직 마스터, HRIS, 관리 API)은 제품 범위의 결정이 먼저다(설계 2026-10-20 §14).

### 2.3 변경 락 하나라 쓰기 처리량에 상한이 있다

- **무엇.** 모든 [SCIM 쓰기](02-용어집.md#scim-쓰기)는 [변경 락](02-용어집.md#변경-락) 하나를 차례로 잡는다. 서버를 늘려도 처리량 상한(락을 쥐는 시간의 역수)은 그대로다.
- **영향.** 설계는 초당 약 20~30건으로 추정했다(설계 2026-10-07 §11, 개발 노트북 실측과 추정). 이 속도로 셈하면 10만 명 초기 POST 는 락 시간만으로 약 0.9~1.4시간, 멤버십 15만 건을 한 명씩 PATCH 로 받으면 약 1.4~2.1시간이다(15만 ÷ 초당 20~30건). 설계 문서는 앞의 것을 "최소 약 1시간", 뒤의 것을 "약 3시간" 으로 적었는데, 3시간의 근거는 적혀 있지 않아 이 묶음은 같은 절의 속도로 다시 셈한 값을 쓴다(추정). 들어오는 속도가 더 빠르면 3초(`dynamodb.lock-acquire-timeout`)를 넘긴 요청이 503 이다.
- **우회.** IdP 가 503 을 받으면 다시 보낸다. 초기 적재는 시간이 든다고 보고 계획한다.
- **상태.** 남김 — 직원·조직마다 따로 잠그기는 "실제 요구가 확인될 때"(리뷰 §4, 설계 2026-10-07 §12). 지표 `scim.lock.contended` 가 꾸준히 오르면 다시 볼 신호다.

### 2.4 멤버 빼기가 일부 실패하면 IdP 의 재시도에 기댄다

- **무엇.** 조직 PATCH·PUT 의 멤버 빼기가 일부 실패하면 지우지 못한 멤버의 멤버 줄을 남기고 503 이다. 서버 스스로 다시 맞추는 길이 없다.
- **영향.** IdP 가 다시 보내지 않으면 현재상태와 장부가 그 멤버를 함께 가진 채라 [드리프트](02-용어집.md#드리프트)가 아니다. 아카이빙도 재적재도 고치지 못한다. 이동자가 옛 조직의 권한을 계속 갖는다. Okta 의 5xx 재시도 동작은 문서에 없어 확인하지 못했다.
- **우회.** IdP 프로비저닝 로그에서 실패한 그룹 변경을 찾아 다시 보내게 한다.
- **상태.** 받아들임(설계 2026-10-20 §6.3). 줄을 지우면 PUT 재시도가 뺄 멤버를 알 수 없고, "빼는 중" 표시는 멤버를 읽는 모든 곳이 걸러야 해서 버렸다.

### 2.5 재활성화가 실패하면 경보와 재적재가 필요하다

- **무엇.** `active` false→true 의 OpenFGA 쓰기가 실패하면 현재상태는 이미 활성이고 줄이 빠진다. 대상을 다시 읽고 차이만 보내는 IdP 는 다시 보내지 않을 수 있다. 하루 아카이빙은 빠진 줄을 쓰지 않는다.
- **영향.** 그 직원을 건드리는 다음 쓰기가 올 때까지 권한이 없다.
- **우회.** `scim.archive.drift{kind=missing}` 경보(루트 README.md 의 식, `for: 36h`)가 울리면, 지운 직원의 줄이 아닌지 확인한 뒤 `POST /admin/sync/rebuild?mode=tuples`([12 장애와 복구 5.2](12-장애와-복구.md#52-재활성화가-실패)).
- **상태.** 받아들임(설계 2026-10-20 §10). 자동으로 다시 쓰는 복구는 낡은 현재상태(커밋이 실패한 직원 삭제)와 구별되지 않아 두지 않았다.

### 2.6 IdP 재시도 없이 SCIM 회수가 끝나기까지 최대 하루

- **무엇.** 비활성화·삭제가 OpenFGA 에서 실패하면 요청한 값(비활성)을 저장하고 503 이다. IdP 가 다시 보내지 않으면 남은 줄은 그 직원을 건드리는 다음 쓰기나 하루 [아카이빙](02-용어집.md#아카이빙)이 지운다.
- **영향.** 그 사이(최대 약 하루) 퇴사자의 권한이 남는다.
- **우회.** 급하면 `mode=tuples`.
- **상태.** 받아들임(설계 2026-10-20 §10). IdP 가 비활성을 보고 다시 보내지 않는지는 확인하지 않았다.

### 2.7 고아 튜플은 재적재만 지운다

- **무엇.** 장부에는 있는데 현재상태의 어떤 멤버십에도 이어지지 않는 튜플이 [고아 튜플](02-용어집.md#고아-튜플)이다. 생기는 길은 셋이다.
  - 결과를 모르는 SCIM 쓰기 — OpenFGA 는 반영했는데 멤버 줄은 커밋하지 않은 것.
  - 실패한 `POST /Groups` 가 첫 id 로 써 둔 튜플.
  - 멤버십을 지우는 커밋 직전의 크래시.
- **영향.** 아카이빙은 후보를 현재상태의 멤버십에서 뽑으므로 보지 못한다. 실패한 POST 의 고아는 어떤 현재상태·응답에도 없는 id 라 권한이 새지는 않는다. 그 밖의 고아는 권한을 줄 수 있다.
- **우회.** 가끔 `POST /admin/sync/rebuild?mode=tuples`.
- **상태.** 받아들임(설계 2026-09-01 §5.4, 2026-10-04 §11, 2026-10-20 §10).

### 2.8 `active` 가 없으면 활성이다

- **무엇.** SCIM 의 `active` 는 선택 속성이다. POST·PUT·PATCH `remove` 모두 "없음 = 활성" 한 규칙이다(`ScimMapper.toDirectoryUser`, `ScimPatchApplier`).
- **영향.** 권한을 여는 방향(fail-open)이다(리뷰 §3, 리뷰어 셋이 짚었다). 비활성 직원에게 `active` 를 싣지 않은 PUT 이 오면 다시 활성이 되어 권한이 돌아온다. 오류도 경보도 없다.
- **우회.** IdP 매핑이 PUT 에 `active` 를 늘 싣게 한다. 감사 이력의 `attributes`(`active`)로 사후에 찾는다.
- **상태.** 받아들임(설계 2026-10-20 §11). 뒤집으면 `active` 를 싣지 않는 POST 가 권한 없는 직원을 만들고, 지금 쓰는 IdP 는 비활성화를 `active=false` 로 명시해 보낸다(루트 README.md).

### 2.9 `externalId` 없는 조직 POST 의 재시도는 조직을 하나 더 만든다

- **무엇.** 응답을 잃은 조직 POST 를 IdP 가 다시 보내면, `externalId` 가 없을 때는 막을 신호가 없다. 조직 `displayName` 은 겹쳐도 되는 속성이다.
- **영향.** 같은 이름의 빈 조직이 하나 더 생긴다.
- **우회.** 관리 API `GET /admin/organizations?displayName=…` 로 찾아 멤버 없는 쪽을 IdP 에서 정리한다. IdP 가 조직 `externalId` 를 보낼 수 있으면 매핑한다.
- **상태.** 받아들임(루트 README.md).

### 2.10 IdP 마다 다른 동작은 확인하지 못했다

- **무엇.** 503·`Retry-After` 를 지키는지, 대상을 GET 해 차이만 보내는지, 409 를 받고 기존 리소스를 찾아 잇는지. 루트 README.md 는 Entra 가 개별 오류를 다음 주기에 다시 보낸다고 문서화했고 Okta 의 5xx 반응은 문서에 없다고 적는다.
- **영향.** 회수의 수렴 속도가 IdP 에 달렸다. 아카이빙이 하루 단위로 받쳐 준다(2.6).
- **우회.** 실제 IdP 로 시험한다.
- **상태.** 확인하지 못함(설계 2026-10-05 §10, 2026-10-20 §6.1).

### 2.11 받지 않는 IdP 요청 모양

- **무엇.**
  - Entra 는 `?aadOptscim062020` 없이 멤버 하나를 값 붙은 `remove members` 로 뺀다 → 400. 같은 요청의 다른 연산도 반영되지 않는다.
  - `manager` 필터, 이메일 매칭 필터, `co` 연산자, RFC 에 없는 커스텀 확장 path 도 400 이다.
- **영향.** 옵션이 없는 Entra 테넌트에서는 이동자의 옛 소속 권한이 남는다. 이 원인만 세는 지표가 없다.
- **우회.** 테넌트 URL 끝에 `?aadOptscim062020` 을 붙이고, 커스텀 확장 매핑을 뺀다. IdP 의 매칭 속성은 `userName` 이나 `externalId` 로 둔다.
- **상태.** 받아들임 — "표준이 정한 신호만 받는다" 원칙(루트 README.md, 설계 2026-09-26 §2). 리뷰는 Entra 설정을 우리가 통제한다는 전제가 깨지면 Medium 이라고 봤다(리뷰 §3).

## 3. 보호 장치의 빈틈

### 3.1 정기 장부 대조가 없다 — 원칙이다

- **무엇.** OpenFGA Read([장부 훑기](02-용어집.md#장부-훑기))는 재적재와, 기준선을 믿을 수 없는 LDAP 회차(기준선 없음·기록 중)에서만 쓴다. 판단과 쓰기는 `Check` 만 쓴다. 장부 전체를 정기적으로 훑어 잉여를 찾는 일은 하지 않는다.
- **영향.** 장부에만 있는 줄은 사람이 재적재를 걸 때까지 남는다 — 이 서버를 거치지 않고 OpenFGA 에 직접 쓴 줄, 펜싱 틈의 늦은 쓰기(3.2), 고아 튜플(2.7). LDAP 의 평소 회차([비교 경로](02-용어집.md#비교-경로))도 장부를 읽지 않는다 — 기준선이 있는 평소 회차는 방금 읽은 디렉터리와 직전 스냅샷만 비교한다(`FullSyncUseCase.비교해_맞춘다`). 그래서 장부와 스냅샷이 어긋난 줄(장부에만 있는 줄, 장부에서 빠졌는데 B 에 남은 줄)을 보지 못하고 고치지 않는다. 장부를 훑어 고치는 것은 재적재와, [기준선 상태](02-용어집.md#기준선-상태)가 없음·기록 중인 회차의 장부 맞추기뿐이다.
- **우회.** app-ldap 은 `POST /admin/sync/rebuild`, app-scim 은 `mode=tuples` 를 주기적으로(사람이) 건다. 관리 API 의 `shouldHaveAccess`·`openFgaCheck` 비교(`authz_drift_detected`)로 표본을 본다.
- **상태.** 받아들임(설계 2026-09-29 §2, 2026-09-30 §2, 2026-10-20 §11). 다시 열 시점으로 설계는 `scim.archive.drift{kind=extra}` 나 `scim.lock.lease_lost` 가 실제로 오를 때, OpenFGA 직접 수정이 위협 모델에 들어올 때(인증 슬라이드)를 적었다.

### 3.2 펜싱이 없다

- **무엇.** 변경 락은 DynamoDB 조건부 쓰기로 만든 [리스](02-용어집.md#리스)다. OpenFGA 에 [펜싱](02-용어집.md#펜싱) 토큰이 없어, 리스가 끝난 옛 주인의 쓰기를 거절할 수 없다([08 동시성과 작업](08-동시성과-작업.md)).
  - SCIM 쓰기는 OpenFGA 쓰기 직전과 DynamoDB 커밋 직전에 리스를 다시 확인해 틈을 좁혔다.
  - LDAP 회차는 쓰기 직전에 다시 확인하지 않는다. 갱신(`LeaseKeeper`)에만 기댄다(리뷰 N11).
- **영향.** 긴 GC 정지처럼 프로세스 전체가 30초 넘게 멈추면, 깨어난 뒤의 쓰기가 남이 락을 잡은 뒤에 떨어질 수 있다. 커밋이면 다른 인스턴스의 저장(예: 비활성화)을 덮을 수 있다. 장부에만 남은 줄은 재적재가 지운다.
- **우회.** `scim.lock.lease_lost` 를 지켜보고 오르면 `mode=tuples`. GC 정지가 긴 JVM 설정을 피한다.
- **상태.** 받아들임(설계 2026-09-30 §11, 2026-10-02 §10, 리뷰 §4). LDAP 쓰기 직전 리스 확인(N11)은 더하지 않기로 했다 — 멈춤 한도가 TTL 전에 일을 취소한다(운영 준비 설계 §17.6).

### 3.3 부여 쪽에는 가드가 없고, 절대 수 상한도 없다

- **무엇.** 삭제 가드는 지우기만 본다. 비율(기본 30%)만 보고 절대 수는 보지 않는다. 기준 수가 `min-baseline`(10) 미만이면 가드를 보지 않는다. SCIM 에는 가드가 없다.
- **영향.**
  - 계정 상태 속성을 못 읽어 전원이 활성으로 읽히면 막힌 계정의 권한이 그대로 다시 쓰인다([12 장애와 복구 4.6](12-장애와-복구.md#46-서비스-계정이-계정-상태-속성을-못-읽음--전원-활성)).
  - 30% 미만의 대량 회수(예: 10만 명 중 2만 명)는 통과한다.
  - SCIM 의 대량 회수에도 누적 상한이 없다(리뷰 N11). 막지는 않고 `scim.revocations{kind}` 로 센다.
- **우회.** LDAP 은 `sync.tuples.written`·`sync.tuples.deleted` 의 급변을 경보로 둔다(루트 README.md 에 예는 없다). SCIM 은 `scim.revocations` 의 1시간 증가량 경보(루트 README.md 에 예가 있다, [11 — 경보 예](11-운영.md#36-경보-예)).
- **상태.** 남김(설계 2026-10-20 §11·§14 "부여 쪽 가드와 절대 수 상한"). SCIM 대량 회수를 시간 창으로 막는 것은 버렸다 — 정당한 회수가 늦어진다(운영 준비 설계 §17.4).

### 3.4 장부 맞추기의 가드는 비교 경로보다 약하다

- **무엇.** [장부 맞추기](02-용어집.md#장부-맞추기)(재적재, 기준선 없음·기록 중 회차)는 D 를 먼저 다 쓰고 훑는다. 그래서 가드의 기준 수가 "훑은 장부"(옛 장부 ∪ D)다.
- **영향.** D 에 새 줄이 많으면 비율이 낮아진다. 예: 11만 줄 중 40% 가 새 id 로 바뀌면 44k/154k ≈ 28.6% 라 통과한다. 비교 경로였다면 40% 로 멈춘다. LDAP 이 0명을 돌려주는 대표 사고(D = ∅)는 그대로 막는다.
- **우회.** 없음. 큰 id 변경은 미리 알고 건다.
- **상태.** 받아들임(설계 2026-09-30 §11).

### 3.5 장부 맞추기 동안 옮기는 직원이 두 조직의 권한을 함께 갖는다

- **무엇.** [쓰기 단계](02-용어집.md#쓰기-단계)의 보장은 쓰기 한 번(`apply`) 안의 것이다. 장부 맞추기는 "D 쓰기" 와 "지우기" 가 서로 다른 쓰기다.
- **영향.** 그 사이 조직을 옮기는 직원이 옛 조직과 새 조직의 권한을 함께 갖는다. 이 경로에서 가드가 걸려 [전부 보류](02-용어집.md#전부-보류)면 그 상태가 다음 회차까지 이어진다.
- **우회.** 없음.
- **상태.** 받아들임 — 장부를 비우는 순간을 두지 않으려고 고른 틈이다(설계 2026-10-05 §11, 2026-10-20 §10).

### 3.6 영구히 거절되는 줄 하나가 뒤 단계의 부여를 막는다

- **무엇.** [앞 단계 실패 규칙](02-용어집.md#앞-단계-실패-규칙) — 앞 단계에서 줄이 하나라도 실패하면 뒤 단계의 쓰기를 보내지 않는다.
- **영향.**
  - 형식이 틀린 id 같은 줄 하나가 데이터를 고칠 때까지 매 회차 뒤 단계의 부여를 막는다. 첫 적재라면 하위 조직 연결 쓰기 전부, 곧 롤업 전체다. 회수는 막지 않는다.
  - LDAP 은 매 회차 `PARTIAL` 인데 `sync.last.success` 는 `PARTIAL` 도 세므로 그 경보가 울리지 않는다.
  - SCIM 은 영구 거절도 503 이라 IdP 가 되풀이한다.
- **우회.** WARN "OpenFGA 가 한 줄을 거절했다 …" 와 `sync.tuples.failed` 를 지켜보고 원인 데이터를 고친다.
- **상태.** 받아들임 — 일부러 fail-closed 를 골랐다(루트 README.md, 설계 2026-10-05 §11, 2026-10-05-scim-error-signals §10).

### 3.7 첫 적재의 일부 누락은 막지 않는다

- **무엇.** 기준선이 없으면 가드가 볼 것이 없다.
- **영향.** 첫 적재에서 필터·검색 범위 탓에 일부 엔트리가 빠져도 `SUCCEEDED` 다. 건너뛴 엔트리의 경고 한 줄이 유일한 신호다. 아무도 남지 않을 때만 실패한다.
- **우회.** 첫 적재 뒤 관리 API 로 직원·조직 수를 디렉터리와 맞춰 본다.
- **상태.** 받아들임(설계 2026-10-05 §11).

### 3.8 가드가 일부만 반영하는 동안 현재상태는 회차 전 그대로다

- **무엇.** [비활성 회수만 반영](02-용어집.md#비활성-회수만-반영)한 회차는 디렉터리 그림을 받아들이지 않은 회차라 [현재상태 교체](02-용어집.md#현재상태-교체)를 하지 않는다.
- **영향.** 관리 API 의 직원 `active` 에 막힌 직원이 활성으로 보인다.
- **우회.** 실제 판정은 `openFgaCheck` 를 본다.
- **상태.** 받아들임(설계 2026-10-20 §10).

### 3.9 `force=true` 전에 무엇이 지워질지 볼 수 없다

- **무엇.** 가드가 멈춘 회차는 수(지울 줄 N건, 기준 M건)만 메시지로 준다. 지울 줄의 목록이나 미리 돌려 보는 기능(dry-run)은 없다(코드로 확인).
- **영향.** 운영자가 개편이 진짜인지 표본으로만 확인하고 `force` 를 건다. 잘못 넘기면 전원의 권한이 지워질 수 있다.
- **우회.** 디렉터리 쪽 변경 수와 메시지의 수를 맞춰 보고, 관리 API 직원 상세로 표본을 본다.
- **상태.** 확인함 — 설계 문서에 판단이 없다.

### 3.10 시계에 기대는 판단

- **무엇.**
  - `accountExpires` 의 만료 판정은 앱 시계로 한다.
  - 락 만료는 각 서버의 벽시계로 판단한다.
  - [하루 1회 표지](02-용어집.md#하루-1회-표지)의 날짜는 앱 시계의 UTC 날짜다.
- **영향.**
  - 시계가 크게 틀어지면 대량 비활성이 생긴다. 비활성 부분이 30% 이하면 가드도 막지 못한다.
  - 서버끼리 `lock-ttl` − 2×`lock-renew-interval`(기본 10초) 넘게 어긋나면 남의 락을 가져갈 수 있다.
  - 하루 창이 UTC 자정을 넘거나 그 근처면 한 창이 두 날로 갈리거나 두 대가 다른 날짜를 잡아, 하루 작업이 두 번 돌 수 있다.
- **우회.** NTP 를 운영 전제로 둔다. 하루 창은 UTC 자정을 넘지 않게 둔다(기본 KST 03~08시 = UTC 18~23시는 괜찮다). 모든 대를 같은 시간대로 띄운다.
- **상태.** 받아들임(설계 2026-09-30 §11, 2026-10-02 §11, 2026-10-20 §10).

## 4. LDAP 배포

### 4.1 긴 DN·식별 값은 미리 막지 않는다

- **무엇.** LDAP 에서 온 id 와 DN 의 길이는 쓰기 전에 보지 않는다. 색인 정렬키(GSI1SK, `displayNameKey`)만 1024바이트로 자른다.
- **영향.**
  - id 는 [멤버 줄](02-용어집.md#멤버-줄)·[소속 줄](02-용어집.md#소속-줄)의 정렬키(1024바이트)에도 들어가므로, 소속이 있으면 약 1,000바이트에서 먼저 거절된다. `externalId`(DN, GSI3 파티션키)나 `USER#<id>` 는 2048바이트가 한도다. 어느 쪽이든 그 아이템 쓰기가 거절되어, 고칠 때까지 매 회차 현재상태 교체가 실패한다([04 — 막지 않는 것](04-데이터-모델.md#막지-않는-것)).
  - id 가 OpenFGA 튜플 `user` 칸의 길이 한도([04 — 튜플 칸의 길이](04-데이터-모델.md#튜플-칸의-길이))를 넘으면 그 줄이 거절된다(3.6).
  - 기본 식별 속성(`entryUUID`, `objectGUID`)은 36자라 해당하지 않는다.
- **우회.** 이름 기반의 긴 속성을 식별 속성으로 쓰지 않는다. 긴 DN 의 엔트리는 검색 범위 밖에 둔다.
- **상태.** 받아들임(설계 2026-10-20 §7·§10). 입구의 id 길이 검사는 남김(설계 2026-09-30 §12).

### 4.2 다른 디렉터리의 계정 잠금 속성

- **무엇.** 비활성으로 읽는 신호는 셋뿐이다 — `userAccountControl` 의 비활성 비트, `accountExpires`, ppolicy 의 영구 잠금 값 `000001010000Z`. 389DS 의 `nsAccountLock`, AD LDS 의 `msDS-UserAccountDisabled`, `shadowExpire` 는 읽지 않는다. ppolicy 의 다른 값(`pwdLockoutDuration: 0` 아래의 사실상 영구 잠금)은 일시 잠금(활성)으로 읽는다.
- **영향.** 그 속성으로 막는 디렉터리에서는 막힌 계정이 활성으로 읽혀 권한이 남는다. 속성을 못 읽는 서비스 계정도 같다 — 전원 활성이다.
- **우회.** 막힌 계정을 직원 검색 필터에서 빼는 필터를 쓴다(예: `(!(nsAccountLock=TRUE))` 를 `user-filter` 에 더한다). 그러면 비활성이 아니라 엔트리가 사라진 것으로 보고 지운다 — 가드의 비활성 회수만 반영이 적용되지 않는다. 이 저장소에서 시험하지 않은 우회다.
- **상태.** 남김(설계 2026-10-20 §14).

### 4.3 TLS

- **무엇.** 주소는 URL 하나(`ldap.url`)를 `LdapContextSource.setUrl` 에 넘길 뿐이다. `ldaps://` 는 JNDI 가 JVM 트러스트스토어로 연다. 운영(`prod`)은 `ldap.require-tls` 로 `ldaps://` 가 아니면 기동을 멈춘다. StartTLS 는 지원하지 않는다.
- **영향.** StartTLS 만 여는 디렉터리는 `prod` 로 붙일 수 없다. 사설 CA 가 서명한 인증서는 트러스트스토어에 넣어야 한다.
- **우회.** 디렉터리의 `ldaps` 포트를 연다. 사설 CA 는 `-Djavax.net.ssl.trustStore=<트러스트스토어 파일>` 로 넘긴다.
- **상태.** StartTLS 는 받아들임(운영 준비 설계 §17.2 — 필요한 디렉터리가 나오면 더한다). 실제 `ldaps://` 연결은 확인하지 못함 — 시험은 설정 검증만 본다.

### 4.4 도메인 컨트롤러 여럿, referral

- **무엇.** 주소가 하나라 그 DC 가 내려가면 다른 DC 로 넘어가지 않는다. referral 은 따라가지 않고 경고만 남긴다. 글로벌 카탈로그(3268)로 읽으면 안 된다 — AD 기본 그룹(`primaryGroupID`)을 RID 로만 맞추므로 다른 도메인의 같은 RID 가 맞아 버린다.
- **영향.**
  - DC 가 오래 내려가면 그동안의 회차가 `FAILED` 다. 읽기 재시도 창(약 2~6분)은 재부팅 정도만 버틴다.
  - referral 로 빠진 부분의 직원은 그 회차에 없는 것과 같다. 빠짐이 30% 이하면 그 사람들의 권한이 지워진다.
- **우회.** 여러 DC 를 가리키는 주소(부하 분산기 등)를 쓴다 — 이 저장소에서 시험하지 않았다. 검색 베이스를 한 도메인 안, 위임되지 않은 서브트리로 둔다.
- **상태.** 남김(설계 2026-10-20 §14). AD 중첩 그룹 확장(`LDAP_MATCHING_RULE_IN_CHAIN`)도 남김(설계 2026-10-05 §12).

### 4.5 실제 AD 로 확인하지 못한 동작

- **무엇.** 임베디드 UnboundID 로만 본 것들이다.
  - `objectGUID` 이진 선언과 바이트 변환
  - `member;range=` 로 나뉜 멤버 읽기
  - `objectCategory=person` 필터
  - `primaryGroupID`·`objectSid` 의 RID 해석
  - referral 과 그때의 페이징 컨트롤
- **영향.** 실제 AD 에서 다르게 동작하면 직원·소속이 빠지거나 회차가 실패한다.
- **우회.** 실제 AD 로 시험 환경을 꾸려 본다.
- **상태.** 확인하지 못함(루트 README.md, 설계 2026-10-04 §11, 2026-10-05 §11).

### 4.6 회수는 다음 정각에 닿는다

- **무엇.** LDAP 은 변경 통지를 받지 않고 매 정각 전체를 읽는다. 증분(DirSync·USN·syncrepl)도, 한 사람만 즉시 회수하는 API 도 없다.
- **영향.** 디렉터리에서 막은 계정의 권한은 "다음 정각 + 회차 시간" 까지 남는다. 회차가 실패하면 그만큼 더 늦다.
- **우회.** 급하면 `POST /admin/sync/full`. `sync.cron` 으로 주기를 줄일 수 있다.
- **상태.** 남김(설계 2026-10-20 §8·§14).

### 4.7 건너뛴 엔트리는 로그로만 보인다

- **무엇.** 식별 속성이 없는 엔트리, id 가 겹친 엔트리, 대조되지 않은 `member` 값은 검색마다 경고 한 줄(예시 DN 다섯 개까지)로만 남는다.
- **영향.** 지표로 경보를 걸 수 없다.
- **우회.** 로그 수집기에서 그 경고를 센다.
- **상태.** 남김(설계 2026-10-05 §12).

## 5. 규모 — 재지 않은 것

### 5.1 10만 명 LDAP 전체 읽기 시간

- **무엇.** 매시 기본 주기의 근거는 "변경 없는 회차는 OpenFGA·현재상태·스냅샷 쓰기가 0" 이라는 계산과 추정이다. 10만 명 디렉터리를 한 번 다 읽는 시간은 재지 않았다.
- **영향.** 실제 읽기가 길면 회차가 겹치거나(락이 막는다) 기한(30분)에 닿는다. 첫 전체 동기화가 기한을 넘기면 멈출 때마다 기록 중 표시가 남아 다음 회차가 처음부터 다시 쓴다 — 진행이 되지 않는다.
- **우회.** 첫 적재 전에 실제 디렉터리로 읽기 시간을 잰다. 길면 `sync.job-timeout` 을 늘린다.
- **상태.** 확인하지 못함(설계 2026-10-20 §10). 첫 동기화를 나눠 커밋하는 것은 남김(설계 2026-09-30 §12).

### 5.2 실제 AWS 의 스로틀과 파티션 한도

- **무엇.** 규모 시험은 DynamoDB Local 위에서 돈다. 다음은 실제 AWS 에서 보지 못했다.
  - 파티션당 초당 1,000 WCU 와 [일괄 요청](02-용어집.md#일괄-요청) 재시도 상한(5번)의 상호작용
  - GSI1 고정 파티션(`USER_INDEX`·`GROUP_INDEX`)으로의 쏠림
  - 10만 명 조직의 감사 이력 줄 조각(약 1,470 WCU)이 한 파티션에 몰리는 경계
  - 키 길이 거절과 TTL 삭제 지연
- **영향.** 첫 적재나 큰 개편에서 일괄 요청 재시도를 다 써 실패할 수 있다. 감사 이력 줄이 빠질 수 있다(크게 알린다).
- **우회.** 실제 AWS 에서 규모 시험을 한다. 실패하면 [12 장애와 복구 3.1](12-장애와-복구.md#31-스로틀링).
- **상태.** 확인하지 못함(설계 2026-10-02 §11, 2026-10-10 §10).

### 5.3 OpenFGA 의 실제 부하

- **무엇.** 동시 요청 수(`openfga.request-concurrency` 기본 4)는 개발 환경 기준이다. 큰 SCIM 변경(10만 명 조직 삭제)이 다른 쓰기를 503 으로 만드는 시간은 AWS 기준 1~2분으로 추정했다.
- **영향.** 실제 OpenFGA 가 느리면 회차가 기한에 닿거나 SCIM 쓰기의 503 이 는다.
- **우회.** 실연동에서 동시 수를 조정한다.
- **상태.** 확인하지 못함(설계 2026-10-02 §11).

### 5.4 매시 회차의 비용

- **무엇.**
  - 변경이 없어도 매 회차 디렉터리 전체, 직전 스냅샷(10만 명 약 6MB), 모든 직원·조직 META 와 조직마다 멤버를 읽는다.
  - 변경이 한 줄이라도 있으면 스냅샷 한 벌을 통째로 새로 쓴다. 보관 7일이면 최대 약 168벌, 약 1GB 다.
  - 델타가 있는 회차마다 `TupleMapper.inactiveMemberTuples` 로 소속 전체를 한 번 훑는다.
- **영향.** DynamoDB 읽기·저장 비용이 주기를 따라간다.
- **우회.** `sync.cron`·`dynamodb.snapshot-retention-days` 를 조정한다.
- **상태.** 받아들임(설계 2026-10-20 §8·§13.2).

### 6.6 실행 기록은 이번 달과 지난달만 읽는다

- **무엇.** 실행 기록 읽기(`findRecent`, `findById`)는 `SYNCRUN#<yyyy-MM>` 의 이번 달과 지난달 파티션만 본다([04 데이터 모델](04-데이터-모델.md#실행-기록)).
- **영향.** `dynamodb.syncrun-retention-days` 를 30일보다 늘려도 그보다 앞선 기록은 관리 API 로 찾지 못한다. 감사 이력의 원인 `runId` 로 거슬러 가지 못할 수 있다.
- **우회.** 보관을 늘리지 않는다. 필요하면 DynamoDB 를 직접 읽는다.
- **상태.** 확인함 — 설계 문서에 판단이 없다.

### 6.7 아카이빙의 한계

- **무엇.**
  - 아카이빙은 한 시점의 사진이 아니다. 읽는 도중 SCIM 쓰기가 끼면 거짓 드리프트가 나올 수 있다.
  - 드리프트 게이지 `scim.archive.drift` 는 아카이빙을 돈 인스턴스만 갱신하고, 다른 인스턴스는 낡은 값을 쥔다.
  - 후보를 현재상태의 멤버십에서 뽑아, 고아 튜플(2.7)은 보지 못한다.
- **영향.** 하루 보인 드리프트만으로는 확정하기 어렵다.
- **우회.** 루트 README.md 의 경보 식은 `scim.archive.drift.observed` 가 32시간 안인 계열만 모으고 이틀 연달아(`for: 36h`)일 때 울린다.
- **상태.** 한 시점 사진은 남김(설계 2026-09-30 §12). 인스턴스별 게이지는 받아들임 — 관찰 시각 게이지로 보완했다(설계 2026-10-20 §10).

### 6.8 app-ldap 에는 락 지표가 없다

- **무엇.** app-ldap 은 `LockObserver.NOOP` 를 결선한다. `scim.lock.*` 같은 락 지표가 없다.
- **영향.** LDAP 회차의 리스 상실은 실행 기록 메시지와 ERROR 로그로만 보인다.
- **우회.** 실행 기록 메시지 "작업 도중 락 리스를 잃었습니다" 를 로그 경보로 건다.
- **상태.** 확인함 — 설계 문서에 판단이 없다.

### 6.9 실제 AWS 로 확인하지 못한 기동 검사와 시간 한도

- **무엇.**(운영 준비 설계 §16)
  - 실제 AWS 가 막 만든 테이블의 PITR 요청을 한동안 `ContinuousBackupsUnavailableException` 으로 거절하는지. 2분 재시도는 이것을 전제로 한다. DynamoDB Local 은 PITR API 를 받지 않아 가짜 클라이언트로만 시험했다.
  - 실제 AWS 가 GSI2 의 `INCLUDE` 프로젝션에 GSI3 의 파티션키 속성(`externalId`)을 받는지. DynamoDB Local 2.5.3 으로만 확인했다.
  - 삭제 보호의 동작은 DynamoDB Local 2.5.3 으로 확인했다. 실제 AWS 는 확인하지 못했다.
  - DynamoDB 시간 한도의 기본값(시도 10초·호출 60초)이 실제 AWS 의 부하에 맞는지. 규모 시험은 Local 기준이다.
- **영향.** 첫 실제 배포에서 테이블을 만들 때 드러난다. PITR 이 2분 안에 켜지지 않으면 `테이블은 만들었으나 PITR 을 켜지 못했다 …` 로 멈춘다(테이블은 남는다). GSI2 프로젝션을 거절하면 테이블 생성이 실패한다.
- **우회.** 처음 설치는 테이블을 미리 만들고 보호를 켠 뒤 띄운다. 프로젝션이 거절되면 설계는 GSI2 를 `ALL` 프로젝션으로 바꾸는 길을 적었다(저장량이 늘고 모양 검사의 기대값이 바뀐다 — 코드 변경이다).
- **상태.** 확인하지 못함.

### 7.10 취소된 회차의 늦은 OpenFGA 쓰기

- **무엇.** 회차가 [기한](02-용어집.md#기한)·[리스 상실](02-용어집.md#리스-상실)·서버 종료로 취소되면 이미 보낸 OpenFGA 요청을 거두지 못한다. 차단기는 나간 배치의 결과를 기다리지만 취소는 기다리지 않는다. 그 요청은 락을 반납한 뒤에 반영될 수 있다([펜싱](02-용어집.md#펜싱) 틈과 같은 모양).
- **영향.** 반납 직후 락을 잡은 다음 작업(SCIM 쓰기의 Check 기준선, 다른 회차)이 늦은 쓰기가 닿기 전의 장부를 볼 수 있다. LDAP 은 [기록 중 표시](02-용어집.md#기록-중-표시)가 남아 다음 회차가 장부 맞추기로 수렴한다. SCIM 재적재는 장부가 반쯤 맞은 채 남는다.
- **우회.** 기한 초과·리스 상실로 끝난 SCIM 재적재는 다시 건다.
- **상태.** 받아들임 — 펜싱 틈(3.2)과 같은 부류로 받아들였다. 협조적 멈춤(멈춤 신호를 보내고 나간 묶음을 기다림)은 바꿀 곳이 많고 효과를 잴 수 없어 미뤘다. 배포 중 회차가 자주 끊긴다는 것이 보이면 다시 연다(운영 준비 설계 §2·§17.5).

### 7.12 일시 장애가 아닌 OpenFGA 오류는 SCIM 500 이다

- **무엇.** SCIM 은 [일시 장애](02-용어집.md#일시-장애)로 분류된 실패만 503 으로 옮긴다. 분류되지 않은 OpenFGA 오류는 500 이다 — 예: 같은 이름의 store 가 둘이라 장부를 정하지 못할 때, store 가 없는데 생성이 꺼져 있을 때(`StoreNotFoundException`).
- **영향.** IdP 가 500 을 다시 보내지 않는 실패로 다룰 수 있다. ERROR "SCIM 요청 처리 중 예기치 않은 오류" 가 남는다.
- **우회.** [12 — store 이름이 틀렸거나 같은 이름의 store 가 둘](12-장애와-복구.md#26-store-이름이-틀렸거나-같은-이름의-store-가-둘)을 따라 store 를 정리한다.
- **상태.** 받아들임 — 표준이 정한 신호(일시 장애)만 503 이고 나머지는 한 규칙(500)이다(운영 준비 설계 §10·§20). 관리 API 도 같은 분류기로 같은 규칙이다.

### 7.14 두 앱이 테이블이나 store 를 함께 써도 막지 않는다

- **무엇.** 배포 하나에 커넥터 하나가 전제다. 두 앱의 `application.yml` 이 테이블·store 이름을 서로 다르게 적지만(`organization` / `organization-scim`, 클래스 기본값은 없다), 두 앱이 같은 테이블·store 를 가리켜도 기동이나 실행 중에 막는 검사가 없다.
- **영향.** 한 앱의 재적재가 다른 앱의 튜플을 지운다. 변경 락·스냅샷 포인터·현재상태를 함께 쓴다.
- **우회.** 배포 설정에서 두 이름을 늘 따로 준다([14 — 두 앱을 같이 띄워도 되나](14-개발-가이드.md#46-두-앱을-같이-띄워도-되나)).
- **상태.** 받아들임 — "배포 하나에 커넥터 하나" 원칙상 따지지 않는 경우다. 테이블·store 묶음 표지는 막는 것에 비해 비용이 커 버렸다(운영 준비 설계 §17.1).

### 7.15 락 반납·하루 1회 표지의 로그 문구가 사정과 다를 때가 있다

- **무엇.**(코드로 확인)
  - SCIM 쓰기가 락 획득을 포기하며 결과를 모르는 시도의 토큰으로 반납을 보내면, 그 시도가 서버에 닿지 않았을 때 `DynamoDbMutationLock.release` 가 WARN "변경 락 반납 실패 — 이미 리스를 잃은 상태다. TTL(…)이 작업 시간보다 짧다는 신호다" 를 남긴다. 이때는 TTL 과 상관없다 — 스로틀 중의 503 마다 이 줄이 따라 나올 수 있다.
  - 하루 1회 작업이 실패하면 INFO "<작업>(<날짜>) 이 <까닭> — 표지를 풀어 창 안의 다음 시도가 다시 잡는다" 를 남긴다. 창의 마지막 시도(08:00)에서도 같은 문구다 — 그때는 다음 시도가 다음 날이다.
- **영향.** 로그만 보고 TTL 설정이나 그날 재시도를 잘못 짐작할 수 있다.
- **우회.** 반납 경고는 같은 때의 SCIM 503(`scim.lock.wait`)과 함께 본다. 하루 1회 작업은 실행 기록·`scim.archive.drift.observed` 로 그날 성공했는지 본다.
- **상태.** 확인함 — 구현 점검이 남긴 것이고 동작에는 영향이 없다.
