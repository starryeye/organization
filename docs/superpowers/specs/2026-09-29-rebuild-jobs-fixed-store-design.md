# 재적재를 백그라운드 작업으로, 장부 번호는 고정 — 설계 (점검 권고 슬라이드 ②-1)

**작성일:** 2026-09-29
**근거:** 배포 전 전체 점검 `2026-09-28-full-audit.md` §7 권고 슬라이드 ②. 사용자 결정으로 둘로 나눴고 이것이 ②-1 이다(②-2 는 §12).
**대상:** C3·C2·C7(치명), M13·M17·M6(중)
**브랜치:** `audit-rebuild-jobs` (main `59ae381` 에서)

## 1. 문제

자세한 시나리오·위치는 점검 문서 §4 에 있다. 모두 "재적재가 OpenFGA store(권한 장부)를 어떻게 다루느냐"와 그 주변이다.

| ID | 무엇 | 점검 때 증거 |
|---|---|---|
| C3 | 관리 API 재적재·수동 동기화가 HTTP 요청에 묶여 있다. 앞단 프록시가 60초에 끊으면 작업이 취소돼 store 는 반쯤 빈 채로, 실행 기록은 영원히 RUNNING 으로, 락은 풀린 채 남는다 | 재현(유스케이스) |
| C2 | 재적재가 store 를 지우고 같은 이름으로 새로 만든다. 다른 인스턴스는 옛 storeId 를 캐시한 채 지워진 store 에 쓰고 "성공"으로 답한다 | 재현(메모리 엔진) |
| C7 | OpenFGA 가 느리거나 죽으면 재적재가 전체 기한 없이 배치마다 재시도하며 하트비트로 리스를 계속 갱신해, 수십 분~수십 시간 모든 SCIM 쓰기가 503 이다 | 코드로 셈 |
| M13 | 재적재가 읽기(DynamoDB `loadAll`·LDAP `fetchAll`) **전에** store 를 비운다. 읽기가 실패하면 전사 권한이 0 이다 | 코드 |
| M17 | 빈 OpenFGA 에 인스턴스 둘이 동시에 뜨면 같은 이름 store 가 둘 생겨 둘이 다른 store 에 쓴다 | 코드 |
| M6 | 시작 때 OpenFGA 가 안 닿았고 store 가 없으면, Check 가 store 를 만들지 않아 재시작 전까지 멤버 추가가 전부 500 이다. 인가 모델을 쓰기 전에 storeId 를 캐시해, 모델 쓰기가 실패하면 모델 없는 store 를 쥔 채 남는다 | 코드 |

지금 재적재가 store 를 **지우고 다시 만드는** 이유는 OpenFGA Read(목록 읽기) API 를 쓰지 않기로 했기 때문이다 — 장부에 무엇이 남아 있는지
열거할 수 없으니, 모르는 찌꺼기(버그·중단으로 못 지운 튜플, 직접 써 넣은 튜플)까지 없애려면 장부를 통째로 버리는 수밖에 없었다.
그 대가가 인가 공백(재적재 동안 모든 권한 질의가 false), C2(번호가 바뀜), M13(비운 뒤 읽기 실패)이다.

## 2. 결정 — 사용자와 정한 것 (2026-09-29)

- **슬라이드 ② 를 둘로 나눈다.** ②-1 = 이 문서(재적재 작업과 store 수명), ②-2 = M14·M15·M2·M16(§12).
- **장부(store) 번호는 영구히 고정한다. 재적재에서만 OpenFGA Read 를 허용한다.** 재적재는 장부를 버리지 않고, 있어야 할 줄을 쓴 뒤
  Read 로 장부를 훑어 없어야 할 줄만 지운다. Read 는 이 "장부 훑기"(사람이 거는 드문 백그라운드 작업)에서만 쓰고, 평소 쓰기·판단
  경로는 지금처럼 Check·BatchCheck 만 쓴다.
  - 검토한 대안: 블루-그린 바꿔치기(Read 없음, 대신 모든 앱이 "지금 장부 번호"를 따라와야 함), 쓴 줄 원장(Read 없음, 대신 줄 변경마다
    DynamoDB 쓰기 +1, 직접 써 넣은 줄은 못 찾음) — §10.
- 1~4절 설계는 제안대로 승인.

## 3. 재적재는 장부를 버리지 않고 안에서 청소한다

### 3.1 순서 (app-scim `tuples`, app-ldap 재적재 공통)

1. **먼저 읽는다.** 있어야 할 줄 전체 D 를 계산한다 — app-scim 은 `state.loadAll()` + `TupleMapper`, app-ldap 은 `source.fetchAll()` +
   `TupleMapper`. **여기서 실패하면 장부에 아무것도 쓰거나 지우지 않고** FAILED 로 끝난다(M13).
2. **D 를 전부 쓴다.** `writer.apply(TupleDelta.writeOnly(D))`. 이미 있는 줄은 OpenFGA 가 무시하므로(`on_duplicate: ignore`) 빠진 권한만 채워진다.
3. **장부를 훑어 D 에 없는 줄을 지운다.** 새 포트 `RelationTupleScanner#scanAll()` 이 장부의 모든 줄을 페이지로 흘려 주고, D 에 없는 줄을
   모아 `writer.apply(TupleDelta.deleteOnly(...))` 로 지운다(`on_missing: ignore`). 장부 전체를 메모리에 모으지 않고 흘려 보내며 비교한다
   — 메모리에 드는 것은 D(약 11만 줄)와 지울 후보뿐이다.
4. **기록한다.** 스냅샷 = 실제로 장부에 있다고 볼 줄 = `쓰기 성공(written)` ∪ `지우기에 실패한 줄(failed deletes)` — 지우지 못한 찌꺼기를
   스냅샷에 넣어야 다음 LDAP 동기화가 그 줄을 "있는데 없어야 할 줄"로 보고 다시 지운다. app-ldap 은 이어서 `state.replaceWith(directory)`.

**장부를 비우는 순간이 없다.** 1~2 사이엔 새로 생길 권한이 잠깐 없고, 3 전엔 지워질 권한이 잠깐 남을 뿐이다 — 권한 질의는 내내 정상으로 답한다.

**재적재 동안 SCIM 쓰기는 지금처럼 전역 락으로 막는다(503).** 3단계 도중 들어온 정당한 쓰기를 "D 에 없는 줄"로 잘못 지우지 않기 위해서다.
권한 **조회**(다른 앱의 Check)는 막지 않는다. app-ldap 은 실행 가드로 정기 동기화·수동 동기화와 겹치지 않는다(여러 대 겹침은 ②-2 M14).

### 3.2 장부 훑기 — `RelationTupleScanner`

- core 포트 `RelationTupleScanner { Flux<RelationTuple> scanAll(); }` — "장부의 모든 줄". 재적재만 쓴다. 자바독에 "Read API 를 쓰는 유일한
  자리다 — 판단·쓰기 경로에서 쓰지 않는다"를 적는다.
- authz-openfga 구현: `OpenFgaClient#read(ClientReadRequest(빈 키 = 전체), ClientReadOptions.pageSize(100).continuationToken(...).consistency(HIGHER_CONSISTENCY))`
  를 이어받기 토큰이 빌 때까지 반복한다(SDK 0.9.11 에 있음 — `javap` 로 확인). 캐시를 우회해 방금 쓴 줄도 본다.
- 10만 명 추정: 약 11만 줄 ÷ 100 = 약 1,100 번 호출.

### 3.3 모드 정리 (운영 배포 전이라 API 를 바꾼다)

- **app-ldap:** `mode=snapshot`·`mode=store` 를 없애고 모드 하나로 합친다(`POST /admin/sync/rebuild`). 위 방식이 두 모드의 장점 — 스냅샷에
  없는 줄까지 치우기, 인가 공백 없음 — 을 다 가진다. `mode` 파라미터가 오면 400 으로 알린다("모드가 하나로 합쳐졌다").
- **app-scim:**
  - `tuples` — 위 방식.
  - `wipe` — D = ∅ 로 청소해 장부를 비운 **뒤** 조직도(`state.replaceWith(empty)`)를 지운다. 청소가 실패하면 조직도를 건드리지 않고 FAILED
    (다시 실행하면 된다). 확인값(`confirm=<테이블명>`)은 그대로.
- `RelationTupleWriter#resetStore()`·`StoreBootstrapper#recreateStore()` 와 그 테스트를 지운다(C2 — 번호를 바꾸는 코드가 없어진다).

## 4. 요청은 바로 답하고 작업은 따로 돈다 (C3)

- `POST /admin/sync/rebuild`(두 앱), app-ldap `POST /admin/sync/full`:
  1. **겹침 검사는 요청 안에서** — app-scim 은 전역 락(`LockPurpose.REBUILD`, 재시도 없음), app-ldap 은 실행 가드. 못 잡으면 **409** 를 곧바로 준다(지금과 같음).
  2. 잡았으면 `SyncRun` 을 시작(RUNNING)하고, 작업을 **요청 구독과 분리해** 띄운 뒤 곧바로 **202 Accepted** + 실행 기록(`runId`, `status: RUNNING`)을
     돌려준다. 작업은 앱 수명에 묶인 전용 실행기에서 돈다 — HTTP 연결이 끊겨도 취소되지 않는다.
  3. 결과는 `GET /admin/sync/runs`(지금)와 새 `GET /admin/sync/runs/{runId}`(없으면 404)로 본다.
- **정상 종료:** 앱이 내려갈 때 돌던 작업을 멈추고 FAILED("서버 종료로 중단")로 기록한 뒤 락·가드를 푼다.
- **app-ldap 재시작 정리:** 앱이 뜰 때 app-ldap 의 RUNNING 기록을 FAILED("재시작으로 중단")로 정리한다 — 실행 가드가 프로세스 안에만 있어
  재시작 시점에 살아 있는 작업이 없다(여러 대는 ②-2 M14 에서 다시 본다).
- 스케줄 동기화·아카이빙은 지금도 요청과 무관하게 돌므로 바뀌지 않는다.
- `SyncRunRepository` 에 `findById(runId)` 가 는다(RUNNING 조회·단건 API).

## 5. 작업에 기한을 둔다 (C7)

- **전체 기한** `sync.job-timeout`(기본 30분, 두 앱): 넘으면 남은 일을 멈추고 FAILED("기한 초과 — N분")로 기록하고 락·가드를 푼다.
  10만 명 재적재(쓰기 약 1,100 배치 + 장부 훑기 약 1,100 호출)는 수 분으로 추정하므로 넉넉하다.
- **연속 실패 차단기:** 쓰기 배치가 **3번 연달아** 실패하면(배치마다 재시도한 뒤에도) 남은 배치를 보내지 않고 오류
  (`TupleWriteAbortedException` — 그때까지 실제로 나간 것, 보내지 않은 줄은 실패로)로 끝낸다. `OpenFgaRelationTupleWriter` 에 둔다.
  드문 실패 한두 건은 지금처럼 부분 실패(PARTIAL)로 넘어간다. 배치가 셋보다 적은 쓰기는 해당이 없다 — SCIM 요청 한 건은 대개 여기에 든다.
  멤버가 200명 넘게 바뀌는 조직 PATCH·PUT 은 예외로, 멈추면 5xx 가 되고 IdP 재시도가 Check 기준선으로 수렴한다.
- 차단기로 멈춘 작업도 §3.1 4단계 기록 규칙을 따른다 — 이미 나간 쓰기는 되돌리지 않고 그것으로 스냅샷을 남긴 뒤(app-ldap 은 현재상태도
  바꾼다), 멈췄다는 사실을 FAILED 로 남긴다. 예외는 재적재가 **쓰기 단계**(§3.1 2단계)에서 멈춘 경우다 — 장부를 훑기 전이라 지울 줄을 몰라
  새 스냅샷을 만들지 않는다. **기한·서버 종료**로 멈춘 작업도 새 스냅샷을 만들지 않는다(§11).

## 6. 장부를 처음 만들 때 (M17·M6)

- **동시 첫 생성 수렴(M17):** `StoreBootstrapper` 가 store 를 **만든 직후** 같은 이름 목록을 다시 본다. 둘 이상이면 모두가 **가장 먼저 만들어진
  것**(`createdAt`, 같으면 id 사전순)을 쓰고, 그것이 자기가 만든 것이 아니면 방금 만든 자기 store 를 지운다. 동시에 떠도 결국 하나로 모인다.
  - 이미 오래전부터 같은 이름 store 가 둘 이상인 경우(찾기 단계에서 발견)는 지금처럼 **멈추고 알린다** — 어느 쪽에 진짜 데이터가 있는지 모른다.
- **Check 도 준비 과정을 탄다(M6):** `OpenFgaRelationTupleChecker` 가 `findExistingStore()`(없으면 오류) 대신 쓰기와 같은 `resolveStore()`(없으면
  만들고 모델 등록)를 쓴다. 첫 요청 때 OpenFGA 가 닿으면 그때 준비되고, 안 닿으면 그 요청만 실패하고 다음 요청이 다시 시도한다.
  헬스 체크는 지금처럼 `findExistingStore()`(보기만)다 — 오타 난 이름으로 빈 store 를 만들지 않는다.
- **모델 등록 뒤에만 번호를 기억한다(M6 곁가지):** storeId 캐시는 인가 모델 쓰기가 성공한 뒤에 채운다.

## 7. 다른 앱에게 주는 약속·README

- "장부는 한 번 만들어지면 번호가 바뀌지 않는다. 다른 앱은 이름으로 찾아도, 번호를 설정에 적어 두어도 된다."
- 재적재 절을 새로 쓴다: 202 로 바로 답함·`GET /runs/{runId}`, 인가 공백 없음(대신 쓰기는 503), 모드 정리, `sync.job-timeout`, 연속 실패 차단기,
  정상 종료·재시작 정리. 옛 "인가 공백이 생긴다", "중간에 실패하면 권한이 없는 채로 남는다", "요청이 그동안 매달려 있다" 문단을 바꾼다.
- 76행의 낡은 문장("Read/Check/ListObjects 호출이 없다")을 사실대로 고친다: 판단·쓰기 경로는 Check·BatchCheck, Read 는 재적재의 장부 훑기에서만.

## 8. 검증

테스트 규칙은 기존과 같다(Lombok, AssertJ, BDD, 한글 `@DisplayName`). 각 테스트는 먼저 지금 코드로 실패하는 것을 본 뒤 고친다.

| 대상 | 확인할 것 | 모듈 |
|---|---|---|
| 재적재 순서 | 읽기(`loadAll`/`fetchAll`)가 실패하면 장부에 쓰기·지우기가 하나도 없다. D 를 쓰고, 훑은 줄 중 D 에 없는 것만 지운다. 지우기 실패분은 스냅샷에 남는다. `wipe` 는 청소 뒤에만 조직도를 지운다 | core |
| 장부 훑기 | 테스트용 OpenFGA 에 100줄 넘게(페이지 둘 이상) 넣고 전부 읽는다. 직접 써 넣은 줄도 나온다 | authz-openfga |
| 번호 고정 | 재적재 전후 storeId 가 같다. 재생성 코드가 없다 | authz-openfga·E2E |
| 백그라운드 작업 | 요청 구독이 취소돼도 작업이 끝까지 가 결과를 기록한다(점검 C3 재현을 정식으로). 202 + runId, 겹치면 409, `GET /runs/{runId}` 200·404. 정상 종료 시 FAILED + 락 반납. app-ldap 재시작 시 RUNNING 정리 | core·앱 |
| 기한·차단기 | 기한을 넘기면 FAILED + 락 반납. 배치 3번 연속 실패면 나머지를 보내지 않는다 | core·authz-openfga |
| 장부 준비 | 부트스트래퍼 둘이 빈 OpenFGA 에 동시에 떠도 store 하나로 모인다. store 가 없을 때 Check 가 만든다. 모델 등록이 실패하면 번호를 기억하지 않는다 | authz-openfga |
| E2E | 재적재가 OpenFGA 에 직접 심은 찌꺼기 줄을 지우고 있어야 할 권한은 남긴다. 재적재 중 기존 권한 Check 가 true 로 남는다(공백 없음) | app-scim·app-ldap |

머지 전 컨트롤러가 `./gradlew cleanTest test` 와 `./gradlew cleanScaleTest scaleTest` 를 한 번에 하나씩 돌리고, 규모 테스트에서 재적재의
장부 훑기 비용(읽은 줄 수·호출 수·시간)과 재적재 전체 시간을 §9 에 적는다.

## 9. 결과 (구현 후 기록)

머지 전 `test`·`scaleTest` 시간과 재적재 규모 측정을 구현이 끝나면 여기에 적는다.

## 10. 왜 다른 길을 안 갔나

- **블루-그린 바꿔치기.** 옛 장부는 두고 새 장부를 옆에서 다 채운 뒤 "지금 장부 번호" 표시를 한 번에 바꾼다. Read 가 필요 없고 공백도 없다.
  대신 이 서버의 모든 인스턴스와 **모든 소비자 앱**이 "지금 번호"를 매번(또는 자주) 확인해야 하고, OpenFGA 에 이름 바꾸기가 없어 바꿔치기
  동안 같은 이름 장부가 둘이다. 움직이는 부품(표시 기록·인스턴스별 확인·옛 장부 정리)이 많다.
- **쓴 줄 원장.** 이 서버가 쓰는 모든 줄을 쓰기 **전에** DynamoDB 원장에 적고, 재적재는 원장으로 청소한다. Read 금지를 지키지만 줄 변경마다
  DynamoDB 쓰기가 하나 더 붙고(최초 적재 약 11만 번), 쓰기 경로 전부에 원장을 끼워야 하며, 이 서버를 거치지 않고 직접 써 넣은 줄은 못 찾는다.
- **지금처럼 재생성 + 번호 공유.** 재생성은 두고 새 번호를 DynamoDB 로 모든 인스턴스에 알린다(C2 만 해결). 인가 공백과 M13 이 남고,
  소비자 앱도 새 번호를 따라와야 한다.
- **재적재 중 SCIM 쓰기 허용.** 청소(3단계)가 도중에 들어온 정당한 줄을 지울 수 있어 정확성을 잃는다. 쓰기 중지(503)를 유지한다.

## 11. 이 설계가 말할 수 없는 것

- **재적재 동안 SCIM 쓰기는 여전히 503 이다.** 그 시간은 규모 측정으로 §9 에 적는다(추정 수 분).
- **서버가 강제로 죽으면(kill -9, 정전) 그 작업은 기록에 RUNNING 으로 남는다(app-scim).** 락은 TTL(30초) 뒤 풀려 다음 작업은 할 수 있다.
  app-ldap 은 다음 시작 때 정리된다.
- **기한·서버 종료로 멈춘 작업은 이미 나간 쓰기를 모을 곳이 없어 새 스냅샷을 만들지 않는다.** 그 사이 조직도가 바뀌면 기준선이 장부와
  어긋날 수 있다(②-2 M2 와 같은 부류) — 재적재로 맞춘다. 재적재가 쓰기 단계에서 차단기로 멈춘 경우도 같다(장부를 훑기 전이라 지울 줄을 모른다).
- **장부 훑기의 운영 속도는 모른다.** 테스트용 OpenFGA(메모리 엔진)로만 잰다. 운영(Postgres) Read 속도·페이지 크기 한도는 실연동 뒤 확인한다.
- **Read 로 훑는 동안 다른 앱이 장부에 직접 쓰면**(이 서버를 거치지 않는 쓰기) 그 줄은 D 에 없어 지워진다 — 장부는 이 서버만 쓴다는 전제다.
- **동시 첫 생성 수렴은 OpenFGA store 목록이 생성 직후 바로 보인다는 전제**다(같은 OpenFGA 서버라 성립한다고 본다).

## 12. 범위 밖 (백로그)

- **②-2** — M14 app-ldap 여러 대 겹침(클러스터 락), M15 아카이빙이 인스턴스마다·재적재와 겹침, M2 LDAP 회차가 OpenFGA 반영 뒤·스냅샷 저장
  전에 끊기면 기준선 어긋남, M16 잘못된 줄 하나가 배치 100개를 함께 실패시킴(4xx 재시도 안 함 포함).
- 쓰기 병렬화 등 재적재 성능 — 점검 권고 ③.
