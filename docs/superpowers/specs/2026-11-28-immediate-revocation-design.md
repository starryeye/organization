# 한 사람 즉시 회수 설계 (2026-11-28)

온보딩 13 §4.6 "회수는 다음 정각에 닿는다"의 한 갈래를 닫는다. 관리 API 로 직원 한 사람을 지목하면 LDAP 에서 그 사람만 다시 읽고, 디렉터리가 막았거나 그 사람이 없으면 그 사람의 권한 줄을 바로 지운다. 증분 읽기(누가 부르지 않아도 빨라지는 것)는 범위 밖이다.

사용자 결정은 "추천대로"(2026-11-28)다. 아래 결정은 모두 그 추천이다. 빌더 점검(코드와 대조한 무지식 검토)이 넷을 짚었고 모두 내 판단으로 반영했다 — 없는 DN 의 32 를 "없음" 으로(V3), 주소 넘김과 요청 상한(§5.2), 503 은 일시 장애 신호만(V2⑤), 현재상태가 입력이 되는 데서 오는 놓침(V13·§11).

## 1. 문제

- **막은 계정의 권한이 최대 한 시간 남는다.** LDAP 은 매 정각 전체를 읽는다(`sync.cron` 기본 `0 0 * * * *`). 정각 읽기 직후에 막으면 "다음 정각 + 회차 시간" 까지 권한이 남고, 회차가 실패하면 더 늦다(05 §12).
- **비상 경로가 회차 하나 통째다.** `POST /admin/sync/full` 은 한 사람을 위해 10만 명을 읽는다. 10만 명 전체 읽기 시간은 재지 않았고(13 §5.1), 다른 회차가 돌면 409 다.
- **회수 수렴 설계(2026-10-20 §8)가 "개인 즉시 회수 API 와 증분은 이 슬라이드 밖" 으로 남겼다.** 외부 리뷰(2026-10-19) 지적 가운데 맡은 슬라이드가 없는 갈래다.

## 2. 목표·비목표·반목표

- **목표.** 퇴사 처리처럼 "이 사람을 지금 막아야 한다" 는 때, 디렉터리에서 막은 뒤 요청 하나로 몇 초 안에 그 사람의 권한 줄을 지운다. 요청 하나의 비용은 그 사람 크기다.
- **비목표.** 누가 부르지 않아도 빨라지는 것(증분·변경 통지). 부여(풀린 사람을 바로 다시 쓰기). 현재상태를 바로 고치기. SCIM 배포(IdP 의 `active=false` PATCH 가 이미 즉시다). 여러 사람을 한 요청으로(대량 퇴사는 디렉터리를 고친 뒤 `POST /admin/sync/full`).
- **반목표.** 이것을 넣고 나서 다음 정각 회차의 결론이 틀어지면 실패다. 특히 **회수 뒤 디렉터리에서 다시 풀린 사람의 권한이 영원히 돌아오지 않으면** 실패다 — 직전 스냅샷의 B 가 "그 줄은 장부에 있다" 고 믿으면 다음 회차의 `D − B` 가 그 줄을 다시 쓰지 않는다. 디렉터리를 거슬러 운영자 말만으로 지워 원천이 둘로 갈려도 실패다. 요청마다 전원을 읽어도 실패다.

## 3. 접근안

모든 안이 같은 일을 한다 — LDAP 에서 그 사람을 다시 읽고, 막혔거나 없으면 그 사람의 `direct_member` 줄을 지운다. 다른 것은 **다음 회차의 기준선이 그 사실을 어떻게 아느냐**다.

| 안 | 내용 | 판단 |
|---|---|---|
| **A (고름)** | 지우기 전에 스냅샷 포인터 줄에 "결과를 모르는 줄" 로 먼저 적고, 지운 뒤 "확실히 지운 줄" 로 고친다. 다음 회차는 기준선을 읽을 때 이 표시를 반영한다(지운 줄은 B 에서 빼고, 모르는 줄은 U 로 옮긴다). 새 스냅샷 저장이 표시를 지운다. 거둘 줄은 현재상태의 소속에서 후보를 뽑고 OpenFGA Check 로 실제로 있는 것만 고른다 | 요청 하나가 LDAP 검색 한 번·소속 조회 한 번·BatchCheck·쓰기 한 번·포인터 갱신 두 번이다. 의도를 먼저 적어 어디서 죽어도 다음 회차가 U 의 규칙으로 수렴한다. 대신 다음 회차의 기준선 읽기와 변경 없음 길이 바뀐다 |
| B | 회수마다 직전 스냅샷을 통째로 읽고, 그 사람의 줄을 뺀 스냅샷을 새로 저장한다 | 다음 회차의 코드가 그대로라 가장 단순하다. 그러나 10만 명이면 요청마다 약 6MB 를 강한 일관성으로 읽고 약 6MB 를 쓴다. 락을 몇 초씩 쥐고, 회수마다 스냅샷이 하나씩 보관 기간(기본 7일) 동안 남는다. 300명을 한꺼번에 내보내면 락을 20분 가까이 쥐어 정각 회차가 건너뛰어질 수 있다. "요청당 전원 읽기 금지" 에 걸린다 |
| C | 지운 뒤 기준선을 "기록 중" 으로 둔다(`markWriting`) | 다음 회차가 장부 맞추기로 수렴하니 코드가 작다. 그러나 퇴사자가 나올 때마다 다음 회차가 OpenFGA 장부 전체를 Read 로 훑는다. Read 는 재적재와 기준선을 믿을 수 없는 LDAP 회차에서만 쓰기로 했다(2026-10-20) — 그 밖으로 넓힌다 |
| D | 기준선을 건드리지 않고 지우기만 한다 | §2 반목표 그대로다 — 회수 뒤 다음 회차 전에 다시 풀면 B 가 "있다" 고 믿어 줄이 영원히 안 돌아온다(재적재 전까지) |
| E | LDAP 을 읽지 않고 운영자가 지목한 사람을 지운다 | 디렉터리가 아직 활성이면 다음 회차가 다시 쓴다. 원천이 둘로 갈린다. 막으려면 운영자 거부 목록이 따로 있어야 한다 |
| F | 주기를 줄이거나(`sync.cron`) 바뀐 엔트리만 자주 읽는다 | 주기 단축은 전체 읽기 비용이 그대로 배로 는다. 증분(`modifyTimestamp`·USN·DirSync)은 엔트리 삭제·그룹 탈퇴를 잡기 어렵고, 변경 번호가 DC 마다 따로라 DC 넘김과 맞물려 변경을 놓치며, 스냅샷 비교 모델에 부분 그림을 넣어야 한다 — 범위 밖(§12) |

A 안에서 거둘 줄을 고르는 법도 셋을 견줬다.

| 거둘 줄 | 판단 |
|---|---|
| **현재상태 소속 → Check (고름)** | 그 사람 크기다. Check 는 판단 경로에 허용된 호출이고(`HIGHER_CONSISTENCY`), 장부에 없던 줄을 "회수" 로 이력에 적지 않는다. 현재상태에 없는 소속의 줄(지난 회차의 지우기가 실패해 남은 줄)은 놓친다 — 그 줄은 다음 회차가 지금처럼 지운다(§11) |
| 직전 스냅샷의 B ∪ U | 정확하지만 요청마다 스냅샷 전체(약 6MB)를 읽는다 |
| 현재상태 소속을 Check 없이 | 이미 막혀 줄이 없는 사람(정각 회차가 먼저 막았다)을 부르면 없던 줄을 "회수" 로 이력에 적는다 |

## 4. 결정

| # | 결정 | 이유 |
|---|---|---|
| V1 | **끝점은 `POST /admin/sync/revocations`, 본문 `{"employeeId": "<직원 id>"}`, 범위 `admin.sync`, app-ldap 만.** 받으면 202 와 막 연 실행 기록(RUNNING)이다. 결과는 `GET /admin/sync/runs/{runId}` | 회차와 같은 장치(락·실행 기록·이력)를 타므로 같은 경로 아래 둔다. id 에 경로에 쓰기 어려운 글자가 들 수 있어 본문으로 받는다. 디렉터리가 막았다고 확인한 줄만 지우므로 수동 동기화와 같은 범위다 |
| V2 | **락을 잡기 전에 차례로 본다.** ① `employeeId` 가 없거나 비면 400. ② 현재상태에 그 직원이 없으면 404. ③ LDAP 에서 그 사람을 읽는다(§5.2 — 주소마다 한 번, 요청 전체 상한 30초). ④ 활성이면 409 — `디렉터리에서 활성인 직원은 거두지 않습니다 — 디렉터리에서 먼저 막으세요`. ⑤ 읽기가 실패하면 **표준이 정한 일시 장애 신호만 503** + `Retry-After` 다 — 연결 실패(`CommunicationException`), 서버가 바쁨·쓸 수 없음(RFC 4511 결과 51·52, `ServiceUnavailableException`), 요청 상한 30초 초과. **그 밖은 모르는 종류까지 500** 이다. ⑥ 막혔거나 없으면 작업을 띄운다(V4) | LDAP 입출력(시간 초과·DC 넘김)을 락 밖에 두어 정각 회차를 막지 않는다. 오타 id 가 "거둘 줄 없음" 으로 조용히 끝나지 않는다. 디렉터리를 먼저 막지 않은 요청은 실행 기록 없이 바로 알린다. 정기 읽기의 재시도(약 2~6분)는 요청 하나에 너무 길다. 503 을 허용 목록으로 두는 것은 13 §7.12 와 같은 규칙이다 — 정기 읽기의 `다시_읽어도_같은가` 는 회차를 살리려고 모르는 종류를 일시 장애로 보지만, 요청에서 그렇게 하면 퇴사 처리 스크립트가 코드 버그를 끝없이 다시 부르고 아무도 모른다(빌더 점검 4, 내 판단) |
| V3 | **한 사람 읽기는 정기 읽기와 같은 규칙의 부분집합이다**(§5.2). 전략의 직원 검색(베이스·필터·요청 속성·매퍼·계정 상태·건너뛰기 규칙)에 `(<직원 식별 속성>=<id>)` 를 AND 로 더한다. 정규화한 id 가 요청 id 와 정확히 같은 엔트리만 고른다. id 로 못 찾으면 현재상태의 `externalId`(DN)를 base 범위로 한 번 더 읽는다 — **그 DN 이 없으면(결과 32, `NameNotFoundException`) "없음" 이다.** id 검색의 32(검색 베이스 자체가 없음)는 설정 오류라 500 이다. 고른 것 가운데 활성이 하나라도 있으면 활성, 있으면 막힘, 없으면 없음 | 정기 읽기가 그릴 그림과 다르게 판정하면 이 API 가 정각 회차와 다툰다. 대소문자만 다른 엔트리는 정기 읽기에서도 다른 사람이다. id 정규화가 글자를 `_` 로 바꾼 경우(공백이 든 `cn` 등)에는 id 검색이 그 사람을 못 찾으므로 DN 으로 다시 본다 — 활성인 사람을 "없음" 으로 거두지 않는다. 엔트리를 지운 퇴사자는 id 검색 0건 → DN 다시 읽기 → 32 로 늘 이 길을 탄다. 템플릿은 `NameNotFoundException` 을 삼키지 않으므로(`LdapTemplates.configured`) DN 읽기에서만 그것을 "없음" 으로 바꾼다(빌더 점검 1, 내 판단). id 가 겹치는 엔트리 가운데 하나라도 활성이면 거두지 않는 쪽이 안전하다 |
| V4 | **작업은 `SyncJobs.startLockedThen` 으로 띄운다** — 출처 LDAP, 트리거 `REVOCATION`, 락 용도 `REVOCATION`, 이력 종류 `REVOCATION`(셋 다 새 값). 락을 못 잡으면 409 `다른 동기화·재적재가 진행 중입니다`(`/full` 과 같다). 기한·리스 상실·서버 종료·죽은 기록 닫기 규칙은 그대로다 | 정각 회차·재적재와 동시에 돌면 기준선이 어긋난다(§5.4). 같은 장치라 실행 기록·이력·추적이 그대로 붙는다 |
| V5 | **거둘 줄은 현재상태 소속에서 뽑아 Check 로 거른다.** 후보 = `findGroupIdsContaining(USER u)` 의 조직마다 `(user:u, direct_member, group:g)`. 거둘 줄 E = `RelationTupleChecker.existing(후보)`. E 가 비면 OpenFGA 쓰기도 표시도 없이 `SUCCEEDED`, 메시지 `즉시 회수 — 장부에 거둘 줄이 없습니다` | §3 의 둘째 표. 직원은 `direct_member` 의 주어로만 장부에 든다(`TupleMapper`) |
| V6 | **기준선이 PRESENT 이면 지우기 전에 표시부터 적는다.** 포인터 줄의 `revokedUnknown` 에 E 를 더한다. 조건은 포인터의 스냅샷 번호가 방금 읽은 값과 같고 `writingSince` 가 없는 것. 한도를 넘거나(V9) 조건·쓰기가 실패하면 `FAILED` 이고 아무것도 지우지 않는다. **WRITING·NONE 이면 표시하지 않는다** | 의도가 먼저라, 지우는 도중이나 뒤에 무슨 일이 생겨도 다음 회차는 그 줄을 U 로 보고 디렉터리대로 다시 정한다(쓰거나 지운다). WRITING·NONE 의 다음 회차는 장부를 훑어 맞추므로 고칠 기준선이 없다 |
| V7 | **지우기는 지울 줄만 든 델타로 `RelationTupleWriter.apply` 를 부른다.** 배치·거절 반쪽 쪼개기·차단기·멱등 옵션이 그대로다. 배치가 끝날 때마다 지운 줄을 이력에 [회수]로 남긴다(원인 `REVOCATION`, 행위자는 요청자) | 쓰기 규칙을 하나로 둔다 |
| V8 | **PRESENT 이면 지운 뒤 표시를 정리한다.** 지운 줄은 `revokedUnknown` 에서 빼고 `revokedGone` 에 더한다. 확정 실패한 줄은 `revokedUnknown` 에서만 뺀다(장부에 남았으니 B 가 맞다). 불확실 실패한 줄은 남긴다. 조건은 V6 과 같다. 정리가 실패하면 결론은 쓰기 결과대로 두고 메시지 끝에 ` — 즉시 회수 표시를 정리하지 못했습니다. 다음 동기화가 그 줄을 다시 지웁니다` 를 붙인다. 차단기로 멈추면 그때까지의 결과로 정리하고 `FAILED` 다 | 회차의 새 스냅샷 식(05 §6.6)과 같은 규칙이다 — 확정된 것만 확정으로 옮긴다. 정리가 실패해도 남은 표시는 "모름" 이라 안전한 쪽이다 |
| V9 | **표시는 두 칸의 원소 길이 합 256KB 를 넘지 않는다.** 더하면 넘게 되면 표시 전에 `FAILED` — `즉시 회수 표시가 한도(256KB)를 넘습니다 — 다음 동기화가 기준선을 새로 남긴 뒤 다시 거세요. 여럿이면 디렉터리에서 막은 뒤 POST /admin/sync/full 을 쓰세요` | 포인터 줄은 아이템 하나라 400KB 가 한도다. 줄 하나가 보통 약 90바이트라 약 2,800줄이다. 표시는 다음 회차가 지우므로(V10) 한도에 닿는 것은 전부 보류가 이어지는 동안뿐이다 |
| V10 | **다음 회차(PRESENT)는 표시를 반영한 기준선으로 비교한다.** `B′ = B − gone − unknown`, `U′ = (U − gone) ∪ unknown`. 델타·삭제 가드 기준 수(|B′|+|U′|)·새 스냅샷 식이 모두 B′·U′ 다. 새 스냅샷 저장(포인터 PutItem)이 표시를 지운다. **델타가 비었는데 표시가 있으면 B′ 로 스냅샷을 새로 남긴다** — `SUCCEEDED`, 0건, `snapshotId` 있음, 메시지 `변경 없음 — 즉시 회수를 기준선에 반영해 스냅샷을 새로 남김`. 이때 U′ 는 비어 있고(unknown 은 늘 델타를 만든다), I 는 이번 그림의 비활성 소속 줄이다. 전부 보류(아무것도 쓰지 않은 ABORTED)는 저장하지 않아 표시가 남는다. 장부 맞추기(WRITING·NONE)와 재적재는 표시를 읽지 않고, 그 저장이 표시를 지운다 | 반목표(§2)를 막는 자리다. 다시 풀린 사람의 줄은 B′ 에 없으니 `D − B′` 가 다시 쓴다. 지운 줄을 B′ 에서만 빼고 U′ 에 넣지 않으므로 다음 회차가 같은 줄을 다시 지워 이력에 두 번 적지 않는다. 변경 없음에서 저장하는 것은 표시의 수명을 "다음 성공 회차까지" 로 묶기 위해서다 — 회수된 사람은 다음 그림에서 비활성이라 델타를 만들지 않는다 |
| V11 | **실행 기록.** 트리거 `REVOCATION`, `requestedBy` 는 요청자. 결론은 실패가 없으면 `SUCCEEDED`, 있으면 `PARTIAL`(메시지 `N건의 튜플 적용에 실패했습니다. 다음 동기화가 다시 시도합니다`), 오류면 `FAILED`. 메시지 앞머리는 `즉시 회수 — 디렉터리에서 막힘` 또는 `즉시 회수 — 디렉터리에 없음`. **직원 id 는 싣지 않는다** — 요청자가 알고, 이력의 줄이 담는다. `snapshotId` 는 없다 | 로그·메시지에 직원 id 를 싣지 않는 규칙을 지킨다. 같은 회차 표시(목록·단건·이력의 원인)가 그대로 붙는다 |
| V12 | **새 지표·설정은 없다.** `sync.duration` 에 `trigger=REVOCATION` 계열이 저절로 생기고, `sync.tuples.deleted`·`sync.tuples.failed{source=LDAP}` 에 더해진다(실제로 지운 줄이다). **`sync.last.success` 는 `REVOCATION` 회차를 세지 않는다** | 그 게이지는 "디렉터리 그림을 받아들여 반영까지 마친 회차" 다. 세면 정각 회차가 몇 시간 실패하는 동안에도 회수 요청 하나가 경보를 끈다 |
| V13 | **그대로 두는 것.** 현재상태(다음 회차가 바꾼다), 재활성 가드의 I, 삭제 가드(한 사람이라 보지 않는다), 부여(하지 않는다), SCIM | 현재상태는 회차의 권한 판단에 쓰이지 않는다. 이 API 에서는 처음으로 입력이 된다 — 404(V2②), DN(V3), 거둘 줄 후보(V5). 그래서 현재상태가 장부보다 뒤처진 때의 놓침을 받아들이고 §11 에 적으며, 05 §6.7 의 "현재상태는 판단에 쓰이지 않는다" 문장도 고친다(빌더 점검 3, 내 판단). 현재상태를 이 요청이 고치지 않으므로 그동안 관리 API 의 직원 상세가 옛 활성·소속을 보인다. I 는 "직전 회차 그림의 사실" 이라 이 요청이 바꿀 것이 아니다 |
| V14 | **저장 모양.** 포인터 줄(PK `SNAPSHOT_POINTER`, SK `LATEST`)에 String Set 두 칸 `revokedGone`·`revokedUnknown`. 원소는 튜플 한 줄의 문자열(`Keys.tupleSk` 꼴 `user|relation|object`). 칸이 없으면 빈 집합(DynamoDB 는 빈 집합을 담지 못한다 — 마지막 원소를 빼면 칸이 사라진다). `findLatest` 는 같은 포인터 읽기에서 두 칸을 함께 읽어 스냅샷과 함께 준다. 풀 수 없는 원소는 `SnapshotIntegrityException`(기준선 무결성과 같은 규칙, 처방도 재적재) | 표시가 기준선과 수명이 같다 — 스냅샷 저장이 포인터를 통째로 다시 쓰며 지우고, `markWriting`(UpdateItem)은 남기지만 WRITING 길은 읽지 않는다. 아이템 하나라 조건부 갱신 하나로 기준선과 함께 맞는다. 별도 아이템은 트랜잭션·정리가 따로 든다 |
| V15 | **B′·U′ 계산은 core 가 한다.** 저장소는 표시를 담고 읽어 줄 뿐이다 | 반목표를 막는 규칙이 core 시험(가짜 저장소)에서 보인다 |

## 5. 흐름

### 5.1 요청

```
POST /admin/sync/revocations
Authorization: Bearer <admin.sync 범위의 토큰>
Content-Type: application/json

{"employeeId": "3f6c1d52-8a0e-4b7d-9c21-5e0f7a4d2b18"}

→ 202 Accepted
{
  "runId": "20261128T051203.120Z-9a7c3e1f-…",
  "source": "LDAP",
  "trigger": "REVOCATION",
  "status": "RUNNING",
  …
  "requestedBy": "client:hr-offboarding"
}
```

| 응답 | 때 |
|---|---|
| 202 | 디렉터리가 막았거나 그 사람이 없어 작업을 띄웠다 |
| 400 | `employeeId` 가 없거나 비었다 |
| 401·403 | 토큰·범위(`admin.sync`) |
| 404 | 현재상태에 그 직원이 없다 |
| 409 | 디렉터리에서 활성이다 / 다른 동기화·재적재가 락을 쥐고 있다 |
| 503 + `Retry-After` | LDAP 읽기가 모든 주소에서 일시 장애 신호로 실패했거나 30초를 넘김(V2⑤), 락·실행 기록의 일시 장애(지금과 같다) |
| 500 | 그 밖의 LDAP 실패 — 인증·권한·검색 베이스 없음·데이터 오류·모르는 종류 |

오류는 RFC 9457 problem details 다. 사유는 `detail` 에 싣는다.

### 5.2 한 사람 읽기

`DirectorySnapshotSource` 옆에 한 사람의 계정 상태를 묻는 포트를 둔다(이름은 계획에서). 답은 셋이다 — 활성, 막힘, 없음.

| 전략 | 베이스 | 필터 |
|---|---|---|
| groupOfNames | `ldap.group-of-names.user-search-base` | `(&<group-of-names.user-filter>(<user-id-attribute>=<id>))` |
| DIT | `ldap.dit.root-dn` | `(&<dit.user-filter>(<user-id-attribute>=<id>))` |

- 값 쓰기: 식별 속성이 `objectGUID` 면 GUID 문자열을 16바이트로 되돌려(`LdapIdentifiers.guid` 의 역 — 앞 세 묶음은 바이트를 뒤집는다) `\xx` 로 쓴다. GUID 모양이 아니면 검색하지 않고 "id 로 못 찾음" 이다. 그 밖의 속성은 RFC 4515 로 이스케이프한다.
- 요청 속성·엔트리 매퍼·계정 상태(`AccountStatus.막혔는가`, 읽기 시작 시각과 비교)·건너뛰기(한도 넘음, 식별 속성 없음)는 정기 읽기의 것을 그대로 쓴다.
- 고르는 엔트리: 정규화한 id 가 요청 id 와 **정확히** 같은 것.
- id 로 하나도 못 고르면, 현재상태의 그 직원 `externalId`(서버가 준 절대 DN)가 전략의 직원 검색 베이스 아래일 때만 그 DN 을 base 범위·같은 필터로 한 번 더 읽어 같은 규칙으로 고른다. 그 DN 이 없으면(`NameNotFoundException`) 고른 것이 없다.
- 판정: 고른 엔트리 가운데 활성이 하나라도 있으면 **활성**, 고른 것이 있으면 **막힘**, 없으면 **없음**.
- **주소 넘김과 상한.** JNDI 는 접속·바인드 실패만 다음 주소로 넘기고, 바인드 뒤 검색 실패는 넘기지 않는다(설계 2026-11-14 F6). 정기 읽기는 재시도 k 번째에 주소를 k 번째부터 돌린 템플릿(`시작_주소별_템플릿`)을 써서 넘긴다. 한 사람 읽기는 같은 템플릿들을 **차례로 한 번씩** 쓴다 — 일시 장애 신호(V2⑤)로 실패하면 다음 템플릿, 그 밖의 실패면 바로 멈춘다. 대기(backoff)는 없다. 요청 전체 상한은 30초이고 한 주소의 시도는 `min(남은 상한, 10초)` 에서 끊는다(코드 상수 — V12 대로 새 설정은 없다). 끊어도 JNDI 의 막힌 호출은 그 스레드에서 `ldap.read-timeout`(기본 150초)까지 남는다 — 드문 요청이라 받아들인다. TLS 요구 등 템플릿의 나머지는 정기 읽기와 같다.

### 5.3 작업 (락 안)

1. 거둘 줄 E 를 정한다(V5). 비면 `SUCCEEDED` 로 끝난다.
2. 기준선 상태를 읽는다. PRESENT 면 표시를 적는다(V6·V9). 실패하면 `FAILED`.
3. E 를 지운다(V7).
4. PRESENT 면 표시를 정리한다(V8).
5. 결론을 정한다(V11). 반납 → 이력 → 실행 기록 닫기는 `SyncJobs` 가 한다.

### 5.4 왜 락 안이어야 하나

락 없이 표시를 적으면, 이미 기준선을 읽은 정각 회차가 뒤에 스냅샷을 저장하며 포인터를 통째로 다시 써 표시를 지운다. 그 회차의 그림이 막기 전의 것이면 새 B 는 지운 줄을 "있다" 로 담는다 — 반목표 그대로다. 락 안이면 회차와 회수가 차례로만 돈다. 펜싱이 없는 틈(13 §3.2)은 그대로 남는다.

### 5.5 다음 회차

V10 이다. 기준선 상태별로:

| 기준선 | 표시 | 다음 회차 |
|---|---|---|
| PRESENT | 있음 | B′·U′ 로 비교. 저장하면 표시가 사라진다. 변경 없음이면 B′ 로 스냅샷을 새로 남긴다. 전부 보류면 표시가 남는다 |
| WRITING | 남아 있을 수 있다(PRESENT 때 적은 뒤 회차가 기록 중에 멈춤) | 장부 맞추기 — 표시를 읽지 않는다. 저장이 지운다 |
| NONE | 없다(V6) | 장부 맞추기 |

## 6. 예

김 씨(`user:kim`)가 백엔드(`group:be`)와 플랫폼(`group:pf`)에 속한다. 직전 스냅샷 B = {(kim, be), (kim, pf), …}, U = ∅.

1. 10:05 디렉터리에서 김 씨를 막는다. 10:06 `POST /admin/sync/revocations {"employeeId":"kim"}`.
2. 락 밖: 현재상태에 김 씨가 있다. LDAP 한 사람 읽기 — 막힘. 202.
3. 락 안: 후보 {(kim, be), (kim, pf)}, Check 로 둘 다 있다. 포인터에 `revokedUnknown` = {둘}. 지우기 — (kim, be) 지움, (kim, pf) 결과 모름. 정리: `revokedGone` = {(kim, be)}, `revokedUnknown` = {(kim, pf)}. `PARTIAL`, 지운 줄 1·실패 1.
4. 10:30 디렉터리에서 실수였다며 김 씨를 다시 푼다.
5. 11:00 정각 회차: D 에 둘 다 있다. B′ = B − {(kim, be), (kim, pf)}, U′ = {(kim, pf)}. 쓸 줄 = D − B′ = {(kim, be), (kim, pf)} — 둘 다 다시 쓴다. 새 스냅샷 저장이 표시를 지운다.
   - 4 가 없었다면: D 에 김 씨 줄이 없다. 쓸 줄 ∅, 지울 줄 = U′ − D = {(kim, pf)} — 결과를 몰랐던 줄만 한 번 더 보낸다. (kim, be) 는 다시 지우지 않는다.

D 안(기준선을 건드리지 않음)이었다면 5 에서 B 가 두 줄을 "있다" 고 믿어 쓸 줄이 ∅ — 김 씨의 권한이 재적재 전까지 돌아오지 않는다.

- **core(가짜 저장소).** 유스케이스: 400·404·활성 409·읽기 실패의 두 갈래·거둘 줄 없음·PRESENT 표시→지우기→정리·WRITING/NONE 은 표시 없음·표시 실패면 지우지 않음·한도·확정/불확실 실패의 정리·정리 실패의 메시지·차단기 멈춤. `FullSyncUseCase`: B′·U′ 로 델타·가드 기준 수, **회수 뒤 다시 풀리면 다음 회차가 다시 쓴다**, 결과를 몰랐던 줄만 다시 보낸다, 지운 줄은 다시 지우지 않는다, 변경 없음 + 표시 → 스냅샷 저장, 전부 보류면 표시 유지.
- **storage-dynamodb(DynamoDB Local).** 두 칸의 더하기·옮기기, 조건(스냅샷 번호 다름·`writingSince` 있음)이면 실패, 한도, `save` 가 칸을 지운다, `markWriting` 은 남긴다, `findLatest` 가 칸을 함께 준다, 풀 수 없는 원소는 무결성 오류.
- **connector-ldap(임베디드 LDAP).** 두 전략 각각 활성·막힘(ppolicy 영구 잠금)·검색 베이스 밖·대소문자만 다른 엔트리·id 가 겹치는 엔트리(하나 활성)·DN 으로 다시 읽기(정규화가 바꾼 id)·한도 넘는 엔트리. **없음은 엔트리를 지운 뒤 — id 검색 0건 → DN 다시 읽기의 32 — 길로 시험한다.** 검색 베이스가 없으면(id 검색의 32) 500 쪽 실패. 주소 둘에서 첫 주소의 검색이 일시 장애로 실패하면 둘째 주소로 넘어가 답한다, 인증 실패면 넘어가지 않는다, 상한을 넘으면 일시 장애. `objectGUID` 값 쓰기는 단위 시험(바이트 순서).
- **app-ldap.** 컨트롤러의 응답 표(§5.1)와 범위, `LastSuccessGauge` 가 `REVOCATION` 을 건너뜀. 종단 하나: 동기화 → 디렉터리에서 막음 → 즉시 회수 → 장부에서 줄이 사라짐 → 디렉터리에서 다시 풂 → 다음 동기화가 줄을 다시 씀.
- 전체 `cleanTest test` 와 `cleanScaleTest scaleTest` 를 머지 전에 돌린다. 규모 시험은 새로 두지 않는다 — 요청 비용이 그 사람 크기라는 것은 구조로 보이고, 다음 회차의 B′·U′ 계산은 표시 크기(한도 256KB)에 비례한다.

## 11. 이 설계가 말할 수 없는 것

- **누가 불러야 빠르다.** 부르지 않으면 지금처럼 다음 정각이다. 디렉터리를 먼저 막아야 한다(활성이면 409).
- **정기 읽기와 다르게 판정할 수 있다.** 한 사람 읽기와 정각 읽기가 다른 DC 에 닿고 그 사이 복제가 늦으면, 한쪽은 막힘·다른 쪽은 활성으로 본다. 즉시 회수가 지운 줄을 정각 회차가 다시 쓰고, 복제가 따라잡은 다음 회차가 다시 지운다. 정규화가 바꾼 id 의 직원이 DN 까지 바뀌었으면(옮김) 활성인데 "없음" 으로 거둔다 — 다음 회차가 다시 쓴다. 둘 다 권한이 덜 남는 쪽이다.
- **읽은 뒤 락까지의 틈.** 그 사이 디렉터리에서 다시 풀면 활성인 사람을 거둔다. 다음 회차가 다시 쓴다(V10).
- **현재상태가 장부보다 뒤처지면 놓친다.** 거둘 줄의 후보·404·DN 이 현재상태에서 온다(V13).
  - 지난 회차의 지우기가 거절·불확실로 남은 줄(그 사람이 이미 떠난 조직의 줄)은 후보에 없다.
  - 장부 맞추기는 가드를 보기 전에 D 를 다 쓰고, 전부 보류·일부 반영이면 현재상태를 바꾸지 않는다(`LedgerAlignment.align`). 그 사이 들어온 직원은 장부에 권한이 있는데 404 이고, 옮긴 직원의 새 소속 줄은 후보에 없다.
  - 어느 쪽이든 다음 회차가 지금처럼 지운다. 가드가 막고 있는 동안에도 비활성 회수는 따로 반영되므로(05 §6.4), 막은 계정이면 `POST /admin/sync/full` 이 여전히 비상 경로다.
- **현재상태는 다음 회차까지 그대로다.** 관리 API 의 직원 상세·검색이 그동안 활성·소속을 보인다. 권한(OpenFGA)은 이미 없다.
- **정각에 겹치면 그 시간 회차를 건너뛸 수 있다.** 즉시 회수가 정각에 락을 쥐고 있으면 스케줄 회차는 기록 없이 건너뛴다(지금 규칙). 작업은 보통 1초 안이라 드물다.
- **표시는 전부 보류가 이어지는 동안 쌓인다.** 한도(V9)에 닿으면 즉시 회수가 실패한다. 가드를 풀거나(force) 재적재하면 저장이 지운다.
- **정리에 실패한 줄은 이력에 두 번 남을 수 있다.** 모름으로 남아 다음 회차가 한 번 더 지우고 그 회차의 이력에도 회수로 적는다.
- **펜싱 없음(13 §3.2)·취소된 회차의 늦은 쓰기(13 §7.10)** 와 같은 틈이 이 작업에도 있다.
- **확인하지 못함.** 실제 AD 의 `objectGUID` 이진 필터, 실제 AD·OpenLDAP 의 대소문자 무시 일치, 실제 OpenFGA 의 `HIGHER_CONSISTENCY` Check, 10만 명 규모의 다음 회차 비용(B′·U′ 계산은 표시 크기 비례라 재지 않았다).

### 13.3 구현 중 판정

설계의 V1~V15 와 계획의 P1~P8 위에 더한 것이다.

- **`LdapMappingStrategy.readAccount` 는 default 다**(던진다). 시험의 람다·클래스 전략 여섯 곳이 그대로 컴파일된다. 두 실제 전략이 재정의한다.
- **`FullSyncUseCase` 는 계속 `baselineState()` 를 부른다.** 포트에서는 `baselinePointer()` 위의 default 다. 기존 시험의 익명 재정의 둘이 그대로 돈다.
- **표시 적기 실패의 문구.** 한도 예외는 V9 문구 그대로 둔다. 그 밖의 실패는 `즉시 회수 표시를 남기지 못해 거두지 않았습니다 — <원인>` 이고 아무것도 지우지 않는다. 정리 실패는 회차를 실패시키지 않는다(꼬리 문구와 WARN 하나). 차단기가 아닌 쓰기 오류는 정리하지 않는다(표시가 "모름" 으로 남는 안전한 쪽).
- **풀 수 없는 `externalId`(DN 이 아님)는 "베이스 밖" 으로 본다** — DN 으로 다시 읽지 않는다. 정기 읽기는 그런 값을 만들지 않는다.
- **한 사람 읽기는 정기 읽기의 페이징 검색(`PagedLdapSearch`)을 쓰지 않는다**(계획에서 벗어남). 그 검색은 "참조 + 0건" 을 "검색 베이스 자체가 참조" 로 보고 실패시키고, 경고·예외 문구에 필터(직원 id)와 베이스(직원 DN)를 싣는다. AD 도메인 루트를 베이스로 쓰면 참조가 늘 오므로, 지운 퇴사자 길(0건 → DN 다시 읽기)이 늘 500 이 되었다. 그래서 한 사람 읽기는 커넥션 하나에서 페이징 없이 검색한다(`SearchControls` 는 `PagedLdapSearch.controlsOf` 를 같이 쓴다). id 검색의 참조는 정기 읽기처럼 건너뛰고 받은 것으로 계속 간다. DN 다시 읽기가 참조만 받으면 "없음" 이 아니라 데이터 오류(500)다. 판정 규칙(베이스·필터·속성·매퍼·건너뛰기)은 그대로다.
- **로그·문구.** 우리 코드가 만드는 로그와 문구에는 직원 id·DN 을 싣지 않는다. 매퍼·라이브러리의 데이터 오류 문구(예: 계정 상태의 `dn=`)는 정기 읽기와 같은 기존 동작이라 둔다.
- **이스케이프 시험.** JNDI 는 이스케이프하지 않은 괄호도 같은 BER 로 보낸다. 그래서 이스케이프를 빼도 전략 시험이 통과했다. 판별은 `*` 로 읽은 엔트리 수가 0 인지를 보는 시험이 한다.

### 13.4 최종 리뷰와 수정

최종 리뷰(브랜치 전체)는 "고치면 머지" 였다. Critical 0, Important 1 이다.

- **Important — 503 길에 서버 쪽 원인 로그가 없었다.** 주소가 하나인 배포에서는 한 줄도 남지 않아 운영자가 바쁨·연결 실패·느린 DC 를 가를 수 없었다. 이제 다 썼을 때와 전체 상한에서 WARN 한 줄(시도한 주소 수, 마지막 원인의 단순 클래스명)을 남긴다. 넘김 WARN 에는 실패한 주소와 원인 클래스명을, 정리 실패 WARN 에는 예외 클래스명을 더했다.
- **머지 전에 고칠 것 둘.**
  - `U − gone` 항을 못박는 시험이 없었다(확실히 지운 줄을 다시 지워 이력에 두 번 적는 것을 막는 유일한 항이다).
  - 온보딩 네 줄이 가드 기준 수를 |B|+|U| 로만 적었다.
- **함께 고친 것.**
  - 낡은 B·U 주석 둘.
  - 두 상한 시험의 시간 여유(부하 걸린 CI).
  - 표시 칸이 String Set 이 아니면 무결성 오류.
  - 괄호 없는 사용자 필터의 단위 시험.
  - 13 의 비용 문구 — 표시가 있는 회차는 B 를 한 번 복사한다. 표시 크기 비례가 아니다.
  - 13 의 "변경 없는 회차는 스냅샷 쓰기 0" 의 예외.
  - 12 §4.9 의 "한 사람만으로 한도를 넘으면 `POST /admin/sync/full`".

재검토는 열한 항목 모두 반영, 새로 깨진 것 없음이었다.

### 13.5 남긴 것

- **정규화 충돌.** 활성 uid `a b` 와 막힌 uid `a_b` 가 같은 id(`a_b`)로 정규화되면, id 검색이 막힌 엔트리를 골라 BLOCKED 로 판정할 수 있다. DN 다시 읽기는 id 검색이 아무것도 못 골랐을 때만 한다(V3). 정기 읽기가 활성 엔트리를 택했다면 활성인 사람을 한 시간 이하 거둔다 — 다음 회차가 다시 쓴다. 닫으려면 "externalId 가 베이스 아래면 DN 읽기 결과도 늘 판정에 넣는다" 로 V3 를 바꿔야 한다. 정기 읽기도 이 충돌을 겹침으로 보고 먼저 온 것을 택하는 드문 경우라 두었다.
- **참조 너머의 사람.** id 검색이 참조만 받고 쓸 만한 `externalId` 가 없으면(null·베이스 밖) "없음" 이다. 현재상태는 참조 부분을 읽지 않는 정기 읽기에서 오므로 보통은 생기지 않는다(13 에 적었다).
- **깨진 표시는 기록 중 회차·재적재의 직전 I 읽기도 막는다.** 그 두 길은 표시를 쓰지 않는데도 무결성 오류로 재활성 가드를 건너뛴다(WARN). 표시는 우리 코드만 String Set 으로 쓴다.
- **`ldap.read-timeout` 이 주소 상한(10초)보다 짧으면** 그 시간 초과는 일시 장애가 아니라 500 쪽이다(허용 목록 밖).
- **미뤄 둔 작은 것.**
  - 매개변수가 많은 `SingleAccountRead.읽는다`.
  - 단일 템플릿·빈 목록·`UncategorizedLdapException` 의 500 시험.
  - GUID 왕복의 음수 바이트 시험.
  - 차단기 시험이 아직 보내지 않은 줄을 보지 않음.
  - 관리 API 의 모르는 오류 시험이 부재만 단언함.
  - 종단 시험의 `(Integer)` 캐스트.
- §11 의 한계(실제 AD 의 `objectGUID` 필터, 실제 OpenFGA 의 `HIGHER_CONSISTENCY`, 10만 명 규모의 다음 회차 비용 — 표시가 있으면 B 를 한 번 복사한다)는 그대로다.
