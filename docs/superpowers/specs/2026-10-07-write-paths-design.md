- 날짜: 2026-10-07
- 근거:
  - `docs/superpowers/specs/2026-09-28-full-audit.md` §7 권고 ⑥ — 성능 P3·P6.
  - ⑤-1 이월: `docs/superpowers/specs/2026-10-05-scim-error-signals-design.md` §11, 재적재 중 획득 재시도를 바로 끝내기.
  - ⑤-2 이월: `docs/superpowers/specs/2026-10-06-scim-request-interpretation-design.md` §12, 버린 연산만 있는 직원 PATCH 의 락 안 전체 diff.
- 나눔: ⑥ 은 둘이다(사용자 결정). ⑥-1 읽기 길(P4·P5·S16)은 끝났다(PR #41). 이 문서는 ⑥-2 쓰기 길이다.

  - 전역 락 하나는 유지한다. 직원·조직마다 따로 잠그는 근본 해결은 범위 밖이다(§12).

## 1. 문제

| 항목 | 지금 | 결과 |
|---|---|---|
| P3 | SCIM 쓰기는 전역 락을 못 잡으면 200ms 고정 간격으로 다시 시도한다. 시도는 `lock-acquire-timeout`(3초) 안에서 약 15번이다(`IncrementalSyncUseCase.ACQUIRE_RETRY_DELAY`). 먼저 온 요청이 먼저 잡는 보장이 없다 | 앞 요청이 40ms 만에 끝나도 다음 요청은 최대 200ms 뒤에 온다. 그동안 락이 빈다. 운 나쁜 요청은 계속 밀려 3초를 넘기고 503 이 된다. 점검 추정으로 동시 40개면 약 18% 가 503 이다. 실측은 동시 16 × 200건에 503 4건(7.0초, 약 29건/초)이다 |
| ⑤-1 이월 | 재적재(`REBUILD`)나 동기화(`SYNC`)가 락을 쥔 동안에도 SCIM 쓰기는 3초 동안 재시도한다 | 요청마다 3초와 PutItem 약 15번을 쓴 뒤에야 503(`Retry-After` 60초)이다. 재적재는 몇 분이 걸리므로 그 재시도는 결과를 바꾸지 못한다 |
| ⑤-2 이월 | 모든 연산이 버리는 속성인 직원 PATCH 도 락을 잡는다. 그 안에서 직원 그림 비교, OpenFGA Check, 저장을 돈다. 예: Entra 기본 매핑의 `manager`·`phoneNumbers` | 우리가 저장하는 상태에 아무 말도 하지 않는 요청이 쓰기 줄을 함께 선다. Entra 초기 동기화는 직원마다 `manager` PATCH 를 보내므로 10만 명이면 10만 번이다 |
| P6 | OpenFGA 쓰기 결과를 합칠 때 묶음마다 누적 결과 전체를 새 집합에 복사한다. `TupleWriteResult` 생성자가 한 번 더 복사한다(`OpenFgaRelationTupleWriter.merge`) | 비용이 묶음 수의 제곱이다. 튜플 11만(묶음 약 1,100개)이면 해시 삽입 약 1.2억 번이고, 11만 칸 집합이 묶음마다 새로 생긴다(추정). SCIM 재적재와 큰 조직 변경에서는 이 시간이 락 안이다 |

## 2. 결정 (사용자 확인, 2026-10-07)

- **P3 — 서버 안 줄 + 서버끼리 백오프.**
  - 같은 서버의 SCIM 쓰기는 온 순서대로 줄을 선다. 차례가 된 요청 하나만 DynamoDB 락을 시도한다.
  - 다른 서버와 겨룰 때는 지수 백오프에 지터를 섞는다.
  - 고르지 않은 안은 §9 에 적는다: 백오프만, 간격만 줄이기, 지금처럼 두기.
- **⑤-1 이월** — 쥔 쪽이 재적재·동기화면 바로 503 이다(설계 중 정함, §3.3).
- **⑤-2 이월** — 모든 연산이 버리는 속성인 PATCH 만 락 없이 끝낸다.
  - 저장하는 속성을 같은 값으로 다시 보내는 PATCH 는 지금처럼 락 안이다.
  - 고르지 않은 안: 결과가 같은 PATCH 를 모두 락 없이 끝내기(§9).
- **P6** — 결과를 누적기 하나에 모으고 끝에서 한 번만 만든다.

## 3. P3 — 락 획득

바꾸는 곳은 core 의 SCIM 쓰기 입구(`IncrementalSyncUseCase` 가 락을 잡는 `잡고_돌린다`)뿐이다. 다음은 지금처럼 락을 바로 잡고, 이 문서의 줄과 백오프를 타지 않는다:
- LDAP 동기화(`SyncJobs`)
- 재적재(`RebuildUseCase`·`ScimRebuildUseCase`)
- 아카이빙의 `peek`

### 3.1 서버 안의 줄

- 새 부품 `LocalWriteQueue`(core). `IncrementalSyncUseCase` 하나에 하나다. 운영에서는 서버(앱 인스턴스)마다 하나다.
- SCIM 쓰기는 이 줄에 서서 **차례**를 받는다. 차례를 받은 요청 하나만 DynamoDB 락 획득(§3.2)을 시도한다.
- 차례는 그 요청이 끝날 때 다음 요청으로 넘어간다. 끝나는 경우는 다음 셋이다:
  - 락을 잡고 일을 마치고 **반납까지 끝냈을 때**
  - 획득에 실패했을 때
  - 획득 중 오류가 났을 때
- 반납이 끝나야 넘기므로, 다음 요청의 첫 시도는 이 서버가 방금 비운 락을 본다. 같은 서버 안에서는 반납과 다음 획득 사이에 빈 시간이 없다.
- 차례는 결과를 내기 **전에** 넘긴다. 결과를 낸 뒤에 넘기면 그 결과를 받은 IdP 의 다음 요청이 아직 넘어가지 않은 차례 뒤에 줄을 선다.
- 줄에서 기다린 시간도 획득 한도 `lock-acquire-timeout`(3초)에 들어간다. 한도는 줄에 선 순간부터 잰다.
  - 한도 안에 차례가 오지 않으면 줄에서 빠지고 `LockUnavailableException.잡혀_있다(WRITE)`(503, `Retry-After` 2초)다. 앞에 선 것이 이 서버의 SCIM 쓰기이기 때문이다.
  - 줄에서 기다리는 동안에는 DynamoDB 를 부르지 않는다. 그래서 이 시간 초과는 아무것도 새지 않게 한다.
- 차례를 주는 순간과 기다리던 요청이 빠지는 순간(시간 초과·취소)이 겹칠 수 있다. 그때 차례를 잃지 않는다. 이미 떠난 요청에 간 차례는 다음 요청으로 넘긴다.
- 쓰기는 지금도 요청과 떼어 끝까지 돈다(`withLock`). IdP 연결이 끊겨도 줄의 요청은 차례나 한도까지 남는다. 지금 락 대기와 같은 성질이다.
- 구현 중 정한 것: 줄이 비어 바로 받는 차례도 줄에서 받은 차례와 같은 상태 기계를 탄다. `Mono.just` 로 건네면 요청 전 취소에 차례가 버려져, 그 서버의 쓰기가 재시작 전까지 멈췄다(Task 1 검토).
- 구현 중 정한 것: 건넬 때 `GRANTED→TAKEN` CAS 를 이긴 쪽만 값을 받는다. 시간 초과 대체는 `GRANTED` 일 때만 차례를 낸다. 취소가 이미 넘긴 차례가 다시 건네져 한 서버에 쥔 쪽이 둘이 되던 틈을 막았다.
- 구현 중 정한 것: 받는 쪽은 차례를 늦은 onNext 를 버리지 않는 연산자(`flatMap`)로 받고, 반드시 `doFinally(넘긴다)` 로 넘긴다(`LocalWriteQueue.줄을_선다` 자바독).

### 3.2 서버끼리 — 지수 백오프 + 지터

- 차례를 받은 요청이 다른 서버의 락에 막히면(`LockUnavailableException`, 쥔 쪽이 `WRITE` 이거나 모름) 기다렸다 다시 시도한다.
- 기다리는 시간은 AWS 권고의 "full jitter" 로 정한다.
  - n번째 재시도의 대기는 `0 ~ min(100ms, 10ms × 2ⁿ)` 사이의 무작위 값이다.
  - 경합이 짧으면 곧 다시 시도하고, 길면 많아야 100ms 간격으로 두드린다.
- **다음 시도 전에 남은 한도를 본다.** 지금까지 걸린 시간에 이번 대기를 더한 값이 한도에 닿으면(≥) 시도하지 않고 멈춘다. 그때의 503 은 마지막 실패의 대기를 물려받는다(지금 `마지막_대기` 와 같다).
- **날아가는 중인 PutItem 은 끊지 않는다.** 서버에서 성공한 획득의 응답을 끊으면 그 락은 TTL(30초) 동안 새어 모든 쓰기를 막는다. 한도는 시도와 시도 사이에서만 본다. 그래서 한도를 넘는 것은 마지막 PutItem 한 번의 왕복만큼뿐이다.
- 재시도는 지금처럼 **같은 토큰**으로 한다. `lock.acquire(WRITE)` 가 만든 같은 `Mono` 를 다시 구독한다. 응답만 잃은 획득이 자기 락에 막히지 않는 보호(S14)가 그대로다.
- 시도 빈도: DynamoDB 락 항목을 두드리는 것은 서버마다 많아야 하나다. 경합이 이어지면 평균 대기가 약 50ms 라, 서버 하나가 초당 약 15~20번 시도한다(추정). 서버 3대면 약 60번이다.
  - 지금은 대기자마다 초당 5번이다. 80명이면 초당 400번이다.
  - 항목 하나의 쓰기 한도는 초당 1,000번이다.
- 구현 중 정한 것: 경계를 ≥ 로 둔다 — 한도 0 이면 시도는 한 번이다.

### 3.3 쥔 쪽이 재적재·동기화면 바로 503 (⑤-1 이월)

- `LockUnavailableException` 이 쥔 쪽의 용도를 싣는다. 실을 수 있는 것은 `잡혀_있다(용도)` 로 만든 경우뿐이고, 그 밖에는 모름이다.
- 재시도는 용도가 `WRITE` 이거나 모를 때만 한다. `REBUILD`·`SYNC` 면 첫 실패에서 멈추고 503(`Retry-After` 60초)이다. 지금 `잡혀_있다` 의 대기 규칙과 같다.
- 용도를 모르면 지금처럼 쓰기 경합으로 보고 계속 시도한다. 예: 조건 실패 때 돌려받은 줄에 `purpose` 가 없거나 문자열이 아닌 경우다.
- 줄의 다음 요청들도 차례가 오면 한 번 시도하고 곧 끝난다. 재적재 동안 요청마다 PutItem 한 번이다(지금은 약 15번).

### 3.4 지표

- `scim.lock.wait`(락을 잡거나 포기하기까지 기다린 시간)에 줄에서 기다린 시간이 함께 들어간다. 이름과 뜻은 그대로다.
- `scim.lock.contended` 는 "실제로 밀렸을 때" 다. 줄 앞에 다른 요청이 있었거나 DynamoDB 가 쥔 쪽을 돌려줬으면 켠다.
- 새 지표는 만들지 않는다. 줄 길이는 대기 시간 꼬리로 보인다.

### 3.5 기대 효과(추정)

- 서버 한 대에서는 반납과 다음 획득 사이의 빈 시간이 사라진다.
- 동시 40개면 맨 뒤 요청이 약 40 × (락 보유 약 40ms) ≈ 1.6초 뒤에 차례를 받는다. 한도 3초 안이라 503 이 거의 없다.
- 처리량 상한은 그대로다. 전역 락 하나라 서버를 늘려도 락 보유 시간의 역수(초당 약 20~30건)를 넘지 못한다(§11).

## 4. 버리는 속성만 있는 직원 PATCH (⑤-2 이월)

- connector-scim `ScimPatchApplier` 에 판정 하나를 더한다: "이 PATCH 의 어떤 연산도 저장하는 속성에 닿지 않는다".
  - 가르는 규칙은 적용 코드와 **같은 하나**다. 저장하는 속성이면 적용하고 아니면 받아서 버리거나 400 이다. 분류가 두 벌이 되어 갈라지지 않게 한다.
  - 저장하는 속성인지는 path 이름(와 이메일 필터의 `type`)만으로 정해지고, 직원의 현재 값과는 무관하다. 그래서 요청만 보고 정한다.
  - 검사는 지금과 같다:
    - 모르는 연산·모르는 path 는 400 이다.
    - 경로 없는 `remove` 는 `noTarget` 이다.
    - 경로 없는 값이 객체가 아니면 400 이다.
  - 경로 없는 값의 키가 모두 저장하지 않는 것이어도 해당한다. 모르는 키는 지금처럼 무시한다.
- 해당하면 `ScimUserHandler.patch` 가 락 없이 끝낸다.
  - 직원을 강한 일관성으로 읽는다(`state.findUser`).
  - 없으면 404 다.
  - 있으면 200 과 지금 모습이다. `attributes`·`excludedAttributes` 투영도 같다.
  - 버린 속성 이름은 지금처럼 `IgnoredAttributeObserver` 에 알린다(`scim.patch.ignored`).
  - Check, OpenFGA 쓰기, 저장, 락 대기는 없다.
- 저장하는 속성이 하나라도 섞인 PATCH 는 지금처럼 `sync.changeUser` 로 락 안에서 처리한다. 같은 값을 다시 보낸 것도 마찬가지다.
  - IdP 가 같은 값을 다시 보내 그 직원의 어긋남(OpenFGA 와 우리 기록의 차이)을 고치는 길이 남는다.
- 같은 순간 그 직원이 지워지면 지우기 직전 모습으로 200 이 나갈 수 있다. 읽은 시점 기준으로 맞는 답이고 GET 과 같은 성질이다.
- 대상이 아닌 것:
  - 조직 PATCH — 저장하지 않는 속성이면 400 이라 버리는 연산이 없다.
  - 직원 PUT — 저장하는 속성 전부를 바꾼다.
- 구현 중 정한 것: 모르는 path 400 메시지는 앞뒤 공백을 뺀 path 를 보인다(적용과 판정이 같은 `Target` 을 쓰므로).

## 5. P6 — 쓰기 결과는 한 번에 모은다

- authz-openfga `OpenFgaRelationTupleWriter` 에서 묶음 결과를 합치는 곳 두 군데가 결과 누적기 하나에 더해 가다가, 끝에서 `TupleWriteResult` 를 한 번만 만든다. 누적기는 쓴 튜플·지운 튜플·실패 목록을 가진다. 두 군데는 다음이다:
  - 연속 실패 차단기의 `reduce`
  - 거절된 묶음을 반으로 쪼개 보낸 결과의 `reduce`
- 동작은 그대로다. 다음이 같다:
  - 연속 실패 차단기, 단계 순서, 보내지 않은 줄을 실패로 담는 규칙
  - 멈췄을 때 `TupleWriteAbortedException` 에 싣는 부분 결과 — 그 순간의 누적기에서 만든다
- `reduce` 는 신호를 한 번에 하나씩 받으므로 누적기를 잠그지 않아도 안전하다. 누적기는 구독마다 `Mono.defer` 안에서 새로 만든다.
- `TupleWriteResult` 생성자의 복사는 끝에서 한 번이라 그대로 둔다.
- core `TupleReconciler` 는 쓰기와 지우기 결과를 한 번만 합쳐 바꿀 것이 없다.
- 효과(셈): 튜플 11만이면 해시 삽입이 약 1.2억 번에서 약 11만 번으로 준다. 묶음마다 새로 만들던 큰 집합도 없어진다.

## 9. 왜 다른 길을 안 갔나

- **백오프 + 지터만(줄 없음).**
  - 가장 간단하고, 경합이 적을 때 빈 시간이 준다.
  - 순서가 없어 운 나쁜 요청이 계속 밀린다. 동시 요청이 많으면 503 꼬리가 남는다.
  - 대기자 모두가 DynamoDB 를 두드려 시도 빈도가 대기자 수에 비례한다.
- **간격만 짧게(예: 20ms 고정).** 대기자 80명이면 초당 4,000번이라 항목 하나의 쓰기 한도(초당 1,000번)에 걸린다. 순서 문제도 그대로다.
- **서버 안에서 락을 넘겨주기(반납·획득 생략).**
  - 요청마다 DynamoDB 쓰기 두 번과 왕복을 아껴 처리량이 더 오른다.
  - 대신 한 서버가 락을 계속 쥐어 다른 서버가 굶는다. 넘겨주기 상한이 따로 필요하다.
  - 요청마다 다른 토큰으로 리스를 확인하는 지금 규칙(커밋 직전 확인)도 바꿔야 한다. 처리량이 실제로 모자랄 때 다시 본다.
- **DynamoDB 위의 공정한 분산 대기열.** 서버끼리 순서까지 맞추지만 항목·조건이 늘고, 죽은 대기자 정리가 필요하다. 배포가 몇 대뿐이라 서버 안 줄로 대부분을 얻는다.
- **직원·조직마다 따로 잠그기.** 처리량 상한을 푸는 근본 해결이다. 무엇을 잠글지 정하는 것 자체가 읽기라 큰 재설계다(동시성 설계 §4.1). 범위 밖이다.
- **PATCH 결과가 지금과 같으면 모두 락 없이 끝내기.**
  - IdP 가 같은 값을 자주 다시 보내므로 더 많이 아낀다.
  - 대신 그런 PATCH 에서 그 직원의 어긋남 고치기를 잃는다. "모든 쓰기가 자기 대상의 어긋남을 고친다" 는 Check 기준선 설계와 부딪힌다.

## 11. 이 설계가 말할 수 없는 것

- **효과 수치는 추정과 개발 노트북 실측이다.** 락 보유 시간과 503 비율은 DynamoDB Local·OpenFGA 컨테이너에서 잰 값이다. 실제 AWS 의 왕복 시간에서는 다르다.
- **실제 IdP 의 동시 요청 수를 모른다.** Entra·Okta 모두 공식 문서에 없다.
- **처리량 상한은 그대로다.** 전역 락 하나라 서버를 늘려도 쓰기는 초당 약 20~30건을 넘지 못한다(추정).
  - 10만 명 초기 POST 는 락 시간만으로 최소 약 1시간이다.
  - 멤버십 15만 건을 한 명씩 PATCH 로 받으면 약 3시간이다.
- **과부하에서는 성공한 요청도 오래 기다린다.** 들어오는 속도가 처리 속도보다 빠르면 줄이 길어진다. 그러면 한도(3초) 가까이 기다린 요청만 차례를 받고, 그 뒤는 503 이다. 한도가 대기의 상한이자 줄 길이의 사실상 상한이다.
- **서버끼리는 순서가 없다.** 여러 서버에서는 503 꼬리가 남을 수 있다. 서버 안의 순서만 보장한다.
- **줄은 메모리에 있다.** 서버가 죽으면 줄의 요청은 연결이 끊긴다. IdP 가 재시도한다. 지금 락 대기와 같다.
- **차례를 쥔 요청의 획득(PutItem)이 멈추면 그 서버의 쓰기 전체가 기다린다.** SDK 시간 초과까지 줄의 뒤 요청은 한도(3초)를 넘겨 503 이다. 날아가는 시도를 끊지 않는다는 규칙(§3.2)의 대가다.
- **버리는 속성만 있는 PATCH 는 어긋남을 고치지 않는다.** 그 직원의 어긋남은 다음 쓰기나 `mode=tuples` 재적재가 고친다.
- **P6 의 시간 절약은 재지 않았다.** 비용은 코드로 셌다.
