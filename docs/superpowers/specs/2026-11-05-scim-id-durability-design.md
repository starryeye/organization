# SCIM id 내구성 설계 (2026-11-05)

이 슬라이드는 외부 리뷰(2026-10-19)의 N4 가운데 남은 것, **복구 뒤 SCIM id 보존**을 다룬다.
- **N4 의 나머지.** 운영 준비 슬라이드가 생성·보호(prod 는 테이블을 만들지 않음, 삭제 보호·PITR 필수)를 고쳤다(운영 준비 설계 §3). 남은 것은 "복구하면 id 가 바뀐다" 다. 근거: `docs/superpowers/specs/2026-10-19-outsider-review/0-종합.md` 47행, 온보딩 13 §2.1.

사용자는 "N4 남은 것 진행" 다음 "추천대로" 라고 했다. **이 문서의 결정은 모두 내 추천이다.** 질문 없이 정했고, 이 문서를 승인하는 것이 §2 의 결정을 승인하는 것이다.

코드 사실은 main `f974661` 에서 읽었다. 파일:줄은 구현 때 다시 확인한다(§13).

## 1. 문제

### 1.1 복구하면 SCIM id 가 바뀐다

- SCIM 직원·조직 id 는 POST 처리기가 `UUID.randomUUID()` 로 만든다(`ScimUserHandler.create`, `ScimGroupHandler.create`). DynamoDB 테이블이 그 id 의 유일한 기록이다.
- **PITR 복원.** 복원 시점 뒤에 발급한 id 는 테이블에 없다. IdP 는 그 id 를 기억하고 PATCH 를 보내 404 를 받는다. Entra 는 404 를 받아도 다시 만들지 않는다 — 운영자가 프로비저닝을 다시 시작하면 그때 POST 하고, 서버는 **새 id** 를 준다(Microsoft Q&A·벤더 문서, 확인하지 않음).
- **`mode=wipe` 뒤 재프로비저닝**(문서화된 마지막 복구). 장부와 조직도를 비우고 IdP 가 전부 다시 POST 한다. **모든 id 가 바뀐다.**
- **결과.**
  - 권한을 묻는 앱이 저장한 employeeId·orgCode 가 낡는다. 정확 조회(`/admin/*/lookup`)로 다시 찾게 해야 한다.
  - PITR 의 경우 장부의 옛 id 줄은 지울 주체 없이 남는다. 재적재(`mode=tuples`)의 장부 훑기만 지운다.
  - OpenFGA store 번호는 영구 고정인데 신원은 복구마다 갈라진다(리뷰가 짚은 비대칭).

### 1.2 IdP 가 `externalId` 에 싣는 것

- **Entra 직원:** 기본 매핑이 `mailNickname` → `externalId` 다. 이 값은 바뀌고, 다른 사람에게 다시 쓰일 수 있다. 여러 SaaS 가 이것을 `objectId`(영구 식별자)로 바꾸라고 안내한다.
- **Entra 조직:** 기본이 `objectId` → `externalId` 다.
- **Okta:** POST 에 `externalId` 를 싣지 않을 수 있다(Okta 는 서버가 준 id 를 자기 쪽 externalId 로 저장한다). 앱 설정으로 Okta 사용자 id(`00u…`)를 싣게 하는 곳도 있다. 조직(Group Push)에는 싣지 않는다(README "SCIM").
- 근거는 벤더 문서다(Microsoft SCIM 튜토리얼 미러, Bitwarden·SuperOffice·Simpplr·Okta 개발자 문서). 실제 테넌트로 확인하지 않았다.

## 2. 결정

| # | 결정 | 이유 |
|---|---|---|
| I1 | **설정 `sync.id-from-external-id`(기본 `false`, app-scim 의 `ScimSyncProperties`)를 켜면, `externalId` 가 있는 POST 의 id 후보를 그 값에서 정한다.** 후보 = RFC 9562 이름 기반 UUID(v5, SHA-1), 네임스페이스는 코드에 박은 고정 UUID, 이름은 `"User:" + externalId` 또는 `"Group:" + externalId`(UTF-8, 그대로 — `externalId` 는 대소문자를 가린다). `externalId` 가 없거나 비었거나 설정이 꺼져 있으면 지금처럼 무작위 UUID(v4)다 | IdP 가 같은 리소스를 다시 POST 하면 같은 id 가 나온다 — wipe·복원 뒤 신원이 이어진다. SCIM 의 `id` 는 서버가 정한다(RFC 7643 §3.1) — 어떻게 정할지는 서버 몫이라 표준을 어기지 않는다. `externalId` 는 RFC 7643 §3.1 의 "클라이언트가 정한 리소스 식별자" 다 |
| I2 | **기본은 꺼짐이다. `externalId` 가 IdP 의 영구 식별자일 때만 켠다.** Entra 는 직원 매핑을 `objectId` → `externalId` 로 바꾼 뒤, Okta 는 앱이 Okta 사용자 id 를 싣는 경우에 켠다 | Entra 의 기본(`mailNickname`)은 다시 쓰일 수 있다. 켠 채로 wipe 하면 같은 별명을 받은 새 사람이 옛사람의 id 를 받는다 — 권한을 묻는 앱의 기록이 두 사람을 섞는다. "불변 id 는 이름에서 만들지 않는다" 를 지키려면 운영자가 값의 성질을 보장하고 켜야 한다 |
| I3 | **id 는 락 안에서, 저장 전에 정한다.** 후보 id 의 리소스가 없으면 그 id 로 만든다. **있고 그 `externalId` 가 POST 의 것과 같으면 409 `uniqueness`** 다 — 같은 리소스가 이미 있다(RFC 7644 §3.3: 기존 리소스와 부딪히는 생성은 409 `uniqueness`). 있지만 `externalId` 가 다르면(만든 뒤 바뀐 경우) 무작위 UUID 로 만든다. 조직은 지금의 `externalId` 표지가 앞에서 같은 결과(409)를 낸다 | 지금 POST 는 같은 id 의 기록을 덮어쓴다(`upsertUserInternal`) — 검사가 꼭 있어야 한다. I2 의 전제에서 같은 `externalId` 의 기록은 같은 사람이다. 무작위로 물러서면 한 사람이 둘로 갈라지고, 옛 기록은 옛 소속을 쥔 채 남는다(PITR 뒤 이름이 바뀐 사람, DELETE 가 실패해 남은 비활성 기록, 응답을 잃은 POST 의 재시도). 409 를 받은 IdP 는 `filter=externalId eq` 로 찾아 PATCH 한다(Entra 는 `objectId` 매칭을 우선으로 두면 처음부터 그렇게 한다) |
| I4 | **같은 `externalId` = 같은 리소스로 본다. 지운 id 를 막아 두지 않는다(은퇴 표지 없음).** IdP 가 지웠다 되살린 사람이 같은 `externalId` 로 다시 POST 하면 옛 id 를 받는다 | I2 의 전제(영구 식별자)에서는 그 사람이 맞다. 은퇴 표지를 두면 정당한 되살리기가 새 id 를 받고, 저장소에 영구히 쌓이는 아이템이 생긴다 |
| I5 | **POST 뒤 `externalId` 가 바뀌어도 id 는 그대로다.** 복원·wipe 뒤 다시 POST 하면 그때의 `externalId` 로 정한다 — 바뀐 적이 있으면 다른 id 가 된다 | SCIM `id` 는 불변이다. I2 의 전제에서는 영구 식별자가 바뀌지 않는다 |
| I6 | **네임스페이스 UUID 는 영구 고정이다.** 바꾸면 그 뒤의 모든 후보가 달라진다 — OpenFGA store 번호와 같은 취급이다 | 복구 뒤 같은 id 가 나오는 것의 전제다 |
| I7 | **설정을 바꿔도 이관하지 않는다.** 켜기 전에 만든 리소스는 무작위 id 그대로다. wipe 뒤 재프로비저닝부터 모두 결정적 id 가 된다 | 운영 배포 전이다. 이미 발급한 id 는 바꿀 수 없다(불변) |
| I8 | **wipe·재적재는 바꾸지 않는다.** wipe 는 지금처럼 장부·조직도·지정 연결을 지운다. 켜져 있으면 재프로비저닝이 같은 id 를 다시 만든다 — 지정 스크립트를 다시 돌리면 같은 orgCode 로 걸린다(Entra 조직은 `objectId` 가 기본이라 대부분 그대로다) | wipe 는 상태를 비우는 것이다. id 가 같아지는 것은 POST 쪽 성질이다 |
| I9 | **LDAP 배포는 그대로다.** id 는 디렉터리가 준 `entryUUID`/`objectGUID` 다 | 이미 영구 식별자다 |
| I11 | **저장하지 못한 새 조직 POST 는 자기가 쓴 줄을 되지운다.** 멤버를 실은 POST /Groups 가 일부 실패하면 지금은 조직을 저장하지 않고 503 이다 — 이미 쓴 줄(`direct_member`·`child`)이 남는다. 그 묶음이 쓴 줄과 결과를 모르는 줄을 "없으면 무시" 로 지운 뒤 503 을 낸다. 되지우기가 실패하면 WARN 을 남기고 줄은 남는다. 설정과 상관없이 한다 | 지금은 재시도가 새 무작위 id 를 받아 남은 줄이 아무도 모르는 id 에 붙어 있다(무해 — 점검 M7). 결정적 id 에서는 재시도가 같은 id 로 오고, 그 사이 빠진 멤버의 줄은 새 그림의 후보에 없어 지워지지 않는다 — 롤업이 샌다. 쓴 줄은 쓰기 결과로 알므로 OpenFGA Read 가 필요 없다. 되지우기도 실패하는 이중 장애는 재적재(`mode=tuples`)가 지운다 |
| I10 | **문서.** README(불변 id 절, SCIM 절, 설정, 복구 절차)와 온보딩(13 §2.1 고침, 12 §3.4·§3.7·wipe, 11 설정, 02, 07, 15)을 코드대로 고친다. 기준 커밋은 이 브랜치의 마지막 코드 커밋 | 온보딩은 늘 현재 동작이다 |

**고치지 않기로 한 것.**
- **`userName`·이름에서 id 를 만들기.** 이름은 바뀌고 다시 쓰인다(README "불변 id 는 이름에서 만들지 않는다").
- **클라이언트가 보낸 `id` 를 받기.** RFC 7643 §3.1 은 클라이언트의 `id` 를 무시하게 한다. 지금도 쓰지 않는다.
- **테이블 밖의 id 대장(별도 테이블·파일).** 그것도 같은 장애·복원 시점을 겪는다. `externalId` 라는 열쇠가 IdP 에 있으므로 서버가 따로 기억할 것이 없다.
- **`externalId` 를 보내지 않는 IdP(Okta 조직 등)의 보존.** 열쇠가 없다. 지금처럼 새 id 를 받는다.
- **IaC.** 운영 준비 설계 §3 이 버린 길이다.

## 3. 동작

### 3.1 POST /Users, POST /Groups

1. 처리기가 후보 id 를 만든다 — 설정이 켜져 있고 `externalId` 가 비지 않았으면 결정적 UUID, 아니면 무작위 UUID.
2. 유스케이스가 락 안에서 맨 먼저 후보를 본다(I3).
   - 그 id 의 직원(조직)이 없으면 후보 그대로다.
   - 있고 `externalId` 가 같으면 409 `uniqueness` — 직원은 `같은 externalId 의 직원이 이미 있다: <id>`. 아무것도 쓰지 않는다. 조직은 지금의 `externalId` 표지가 먼저 409 를 낸다.
   - 있지만 `externalId` 가 다르면 무작위 UUID 로 바꾸고 INFO 로그 한 줄(후보 id, 정한 id, 리소스 종류)을 남긴다. `externalId` 값은 로그에 싣지 않는다.
   그 뒤는 지금과 같다(키 한도, `userName`·`externalId` 표지 차지, 저장, 튜플).
3. 응답의 `id`·`Location`·`meta.location` 은 정해진 id 다.
4. 새 조직 POST 가 일부 실패해 저장하지 않으면, 그 요청이 쓴 줄을 되지운 뒤 지금처럼 503 이다(I11).
- 무작위 후보(설정이 꺼졌거나 `externalId` 가 없음)도 같은 검사를 지난다 — 규칙이 하나이고, 무작위 UUID 가 겹칠 일은 없다. 비용은 POST 마다 GetItem 하나다.

### 3.2 복구 시나리오

- **wipe 뒤 재프로비저닝(켜짐).** IdP 가 같은 `externalId` 로 다시 POST 한다 → 같은 id. 권한을 묻는 앱이 저장한 id 가 그대로 맞는다. 장부는 wipe 가 비웠으므로 새로 쓰는 줄이 옛 id 와 같다.
- **PITR 복원(켜짐).** 약속하는 것은 **id 가 같다**는 것까지다.
  - 복원본에 없는 리소스는 IdP 가 프로비저닝을 다시 시작할 때 POST → 같은 id. 복원본에 있는 리소스는 IdP 가 `externalId` 로 찾아(매칭) PATCH 한다 — 이름이 바뀌었어도 POST 하면 409 라 갈라지지 않는다.
  - 복원 시점 뒤에 만든 소속(조직의 멤버 줄)은 복원본에 없다. IdP 가 멤버십을 다시 보낸 뒤에야 장부의 옛 줄이 조직도와 다시 맞는다 — 같은 id 라서 다시 쓸 필요가 없을 뿐이다. 그래서 순서는 지금(온보딩 12 §3.7)과 같다: 복원 시점 뒤에 지운·바꾼 것을 고치고, IdP 가 멤버십까지 다시 보냈는지 확인한 뒤, 맨 마지막에 `mode=tuples`. 먼저 걸면 아직 멤버십이 없는 줄을 지운다(다시 보내면 돌아온다).
  - 프로비저닝을 다시 시작했을 때 Entra 가 이미 있는 조직의 멤버를 다시 보내는지는 확인하지 않았다(§6).
- **꺼짐.** 지금과 같다.

### 3.3 설정

- `sync.id-from-external-id`(app-scim `ScimSyncProperties`, 기존 `sync.*` 와 같은 클래스). 기본 `false`. prod 검사는 두지 않는다 — 꺼짐은 지금 동작이고, 켬이 안전한지는 IdP 매핑에 달려 서버가 판정할 수 없다(§6).
- 켠 상태를 기동 로그 한 줄로 알린다(INFO, 값과 "externalId 가 IdP 의 영구 식별자여야 한다").
- 문서에 Entra 설정을 함께 적는다: 직원 매핑 `objectId` → `externalId`, 매칭 속성 `externalId` 를 우선순위 1 로(벤더 문서 근거).

## 4. 시험

- **id 함수(connector-scim 단위).** 같은 입력 → 같은 UUID, `User`·`Group` 이 다르다, `externalId` 대소문자가 다르면 다르다, 결과의 version 이 5 이고 variant 가 RFC 9562 다. 알려진 값 하나를 고정한다(네임스페이스가 바뀌면 깨지게).
- **유스케이스(core, 가짜 저장소).**
  - 후보가 비어 있으면 그 id 로 저장하고 결과가 그 id 를 돌려준다.
  - 후보의 직원이 있고 `externalId` 가 같으면 409(`DirectoryConflictException`), 아무것도 쓰지 않는다. 기존 직원은 그대로다.
  - 후보의 직원(조직)이 있지만 `externalId` 가 다르면 무작위 id 로 저장하고 기존 리소스는 그대로다(덮지 않는다).
  - 멤버를 실은 새 조직 POST 가 일부 실패하면 조직을 저장하지 않고, 그 요청이 쓴 줄이 지워진다(가짜 writer 의 장부가 비어 있다). 되지우기도 실패하면 WARN 이고 503 그대로다.
- **처리기·라우터(connector-scim).** 꺼짐 → 무작위. 켜짐 + `externalId` → 결정적 id 가 응답 `id`·`Location` 에 실린다. 켜짐 + `externalId` 없음 → 무작위. 켜짐 + 같은 `externalId` 의 두 번째 직원(다른 `userName`) → 409 `uniqueness`.
- **종단(app-scim, Testcontainers, 켜짐 프로필).**
  - 직원·조직을 POST → `mode=wipe` → 같은 본문으로 다시 POST → 같은 id, 롤업 Check 참.
  - 기록을 잃은 뒤: 저장소에서 직원(소속 포함, `deleteUser`)을 지우고 장부 줄은 남긴 채, 같은 본문으로 직원을 다시 POST 하고 조직에 멤버를 다시 PATCH → 같은 id, 롤업 Check 참, 재적재(`mode=tuples`) 뒤에도 참.
  - 같은 `externalId` 로 이름만 다른 직원 POST → 409, 첫 직원 그대로.
- **규모.** POST 마다 GetItem 하나(후보 검사)가 는다. 새 규모 시험은 두지 않는다. 기존 `scaleTest` 가 그대로 통과하는지만 본다.

## 5. 바뀌는 곳 (어림)

- **connector-scim:** id 함수(새 클래스), 두 처리기(후보 만들기, 정한 id 로 응답).
- **core:** `IncrementalSyncUseCase.createUser`·`createGroup`(락 안 후보 검사 — 409 또는 무작위, 정한 id 돌려주기), 새 조직 POST 일부 실패의 되지우기(`upsertGroupInternal` 의 커밋 경로). `createUser` 자바독의 "지운 직원의 아이디가 다시 쓰이지 않아"(점검 M7 근거)를 고친다.
- **app-scim:** 설정 속성, 처리기 배선, 종단 시험.
- **문서:** README, 온보딩.

## 6. 이 설계가 말할 수 없는 것

- **벤더 동작은 문서 근거다.** Entra 의 기본 매핑, 404 뒤 다시 POST 하지 않는 것, Okta 의 `externalId` 동작을 실제 테넌트로 확인하지 않았다.
- **운영자의 매핑이 맞는지는 서버가 모른다.** 켜 놓고 다시 쓰일 수 있는 값을 `externalId` 로 보내면 I2 의 위험(사람이 섞임)이 생긴다. 서버는 값의 모양으로 판정하지 않는다.
- **`externalId` 를 보내지 않는 리소스는 보존되지 않는다.**

## 7. 왜 다른 길을 안 갔나

| 길 | 버린 이유 |
|---|---|
| **기본 켜짐** | Entra 의 기본 직원 매핑(`mailNickname`)이 다시 쓰일 수 있다. 조용히 켜지면 wipe 뒤 사람이 섞일 수 있다(I2) |
| **은퇴 표지(지운 id 는 다시 내주지 않음)** | I2 의 전제에서는 같은 `externalId` 가 같은 사람이다 — 되살아난 사람이 새 id 를 받게 된다. 아이템이 영구히 쌓인다. 게다가 wipe 는 DELETE 가 아니라 표지를 남기지 않으므로 다시 쓰인 별명의 위험을 막지 못한다 |
| **후보가 같은 `externalId` 의 기록에 차 있으면 무작위로 물러서기(처음 쓴 안)** | I2 의 전제에서 그 기록은 같은 사람이다 — 한 사람이 둘로 갈라지고 옛 기록이 옛 소속을 쥔 채 남는다. 구현 전 점검이 찾았다(§13) |
| **같은 `externalId` 면 기존 기록을 받아들여 POST 를 갱신으로 바꾸기** | POST 는 만들기다. 기존 리소스와 부딪히면 409 `uniqueness` 가 표준이다(RFC 7644 §3.3). 표지 옮기기·멤버 합치기 같은 경우가 생긴다 |
| **직원 `externalId` 전체의 유일성 강제(표지)** | 켜기 전에 무작위 id 로 만든 직원까지 막게 되고, 지금 동작을 넓게 바꾼다. 결정적 후보 하나만 보면 이 기능이 지키려는 경우를 덮는다 |
| **새 조직 POST 실패를 저장해 두기(409 로 재시도를 막고 매칭으로 넘김)** | 실패한 POST 를 받은 IdP 는 id 를 모른다. 매칭이 늦거나 없는 IdP 는 409 를 되풀이한다. 쓴 줄을 되지우는 편이 지금 동작(저장하지 않음)을 지킨다(I11) |
| **`externalId` 그대로를 id 로 쓰기** | 길이·문자 제약이 없고(키 한도, 경로), IdP 의 식별자를 그대로 드러낸다. 이름 기반 UUID 는 길이가 고정이고 지금 id 와 모양이 같다 |
| **id 대장을 테이블 밖에 두기** | 같은 장애를 겪고, 열쇠(`externalId`)는 이미 IdP 에 있다 |
| **값의 모양(GUID 인지)으로 자동 판정** | 휴리스틱이다. Okta 사용자 id 는 GUID 가 아니고, GUID 꼴의 값도 다시 쓰일 수 있다 |

## 10. 범위 밖

- IaC, 테이블 밖 id 대장, 이름에서 id 만들기, `externalId` 없는 리소스의 보존.

## 13. 확인할 것 (구현 때 사실로 정한다)

- 처리기가 정한 id 를 받는 길 — `createUser`·`createGroup` 의 결과에 id 를 실을지, 처리기가 넘긴 후보와 바뀐 id 를 어떻게 잇는지.
- `upsertGroupInternal`·`upsertUserInternal` 이 후보 검사 뒤에도 덮어쓰기 경로를 다른 곳에서 타지 않는지.
- 새 조직 POST 의 일부 실패 경로에서 "그 요청이 쓴 줄" 을 어디서 얻는지(쓰기 결과의 `written`·불확실 줄) — 같은 요청이 보류 목록에 넣은 줄은 함께 거둔다.

**구현 전 점검에서 고친 것.** 처음 보는 리뷰어가 이 문서만으로 계획을 세워 보며 코드와 맞댔다.
- 후보가 같은 `externalId` 의 기록에 차 있을 때 무작위로 물러서면 한 사람이 갈라진다 → 409(I3).
- 결정적 id 가 지금은 닿지 않는 고아 줄(실패한 새 조직 POST 가 남긴 것)을 살아 있는 id 에 다시 붙인다 → 되지우기(I11).
- PITR 뒤 "장부 줄이 다시 유효하다" 는 IdP 가 멤버십을 다시 보낸 뒤에만 참이다 → 약속을 "같은 id" 로 좁히고 순서를 적었다(§3.2).
- 설정 접두는 기존 `ScimSyncProperties` 의 `sync` 다 → `sync.id-from-external-id`.

같은 점검에서 확인된 사실: wipe 는 장부를 먼저 비우고 조직도·표지·보류 목록을 비운다. PUT·PATCH 는 대상이 없으면 404 이고 리소스를 만들지 않는다. SCIM 필터는 직원·조직 모두 `externalId eq` 를 받는다.
