# LDAP 주소 여럿 — 도메인 컨트롤러 장애 넘김 설계 (2026-11-14)

온보딩 13 §4.4 "도메인 컨트롤러 여럿, referral" 가운데 **DC 여럿**을 다룬다. 같은 절의 referral 따라가기와 글로벌 카탈로그는 이 슬라이드 밖이다.
가드 상한 설계(2026-11-13) §9.5 가 남긴 "비율만 말하는 코드 주석" 정리도 함께 한다(§2 F9).
사용자 결정: "추천대로"(2026-11-14) — 아래 결정은 모두 그 추천이다. 접근안 A(JNDI 주소 목록)를 골랐다(§7).

## 1. 문제

- app-ldap 은 LDAP 주소를 하나만 받는다(`ldap.url` → `LdapContextSource.setUrl`, `LdapConfig.ldapContextSource`).
  그 도메인 컨트롤러(DC)가 내려가면 매시 회차가 `FAILED` 다. 읽기 재시도 창(약 2~6분, `ldap.max-retries` 5)은 재부팅 정도만 버틴다.
- 10만 명 규모의 AD 는 DC 가 여럿이고, 패치·점검으로 한 대가 몇 시간 내려가는 일이 흔하다. 그동안 퇴사자 회수가 멈춰 회수 목표("다음 정각 + 회차 시간", 설계 2026-10-20 §8)가 깨진다.
- 지금 문서의 우회는 "여러 DC 를 가리키는 주소(부하 분산기 등)" 인데 이 저장소에서 시험하지 않았다(13 §4.4).
- 상태 점검(`LdapHealthIndicator`)은 바인드 하나를 2초(`PROBE_TIMEOUT`) 안에 보고, 접속 한도는 10초(`ldap.connect-timeout`)다. 주소가 하나라 지금은 맞는 신호지만,
  주소가 여럿이 되면 첫 주소가 패킷을 버리는 동안 둘째가 멀쩡해도 2초 안에 끝나지 않아 DOWN 이 된다.

## 2. 결정

| # | 결정 | 이유 |
|---|---|---|
| F1 | **설정 키를 목록 `ldap.urls` 로 바꾼다**(기본 `[ldap://localhost:1389]`). `ldap.url` 은 없앤다. 목록의 순서가 선호 순서다 — 가까운 DC 를 앞에 둔다. yml 목록이나 쉼표로 이은 문자열(`LDAP_URLS=ldaps://dc1:636,ldaps://dc2:636`)로 준다 | 스프링 부트의 `spring.ldap.urls` 와 같은 모양이다. 배포 전이라 이름을 바꾸는 이관 비용이 없다. 키 이름이 단수면 목록을 받는다는 것이 보이지 않는다 |
| F2 | **넘김은 JNDI 표준 동작에 맡긴다.** `LdapContextSource.setUrls(목록)` 이 JNDI 의 주소 목록(`java.naming.provider.url` 에 공백으로 이은 URL)을 만든다. 새 커넥션마다 JNDI 가 앞 주소부터 접속·바인드를 시도하고 실패하면 다음 주소로 간다 | 새 장치를 만들지 않고 표준을 켠다. 회차가 여는 커넥션(직원 검색·조직 검색·member 이어받기)이 모두 같은 컨텍스트 소스를 타므로 한 곳만 바뀐다 |
| F3 | **인증 실패는 다음 주소로 넘기지 않는다** — JNDI 의 동작 그대로다(인증 실패 `AuthenticationException` 은 목록을 더 돌지 않고 던진다). 앱이 이것을 바꾸지 않는다. 읽기는 지금처럼 인증 실패를 재시도하지 않고 `FAILED` 다 | 한 도메인의 DC 는 자격 증명을 함께 쓴다. 틀린 비밀번호로 DC 마다 바인드하면 AD 잠금 기준에 더 빨리 닿는다(설계 2026-10-05 §4.3 과 같은 까닭) |
| F4 | **주소 모양을 기동 때 검사한다.** 목록이 비었거나, 빈 항목이 있거나, 스킴이 `ldap://`·`ldaps://` 가 아니거나, 호스트 뒤에 `/` 말고 경로(DN)·질의가 붙으면 멈춘다. `ldap.require-tls` 면 **모든** 주소가 `ldaps://` 여야 한다 | 검색 베이스는 `ldap.base-dn` 이 따로 붙인다 — 주소에 DN 을 쓰면 스프링이 그 뒤에 베이스를 또 붙인다. 쉼표로 이은 문자열은 부트가 쉼표에서 나누므로 DN 이 든 주소는 조각나는데, 그 조각은 스킴 검사에 걸린다. 평문 주소 하나가 목록에 섞이면 그 DC 로 넘어갈 때 자격 증명이 평문으로 간다 |
| F5 | **상태 점검은 주소마다 따로 바인드한다.** 주소마다 컨텍스트 소스 하나(운영과 같은 베이스·자격 증명·JNDI 환경, 주소만 하나)로 동시에 바인드하고, 각각 2초 상한이다. **하나라도 되면 UP**, 모두 안 되면 DOWN 이다. 세부에 주소마다 결과(되었는지, 안 되었으면 오류)를 적는다. **인증 실패가 하나라도 있으면 DOWN 이고** 지금처럼 30분 동안 어느 주소에도 바인드하지 않는다 | 질문은 "회차가 읽을 수 있는가" 다 — 주소 하나라도 닿으면 회차가 읽는다. JNDI 목록 하나로 바인드하면 첫 주소가 응답하지 않을 때 2초 안에 다음으로 가지 못한다. 넘김은 JNDI 안에서 조용하므로, 앞 DC 가 내려간 것을 운영자가 볼 곳이 세부뿐이다. 인증 실패는 회차도 그 주소에서 멈추게 하므로(F3) DOWN 이 맞다 |
| F6 | **회차가 여러 DC 를 섞을 수 있음을 받아들인다.** JNDI 는 늘 앞 주소부터 시도하므로 보통 한 회차는 한 DC 에서 읽는다. 회차 도중 DC 가 죽으면 그 검색이 실패하고, 지금 재시도(`LdapDirectorySnapshotSource.fetchAll` 의 `retryWhen`)가 **그림 전체**를 처음부터 다시 읽으며 그때 다음 주소로 간다 | 섞이는 것은 DC 가 짧게 오락가락할 때뿐이다. 다음 회차가 맞추고, 큰 차이는 삭제 가드가 잡는다. 회차마다 DC 하나를 고르는 앱 수준 장치(§7 B)는 이 작은 틈을 막으려고 표준을 다시 만든다 |
| F7 | **새 지표를 두지 않는다.** 넘김 로그도 없다 | JNDI 는 어느 주소로 붙었는지 공개 API 로 알려 주지 않는다. 앞 DC 가 내려간 신호는 상태 점검 세부(F5)다. 회차 비용(§3.2)은 그대로 회차 시간에 보인다 |
| F8 | **주소 하나인 배포는 지금과 같다.** 목록에 하나만 있으면 접속·재시도·상태 점검의 판정이 지금과 같다(세부의 모양만 주소별 목록이 된다) | 한 규칙이다 |
| F9 | **비율만 말하는 코드 주석을 고친다.** `RebuildUseCase`(약 32행 "임계치를 넘으면")·`AdminSyncController`(약 65행 "임계치를 넘으면")·`LedgerAlignment`(약 38행 "임계 아래로 내려가면")에 상한을 더하고, connector-ldap 의 "삭제 가드(30%)"(`IncompleteAttributeReadException`·`UnmatchedMemberGuard`·`MemberMatchingFailedException`)를 "삭제 가드(30% 또는 5,000줄)" 꼴로. 동작은 바꾸지 않는다 | 가드 상한 설계 §9.5 가 "그 파일을 다음에 고치는 코드 슬라이드" 로 넘겼다. 이 슬라이드가 코드 커밋이라 온보딩의 기준 커밋 줄이 어차피 움직인다 |
| F10 | **문서.** README 와 온보딩(02 "도메인 컨트롤러", 05 접속 설정, 11 설정 표·운영 주소, 12 LDAP 장애, 13 §4.3·§4.4, 14 개발 가이드의 주소, 15 결정 색인)을 코드대로 고친다 | 온보딩은 늘 현재 동작이다 |

**고치지 않기로 한 것.**
- **referral 따라가기, 글로벌 카탈로그(3268).** 13 §4.4 그대로다(다른 DC 의 주소·자격 증명이 필요하고, GC 는 AD 기본 그룹의 RID 대조를 깨뜨린다).
- **DNS SRV 로 DC 찾기**(`_ldap._tcp.<도메인>`). JNDI 는 호스트 없는 URL(`ldap:///dc=example,dc=com`)로 이것을 한다. 임베디드 LDAP 으로 시험할 수 없고, F4 가 경로 있는 주소를 막는다. 실제 요구가 보이면 따로 다룬다.
- **앞 주소를 기억하거나 섞기**(마지막에 된 주소를 먼저, 부하 나누기). 표준 목록은 늘 앞에서부터다. 응답 없는 첫 주소의 비용(§3.2)은 회차당 수십 초라 장치를 둘 값이 없다.
- **넘김 지표**(F7).

## 3. 동작

### 3.1 접속

```
새 커넥션(검색 하나, member 이어받기 하나)마다:
  urls[0] 부터 차례로
    접속 실패(거절·닿지 않음·connect-timeout) 또는 바인드 응답 없음(connect-timeout) 또는 그 밖의 접속 오류 → 다음 주소
    인증 실패(결과 코드 49)                                                         → 멈추고 그 오류를 던진다(F3)
    성공                                                                           → 그 주소로 검색한다
  모두 실패 → 마지막 주소의 오류를 던진다 → 지금 재시도 규칙(일시 장애는 재시도, 다시 읽어도 같은 실패는 즉시 FAILED)
```

- 접속한 뒤의 실패(검색 도중 끊김·읽기 한도)는 JNDI 가 넘기지 않는다. 그 검색이 실패하고, 재시도가 그림 전체를 다시 읽을 때 새 커넥션이 다시 목록을 앞에서부터 돈다(F6).
- 이 표의 "다음 주소" 갈래는 JDK 17 의 `com.sun.jndi.ldap.LdapCtxFactory` 동작이다. 구현 때 그 코드로 사실을 확인하고(§11), 시험이 고정한다(§4).

### 3.2 회차 비용

- 앞 DC 가 **연결을 거절**하면(포트 닫힘·호스트가 RST) 넘김은 거의 즉시다.
- 앞 DC 가 **패킷을 버리거나 접속만 받고 답하지 않으면** 새 커넥션마다 `ldap.connect-timeout`(기본 10초)을 기다린 뒤 넘긴다. 회차가 여는 커넥션은 2~3개라 회차마다 약 20~30초가 는다.
  재시도 시도마다 다시 든다. 작업 기한(`sync.job-timeout` 30분) 안이다.
- 그 상태가 길면 운영자는 그 주소를 목록 뒤로 옮기거나 뺀다.

### 3.3 상태 점검

| 주소들의 상태 | 판정 | 세부(actuator 범위 토큰에만 보인다 — 지금과 같다) |
|---|---|---|
| 하나라도 2초 안에 바인드됨 | UP | 주소마다 결과, `baseDn`, `strategy` |
| 모두 실패·2초 초과 | DOWN | 주소마다 오류 |
| 어느 주소든 인증 실패 | DOWN, 30분 동안 어느 주소에도 바인드하지 않음 | 마지막 인증 실패와 다음 확인 시각(지금과 같다) |

- 상태 점검은 지금처럼 liveness·readiness 그룹에 들지 않는다 — 재시작을 부르지 않는다(app-ldap `application.yml` 의 `management` 주석).
- 프로브 하나가 주소 수만큼 바인드한다. 몇 초마다 오는 프로브에 DC 여럿이면 바인드도 그만큼이다 — 읽기 없이 바인드뿐이라 DC 부담은 작다.

### 3.4 운영자가 보는 것

| 상황 | 지금 | 바뀐 뒤 |
|---|---|---|
| `ldap.urls: [dc1, dc2]`, dc1 이 패치로 3시간 내려감(연결 거절) | (주소 하나라면) 3시간 동안 매시 `FAILED`, 회수 멈춤 | 회차는 dc2 에서 읽어 `SUCCEEDED`. 상태 점검 UP, 세부에 dc1 실패 |
| dc1 이 패킷을 버림 | 같다 | 회차는 dc2 에서 읽고 약 20~30초 늦다. 상태 점검 UP, 세부에 dc1 2초 초과 |
| 서비스 계정 비밀번호가 틀림 | `FAILED`(인증 실패, 재시도 없음), 상태 점검 DOWN 후 30분 쉼 | 같다 — dc2 로 넘기지 않는다 |
| 모든 DC 가 내려감 | `FAILED`(재시도 뒤) | 같다. 메시지는 마지막 주소의 오류다 |
| `require-tls` 인데 목록에 `ldap://` 하나 | — | 기동이 멈춘다 |

## 4. 시험

각 시험에 "이 시험을 깨뜨릴 운영 코드 변경"을 적는다. 시간 임계치를 단언하지 않는다(온보딩 14 "벽시계 단언").

### 4.1 connector-ldap

| 시험 | 단언 | 깨뜨릴 변경 |
|---|---|---|
| 주소 목록이 컨텍스트 소스에 순서대로 실린다 | `ldapContextSource(properties).getUrls()` 가 설정 순서 그대로 | `setUrl(첫 주소)` 만 넘기기 |
| 첫 주소가 연결을 거절하면 둘째 주소에서 그림을 읽는다 | 닫힌 포트 + 임베디드 LDAP → 그림이 임베디드의 내용과 같다 | 목록 대신 첫 주소만 쓰기 |
| 첫 주소가 접속만 받고 답하지 않으면 접속 한도 뒤 둘째에서 읽는다 | 침묵하는 서버(`LdapTimeoutTest` 의 도우미) + 임베디드, 짧은 `connect-timeout` → 그림을 읽는다 | 같다 |
| 첫 주소가 인증을 거절하면 둘째로 넘기지 않는다 | 다른 비밀번호의 임베디드 + 맞는 비밀번호의 임베디드 → 인증 실패로 끝나고, 둘째 서버는 바인드를 받지 않았다 | 앱이 인증 실패에도 다음 주소를 시도하게 바꾸기 |
| 기동 검사 | 빈 목록, 빈 항목, `http://`, 경로 있는 주소(`ldap://h/dc=x`)는 멈춤. `ldap://h:389/` 는 통과. `require-tls` 에서 하나라도 `ldap://` 면 멈춤, 모두 `ldaps://` 면 통과. 오류 문구에 비밀번호가 없다(지금 규칙) | 검사 빼기, 첫 주소만 보기 |

- 지금 시험이 `setUrl` 로 주소를 넣는 곳(`EmbeddedLdapSupport`·`LdapTimeoutTest` 등)은 목록으로 바꾼다.

### 4.2 app-ldap

| 시험 | 단언 | 깨뜨릴 변경 |
|---|---|---|
| `LdapHealthIndicatorTest` — 첫 주소가 답하지 않고 둘째가 바인드되면 UP | 세부에 두 주소의 결과(첫째 실패, 둘째 됨) | 목록 하나로 바인드하기 |
| 모든 주소가 실패하면 DOWN | 세부에 주소마다 오류 | 하나만 보고 판정 |
| 어느 주소든 인증 실패면 DOWN 이고 30분 동안 어느 주소에도 바인드하지 않는다 | 바인드 시도 수 | 인증 실패를 주소별로만 쉬기 |
| 주소 하나면 지금과 같은 판정 | 지금 시험들(응답 없음·끊김·성공·인증 실패 쉼·30분 뒤 다시) 그대로 통과 | — |
| `ldap.urls` 바인딩 | 쉼표로 이은 문자열과 yml 목록이 같은 목록이 된다 | 키 이름·형 바꾸기 |

- 앱 시험의 `registry.add("ldap.url", …)`(약 17곳)는 `ldap.urls` 로 바꾼다. 새 규모 시험은 두지 않는다 — 회차의 읽기·쓰기는 바뀌지 않는다.

## 5. 바뀌는 곳 (어림)

- `connector-ldap/.../LdapProperties.java` — `url` → `List<String> urls`(기본 `List.of("ldap://localhost:1389")`), 자바독.

## 6. 이 설계가 말할 수 없는 것

- **실제 AD 의 DC 여럿으로 넘김을 시험하지 않는다.** 시험은 임베디드 LDAP 과 닫힌 포트·침묵하는 소켓이다. 실제 DC 의 점검 모드(결과 코드 52 "unavailable" 등)가 넘김을 부르는지는 JNDI 코드로만 따진다.
- **DC 사이 복제 지연의 영향은 재지 않았다.** 넘긴 DC 가 몇 초~몇 분 늦은 그림을 주면, 그 사이의 입사·퇴사가 한 회차 늦거나 한 회차 동안 되돌려졌다가 다음 회차에 맞춰진다.
- **`ldaps://` 여럿의 인증서 검증**은 지금처럼 확인하지 못한다(13 §4.3 — 시험은 설정 검사만 본다).
- 상태 점검이 주소 수만큼 바인드하는 부담은 재지 않았다.

## 7. 왜 다른 길을 안 갔나

| 길 | 버린 까닭 |
|---|---|
| B. 앱이 회차마다 살아 있는 DC 하나를 골라 그 회차를 거기서만 읽는다 | 한 회차 = 한 DC 가 보장되고 응답 없는 DC 의 비용을 회차당 한 번만 낸다. 그러나 JNDI 가 이미 하는 넘김을 앱이 다시 만들고(주소별 컨텍스트 소스·고르기·재시도와의 맞물림), 재시도가 그림 전체를 다시 읽는 지금 구조에서 A 와의 차이는 DC 가 오락가락하는 짧은 틈뿐이다 |
| C. 주소 하나를 두고 부하 분산기·DNS 로 여러 DC 를 가린다(지금 우회) | 코드가 없지만 시험하지 않은 인프라에 맡긴다. 부하 분산기가 한 회차의 커넥션을 다른 DC 로 보내 섞는 것은 A 보다 잦다 |
| `ldap.url` 을 두고 공백으로 이은 JNDI 형식을 받는다 | 키 하나로 끝나지만 단수 이름이 목록을 숨기고, 환경 변수로 줄 때 부트 관례(쉼표)와 어긋난다 |
| 상태 점검을 목록 하나로 바인드하고 상한만 늘린다(2초 → 접속 한도 × 주소 수) | 코드가 작지만 프로브가 수십 초 매달린다 — "매달린 프로브는 죽은 것보다 나쁘다"(지금 자바독). 어느 DC 가 내려갔는지도 보이지 않는다 |
| 인증 실패에도 다음 주소로 넘긴다 | DC 하나만 비밀번호가 다른 경우는 없다(한 도메인). 틀린 비밀번호의 바인드가 DC 수만큼 늘어 잠금에 빨리 닿는다 |

## 11. 확인할 것 (구현 때 사실로 정한다)

- **JDK 17 `LdapCtxFactory` 의 목록 처리.** 인증 실패만 목록을 멈추고 그 밖의 `NamingException`(접속 거절·접속 한도·바인드 응답 없음)은 다음 주소로 가는지. 다르면 §3.1 과 F3 을 고치고 시험이 그 사실을 고정한다.
- **스프링 LDAP 3.3 `AbstractContextSource.setUrls` 가 주소마다 베이스를 붙이는 모양**(`assembleProviderUrlString`). 끝에 `/` 가 있는 주소(`ldap://h:389/`)도 맞게 붙는지.
- **주소 하나짜리 컨텍스트 소스를 손으로 만들 때** `afterPropertiesSet()` 등 초기화가 운영 컨텍스트 소스와 같은지(같은 JNDI 환경·자격 증명·베이스).
- **임베디드 LDAP 이 받은 바인드 수를 셀 길**(F3 시험의 "둘째 서버는 바인드를 받지 않았다"). 마땅한 길이 없으면 그 단언을 "인증 실패로 끝났다" 로 줄이고 이 절에 적는다.
