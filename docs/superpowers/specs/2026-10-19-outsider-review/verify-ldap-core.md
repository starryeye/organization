## L-a "결과를 모르는 쓰기가 '안 씀'이 된다" (backend H1, authz H1)

**코드 사실: 맞음 — 리뷰어가 적지 않은 반대 방향이 하나 더 있다.**
- `authz-openfga/.../OpenFgaRelationTupleWriter.java:387-397` 은 일시 오류만 재시도한다. 재시도가 다 끝나면 `:406-428` 에서 400 이 아닌 오류도 `batch.failed(...)` 가 된다. `:533-536` 의 `failed()` 는 written·deleted 를 비운다. 서버가 커밋하고 응답만 잃었어도 결과는 "실패"다.
- `core/.../usecase/FullSyncUseCase.java:134-140` — PARTIAL 로 끝난 회차도, 차단기로 멈춘 회차(`TupleWriteAbortedException`)도 `saveSnapshotAndState` 로 간다. `:166-170` 은 committed = 기준선 − deleted + written 이다. 이어서 `storage-dynamodb/.../DynamoDbTupleSnapshotRepository.java:134-141` 이 포인터 줄을 통째로 PutItem 해 "기록 중" 칸을 지운다.
- 결과: 커밋된 줄이 기준선에 없다. 다음 성공 회차 전에 그 줄이 목표에서 빠지면 `TupleDiff` 가 지울 대상으로 잡지 못해 영원히 남는다. 실패가 이어지거나 가드가 걸리면(L-c) 이 위험 창은 길어진다. 아직 목표에 있으면 다음 회차가 다시 쓰므로(on_duplicate IGNORE) 저절로 낫는다.
- 반대 방향: 지우기 배치가 반영되고 응답을 잃으면 그 줄은 기준선에 남는다(`:169` 의 removeAll 에 들지 않는다). 그 사이 그 사람이 다시 들어오면 기준선과 목표에 모두 있어 다시 쓰지 않는다. 권한이 영구히 빠진다(거부 쪽).
- 문제가 없는 경로:
  - 취소(리스 상실·기한·서버 종료)는 스냅샷을 남기지 않아 칸이 남는다. 다음 회차가 장부를 훑어 맞추므로 안전하다.
  - 장부 맞추기(`TupleReconciler.java:98-113`)는 쓴 뒤에 훑으므로 쓰기 쪽 문제가 없다. `2026-09-30-cluster-jobs-baseline-design.md:184-185`(§9 "리뷰에서 고친 것")가 바로 이 부류를 재적재 경로에서 고쳤다. 비교(diff) 경로는 다시 보지 않았다.
- 정리: 문제는 "끝까지 간 PARTIAL" 과 "차단기 FAILED" 두 경로뿐이다.

**문서상 지위: 처음 드러남.**
- "결과를 모르는 묶음은 실패로 센다"는 사실은 이력 쪽 한계로만 적혀 있다: `2026-10-15-failed-run-audit-design.md:109`(§8), `README.md:433`, 포트 자바독 `core/.../port/RelationTupleWriter.java:23-29`.
- 기준선 쪽 결과는 어디에도 없다. 문서는 오히려 반대로 단언한다:
  - `2026-09-30-cluster-jobs-baseline-design.md:65`: "차단기로 멈춘 동기화는 … 칸이 사라진다(**기준선이 정확하다**)"
  - `README.md:212-213`: "(LDAP 기준선이 장부를 따라간다)"

**원칙과의 관계: OpenFGA Read 원칙.**
- 고침 ① "400 이 아닌 실패가 있으면 칸을 남긴다" 는 다음 회차를 장부 맞추기(Read)로 보낸다.
  - 차단기 경로는 말 그대로 "멈춘 회차"라 원칙의 글자("멈춘 뒤 첫 LDAP 동기화") 안이다. 차단기 경로에서 칸을 지운 것은 "기준선이 정확하다"는 틀린 전제 때문이었다.
  - 차단기 없는 PARTIAL 까지 넓히는 것은 Read 를 쓰는 조건을 넓히는 일이라 소유자 확인이 필요하다.
- 고침 ② (authz H1) "불확실한 묶음의 줄을 따로 기록해 다음 회차가 목표에 있는 것은 쓰고 없는 것은 지운다" 는 Read 없이 되므로 원칙 안이다.
  - `2026-09-30 …:198-199`(§10)가 기각한 "의도 기록"과 닮았다.
  - 다만 대상이 실패한 묶음(동시 4 × 100줄 안팎)뿐이라 그 기각 사유(매 회차 11만 줄 기록, 복잡도)가 거의 해당하지 않는다.

**심각도: High.**
- 확률은 낮다. 커밋 직후 OpenFGA 장애가 나고, 재시도 동안 장애가 이어지고, 다음 성공 회차 전에 되돌림이 있어야 한다.
- 그래도 결과가 조용한 영구 과잉 권한이고, 찾는 장치가 없다(L-e). 리뷰어와 같다.

## L-b "포인터가 없으면 빈 기준선 → 지우기 0" (authz H2, IAM H3)

**코드 사실: 맞음 — PITR 은 리뷰어 설명과 조금 다르다.**
- 포인터가 없을 때의 흐름:
  - `DynamoDbTupleSnapshotRepository.java:150-153` — 포인터가 없으면 id 가 빈 값이다.
  - `:143-148` — `findLatest` 가 빈 값이다.
  - `FullSyncUseCase.java:144-148` — `defaultIfEmpty(Set.of())` 로 빈 기준선이 된다.
  - `:178-183` — `isWriting` 도 false 라 비교 경로(`FullSyncUseCase.java:93-95`)를 탄다.
- 지울 것을 하나도 계산하지 않으므로, store 에 이미 있던 줄은 영원히 남는다.
- 칸만 있고 스냅샷 번호가 없는 포인터(첫 회차가 쓰다 멈춘 경우)는 `isWriting=true` 라 장부 맞추기로 간다. 문제는 포인터 줄 자체가 없을 때뿐이다.
- PITR 복원은 포인터도 함께 복원한다. 그래서 빈 기준선이 아니라 낡은 기준선이 된다.
  - 복원 뒤 첫 회차가 목표에 있는 줄을 다시 써 메운다.
  - 남는 것은 "복원 시점 뒤에 생겼다가 첫 회차 전에 목표에서 빠진 줄" 뿐이다(IAM H3 의 PITR 예와 같다, 좁다).
  - 넓은 경우는 새 빈 테이블과 기존 store 의 조합이다. 테이블 재생성, 다른 테이블 지정, 설정 오타로 생긴 테이블(`create-table-on-startup: true`)이 여기에 든다.

**문서상 지위: 동작은 결정됐고, 이 결과는 처음 드러남.**
- `2026-09-29-integrity-quick-fixes-design.md:60`(§3.4): "포인터가 없으면 빈 결과 — 처음 설치·재적재 직후. 지금처럼 빈 기준선으로 첫 적재를 한다(정상 흐름)". 빈 store 의 첫 설치만 상정한 결정이다.
- "store 에는 줄이 있는데 포인터가 없다"는 경우와 "테이블을 다시 만들면 재적재부터"라는 규칙은 어느 문서에도 없다.
- 오히려 README 는 테이블만 다시 만들라고 여러 번 지시한다:
  - `README.md:60`: 옛 형식 스냅샷이면 "재적재로 새 스냅샷을 남기거나 테이블을 다시 만든다"
  - `README.md:129-146`: 키 레이아웃 변경
  - store 도 새로 만들라는 말은 불변 id 이관(`README.md:928-931`)에만 있다.
- `README.md:53-54` 의 "빈 기준선으로 넘어가지 않는다"는 포인터가 있는데 스냅샷이 깨진 경우만 말한다.

**원칙과의 관계:**
- "운영 배포 전, 초기화 가능": README 의 테이블 재생성 지시는 배포 전 이관 메모라 그 자체는 비용이 아니다. 그러나 배포 뒤 DR(새 테이블로 복원, 리전 이동, 설정 오타)에서는 그대로 남는다.
- Read 원칙: "포인터 없음 = 기준선 의심 → 장부 맞추기"는 Read 를 쓰는 조건을 넓히므로 소유자 확인이 필요하다.
- 원칙 안의 대안도 있다: "새 테이블의 첫 회차는 재적재"를 런북·기동 검사로 강제한다. 재적재는 이미 Read 가 허용된다.

**심각도: Medium.**
- 운영 사건이 있어야 발동한다. 발동하면 마지막 기준선 이후에 빠진 사람 전원의 권한이 신호 없이 영구히 남는다. 고침은 한 줄 수준이다.
- 리뷰어(High)보다 낮게 본 까닭: 배포 전에는 원칙상 비용이 아니고, 배포 뒤에는 계획된 테이블 재생성이 없다.

## L-c "삭제 가드가 전부 아니면 전무이고 회수를 막는다" (backend H2, authz M2, SA H-5, IAM H2·M5)

**코드 사실: 대체로 맞음 — 장부 맞추기 경로에 대한 서술 하나가 틀렸다.**
- 비교 경로:
  - `FullSyncUseCase.java:126-131` — 가드에 걸리면 쓰기·지우기·현재상태 교체 없이 ABORTED 다.
  - 비활성 계정 때문에 생긴 지우기도 `core/.../guard/DeletionGuard.java:23-25,40` 의 "지울 수 / 기준 수"에 함께 들어간다. 원인을 가르지 않는다.
- 매일 다시 걸린다:
  - ABORTED 는 스냅샷을 남기지 않아 기준선이 그대로다. 같은 델타가 나와 다시 ABORTED 다(`app-ldap/.../SyncScheduler.java:32-45`).
  - `force` 가 이를 끝내지만 가드 전체를 끈다(`FullSyncUseCase.java:126`). 일부만 승인하는 길은 없다.
- 부여 쪽 가드는 없다. `DeletionGuard` 는 지울 수만 세고, `TupleReconciler.java:98-104` 는 D 를 먼저 다 쓴 뒤 지우기에만 가드를 건다.
- 30% 이하는 그대로 통과한다(`DeletionGuard.java:41`, `ratio <= threshold`). 튜플 15만 줄이면 4.5만 줄 회수가 경고 없이 반영된다. 장부 맞추기는 분모가 "훑은 장부(옛 ∪ D)"라 더 약하다(`2026-09-30 …:220-221`).
- 틀린 부분: IAM H2 의 "장부 훑기도 같다(`LedgerAlignment.java:49-55`)"와 "아무것도 쓰지 않는다"는 장부 맞추기 경로에서는 틀렸다.
  - `LedgerAlignment.java:50-55` → `TupleReconciler` 가 D 를 먼저 쓰고 지우기만 보류한다. 그 경로에서는 부여가 나간다(backend H2 는 이것을 정확히 적었다).
  - 현재상태 교체는 두 경로 모두 하지 않는다(`LedgerAlignment.java:53-54`).

**문서상 지위: 일부는 결정·수용, 원인별 분리·부여 가드·절대 수 상한은 처음 드러남.**
- 대량 비활성화를 가드 안에 두는 것은 결정이다: `2026-09-25-ldap-disabled-account-design.md:86`(§4) "대량 비활성화는 권한을 많이 지우는 일이라 기존 삭제 가드(30%)가 그대로 막는다".
- "가드가 걸린 동안 퇴사도 반영되지 않는다"는 비용은 알려져 있다: `README.md:462`, `2026-09-28-full-audit.md:848`(M9), `2026-10-04-immutable-identifiers-design.md:19`.
  - 다만 셋 다 이름 기반 id 의 개명 맥락이다. 불변 id 로 원인을 없앴다며 끝냈고, 가드 자체는 다시 보지 않았다.
- 30% 미만 대량 회수가 통과한다는 것도 알려져 있다: `2026-09-09-ad-range-retrieval-design.md:32` "전체가 10만이면 6% 라 그냥 지워진다". 가드는 그대로 두고 원인(범위 검색)을 고쳤다.
- 가드의 목적은 0건·부분 응답이다(`2026-08-14-organization-sync-design.md:644-646`, §9.2).
- 원인별(비활성 vs 사라짐) 분리, 절대 수 상한, 부여 가드는 어느 문서에도 없다.

**원칙과의 관계: "표준대로, 경우 나열 말고".**
- 비활성은 표준 신호(MS-ADTS 의 UAC·accountExpires, ppolicy)다. 그 신호로 생긴 회수를 가드 밖에 두는 것은 "표준이 말한 신호를 믿는다"로 읽힌다. 동시에 가드에 경우를 하나 더하는 일이기도 하다.
- 반대 근거도 있다. 잘못 읽은 디렉터리도 비활성으로 보일 수 있다. 예: 서버 시계가 크게 앞서면 `accountExpires` 로 전원이 만료된다(`AccountStatus.java:58-65` 는 앱 시계로 판단한다).
- 그래서 비활성 지우기를 가드에서 통째로 빼면 그런 사고를 막지 못한다. 원인별 비율로 나누는 정도가 중간이다. 소유자가 정할 일이다.

**심각도: High.**
- 불변 id 기본값에서는 개명이 원인이 아니다. 그러나 정상적인 큰 개편(그룹 폐지)이나 AD 기본 그룹을 범위에서 빼는 일만으로도 30% 를 넘을 수 있다.
- 그러면 사람이 `force` 할 때까지 입사·퇴사가 매일 멈춘다.
- 다수 리뷰어(High)와 같고, authz(M2)보다 높다.

## L-d "LDAP 회수 지연" (backend H2, authz M3, SA H-5, IAM H1)

**코드 사실: 맞음 — 두 가지를 보충한다.**
- 기본 cron 은 매일 03:00 이다: `app-ldap/.../SyncProperties.java:14`, `app-ldap/src/main/resources/application.yml:20`.
- 읽기 재시도:
  - `connector-ldap/.../LdapDirectorySnapshotSource.java:61` 이 `Retry.backoff(getMaxRetries(), 200ms)` 이고, `LdapProperties.java:27` 의 기본이 3번이다. 대기는 약 0.2·0.4·0.8초(지터 ±50%)다.
  - 시도마다 처음부터 다시 읽고, 응답 없는 DC 면 시도당 `connect-timeout` 10초(`LdapProperties.java:36`)까지 걸린다. 합쳐도 수 초에서 약 40초다.
  - DC 재부팅(수 분)을 버티지 못하고 그날 회차는 FAILED 다. 다음 시도는 다음 cron 이다.
- 증분 경로가 없다: `core/.../port/DirectorySnapshotSource.java:9-10`.
- 개인 즉시 회수가 없다: app-ldap 의 쓰기 입구는 `/admin/sync/full`·`/rebuild` 뿐이다(`AdminSyncController.java:48,61`). 보충: 수동 `POST /admin/sync/full` 이 비상 경로로는 있다(10만 명이면 수 분).
- 마지막 성공 게이지가 없다: `SyncMetrics.java:20-43` 은 끝난 회차의 타이머·카운터뿐이다.
  - 보충: 락을 못 잡아 건너뛴 회차는 INFO 로그만 남는다(`SyncScheduler.java:40-43`).
- IAM H1 의 "만료 판정 시각 = 회차 시작"도 맞다(`GroupOfNamesStrategy.java:56`).

**문서상 지위: 하루 주기는 결정이다. 회수 SLO·신선도 게이지는 알려졌으나 미결정이고, 개인 즉시 회수는 처음 드러남.**
- 하루 주기는 설계 전제다(결정·수용):
  - `2026-08-14-organization-sync-design.md:11` "LDAP: pull 모델. 서버가 하루 1회 전체를 읽어온다"
  - 같은 문서 `:453`(§7.1) "매일 03:00 (설정 가능)"
  - 증분 없음도 결정이다: 같은 문서 `:221`
- 지연은 인정했다: `README.md:535` "막힌 직후부터 다음 동기화까지는 권한이 남는다", `2026-09-25-ldap-disabled-account-design.md` §6.

## L-e "정기 장부 대조가 없고 아카이빙 비교는 로그뿐" (authz M5, SA H-3, IAM M6, backend H1.3)

**코드 사실: 맞음.**

  - 스냅샷하고만 비교한다(`FullSyncUseCase.java:117-121`).

**문서상 지위: 이미 결정·수용 — 다만 외부에서 생긴 어긋남만 상정했다.**
- `2026-08-14-organization-sync-design.md:64-66` "감수하는 트레이드오프 — 드리프트를 전수로 감지할 수 없다 … 되돌리는 수단이 rebuild … 표본 검증은 가능하다 — 아직 구현하지 않았다", `README.md:41-44`.

**원칙과의 관계 — "OpenFGA Read 는 재적재에서만":**
- 원칙을 정한 문서:
  - `2026-09-29-rebuild-jobs-fixed-store-design.md:28-31`(§2): "재적재에서만 OpenFGA Read 를 허용한다 … Read 는 이 '장부 훑기'(사람이 거는 드문 백그라운드 작업)에서만 쓰고, 평소 쓰기·판단 경로는 Check·BatchCheck 만"
  - 확장: `2026-09-30-cluster-jobs-baseline-design.md:28-29`(§2) — "멈춘 뒤 첫 LDAP 동기화"에도 쓴다.
- 문서에 적힌 이유:
  1. 출발점은 "열거 API(Read/ListObjects)만 금지"라는 주어진 제약이다(`2026-08-14 …:55`). 그 문서에는 이유가 없다.
  2. 재적재에 Read 를 연 이유는 store 번호 고정과 인가 공백 제거다. 대안(블루-그린, 쓴 줄 원장)은 움직이는 부품과 줄마다 DynamoDB 쓰기 +1 때문에 기각했다(`2026-09-29 …:156-165`, §10). 쓴 줄 원장은 "직접 써 넣은 줄은 못 찾는다"는 약점도 적었다.
  3. 판단·쓰기 경로에서 금지하는 이유는 비용이다: `RelationTupleScanner.java:10-11` "판단·쓰기 경로에서 부르면 안 된다 — 요청마다 장부 전체를 읽게 된다". 이는 "요청당 전원 읽기 금지"와 같은 뿌리다.
  4. 멈춘 뒤 첫 회차로 넓힌 이유: Read 없는 의도 기록은 매 회차 쓰기가 늘고 규칙이 복잡해진다(`2026-09-30 …:198-199`).
- 백엔드 H1.3 의 락 없는 탐지 전용 야간 훑기는 이유 2·3 어느 것도 어기지 않는다.
  - 요청 경로가 아니다. 하루 한 번 약 1,100번 호출, 약 2초다(10만 명 추정, `2026-09-29 …` §9).
  - 쓰지 않으므로 "판단·쓰기는 Check" 라는 핵심도 그대로다.
- 어기는 것은 원칙의 글자("재적재와 멈춘 뒤 첫 동기화에서만")뿐이다. 그래서 소유자 결정이 필요하다.
- 글자 안에서 하는 길도 있다.
  - 정기 재적재: LDAP 은 가드가 걸린 `LedgerAlignment` 다. 예약으로 거는 재적재도 재적재다.
  - 원래 설계가 남긴 Check 표본 검증: 표본을 스냅샷이나 상태에서 뽑으므로, 거기에 없는 잉여(L-a·L-b·L-m 이 만드는 방향)는 찾지 못한다. 잉여는 열거로만 찾는다.
- 주의: 락 없는 훑기가 03:00 동기화와 겹치면 거짓 양성이 나온다. 시간을 비키거나 다음 날 다시 확인해 거른다.

**심각도: High.**
- 혼자서는 수용된 트레이드오프다. 그러나 L-a·L-b·L-m 이 만드는 영구 잉여를 찾을 유일한 길이고, 10만 명에서도 비용이 작다.
- 리뷰어 의견이 갈렸는데(authz·IAM Medium, SA High) SA 쪽에 선다.

## L-f "계정 상태 fail-open" (backend L5, authz M1 LDAP 부분, IAM M4)

**코드 사실: 맞음.**
- 속성이 없으면 막히지 않은 것으로 본다: `connector-ldap/.../strategy/AccountStatus.java:22-24, 53-56, 58-61, 68-72, 80-84`.
- 읽는 상태 속성은 셋뿐이다: `UserAttributes.java:16-19` 의 userAccountControl·accountExpires·pwdAccountLockedTime.
- `nsAccountLock`·`msDS-UserAccountDisabled`·`shadowExpire` 는 요청도 해석도 하지 않는다(코드 어디에도 없다).
- AD 에서 ACL 로 UAC 를 못 읽으면 엔트리에 속성이 실리지 않아 전원이 활성이 된다. 경고도 지표도 없다.

**문서상 지위: 이미 결정·수용(389DS·AD LDS·posix 속성만 처음 드러남).**
- `2026-09-25-ldap-disabled-account-design.md:28,38`(§2): "속성이 없으면 막히지 않은 것으로 본다. 설정 스위치를 두지 않는다". 대안("스위치를 켜면 속성 필수")은 "AD 배포에서 스위치를 잊으면 결함이 그대로 남는다"며 기각했다.
- 같은 문서 §6 `:105-106`: 동기화 계정이 속성을 읽지 못하면 전원이 활성으로 읽힌다(§2 에서 받아들인 것). "AD 기본 권한은 인증된 계정에게 읽기를 허용하므로 비표준 설정에서만 생긴다". `README.md:531,533` 도 같다.
- ppolicy 는 `2026-10-05-ldap-read-design.md` §3.3 에서 더했다.
- 389DS/FreeIPA·AD LDS·shadowExpire 는 어느 문서에도 없다.

**원칙과의 관계: "표준 신호만".**
- `nsAccountLock` 은 389DS 계열 고유 속성이라 원칙상 읽지 않는 것이 맞다.
- `msDS-UserAccountDisabled` 는 지금 읽는 AD 두 속성과 같은 MS-ADTS(AD LDS) 신호다. `shadowExpire` 는 RFC 2307 속성이다. 원칙의 잣대로는 같은 반열이다.
- 결국 그 디렉터리들을 지원 대상으로 삼을지의 문제다.

**심각도: Low.**
- AD 기본 ACL 에서는 생기지 않는다. 대상이 AD·OpenLDAP 이면 해당 없다.
- 리뷰어(authz·IAM Medium)보다 낮다.
- 값싼 보강: AD(objectGUID) 설정인데 회차 전원에게 UAC 가 없으면 경고한다.

## L-h "긴 LDAP description → GSI 키 초과 → 매 회차 실패" (backend M2)

**코드 사실: 맞음 — 리뷰어가 적은 것보다 넓다.**
- 기본 조직 표시명 속성이 `description` 이다: `connector-ldap/.../LdapProperties.java:78,95`, `application.yml:52,60`(DIT 도), `GroupOfNamesStrategy.java:259`.
- 소문자로 바꿔 GSI1 정렬키에 그대로 넣는다:
  - `storage-dynamodb/.../DynamoDbDirectoryStateRepository.java:562-571`
  - `Keys.indexKey` = `toLowerCase(Locale.ROOT)`(`Keys.java:147-149`)이고 접두어도 자르기도 없다. 한도는 1024바이트다(`Keys.java:62`).
  - 직원은 GSI1SK=userName, GSI2SK=displayName 이다(`:196-208`).
- 길이 검사는 SCIM 에만 있다: `KeyValueLimits.over` 를 부르는 곳은 `IncrementalSyncUseCase.java:233,276,296,335,380,419` 뿐이다.
- `replaceWith` 가 통째로 실패한다:
  - 단계 안이 flatMap 이다(`:773-778`). 한 건이 실패하면 같은 단계의 나머지가 취소된다.
  - 단계는 순서대로 돈다(`:801`). 뒤 단계(사라진 조직 지우기·퇴사 직원 지우기)도 돌지 않는다.
- 스냅샷이 먼저 저장된다(`FullSyncUseCase.java:179-181`). 그래서 튜플과 기준선은 맞게 나아가고, 실패는 상태 쪽에 갇힌다.
- 매 회차 실패한다. 어느 경로든 `replaceWith` 를 부르기 때문이다:
  - 변경이 없으면 `FullSyncUseCase.java:121-124`
  - 변경이 있으면 `:179-181`
  - 장부 맞추기면 `LedgerAlignment.java:70-71`
  - 리뷰어는 "변경 없음" 경로만 적었다.
- 보충: 뒤 단계가 돌지 않으므로 퇴사 직원이 현재상태에서 지워지지 않는다. 로그인 → employeeId 변환 경로인 관리 API(`README.md:336-345`)에 퇴사자가 계속 보인다. 튜플은 지워졌으므로 Check 는 false 다.

**문서상 지위: 알려졌으나 미결정.**
- `2026-10-17-scim-standard-rest-design.md:149`(§7): "LDAP 에서 온 긴 값은 막지 않는다. 1KB 넘는 표시명 같은 값이 오면 지금처럼 **그 회차의** 현재상태 교체가 실패한다(FAILED). 사내 디렉터리에서 현실적이지 않다"
- 같은 문서 `:208`(§10 남긴 것), `:214`(§11 범위 밖 "LDAP 에서 온 긴 값의 회차 처리(건너뛰기·잘라 넣기 등)"), `README.md:630`.
- §7 의 판단은 두 점에서 약해진다.
  1. "그 회차"가 아니다. 데이터를 고칠 때까지 매 회차 실패한다. 그 FAILED 가 다른 실패를 가리고, L-d 의 신선도 게이지도 없다.
  2. 기본 속성이 이름이 아니라 자유 문장인 `description` 이다. AD `description` 은 최대 1024자라 한글 342자(약 1,026바이트)면 넘는다. "현실적이지 않다"는 이름에는 맞지만 설명 문장에는 덜 맞는다.
- 권한(튜플)에는 영향이 없다는 점은 그대로다.

**원칙과의 관계: "표준대로, 한 규칙".**
- RFC 4519 의 description 에는 길이 한도가 없다. 잘라 넣기는 우리 규칙이 되고, 키 해시는 `2026-10-17 …` §8 이 "정렬·접두어 검색이 깨진다"며 기각했다.
- 한 규칙으로 맞추려면 기존 건너뛰기 규칙(`README.md:537-543`, 건너뛰고 요약 한 줄)에 "키 한도(SCIM 과 같은 값)를 넘는 엔트리"를 더하는 것이 원칙에 맞는다.

**심각도: Medium.**
- 확률은 낮고 권한은 맞다. 그러나 한 번 생기면 매일 FAILED 이고, 상태가 멈춰 퇴사자가 계속 보인다.
- 리뷰어와 같다.

## L-m "펜싱이 없다 — 리스를 잃은 뒤의 늦은 쓰기가 다음 회차의 장부 훑기 뒤에 떨어지면 남는다" (authz M4, SA L-2)

**코드 사실: 맞음 — 창은 좁다.**
- OpenFGA 쓰기는 `Mono.fromFuture(client.write)` 다(`OpenFgaRelationTupleWriter.java:388-394`). 취소해도 이미 나간 요청은 서버에 닿는다.
- LDAP 작업은 리스를 하트비트로만 지킨다(`SyncJobs.java:150` → `LeaseKeeper.keep`). SCIM 처럼 OpenFGA 쓰기 직전에 리스를 다시 확인하지 않는다(SCIM 은 `IncrementalSyncUseCase.java:967-979`).
- 그래서 A 가 오래 멈췄다 깨어나면, 하트비트 타이머와 다음 묶음 전송이 경주한다.
- 그 사이 B 는 "기록 중" 칸을 보고 장부 맞추기를 한다: LDAP 읽기 → D 쓰기 → 훑기 → 지우기(`TupleReconciler.java:98-113`).
- A 의 쓰기가 B 의 훑기 뒤에 닿으면 B 의 스냅샷에 없다.
  - 그 줄이 목표에도 없으면 영원히 남는다.
  - 지우기였다면 그 권한이 영원히 빠진다.
- 창: A 의 멈춤이 리스 30초 + B 의 LDAP 전체 읽기·D 쓰기·훑기(10만 명이면 분 단위)보다 길어야 한다. GC 정지가 아니라 VM 이 멈추는 정도다.

**문서상 지위: 이미 결정·수용(일반 한계로) — LDAP 에서는 새어 나간 줄이 낫지 않는다는 점만 처음 드러남.**
- `2026-09-30-cluster-jobs-baseline-design.md:210`(§11): "락은 완벽한 상호 배제가 아니다 … 늦은 쓰기가 새어 나갈 수 있다(… OpenFGA 에 펜싱 토큰이 없다)".
- `2026-10-02-big-change-lock-design.md:31, 170-171, 178`(§2·§10·§11): 사용자가 "갱신 + 커밋 직전 확인"을 골랐다.
- `2026-09-01-scim-concurrency-design.md:388-406`(§4.7), `DynamoDbMutationLock.java:34-36`, `README.md:856`(S15 시계 — 점검 `2026-09-28-full-audit.md:1261` "문서로 정리"), `README.md:901`.
- 문서가 기댄 치유책 "Check 기준선이 다음 터치에 걷어낸다"(scim-concurrency `:403`, §4.7 3항)는 SCIM 에만 있다. LDAP 에서는 새어 나간 줄이 그대로 남는다는 결과는 적혀 있지 않다.

**원칙과의 관계:** Read 원칙. LDAP 에서 근본적으로 고치는 길은 정기 대조(L-e)뿐이다.

**심각도: Low.**
- 창이 아주 좁고(분 단위 정지), 펜싱이 안 된다는 것은 이미 받아들인 사실이다.
- authz(M4 Medium)보다 낮고 SA(L-2 Low)와 같다.
- 더 좁히는 값싼 길: LDAP 쓰기 묶음을 보내기 직전에 단조 시계로 "마지막 갱신 성공 + 2×주기"가 지났는지 본다. 네트워크 호출이 없다.

## 요약 (확인된 새 문제, 순위)

1. **L-a (처음 드러남, High)** — 결과를 모르는 쓰기를 기준선에서 빼고 "기록 중" 칸까지 지운다. 문서는 오히려 "기준선이 정확하다"고 적었다. 차단기 경로는 원칙 안에서 바로 고칠 수 있다.
2. **L-c 의 미결정 부분 (High)** — 가드 안에 비활성을 둔 것은 결정이다. 그러나 원인별 분리·부여 가드·절대 수 상한은 논의된 적이 없다. 불변 id 이후에도 큰 개편 하나가 모든 입·퇴사를 매일 멈춘다.
3. **L-b (결과는 처음 드러남, Medium)** — 포인터가 없는 첫 회차는 기존 store 를 지우지 않는다. "빈 store 의 첫 설치"만 상정한 결정이고, 배포 뒤 DR 에서는 반드시 발동한다.
4. **L-h (알려졌으나 판단 근거가 약해짐, Medium)** — "그 회차"가 아니라 매 회차 실패하고, 기본 속성이 자유 문장인 description 이다.
5. **L-k·L-l (처음 드러남, Low)** — 헬스가 기동 뒤 OpenFGA 를 묻지 않아 README:184 와 어긋난다. 하루 1회 표지를 잡은 뒤 실패하면 그날 작업이 없다. L-e 는 수용된 트레이드오프지만 L-a·L-b·L-m 의 공통 완화책이라 소유자가 다시 정할 일이다.
