# 직원 한 명 변경의 스냅샷을 그 한 명으로 좁힌다

**작성일:** 2026-09-10
**상태:** 설계. 구현 전
**발단:** 픽스처 최대 조직을 500명 → 1,600명으로 키우자 S1(조직 먼저 순서)이 46.5초 → 835.4초
**바꿀 것:** `IncrementalSyncUseCase`, `DirectoryStateRepository`(+구현체), `GroupHeader`(신규)

---

## 1. 문제

SCIM 으로 직원 한 명이 바뀌면 — 퇴사, 복직, 새 직원 도착 — `IncrementalSyncUseCase`
가 **그 직원이 속한 조직의 멤버를 전부 읽는다.**

읽는 이유는 있다. 조직을 튜플로 바꾸려면 멤버마다 재직 여부(`active`)를 알아야 하고,
퇴사자는 튜플이 없어야 하기 때문이다(`TupleMapper.collectDirectMembers`).

**그런데 그 결과를 쓰지 않는다.** `diffAndApply` 가 델타를 계산하기 직전에 양쪽 튜플
집합을 `mentioning(focus)` 로 거른다. `focus` 는 `user:kim` 이므로 **kim 을 언급하는
튜플만 남고 나머지는 전부 버려진다.**

### 1,600명 조직에 직원 하나가 도착할 때

| | 왕복 | 읽는 아이템 | 쓰이는가 |
|---|---|---|---|
| `findGroupIdsContaining(kim)` | 1 (GSI) | 소속 수 | **쓴다** |
| `findGroup(제1공장)` | 1 (Query) | **1,601** (파티션 통째) | 조직 id 만 |
| `findUser(kim)` | 1 | 1 | **쓴다** |
| `loadMemberUsers` (before) | **1,600** | 1,600 | 전부 버려짐 |
| `loadMemberUsers` (after) | **1,600** | 1,600 | 전부 버려짐 |
| **합계** | **≈3,203** | **≈4,803** | 쓰이는 것은 2개 |

왕복과 아이템을 나눠 적는 이유: `findGroup` 은 **왕복 1회지만 1,601 아이템**이라
지연은 한 번이어도 소비 RCU 가 조직 크기를 따라간다. `loadMemberUsers` 는 반대로
**아이템은 1개씩이지만 왕복이 1,600번**이라 지연이 그만큼 쌓인다. 둘의 성격이 달라서
고치는 방법도 다르다(§4.6 과 §4.2).

그 시점에 동료 대부분이 아직 도착 전이면 `TupleMapper` 가 "스냅샷에 없어 건너뜁니다"
경고 문자열까지 그 수만큼 만든다.

### 느린 것만이 문제가 아니다

이 전부가 **전역 락을 쥔 채로** 일어난다. 조직이 클수록 오래 쥐고, 그동안 다른 요청은
대기하거나 503 으로 거절된다. S3(동시 16스레드 × 200건)의 `{200=71, 503=129}` 가 그
모양이다.

**운영에서 대형 조직 직원 한 명을 퇴사시킬 때마다 이 일이 벌어진다.**

### 어떤 테스트도 이것을 못 잡는다

**결과가 맞기 때문이다.** 튜플도 맞고 규모 E2E 도 전부 통과한다. 읽는 횟수를 보는
테스트가 하나도 없다. 픽스처 최대 조직이 500명일 때는 1,000 왕복이라 "느리긴 해도
고장은 아닌" 범위였다.

## 2. 왜 이렇게 되어 있었나

이력이 남아 있다. **같은 문제를 한 번 찾았고, 반만 고쳤다.**

커밋 `9c9fc06` ("후보 집합을 이번 연산의 초점 엔티티로 좁힌다"):

> 최소 스냅샷은 영향 조직을 **멤버 목록째로 싣는다.** 그래서 `candidateTuples` 를 그대로
> 쓰면 `PUT /Users/kim` 한 번이 5000명 조직 전체를 **BatchCheck** 하게 된다 — 전역 락을
> 쥔 채로.

그때 보인 것은 **OpenFGA 쪽 비용**이었다. `mentioning(focus)` 필터를 달아 Check 호출을
줄였다. **DynamoDB 에서 읽어오는 것 자체는 그대로 뒀다.**

파이프 끝에서 막고 수도꼭지를 안 잠갔다. 그리고 필터를 달자 결과가 정상이 되어
**위쪽의 낭비가 보이지 않게 됐다.**

같은 커밋이 인용한 설계 §5.2 는 이미 이걸 요구하고 있었다:

> "upsertUser 가 소속 조직의 **전체 멤버를 확인하지 않는 것이 중요하다**"

"확인" 을 "Check 한다" 로만 읽고 "읽는다" 로는 읽지 않았다.

**저장소 쪽은 따로다.** 커밋 `393e086`("이미 손에 있는 값을 다시 읽던 세 곳")이
`findUser` 를 Query → `GetItem` 으로 바꿨다. `findGroup` 은 안 걸렸다 — **조직 경로에서는
멤버가 진짜로 필요하므로 낭비처럼 보이지 않았기 때문이다.**

## 3. 접근안 비교

### 3.1 core — 어떻게 좁히나

**A. 스냅샷 자체를 좁힌다 — 선택**

직원 경로의 그림에서 조직의 멤버 목록을 **바뀐 그 사람 하나로** 줄인다. 뒤쪽
(`TupleMapper` → 필터 → 델타 → 쓰기 → 커밋)은 한 줄도 안 바뀐다. 어차피 필터가
나머지를 버리고 있었으므로 **결과가 같다.**

**B. 직원 경로를 따로 만든다**

그림과 `TupleMapper` 를 거치지 않고 바로 계산한다 — "소속 조직 목록 × `active` = 있어야
할 튜플". 읽기에 가장 명확하다.

**그러나 `diffAndApply` 는 튜플 계산만 하지 않는다** — 어긋남 관측, 쓰기 직전 리스 재확인
(설계 §4.7), 부분 실패 시 "실제 반영된 만큼만 저장"(§7.2). 이것을 복제하거나 인자로
빼야 하고, **길이 둘로 갈라져 앞으로 계속 같이 관리**해야 한다. A 는 같은 결과를 입구만
바꿔서 얻는다.

### 3.2 storage — 조직을 어떻게 읽나

**b. 헤더만 읽는 메서드를 더한다 — 선택**

`GetItem(조직PK, META)`. `findUser` 와 같은 모양. **1,601 아이템 → 1 아이템.**

**c. 조직을 아예 안 읽는다**

`TupleMapper` 는 튜플을 만들 때 조직의 **id 만** 쓴다(`collectDirectMembers` 는
`group.id()`, `collectChildEdges` 는 id 간선). 그러니 소속 조직 id 목록만으로 그림을
만들 수 있다 — 읽기 0회.

**그러나 "그 조직이 실재하는가" 를 확인하지 못하게 된다.** 지금은 META 가 없으면
`toGroup` 이 `null` 을 돌려주고 그 조직이 조용히 빠진다. c 로 가면 없는 조직에 권한을
쓴다. 왕복 하나를 더 아끼자고 바꿀 동작이 아니다.

**a. 그대로 두기** — core 만 고치면 왕복 3,200 은 사라지지만 조직 읽기가 여전히 파티션
크기를 따라간다. 측정했을 때 개선폭을 설명하기 어려워진다.

## 4. 설계

### 4.1 핵심 구분 — 그림과 저장은 다른 것이다

한 연산 안에서 조직을 **두 용도**로 쓰는데 지금은 같은 객체 하나로 쓴다.

| 용도 | 필요한 것 | 좁혀도 되나 |
|---|---|---|
| **그림** — 튜플 계산용 스냅샷 | 바뀐 사람 하나 | **된다** |
| **저장** — `saveGroup` 에 넘길 멤버 목록 | **전체 멤버** | **절대 안 된다** |

**`saveGroup` 은 `group.members()` 를 "이것이 최종 멤버 목록" 으로 받아, 거기 없는 멤버
줄을 전부 지운다**(`DynamoDbDirectoryStateRepository.saveGroup` 의 `떠난멤버`). 좁힌
그림이 거기까지 흘러가면 **1,600개의 멤버 줄이 통째로 삭제된다.**

이것이 이 설계에서 가장 위험한 지점이다.

### 4.2 새로 만드는 것 — 한 사람짜리 그림

`snapshotOf` 옆에 직원 경로 전용을 하나 둔다:

```
직원한명_그림(조직들, 그사람)
  → 조직마다 멤버 목록을 { user:그사람 } 하나로 바꾼 그림
  → users 에는 그 한 명만
```

`loadMemberUsers` 를 부르지 않는다. `expandWithReferencedGroups` 도 사실상 무동작이다 —
멤버에 GROUP 타입이 없으므로.

**왜 결과가 같은가.** `diffAndApply` 가 후보·목표·상태기준선 셋 모두를
`mentioning(user:kim)` 으로 좁힌다. 동료의 튜플은 `direct_member(user:X, group:G)` 라
어느 자리도 `user:kim` 이 아니므로 **세 집합 전부에서 사라진다.** 좁힌 그림은 처음부터
그 튜플들을 만들지 않을 뿐, 걸러진 결과는 동일하다.

**child 간선과 순환은 해당 없다.** child 튜플은 `group:` 두 개로만 이루어져 `user:kim`
을 언급하지 않고, 사용자는 조직 그래프에 순환을 만들 수 없다.

### 4.3 `upsertUser` — 온전히 좁힌다

커밋이 `state.saveUser` 하나뿐이다. **`saveGroup` 을 부르지 않는다.** 그래서 전체 멤버
목록이 아예 필요 없다.

소속 조직은 `findGroupIdsContaining` → **`findGroupHeader`** 로 얻는다.

```
전:  소속조회 1  +  findGroup 1(1,601 아이템)  +  findUser 1  +  loadMemberUsers 3,200
     →  왕복 ≈3,203 / 아이템 ≈4,803

후:  소속조회 1  +  findGroupHeader 1(1 아이템) +  findUser 1
     →  왕복 3 / 아이템 3
```

### 4.4 `removeUser` — 그림만 좁힌다

커밋이 `reconcileRemovedMember` → `saveGroup` 을 부르므로 **전체 멤버 목록이 진짜로
필요하다.** 따라서 `affectedGroupsOf`(전체 조직)는 그대로 두고, **그림만** 좁힌다.

```
전:  소속조회 1  +  findGroup 1(1,601 아이템)  +  findUser 1  +  loadMemberUsers 3,200  +  saveGroup
후:  소속조회 1  +  findGroup 1(1,601 아이템)  +  findUser 1                            +  saveGroup
```

왕복이 ≈3,203 → 3 으로 줄고, 아이템은 ≈4,803 → 1,603 으로만 준다.

사람 읽기는 사라지고 조직 읽기는 남는다. **온전한 승리는 아니지만 정직한 경계다.**

> 여기까지 온전히 고치려면 저장소에 "멤버 한 줄만 지운다" 를 더해야 하는데, 부분 실패
> 처리(`reconcileRemovedMember`)가 "전체 목록 다시 쓰기" 를 전제로 짜여 있어 그것까지
> 바뀐다. **이번 범위 밖이다** — §6 에 남긴다.

### 4.5 `upsertGroup` / `removeGroup` — 손대지 않는다

`focus` 가 `group:G` 라 **모든 멤버의 튜플이 그 조직을 언급한다.** 필터가 아무것도
버리지 않으므로 전체 멤버가 진짜로 필요하다. 조직에서 100명을 빼면 그 100명의 튜플을
지워야 한다.

### 4.6 저장소 — `findGroupHeader`

```
findGroupHeader(조직id)  →  Mono<GroupHeader>
GroupHeader { id, externalId, displayName }
```

DynamoDB 구현은 `findUser` 와 같은 모양 — `GetItem(조직PK, META)`, 강한 일관성.
아이템이 없으면 빈 `Mono` 이므로 **"없는 조직은 건너뛴다" 가 지금과 동일하다.**

**`DirectoryGroup(id, 이름, 멤버 없음)` 으로 돌려주지 않는다.** 이 코드베이스에서
"멤버 0개" 는 이미 다른 뜻으로 쓰인다 — `expandWithReferencedGroups` 가 "존재만 확인하고
튜플은 만들지 마라" 는 표시로 빈 멤버를 쓴다. 거기에 "진짜 멤버가 없는 조직" 과
"헤더만 읽은 조직" 까지 겹치면 **한 값이 세 가지 뜻**을 갖는다. 그러면 누군가 헤더를
그림에 그대로 넣고 "멤버 0명이네" 로 읽는 사고가 난다 — **그것이 정확히 L-1 이었다.**

별도 타입이면 그림에 넣으려면 `DirectoryGroup(id, ..., {user:kim})` 을 손으로 만들어야
하고, 그 순간 "누구를 넣을지" 를 명시하게 된다.

**`findGroupIdsContaining` 은 건드리지 않는다.** 원래 최종 일관성이고 그대로 둔다 —
이번 변경이 더 나쁘게 만들지 않는다.

## 5. 검증

### 5.1 기존 테스트로는 못 잡는다

이 변경의 목표는 **읽는 횟수**인데 지금 결과는 이미 맞다. **어떤 기존 테스트도 실패하지
않고, 어떤 기존 테스트도 성공을 증명하지 못한다.** 전부 통과해도 아무것도 안 고쳤을 수
있다. 이것이 애초에 이 결함이 살아남은 이유다.

### 5.2 A. 읽기 횟수 — 이것만이 "고쳤다" 를 직접 말한다

저장소를 감싸 호출을 세는 것을 두고 core 단위 테스트에서:

```
given  1,600명 조직에 kim 이 소속
when   upsertUser(kim, active=false)
then   findUser        1회   (지금 3,201회 — 본인 1 + 동료 1,600×2)
       findGroup       0회   (지금 1회)
       findGroupHeader 1회
```

**이것이 TDD 의 RED 다.**

### 5.3 B. 결과 동등성 — 이미 있는 것을 쓴다

SCIM 시나리오 S1~S20, 규모 E2E, 하네스 ①②③④가 전부 "튜플이 정확히 맞는가" 를 본다.
좁힌 그림이 다른 델타를 내면 **여기서 터진다.** 새로 만들지 않는다.

### 5.4 C. `removeUser` 가 멤버 줄을 보존하는가 — §4.1 의 지뢰

```
given  1,600명 조직
when   removeUser(kim)
then   OpenFGA 에서 kim 튜플만 사라지고
       DynamoDB 에 나머지 1,599명의 멤버 줄이 그대로
```

좁힌 그림이 `saveGroup` 까지 새면 1,599 → 0 으로 잡힌다.

### 5.5 D. 변이 검사

| 망가뜨릴 것 | 잡혀야 할 테스트 |
|---|---|
| 좁히기를 되돌린다 | A |
| 좁힌 그림을 `saveGroup` 까지 흘린다 | C |
| 그림의 멤버를 `{}` 로 (kim 도 뺀다) | B — 삭제가 일어나지 않음 |
| `findGroupHeader` 가 없는 조직에 헤더를 지어낸다 | B |

### 5.6 E. 실측

전체 빌드 `BUILD SUCCESSFUL in 4m 40s`, 569 tests, 실패 0. (`:app-scim:test` 단독은
`6m 47s`, 58 tests, 실패 0 — 전체 빌드에 포함된 결과다.)

| | 지금 | 후 |
|---|---|---|
| S1 조직 먼저 6,476건 (직원 6,124명 도착) | **835.4초** | **57.9초** |
| SCIM 최초 싱크 (직원 먼저, 6,476건) | 46.5초 (건당 7.2ms) | 47.9초 (건당 7.4ms) |
| S3 동시 16스레드 × 200건 | `{200=71, 503=129}` | **`{200=200}`** |
| `ScimProvisioningOrderScaleTest` 결과 XML 크기 | 738 MB | **1.7 MB** |

**S1: 14.4배 빨라졌다(835.4초 → 57.9초).** 이 경로가 이 설계의 목표였다 — §1 의
발단이 정확히 이 숫자다.

**직원 먼저 싱크는 안 변했다(46.5 → 47.9초).** 예상대로다. 이 순서에서는 직원이
도착하는 시점에 아직 어느 조직에도 안 속해 그림이 처음부터 비었다 — §4.2 가 좁히는
것은 "조직이 이미 갖고 있던 멤버 목록"인데, 이 경로에는 애초에 좁힐 멤버 목록이 없다.
1.4초 차이는 개선이 아니라 회차 잡음이다.

**S3 의 503 이 129건 → 0건.** 위 5.2 는 "락 보유 시간이 줄면 503 이 줄어야 한다"
고만 예측했다 — 방향만 맞춘 예측이었지 소멸까지는 말하지 않았다. 실측은 그 예측을
넘어 전부 없앴다. 그런데 §5.7 이 이미 적어 둔 대로 **이것은 관측이지 단정이 아니다.**
락 보유 시간이 줄어든 것과 503 이 사라진 것은 둘 다 사실이지만, 이 측정은 락 보유
시간이 그 유일한 원인이라는 것까지는 증명하지 않는다 — 같은 회차에서 다른 변수(GC,
스레드 스케줄링, 순차 배정 순서)도 함께 바뀌었다.

**XML 738MB → 1.7MB 는 사라진 읽기의 부산물이다.** S1 은 조직이 먼저 도착하는
순서라, 조직이 자리를 잡을 때 동료 대부분이 아직 그림에 없다. 전에는 `loadMemberUsers`
가 그 동료들을 그대로 읽어 `TupleMapper` 에 넘겼고, 대부분이 "스냅샷에 없어
건너뜁니다" 경고 문자열을 만들어 테스트 결과 XML 에 수백만 줄로 쌓였다. 그림을 한
사람으로 좁히자 그 읽기 자체가 없어져 경고도 함께 없어졌다.

**S15(대형 조직 1,600명 멤버 교체)·S18(`mode=tuples` 재적재)·S19(아카이빙)은
그대로다(각각 0.5초·3.1초·2.5초, 변화 없음).** 예상대로다. S15 는 `upsertGroup` 경로라
§4.5 가 이미 "손대지 않는다"고 적어 뒀다 — 조직이 `focus` 인 연산은 필터가 아무것도
버리지 않으므로 전체 멤버가 진짜로 필요하다. S18·S19 는 애초에 `upsertUser`/`removeUser`
경로가 아니라 이 변경과 무관한 별도 메커니즘(전체 재적재, `loadAll`+아카이빙)이다.

**위 표는 `upsertUser` 경로의 개선이다.** `removeUser` 는 §4.4 대로 조직 읽기가
남는다 — `reconcileRemovedMember` → `saveGroup` 이 최종 멤버 목록 전체를 요구하기
때문이다. 이 표에 `removeUser` 항목이 없는 것은 그래서다.

### 5.7 이 설계가 말할 수 없는 것

- **실제 IdP 로는 검증하지 못한다.** 인증(S-2)이 선행 조건이다. 요청은 우리가 만든다.
- **DynamoDB Local 기준이다.** 실제 DynamoDB 의 RCU·지연 특성은 다르다. 왕복 수가
  줄어드는 것은 확실하지만, 시간이 얼마나 줄지는 로컬 측정값일 뿐이다.
- **S3 의 503 감소는 인과가 아니라 상관이다.** 락 보유 시간이 유일한 변수가 아니다.

## 6. 남은 것

- **`removeUser` 의 조직 읽기** — `saveGroup` 이 전체 목록을 요구하는 한 남는다.
  저장소에 "멤버 한 줄만 지운다" 를 더하면 없앨 수 있으나 `reconcileRemovedMember` 의
  부분 실패 처리가 함께 바뀐다.
- **조직 경로 핸들러의 중복 읽기** — `ScimGroupHandler.patch` 가 PATCH 적용용으로
  `findGroup` 을 부르고, `respond` 가 저장된 결과를 돌려주려고 또 부른다. 이번 범위 밖.
- **`findGroup` 자체는 그대로 둔다** — 조직 경로에서는 멤버가 진짜로 필요하다.
