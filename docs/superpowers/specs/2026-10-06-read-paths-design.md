# 점검 ⑥-1 읽기 길 — 관리 API 멤버 목록은 키 커서로 한 쪽씩, 멤버를 싣는 SCIM 조직 응답은 흘려 쓴다

- 날짜: 2026-10-06
- 근거: `docs/superpowers/specs/2026-09-28-full-audit.md` §7 권고 ⑥ — 성능 P4·P5, 사소 S16(멤버 목록 오프셋 커서가 흔들림).
- 나눔: ⑥ 은 둘이다(사용자 결정).
  - ⑥-1 은 읽기 길(이 문서)이다.
  - ⑥-2 는 쓰기 길이다. 다룰 것:
    - P3 전역 락 재시도 간격
    - P6 OpenFGA 결과 합치기
    - ⑤-1 §11 의 재적재 중 획득 재시도 조기 종료
    - ⑤-2 §12 의 버린 연산만 있는 PATCH
- 순서: 읽기 길을 먼저 한다. 요청 하나가 10만 명 조직을 통째로 힙에 올리는 OOM 위험이 같은 프로세스의 SCIM 쓰기까지 함께 죽일 수 있기 때문이다. 쓰기 길의 503 은 IdP 가 `Retry-After` 를 보고 다시 보낸다.
- 전제:
  - 실제 규모 10만 명+, 요청당 전원 읽기 금지(예외는 §4.6).
  - 운영 배포 전이다.
  - 표준이 정한 신호만 받는다. 여기서 표준은 RFC 7644, DynamoDB 의 `LastEvaluatedKey`.
  - 배포 하나는 LDAP 아니면 SCIM 이다.

## 1. 문제

| 항목 | 지금 | 결과 |
|---|---|---|
| P4 | 관리 API `GET /admin/organizations/{orgCode}/members` 와 조직 상세가 페이지마다 `findGroup` 으로 조직 파티션 전체를 강한 일관성으로 읽고, 직원 아이디를 메모리에서 정렬해 오프셋으로 자른다 | 10만 명 조직에서 한 쪽(20명)마다 10만 줄(약 1,900 RCU)을 읽는다. 원본 아이템 약 65MB 가 순간 힙에 오른다. 끝까지 넘기면 1억 줄이다(`limit=100`). 인증이 없는 GET 이라 반복 호출로 증폭된다 |
| S16(뒤쪽) | 멤버 목록 커서가 오프셋이다 | 쪽 사이에 멤버가 바뀌면 건너뛰거나 두 번 준다 |
| P5 | 멤버를 싣는 SCIM 조직 응답은 파티션 전체를 읽어 모은 뒤 도메인 객체 → SCIM 객체 → JSON 트리로 **여러 벌을 동시에** 든다. 이런 응답은 `GET /Groups/{id}`, 목록, `.search`, POST·PUT, `PATCH ?attributes=members` 다 | 10만 명 조직이면 요청 하나에 수십~100MB(추정)다. 몇 개가 겹치면 OOM 이다. Okta 는 그룹 연결·푸시 때 쿼리 파라미터 없는 `GET /Groups/{id}` 와 `excludedAttributes` 없는 `filter=displayName eq` 를 보낸다. Entra 는 늘 `excludedAttributes=members` 를 붙여 해당 없다 |

## 2. 결정 (사용자 확인, 2026-10-06)

- ⑥ 을 둘로 나누고 읽기 길(⑥-1)을 먼저 한다.
- **P4 — 키 기반 커서.** 멤버 줄을 `MEMBER#USER#` 접두로 `Limit`·시작 키를 주어 한 쪽씩 읽는다. 다음 쪽 위치는 기존 `Cursor`(검색 범위를 담는 불투명 문자열)로 감싼다. 조직 상세는 파티션 전체를 읽지 않는다.
- **P5 — 스트리밍 응답.** 멤버를 싣는 조직 응답은 멤버 줄을 DynamoDB 한 쪽씩 읽어 JSON 으로 바로 흘려 쓴다. 메모리는 조직 크기와 무관하다.
  - 고르지 않은 안 둘은 §8 에 적는다: 멤버 수 상한(400 `tooMany`), 스트리밍 + 동시 요청 수 상한.

## 3. P4 — 관리 API 조직 상세·멤버 목록

### 3.1 멤버 목록 `GET /admin/organizations/{orgCode}/members?cursor=&limit=`

1. 조직 헤더를 GetItem(강한 일관성)으로 읽는다. 없으면 404(지금과 같다).
2. 직원 멤버 한 쪽을 Query 로 읽는다.
   - 조건: `PK = GROUP#<orgCode>`, `SK begins_with MEMBER#USER#`, `Limit = limit`, 강한 일관성.
   - `PK`·`SK` 만 읽는다(`ProjectionExpression`, `LastEvaluatedKey` 가 그 둘이다).
   - 커서가 있으면 그 위치부터 읽는다.
   - 정렬키가 아이디 순이라 응답 순서는 지금과 같다(아이디 오름차순).
3. 다음 쪽 커서는 DynamoDB 의 `LastEvaluatedKey` 가 있을 때만 준다(표준 신호). 쪽이 정확히 끝나면 마지막에 빈 쪽이 한 번 올 수 있다.
4. 커서의 검색 범위는 "이 조직의 직원 멤버" 다. 다른 검색·다른 조직이 발급한 커서는 400 이다(기존 `Cursor` 규칙).
5. **시작 키는 커서를 그대로 믿지 않고 우리가 만든다.** 커서에서 꺼낸 키는 다음을 모두 만족해야 한다. 아니면 400 이다.
   - 속성이 `PK`·`SK` 둘뿐이다.
   - `PK` 가 이 조직의 키다.
   - `SK` 가 `MEMBER#USER#` 로 시작한다.

   형식만 맞춘 위조 커서가 DynamoDB `ValidationException` 으로 500 이 되는 길(S16 앞쪽)을 이 엔드포인트에서는 막는다.
6. 한 쪽에 든 직원의 읽기와 권한 Check 는 지금처럼 병렬(동시 8)로 하고 결과는 쪽 순서를 지킨다(설계 §8.2 의 동시성 그대로).

구현 중 정한 것: 위조 시작 키 검사에 `SK` 가 1024바이트(UTF-8)를 넘으면 400 을 더했다. 이유: DynamoDB 정렬키 한도다. DynamoDB Local 은 거절하지 않지만, 실제 DynamoDB 는 `ValidationException` 을 내 500 이 된다.

### 3.2 조직 상세 `GET /admin/organizations/{orgCode}`

- 헤더 GetItem, 하위 조직, 멤버 첫 쪽(§3.1 과 같은 Query)만 읽는다.
- 하위 조직은 `MEMBER#GROUP#` 접두로 정렬키만 읽고, 쪽 단위로 이어 읽다가 상한(`MAX_PATHS`)을 넘기면 멈춘다(그 쪽 안의 줄은 읽는다). 상한을 넘으면 지금처럼 경고하고 자른다.
- 상위 계층은 지금 방식 그대로다(소속 줄을 따라 올라가 조직 크기와 무관하다).
- 응답 모양(`OrganizationDetail`)은 바뀌지 않는다.

### 3.3 바뀌는 포트

- 직원 멤버 아이디 한 쪽을 커서로 읽는 메서드를 관리 API 검색 포트(`DirectorySearchRepository`)에 둔다. 커서를 다루는 다른 검색과 같은 곳이다.
- 하위 조직 아이디를 읽는 메서드(`findChildOrgCodes`)도 상태 포트가 아니라 검색 포트(`DirectorySearchRepository`)에 둔다. 상한까지 읽고 멈출 수 있게 `Flux` 로 낸다.
- 이름은 `findGroupUserMemberIds`·`findChildOrgCodes` 다.
- `AdminQueryUseCase` 의 두 진입점에서 `findGroup` 을 뺀다. 오프셋 커서 파싱(`parseCursor`)도 없앤다.

구현 중 정한 것: 하위 조직 아이디 메서드를 상태 포트에 두지 않고 검색 포트에 두었다. 이유: 검색 포트의 자바독이 "조회 관심사를 쓰기 경로의 심장(상태 포트)에 얹지 않는다" 를 원칙으로 둔다.

### 3.4 규모

- 10만 명 조직 멤버 목록 한 쪽의 읽기가 10만 줄에서 쪽 크기(기본 20)로 준다.
- 끝까지 넘겨도 전체를 한 번 읽는 셈이다(지금은 1억 줄).
- 조직 상세도 첫 쪽만큼만 읽는다.

## 4. P5 — 멤버를 싣는 SCIM 조직 응답을 흘려 쓴다

### 4.1 범위

조직 응답에 `members` 가 남는 모든 경로:
- `GET /Groups/{id}`
- `GET /Groups`·`POST /Groups/.search` 목록
- POST·PUT 응답
- `attributes` 가 있는 PATCH 응답

`members` 가 빠지면(`excludedAttributes=members`, 다른 `attributes`) 지금처럼 이름표만 읽는다(S-1 설계 §4.5).

### 4.2 조직 하나

1. 조직 헤더를 GetItem(강한 일관성)으로 먼저 읽는다. 없으면 404 다. 응답의 첫 바이트를 쓰기 전이라, 이 단계의 저장소 장애는 지금처럼 라우터가 503 등으로 번역한다(⑤-1).
2. **앞부분.**
   - 헤더로 SCIM 조직 객체를 만들고 `attributes`·`excludedAttributes` 투영을 지금처럼 적용한다.
   - `members` 를 뺀 트리를 직렬화하고, 닫는 `}` 대신 `,"members":[` 를 잇는다.
3. **멤버.**
   - 기존 `findMemberRefs`(정렬키만, 강한 일관성)를 DynamoDB 한 쪽씩 이어 읽는다.
   - 멤버 하나를 `{"value":<id>,"type":"User"|"Group"}` 로 직렬화한다. 하위 속성 투영(`members.value` 등)이 있으면 멤버마다 적용한다.
   - 멤버 100명씩 묶어 흘려보낸다(묶음 크기를 정한 이유는 아래).
   - 멤버 순서는 지금과 같다(정렬키 순: 하위 조직이 먼저, 그다음 직원, 각각 아이디 순).
4. **뒷부분.** `]}` 로 닫는다.
5. 응답 본문은 `Flux<DataBuffer>` 다. `Content-Length` 없이 청크로 간다.
6. **아래로부터 오는 끌어당김을 따른다.** 클라이언트가 덜 받으면 많아야 한 쪽 앞서 읽고 멈춘다.

구현 중 정한 것 — 쪽 읽기 `Paginator`: 전역으로 `concatMapIterable(…, 1)` 로 바꿨다. 많아야 한 쪽만 앞서 읽는다.
- 이유: 기본 prefetch 32 는 멈춘 소비자 아래에서 최대 32쪽을 미리 읽었다. 검토자가 재현했다: 요청 5개 뒤 멈추면 6쪽을 다 읽었다.
- 배압 테스트가 이것을 고정한다(Query ≤ 2).
- 이 바꿈은 `findGroup`·재적재 훑기 같은 다른 전체 읽기에도 걸린다. 소비가 끊기지 않으면 쪽을 연달아 읽어 결과는 같다.

구현 중 정한 것 — 멤버 묶음 크기: 1,000 이 아니라 100 이다.
- 이유: Reactor Netty 1.2.18(이 빌드 — Spring Boot 3.5.16 → reactor-bom 2024.0.18)의 보내기는 버퍼 128개를 미리 당긴다(`reactor.netty.send.maxPrefetchSize`, 기본 128). 1.3.7 도 상수가 같다(128, 다시 당기기 64).
- 1,000명 묶음(약 50KB)이면 느린 클라이언트 연결당 약 6MB(10만 명 응답 전체)까지 쌓였다. 100명 묶음이면 보내기 창 몫이 약 0.6MB 에서 멈춘다. 연결이 쥐는 양은 이것만이 아니다(§10).
- Netty 속성은 전역이라 바꾸지 않았다.

구현 중 정한 것 — 흘려 쓰기 멤버 읽기에 `Limit` 를 따로 주지 않았다: `findMemberRefs` 는 쓰기 경로도 쓰고, `Limit` 은 RCU 는 같고 왕복만 늘린다(최종 검토).

구현 중 정한 것: 목록의 조직 사이 쉼표는 조직 앞부분에 붙인다. 빈 버퍼를 내지 않는다.

### 4.3 목록 (`GET /Groups`, `.search`)

- 첫 부분 `{"schemas":[ListResponse],"totalResults":…,"startIndex":…,"Resources":[` 를 먼저 쓴다.
- 쪽에 든 조직을 **하나씩 차례로**(`concatMap`) §4.2 방식으로 흘려 쓴다.
  - 앞 조직을 다 쓰기 전에 뒤 조직을 미리 읽지 않는다. 병렬로 미리 읽으면 뒤의 큰 조직 하나를 통째로 쥘 수 있다.
  - 대신 지연이 조직 수만큼 는다. 지금은 동시 8 로 읽는다.
- 목록을 만든 뒤 지워진 조직은 헤더 GetItem 이 비므로 건너뛴다.
- 그래서 `itemsPerPage`(실제로 쓴 수)는 맨 끝에 쓴다. JSON 객체의 필드 순서에는 뜻이 없다(RFC 8259 §4).
- 목록 응답의 다른 필드는 지금과 같다.

### 4.4 쓰기 응답

- POST·PUT, `attributes` 가 있는 PATCH 의 응답도 §4.2 를 쓴다.
- 쓰기가 끝난 뒤(부분 실패면 503 — ⑤-1) 응답을 만들 때 흘려 쓴다.

### 4.5 코드 자리

- connector-scim 에 조직 응답을 흘려 쓰는 클래스 하나(`ScimGroupStream`)를 둔다. `ScimGroupHandler` 와 `ScimGroupListing` 이 함께 쓴다.
- 멤버를 싣지 않는 경로와 직원 응답은 지금 그대로다(트리 → `bodyValue`).

구현 중 정한 것: `ScimGroupStream.group`·`list` 는 늘 `members` 를 쓴다.
- 부른 쪽이 `projection.includes("members")` 일 때만 부른다. 목록은 `count > 0` 일 때만 부른다.
- 아니면 지금처럼 이름표 트리 응답을 쓴다.
- 그 갈래는 `ScimGroupHandler.body` 와 `ScimListHandler.groupsResponse` 에 있다.

### 4.6 원칙과의 관계

"요청당 전원 읽기 금지" 와 부딪히는 유일한 곳이다. 클라이언트가 멤버 전체를 달라는 요청이라 응답이 곧 전원이다. 그래서 읽는 양(10만 줄)은 그대로 두고, 메모리만 조직 크기와 떼어 놓는다.

## 5. 문서

- README 관리 API 절:
  - 멤버 목록 커서는 불투명 문자열이다.
  - 쪽이 정확히 끝나면 빈 마지막 쪽이 한 번 올 수 있다.
  - 다른 조직의 커서는 400 이다.
  - 조직 상세는 멤버 첫 쪽만 읽는다.
- README SCIM 절: 멤버를 싣는 조직 응답은 청크로 전송된다. 응답 도중 저장소가 실패하면 연결이 끊긴다.
- 점검 문서: P4·P5 에 해결 표시, S16 에 뒤쪽 해결과 이 엔드포인트의 앞쪽 해결 표시를 한다.

## 6. 바뀌는 곳

| 모듈 | 바뀌는 것 |
|---|---|
| core | 검색 포트(`DirectorySearchRepository`)에 메서드 둘(직원 멤버 한 쪽·하위 조직 아이디). `AdminQueryUseCase` 의 조직 상세·멤버 목록이 `findGroup` 을 쓰지 않는다. 오프셋 커서 제거 |

| 문서 | README 관리 API·SCIM 절, 점검 문서 |

## 7. 검증

| 무엇 | 어떻게 | 어디 |
|---|---|---|
| P4 멤버 쪽 | 쪽 크기만큼 아이디 순, 커서로 이어 읽기, 끝 쪽, 망가진 커서·다른 조직 커서·`PK`/`SK` 가 이 조직의 직원 멤버가 아닌 위조 커서는 400 | storage(DynamoDB Local), core(검색 포트의 거절을 그대로 흘린다 — 400 으로 옮기는 것은 admin-api 의 기존 매핑) |
| P4 조직 상세 | `findGroup` 을 부르지 않는다(가짜 저장소). 하위 조직 상한 | core |
| P4 규모 | 10만 명 조직의 멤버 첫 쪽과 조직 상세가 읽은 아이템이 쪽 크기 수준이다(`DynamoDbReadCounter`) | 새 규모 테스트 `ScimLargeGroupReadScaleTest`(app-scim) |
| P5 응답 모양 | 지금과 같은 JSON. 투영(`attributes`·`excludedAttributes`·`members.value`), 404, 목록 중간에 지워진 조직은 건너뛰고 `itemsPerPage` 가 실제 수 | connector-scim |
| P5 흘려 쓰기 | `Content-Length` 없음. 멤버를 쪽 단위로 이어 읽고, 끝까지 받지 않으면 많아야 한 쪽 앞서 읽고 멈춘다 | connector-scim, storage(Paginator) |
| P5 도중 오류 | 멤버 중간에 저장소가 실패하면 완결된 200 JSON 이 나가지 않는다 | connector-scim |
| P5 규모 | 10만 명 조직 `GET /Groups/{id}` 응답에 멤버 100,000개, 걸린 시간 기록 | 같은 클래스 `ScimLargeGroupReadScaleTest`(app-scim) |
| 전체 | 머지 전 `test`·`scaleTest` 둘 다 | 전체 |

구현 중 정한 것: P4·P5 규모 측정은 기존 10만 명 규모 테스트에 붙이지 않고 새 클래스 `ScimLargeGroupReadScaleTest`(app-scim)에 모았다. 이 클래스가 자기 10만 명 조직을 심는다.
- 이유: 기존 10만 명 클래스(`ScimGroupMemberPatchScaleTest`)는 끝에서 자기 조직을 지워, 읽기 측정을 그 뒤에 붙일 수 없다.
- 비용: 10만 명을 한 번 더 심는다(약 48초).

## 8. 왜 다른 길을 안 갔나

- **P5 멤버 수 상한(예: 1만 명 넘으면 400 `tooMany` + "`excludedAttributes=members` 를 써라").**
  - 장점: 읽기와 메모리가 모두 막힌다.
  - 막힌 이유 하나: Okta 가 큰 조직을 연결·푸시할 때 실패한다.
  - 막힌 이유 둘: `tooMany` 는 RFC 7644 에서 필터 결과에 쓰는 오류라 이 자리에 맞지 않는다.
- **P5 스트리밍 + 동시 요청 수 상한(넘으면 503).** DynamoDB 용량과 응답 대역폭까지 묶는다. 하지만 상한 값의 근거가 지금 없다. 필요해지면 스트리밍 위에 얹을 수 있다(§10).
- **P4 오프셋 커서 유지 + 정렬키만 읽기.** 메모리는 줄지만 쪽마다 10만 줄을 읽는 것은 그대로다.
- **P5 목록을 병렬로 미리 읽기.** 지연은 줄지만 뒤의 큰 조직 하나를 통째로 쥘 수 있어 스트리밍의 뜻이 없어진다.

## 9. 결과 (구현 후 기록)

머지 전 `test`·`scaleTest` 시간과 결과를 구현이 끝나면 여기에 적는다.

## 10. 이 설계가 말할 수 없는 것

- **메모리가 실제로 고정되는지는 수치로 단정하지 않는다.** 힙 측정은 흔들림이 커서 테스트로 굳히기 어렵다. "끝까지 받지 않으면 많아야 한 쪽 앞서 읽고 멈춘다" 는 지연 읽기를 간접 근거로 고정한다(배압 테스트, Query ≤ 2).
- **연결당 메모리 상한은 셈한 값이다.** 보내기 창 ≈0.6MB + DynamoDB 쪽 둘(읽는 쪽 + 앞서 읽은 쪽, 각각 투영 전 1MB 한도 — SDK 객체로 들면 수 MB) ≈ 멈춘 연결당 약 5~10MB(코드로 셈한 추정, 힙은 재지 않았다). 조직 크기와는 무관하다.
  - 보내기 창 몫: Netty 보내기 창(버퍼 128개) × 묶음(멤버 100명, 약 5KB) ≈ 0.6MB 다. 이것은 연결당 몫의 일부일 뿐이다.
  - DynamoDB 쪽 둘: `Paginator` 는 읽는 중인 쪽에 더해 앞서 받은 응답 하나를 쥔다. 한 쪽은 **투영 전** 아이템 크기로 1MB 한도라, 멤버 줄이면 한 쪽에 약 8천~1만6천 줄이다. SDK 객체(`Map` + `AttributeValue` + `String`)로 들면 한 쪽이 수 MB 다.
  - 이 값은 코드와 라이브러리 상수(Reactor Netty 1.2.18)로 셈한 것이다. 힙을 재 확인하지는 않았다.
  - 이 연결당 값이 동시 요청 상한(§8 에서 미룬 안)을 정할 때의 근거다.
- **멤버를 싣는 큰 조직 조회는 여전히 멤버 전체를 읽는다**(§4.6). 그런 요청이 몰리면 DynamoDB 용량을 쓴다. 동시 요청 상한은 범위 밖이다.
- **응답 도중 저장소 실패는 연결 끊김이다.** 첫 바이트가 나간 뒤에는 상태 코드를 바꿀 수 없다. IdP 는 네트워크 오류처럼 보고 다시 보낸다.
- **여러 쪽 사이의 동시 쓰기는 반영이 섞일 수 있다.** 지금 `findGroup` 도 같다. 스냅샷 격리는 없다.
- **헤더를 읽은 뒤 멤버를 읽기 전에, 또는 흘리는 도중에 조직이 지워질 수 있다.** 그러면 200 과 빈(또는 일찍 끝난) `members` 가 나간다.
  - 첫 바이트 뒤라 상태를 바꿀 수 없다. 여러 쪽 사이의 동시 쓰기와 같은 성질이다.
- **목록은 조직을 하나씩 차례로 읽어 지연이 는다.**
- **관리 API 멤버 목록은 쪽이 정확히 끝나면 빈 마지막 쪽이 한 번 온다**(DynamoDB 신호를 그대로 씀).
- **Okta 가 큰 조직 응답을 얼마나 기다리는지(요청 타임아웃)는 문서에 없다.**
