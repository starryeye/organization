# 원천 없는 부여 줄 설계 (2026-11-11)

SCIM id 내구성 설계(2026-11-05) §9.3 이 다음 후보로 남긴 "되지우지 못한 새 조직 POST 를 세는 지표"에서 시작했다. 코드를 따라가 보니 같은 모양의 구멍이
둘 더 있었다. 셋을 한 규칙으로 닫는다. 사용자 결정: "추천대로"(2026-11-11) — 아래 결정은 모두 그 추천이다. 구현 전 점검(§12)이 처음 안의 U2 를 바꿨다.

## 1. 문제

### 1.1 원천 없는 줄

- **원천**은 저장된 상태가 그 줄을 요구하게 만드는 기록이다.
  - `direct_member(X, G)` 는 조직 G 의 멤버 행 X 와 G 의 존재다.
  - `child(S, G)` 는 G 의 멤버 행 S(또는 지정 연결 S→G)와 두 조직의 존재다.
- **원천 없는 줄**은 장부(OpenFGA)에 있을 수 있는데 저장된 상태가 요구하지 않는 부여 줄이다.
- 요청이 줄을 OpenFGA 에 쓴 뒤 그 원천을 DynamoDB 에 저장하지 못하면 생긴다.
- **아무도 지우지 못한다.**
  - 하루 아카이빙은 상태의 멤버십에서 후보를 뽑는다(`SnapshotArchiveUseCase`). 원천이 없으면 후보에 들지 않는다.
  - 조직 연결 줄(`child`)은 후보에 들어도 수로만 내고 지우지 않는다.
  - 다음 쓰기도 지우지 못한다. 저장된 상태로 그림을 만들므로, 같은 요청이 다시 오지 않고 다른 값이 오면 그 줄은 후보에서 빠진다.
  - 그래서 재적재(`mode=tuples`)를 돌릴 때까지 남는다. 그 사이 원천이 없는 권한(롤업)이 산다.
- **직원이 초점인 쓰기는 범위 밖이다.** 직원의 부여 줄은 조직의 멤버 행이 원천이다. 직원 쓰기는 멤버 행을 만들지 않는다 — 직원 삭제는 줄이 원래 없었거나 지운 행만 뺀다.
  - 멤버 행이 그 줄의 이름을 쥐고 있다. IdP 가 그 멤버를 조직에서 빼면 지금 경로가 Check 없이 지운다(빠지는 멤버).
  - 레코드가 있는 직원은 하루 아카이빙도 본다. 비활성이면 남은 줄을 지운다(설계 2026-10-20 §6.4).
  - 남는 틈 하나: 저장하지 못한 새 직원 POST 가 쓴 줄이다. 이 줄은 조직이 이미 그 id 를 멤버로 쥐고 있을 때만 생긴다 — `sync.id-from-external-id=true` 에서 기록을 잃은 뒤다. 아카이빙은 레코드 없는 직원을 건너뛴다(`revokeLeftovers` 가 빈 결과). 지난 슬라이드가 되지우지 않기로 했다(설계 2026-11-05 §9.2) — 그 줄은 IdP 의 멤버십 의도와 맞고, 멤버 행이 이름을 쥔다. §6 에 한계로 적는다.

### 1.2 원천 없는 줄이 생기는 곳

| # | 경로 | 지금 동작 | 남는 줄 |
|---|---|---|---|
| A | 새 조직 POST 가 일부 실패 | 저장하지 않고 쓴 줄을 되지운다(설계 2026-11-05 I11). 되지우기가 실패하면 WARN | 되지우기에 실패한 줄 |
| B | 지정 요청(관리 API `PUT /admin/organizations/{orgCode}/parent`)이 일부 실패 | 지정을 저장하지 않는다(503) | 새 연결 `child(C,B)` 의 결과를 모를 때(응답 유실) 그 줄 — 저장된 지정은 옛 값 A 다. 다른 값을 걸면 남는다. 지금은 문서로만 막는다(설계 2026-11-04 §15.3) |
| C | 기존 조직에 멤버를 넣는 PUT·PATCH(`changeGroup`)의 넣기가 결과를 모름 | `reconcileGroupMembers` 가 그 멤버를 저장하지 않는다 | `direct_member(X,G)`(또는 `child(S,G)`). 나중에 IdP 가 X 를 빼도 "지금 멤버가 아니다" 로 보고 지우지 않는다(`바뀌는_멤버`) |
| D | 조직 쪽 쓰기가 커밋에 닿지 못하고 끝남(리스 상실, 차단기 중단, 커밋 오류) | 저장하지 않는다(503) | 그때까지 쓴 부여 줄 |

- 넷 모두 **같은 요청이 성공할 때까지 다시 오면** 맞는다. 다시 온 요청의 Check 기준선이 남은 줄을 보고 원천을 저장한다.
- 같은 요청이 다시 오지 않으면 남는다.
  - A 는 `sync.id-from-external-id=true` 에서 같은 id 의 재시도가 다른 멤버로 오는 경우다.
  - B 는 운영자가 다른 값을 거는 경우다.
  - C·D 는 IdP 가 재시도를 그만두고 다음에 다른 멤버 목록을 보내는 경우다.
- **운영 writer 의 단계 규칙.** 줄은 세 단계로 나간다. 조직 연결 지우기, 직원(지우기·쓰기), 조직 연결 쓰기 순서다. 앞 단계에 실패가 있으면 뒤 단계의 쓰기를 보내지 않는다 — 확정 실패다(`OpenFgaRelationTupleWriter`). 그래서 B 에서 "옛 연결 지우기 실패 + 새 연결 쓰임" 은 운영에서 생기지 않는다. B 가 실제로 줄을 남기는 길은 새 연결의 결과를 모를 때와 쓴 뒤 저장이 실패할 때(D)다.
- **일시 오류는 결과를 모르는 실패다.** writer 는 재시도 뒤에도 남은 일시 오류를 불확실로 낸다. OpenFGA 쓰기 장애 중에는 C·B 의 경우가 드물지 않다.

## 2. 결정

| # | 결정 | 이유 |
|---|---|---|
| U1 | **규칙 하나: 커밋에 닿은 조직 쪽 쓰기는, 이 요청이 썼거나 결과를 모르는 부여 줄 가운데 커밋한 뒤의 상태가 요구하지 않는 줄을 되지운다. 그러지 못하고 끝나면 센다(U5).** 조직 쪽 쓰기는 초점이 조직인 쓰기다 — 조직 POST·PUT·PATCH 와 지정 두기·없애기 | 원천 없는 줄은 아카이빙도 다음 쓰기도 지우지 못한다(§1.1). 셋(A·B·C)을 경우마다 따로 막지 않고, 커밋 자리 하나의 성질로 둔다 |
| U2 | **기존 조직의 결과를 모르는 넣기는 저장하지 않고(지금처럼) 되지운다(C).** `reconcileGroupMembers` 는 바꾸지 않는다. 커밋 자리가 조직을 저장한 뒤, 결과를 모르는 넣기의 줄을 지운다. 응답은 지금처럼 503(부분 반영)이다 | 저장하지 않은 넣기는 같은 요청의 재시도가 다시 그림에 싣는다 — 전체 교체(PUT)는 "목표 − 지금"을, 증분(PATCH)은 요청에 나온 멤버를 싣는다(`바뀌는_멤버`). 되지우면 장부와 상태가 함께 "멤버 아님"이라, IdP 가 다시 보내든 다른 목록을 보내든 맞는다. 저장하는 길은 PUT 재시도를 막는다(§7) |
| U3 | **지정을 저장하지 않으면 그 요청이 쓴 줄을 되지운다(B).** 새 조직의 되지우기(I11)와 같은 도우미를 쓴다. 되지운 뒤에도 응답은 503 이다 | 저장된 지정이 옛 값이면 새 연결 줄은 원천이 없다. 되지우면 다른 값을 걸어도 남지 않는다. 지금 문서로만 막는 것(README·온보딩 09·12 "다른 값을 걸기 전에 같은 요청을")을 코드로 바꾼다 |
| U4 | **되지울 줄 = `(written ∪ uncertain) − 커밋한 뒤의 상태가 요구하는 줄`.** 저장하지 않는 커밋(새 조직·지정)에서 "커밋한 뒤의 상태"는 변경 전 상태다. 그래서 `− 있어야했던것` 이다(`diffAndApply` 의 그 값: 순환을 버리지 않은 변경 전 목표를 초점으로 좁힌 것). 기존 조직은 재조정해 저장한 멤버의 줄이 요구된다 — 쓴 넣기는 빠지고 결과를 모르는 넣기가 남는다. 경우마다 이렇게 된다. <br>• 새 조직: 변경 전 그림에 조직이 없어 그 조직을 언급하는 줄이 모두 든다(`TupleMapper` 는 그림에 없는 조직의 `child` 를 만들지 않는다) — 지금 I11 과 같다. <br>• 지정: 새 연결 줄이 든다. 옛 연결 지우기의 결과를 모르는 줄은 들지 않는다 — 저장된 옛 지정이 요구한다. <br>• 같은 상위로 다시 건 요청: 되지울 줄이 없다 | 정의 하나가 세 커밋에 맞는다. 결과를 모르는 지우기를 다시 지우면 저장된 상태가 요구하는 줄을 지우게 된다(지정의 옛 연결). 원래 있던 멤버의 어긋남을 고쳐 쓴 줄도 들지 않는다 |
| U5 | **남은 것을 센다: 카운터 `scim.writes.unsourced`(태그 없음, 기동 때 0).** 요청 하나에 많아야 1 을 더한다. 조건은 조직 쪽 쓰기가 다음 가운데 하나로 끝난 것이다. <br>**(a)** 커밋 자리를 마치지 못하고 끝났다(리스 상실·차단기 중단·쓰기 오류·커밋 오류). 그리고 보냈을 수 있는 부여 줄 가운데 U4 의 "요구하지 않는 줄"이 있다 — 커밋하지 못했으면 변경 전 상태로 본다. <br>**(b)** 되지우기가 실패했다 — 결과에 실패가 담겼거나 리스 상실이 아닌 오류다. <br>되지우기 전에 리스를 잃은 경우는 (a) 로 한 번만 센다 | 운영자가 `mode=tuples` 를 걸 신호다. 지금은 WARN·5xx·`scim.lock.lease_lost` 가 흩어져 있고, 그 가운데 줄을 남긴 요청을 가릴 수 없다. 줄 수가 아니라 요청 수를 센다. 대응(같은 요청이 성공했는지 보고, 아니면 재적재)이 같다. 리스 상실로 끊긴 묶음은 몇 줄이 반영됐는지 모른다. U4 와 같은 정의라 원천이 있는 줄만 남긴 요청(같은 상위 재지정, 기존 멤버의 어긋남 고침)은 세지 않는다 — 거짓 경보가 재적재(몇 분 동안 SCIM 쓰기 503)를 부르지 않게 |
| U6 | **"보냈을 수 있다" 의 뜻.** 묶음마다 알려 온 결과에 쓴 줄이나 결과를 모르는 줄이 있다. 또는 쓰기가 끝나기 전에 취소됐고(리스 상실은 `LeaseKeeper` 가 하던 일을 취소한다) 아직 알려 오지 않은 줄이 있다. 확정 실패만 알려 왔으면 세지 않는다 — 거절, 앞 단계 실패로 보내지 않은 쓰기, 차단기가 멈춰 보내지 않은 묶음이다. Check 오류나 쓰기 직전 리스 확인 실패는 쓰기 전이라 세지 않는다 | 끊긴 묶음은 반영됐을 수 있어 센다. 보내지 않은 것은 반영되지 않았다 |
| U7 | **센 요청마다 WARN 한 줄을 남긴다.** 조직 id 와 끝난 사유를 싣고 `externalId` 는 싣지 않는다. 되지우기 실패는 지금의 WARN 두 줄을 쓰되, 문구의 "새 조직" 을 경로에 맞게 고친다(새 조직·조직·지정). 커밋에 닿지 못한 경우만 새 WARN 이다 | 카운터는 어느 조직인지 말하지 않는다. 운영자가 그 조직의 요청이 다시 와 성공했는지 볼 단서가 필요하다 |
| U8 | **문서.** README(지정 503 문단, 부분 실패 문단, 지표 절과 경보 예)와 온보딩(02·03·06·09·11·12·13·15)을 코드대로 고친다. 기준 커밋은 이 브랜치의 마지막 코드 커밋이다 | 온보딩은 늘 현재 동작이다 |

**고치지 않기로 한 것.**
- **오류로 끝난 조직 쓰기의 의도 저장.** 직원의 `오류여도_의도를_저장한다` 와 같은 길을 조직에 두면 D 의 일부(차단기 중단)를 막는다. 하지만 이름표·`externalId` 표지판·빼는 멤버까지 오류 경로에 다시 세워야 한다. 리스 상실·커밋 오류는 어차피 저장할 수 없다. 차단기 중단은 OpenFGA 장애 중이라 센 뒤 장애가 끝나면 재적재로 맞추는 편이 작다.
- **지정 실패 때 옛 연결 되살리기.** 옛 연결 지우기가 성공하고 새 연결이 실패하면 옛 연결이 장부에 없다(권한이 빠진 쪽). 되살리기는 부여 쓰기라 리스 확인과 실패 처리를 하나 더 세워야 한다. 같은 요청의 재시도가 쓰고, 다른 값을 걸어도 그 값으로 맞는다.
- **직원 쪽 쓰기.** §1.1.
- **테스트에서만 쓰는 기존 조직 `upsertGroup`.** SCIM POST 는 이미 있는 조직에 닿지 않는다(후보가 차 있으면 409 이거나 무작위 id 로 물러선다). `upsertGroupInternal` 의 기존 조직 갈래는 시험만 쓴다. 코드가 한 규칙이 되도록 같은 도우미를 거는 것은 계획이 정한다.

## 3. 동작

### 3.1 경로별

| 경로 | 결과에 실패가 담김(커밋에 닿음) | 커밋에 닿지 못함 |
|---|---|---|
| 새 조직 POST | 저장하지 않고 U4 의 줄을 되지운다 → 503(지금 I11). 되지우기가 실패하면 WARN + 셈(U5 b) | 저장하지 않는다 → 503. U5 (a) 면 WARN + 셈 |
| 기존 조직 PUT·PATCH | 이름표를 저장하고 멤버는 반영된 만큼만 저장한다(지금 그대로). 그 뒤 결과를 모르는 넣기의 줄을 되지운다(U2) → 503. 되지우기가 실패하면 WARN + 셈 | 저장하지 않는다 → 503. U5 (a) 면 WARN + 셈 |
| 지정 두기·없애기 | 지정을 저장하지 않고 U4 의 줄을 되지운다(U3) → 503. 되지우기가 실패하면 WARN + 셈 | 저장하지 않는다 → 503. U5 (a) 면 WARN + 셈 |
| 조직 DELETE | 지우기만 한다 — 부여 줄이 없다. 지금 그대로 | 지금 그대로(세지 않는다) |
| 직원 쪽 쓰기 | 지금 그대로 | 지금 그대로(세지 않는다, §1.1) |

### 3.2 되지우기(공통)

- 되지우기 직전에 리스를 확인한다. 실패하면 `LockUnavailableException` 을 그대로 내보낸다 — 지금 I11 의 규칙이다.
- 지우기는 "없으면 무시" 다. 결과를 모르는 줄을 지워도 안전하다.
- 되지울 줄이 없으면 OpenFGA 를 부르지 않는다.
- 보류 목록은 되지우지 않는다(I11 과 같은 까닭).
- 이력: 되지운 줄은 이 요청의 변경 모음에 회수로 더해진다(지금 I11 과 같다). 되지운 넣기의 멤버는 저장되지 않았으므로 조직도 변경 줄에 들지 않는다.
- 기존 조직은 조직을 저장한 **뒤** 되지운다. 저장이 실패하면 되지우지 않고 커밋 오류다(U5 a).

### 3.3 운영자가 받는 신호

- `scim.writes.unsourced` 가 오른다. 경보 예:
  ```
  sum(increase(scim_writes_unsourced_total[1h])) > 0
  ```
- 대응 순서.
  1. WARN 의 조직 id 로 IdP 프로비저닝 로그(지정이면 스크립트의 503)를 본다.
  2. 같은 요청이 그 뒤 성공했으면 끝이다.
  3. 아니면 한가한 때 `mode=tuples` 를 건다.
- **OpenFGA 쓰기 장애 중에는 함께 오른다.** 일시 오류는 결과를 모르는 실패라, 그동안 멤버를 넣은 조직 쓰기는 정말로 줄을 남겼을 수 있다. 되지우기도 같은 장애로 실패하기 쉽다. 장애가 끝나고 IdP 재시도가 돈 뒤 재적재를 한 번 거는 것이 대응이다.
- 카운터는 맞았는지 모른다(§6). 쌓기만 한다.

## 4. 시험

- **core(가짜 저장소·가짜 writer).** 가짜 writer 는 델타 하나를 묶음 하나로 보고 줄마다 실패를 정한다(`failFor` 확정, `lostResponseFor` 반영하되 결과를 모름). 운영의 단계 규칙은 흉내 내지 않으므로, 시험은 운영에서 생기는 조합을 고른다.
  - U2:
    - 기존 조직 PATCH 의 넣기가 결과를 모르면, 그 멤버를 저장하지 않고 그 줄이 가짜 장부에 없다. 결과는 부분 반영이다.
    - 같은 PATCH 를 다시 보내면 멤버가 저장되고 줄이 있다.
    - 기존 조직 PUT(전체 교체)도 같다 — 같은 PUT 을 다시 보내면 멤버가 저장되고 줄이 있다.
    - 확정 실패한 넣기는 되지울 것이 없어 OpenFGA 를 더 부르지 않는다.
    - 같은 요청의 원래 있던 멤버 줄은 지우지 않는다.
    - 되지우기 직전 리스를 잃으면 지우지 않고 리스 상실로 끝난다. 조직은 이미 저장돼 있다.
  - U3·U4:
    - 지정 A→B 에서 옛 연결 지우기는 성공하고 새 연결 `child(C,B)` 가 결과를 모르면, 지정은 A 그대로이고 `child(C,B)` 가 가짜 장부에 없다. 그 뒤 C→D 로 걸면 `child(C,B)` 도 `child(C,A)` 도 없고 `child(C,D)` 가 있다.
    - 옛 연결 지우기가 결과를 모르고 새 연결 쓰기가 확정 실패면(운영의 단계 규칙이 만드는 조합), 되지울 줄이 없어 OpenFGA 를 더 부르지 않는다.
    - 같은 상위로 다시 건 요청이 실패해도 OpenFGA 를 더 부르지 않는다.
    - 되지우기 직전 리스를 잃으면 지우지 않고 리스 상실로 끝난다.
  - U4: 새 조직의 되지울 줄이 지금과 같다 — 기존 `IncrementalSyncNewGroupUndoTest` 가 그대로 통과한다.
  - U5·U6: 센다/세지 않는다.
    - 센다(1):
      - 새 조직·기존 조직·지정의 되지우기 결과에 실패가 담긴 경우와 되지우기 오류
      - 되지우기 전 리스 상실(한 번만)
      - 기존 조직의 커밋 오류 — 넣기를 쓴 뒤 상태 저장 실패
      - 넣기를 쓴 묶음 뒤 차단기 중단
      - 쓰는 도중 리스 상실(취소)
      - 지정을 쓴 뒤 저장 실패
    - 세지 않는다(0):
      - 성공
      - 부분 반영이지만 커밋과 되지우기를 마침
      - 확정 실패뿐
      - Check 오류
      - 쓰기 직전 리스 확인 실패
      - 같은 상위 재지정의 커밋 오류 — 원천이 있는 줄만 보냈다
      - 직원 쓰기의 커밋 오류
      - 조직 DELETE 의 오류
- **app-scim.** `ScimSyncMetricsTest`: 기동 때 `scim.writes.unsourced` 가 0 으로 있고, 알리면 1 오른다. 결선은 `ScimUseCaseConfig` 가 지표를 관찰자로 넘기는 것이다 — 애플리케이션 컨텍스트를 띄우는 기존 시험이 지난다.
- **종단.** 새 종단 시험은 두지 않는다. 실패 주입이 가짜 writer 로만 된다.
- **규모.** 읽기가 늘지 않는다. 새 규모 시험은 두지 않는다.

## 6. 이 설계가 말할 수 없는 것

- **카운터는 맞았는지 모른다.** 같은 요청이 그 뒤 성공해 줄에 원천이 생겨도 내려가지 않는다. 남은 줄 수를 재려면 장부를 훑어야 하는데, 그것은 재적재뿐이다(OpenFGA Read 원칙).
- **인스턴스마다 따로 센다.** 경보 식은 인스턴스를 더해 본다.
- **끊긴 묶음은 위쪽 어림이다.** 리스 상실로 끊긴 묶음이 실제로 반영됐는지 모른다. 센 요청이 줄을 남기지 않았을 수 있다. 결과를 모르는 실패도 같다 — OpenFGA 쓰기 장애 중에는 실제로 남은 줄보다 많이 셀 수 있다.
- **저장하지 못한 새 직원 POST 의 줄(§1.1).** 켜짐에서 기록을 잃은 뒤에만 생긴다. 아카이빙이 레코드 없는 직원을 건너뛰어 세지도 지우지도 않는다. IdP 가 그 멤버를 조직에서 빼거나 같은 직원을 다시 POST 하면 맞는다.
- **벤더 동작은 문서 근거다.** IdP 가 503 뒤 같은 요청을 다시 보내는지는 확인하지 않았다(설계 2026-11-05 §6).

## 7. 왜 다른 길을 안 갔나

| 길 | 버린 이유 |
|---|---|
| **지표만(처음 후보)** | A 의 신호만 생기고 B·C 는 그대로 남는다. B 는 문서로만 막고 C 는 알려지지도 않았다 |
| **결과를 모르는 넣기를 멤버로 저장(처음 쓴 U2 — N1·N2 처럼 "있을 수 있다" 로 다룸)** | 전체 교체 PUT 의 재시도가 그 멤버를 그림에 싣지 않는다(`바뀌는_멤버` 의 교체는 "지금 − 목표"·"목표 − 지금" 만 싣는다). 줄이 실제로 안 쓰였으면 재시도가 Check 없이 200 으로 끝나고, 권한이 빠진 채 남는다. 지금은 같은 재시도로 고쳐지는 경우다. 구현 전 점검이 찾았다(§12) |
| **오류로 끝난 조직 쓰기도 의도를 저장(직원처럼)** | §2 "고치지 않기로 한 것" |
| **쓰기 전에 "쓸 줄" 을 DynamoDB 에 먼저 적고 커밋 뒤 지우기(앞쓰기 기록)** | 수렴은 하지만 조직 쓰기마다 DynamoDB 쓰기가 둘 는다. 큰 조직 POST 는 수천 줄이라 아이템 한도를 넘어 쪼개야 한다. 남는 경우(D)가 드물어 비용이 맞지 않는다 |
| **다음 요청이나 아카이빙이 OpenFGA Read 로 그 조직의 줄을 훑기** | Read 는 재적재와 기준선을 믿을 수 없는 LDAP 회차만 쓴다(원칙). 10만 명 규모에서 아카이빙의 장부 훑기는 재적재와 같은 비용이다 |
| **보낸 부여 줄을 모두 세기(U4 를 빼지 않음)** | 원천이 있는 줄만 남긴 요청(같은 상위 재지정 뒤 리스 상실, 기존 멤버 어긋남을 고친 PATCH 뒤 리스 상실)까지 센다. 경보가 재적재를 부르면 몇 분 동안 SCIM 쓰기가 503 이다 |
| **줄 수를 세기** | 끊긴 묶음은 줄 수를 모른다. 대응은 요청 단위로 같다 |
| **센 뒤 자동으로 재적재 걸기** | 재적재는 작업 락을 쥐어 몇 분 동안 SCIM 쓰기가 503 이다. 같은 요청의 재시도로 맞는 경우가 많아, 사람이 확인하고 거는 편이 낫다 |
| **지정 실패 때 옛 연결 되살리기** | §2 "고치지 않기로 한 것" |

### 9.3 구현 중 판정 (계획의 판정과 그 뒤의 것)

- **계획이 §11 을 이렇게 정했다.**
  - 커밋 자리의 경계는 조직 쪽 `Commit` 람다가 끝난 때다. 람다 안에서 저장, 이력, 회수 셈, 되지우기가 돈다. 뒤쪽 보류 목록 정리의 실패는 세지 않고, 앞쪽 보류 쓰기의 실패는 커밋 전이라 센다.
  - 저장하는 커밋(기존 조직)이 되지울 줄은 `(written ∪ uncertain) ∩ 저장하지 못한 넣기의 줄` 이다. 원래 멤버, 빼지 못한 멤버, 상위 연결은 저장된 행이 요구해 들지 않는다.
  - 결과에 실패가 없으면 되지울 줄이 없다. 성공한 새 조직 POST 의 상위 연결을 지우지 않는다.
  - "보냈을 수 있는 부여 줄" 은 본 쓰기 델타의 쓰기 줄에서만 고른다. 결과를 모르는 지우기는 들지 않는다.
  - 취소는 `반영하고_커밋한다` 의 비지 않은 갈래 끝 `doOnCancel` 로 본다.
  - 끊긴 묶음은 가짜 writer 의 `delayBeforeReport` 로 만든다 — 반영은 곧바로, 알림과 결과는 늦게.
  - 시험 전용 기존 조직 `upsertGroup` 도 같은 도우미를 건다. 규칙이 하나가 된다.
- **구현 중에 정한 것.**
  - **가짜 writer 는 `onApply` 를 부른 뒤에 `delayBeforeReport` 를 읽는다.** 되지우는 도중의 리스 상실 시험이 같은 부름에서 늦춤을 켜야 해서다.
  - **시험의 결과 모름 주입은 본 쓰기에만 건다(`본_쓰기의(X)`).** 가짜 writer 는 같은 술어를 되지우기의 지우기에도 건다. 맨 술어면 성공한 되지우기가 "결과 모름" 으로 보고되어 U5 (b) 로 세어진다. 셈 자체는 설계대로 맞고, 계획의 시험 준비가 모자랐던 것이다.
  - **되지우기 도우미 본문을 `Mono.defer` 로 감쌌다.** 되지울 줄이 늘 `저장했다` 뒤에 정해진다. 부르는 쪽이 감싸기를 잊어도 저장하는 커밋이 "저장하지 않는 커밋" 식으로 바뀌지 않는다.
  - **`없음()` 추적기는 상태를 바꾸지 않는다**(최종 리뷰). 직원 쓰기, 조직 삭제, 남은 회수가 함께 쓰는 하나의 인스턴스라 요청 사이에 바뀌는 상태를 두지 않는다. `되지울것` 도 빈 집합이다.
- **계획의 사실 오류 둘.**
  - 셈 시험의 갱신 주기 20ms 를 "`IncrementalSyncLeaseTest` 의 수법" 이라 적었지만, 그 시험은 50ms 다. 20ms 는 마감이 40ms 라 부하 걸린 전체 실행에서 흔들릴 수 있어 100ms 로 늘렸다(최종 리뷰).
  - Global Constraints 가 "예외 메시지는 싣지 않는다" 와 "되지우기 오류 WARN 은 예외를 붙인다" 를 함께 적어 스스로 어긋났다. 코드는 I11 부터 되지우기 오류에 예외를 붙인다. README 가 앞의 일반 문장을 따라 잘못 적은 것을 최종 리뷰가 고쳤다.

### 9.4 최종 리뷰와 수정

- **최종 리뷰(브랜치 전체, `da0c06f..fde04c3`) 판정은 "고치면 머지".**

  - Reactor 신호 흐름(쓰기 끝남, 커밋 자리 경계, 리스 상실 취소)과 셈의 정의가 U1–U7 과 맞다는 판정이었다.

  - 셈 시험의 갱신 주기 20ms.

### 9.5 남긴 것

- **지정이 받치는 하위 조직은 U4 식에서 벗어난다.**
  - 기존 조직 G 의 PUT·PATCH 가 하위 조직 S 를 넣는데, S 의 지정 상위가 G 인 경우다. 저장된 지정 S→G 가 `child(S,G)` 를 요구한다. 그런데 저장하는 커밋의 되지울 줄(저장하지 못한 넣기의 줄)은 지정을 모른다. PUT·PATCH 의 그림은 지정 연결을 싣지 않는다.
  - 장부에 `child(S,G)` 가 이미 없는 어긋남이 있을 때만 생긴다(Check 는 높은 일관성이다). 그 어긋남은 이 설계가 받아들인 "지정 실패 때 옛 연결을 되살리지 않음" 에서 생긴다.
  - 그 넣기의 결과를 모르면 되지우기가 `child(S,G)` 를 다시 지운다. 요청 전과 같은 어긋남으로 돌아갈 뿐이고, 같은 요청의 재시도가 고친다. 요청이 찾은 권한을 빼지는 않는다.
  - 같은 어긋남에서 그 PATCH 가 커밋 전에 끝나면 U5 (a) 가 한 번 거짓으로 센다. 대응 2단계(같은 요청이 성공했는지 본다)에서 대개 끝난다.
  - U4 의 경우별 풀이와 계획의 판정이 둘 다 지정 연결을 빠뜨렸다. 식 자체("커밋한 뒤의 상태가 요구하는 줄을 뺀다")는 맞다.
  - 고치려면 실패 경로에서만, 저장하지 못한 하위 조직 넣기에 `지정이_받치는_하위` 를 걸어 뺀다(하위 조직마다 GetItem 하나). 운영에서 드물지 않다고 드러나면 한다. 13 §2.7 에 적었다.
- **커밋 자리 경계의 반은 시험이 고정하지 않는다.** 뒤쪽 보류 목록 정리의 실패를 세지 않는 것과 앞쪽 보류 쓰기의 실패를 세는 것이다. 코드 모양(`보류와_함께_커밋한다` 가운데에서 `커밋을_마쳤다` 를 부름)과 자바독으로만 맞다. **다음 후보:** 보류 목록 쓰기를 실패시키는 저장소로 두 시험을 더한다.
- **프로세스가 죽은 요청은 세지 못한다.** 줄을 쓴 뒤 커밋 전에 프로세스가 죽으면 카운터도 함께 사라진다. 12 §6.1·§6.2 와 13 §2.7 에 적었다.
- **작은 것(그대로 둔다).**
  - 관찰자를 추적기의 모니터를 쥔 채 부른다. Micrometer 카운터는 락이 없어 문제가 없다.
  - "저장하지 못한 넣기의 줄" 계산이 두 커밋에 한 줄씩 있다.
  - 문서에서 "세지 않는 것" 목록과 대응 순서가 여러 곳에 있다. 지금은 서로 맞다.
- **다음 슬라이드 후보:** 바뀐 것 없는 지정 PUT 을 락 없이 끝내는 길(§10, 설계 2026-11-04 §15.3)과 위의 커밋 경계 시험.

## 11. 확인할 것 (구현 때 사실로 정한다)

- **커밋 자리의 경계.** 확인할 것은 `보류와_함께_커밋한다` 의 뒤쪽 보류 목록 쓰기(`changeCutEdges(Set.of(), 뺄것)`)가 실패할 때다. 이때는 조직도 저장은 끝났다. U5 (a) 가 그 경우를 "커밋한 뒤의 상태" 로 보게 하는 모양을 정한다. 되지우기는 조직 저장 뒤·보류 목록 정리 전인가 뒤인가도 함께 정한다.
- **기존 조직의 "결과를 모르는 넣기의 줄".** `reconcileGroupMembers` 가 저장하지 않은 넣기 가운데 결과를 모르는 줄이다. U4 의 식(`(written ∪ uncertain) − 커밋한 뒤의 상태가 요구하는 줄`)으로 셈하는 모양을 정한다.
- **취소의 모양.** `LeaseKeeper.keep` 은 `Mono.firstWithSignal(work, 상실)` 이라 리스 상실 때 하던 일을 취소한다. `반영하고_커밋한다` 가 취소를 보고 "아직 알려 오지 않은 부여 줄" 을 가리는 모양을 정한다.
- **끊긴 묶음의 시험.** 가짜 writer 는 반영하자마자 묶음을 알리고 그 뒤에 늦춘다(`delay`). "알려 오기 전에 취소된 묶음" 을 만들려면 알리기 전에 멈추는 주입이 필요하다 — 가짜 writer 에 더할지, 다른 길로 볼지 정한다.

## 12. 구현 전 점검

계획을 세울 사람의 눈으로 이 문서를 코드와 맞댔다(2026-11-11). 찾은 것과 고친 것:

- **처음 U2(결과를 모르는 넣기를 저장)는 PUT 재시도를 막는다** → 되지우기로 바꿨다(U2, §7).
- **"레코드 없는 직원의 줄은 아카이빙이 지운다" 는 틀렸다** — 건너뛴다(`revokeLeftovers` 빈 결과, `SnapshotArchiveUseCase`). §1.1 의 범위 밖 근거를 멤버 행으로 바로잡고 §6 에 한계로 적었다.
- **차단기는 요청 사이에 열려 있지 않다** — `apply` 호출마다 새로 센다. 처음 U6 의 "차단기가 열린 동안" 을 지우고, 쓰기 장애 중에는 이 카운터가 함께 오른다는 것을 §3.3 에 적었다.
- **운영 writer 는 앞 단계가 실패하면 뒤 단계 쓰기를 보내지 않는다** → 지정 시험을 운영에서 생기는 조합(새 연결의 결과를 모름)으로 바꿨다.
- **U5 (a) 의 셈 기준** → U4 와 같은 정의(원천이 있는 줄은 세지 않음)로 정했다.
- **POST 는 기존 조직에 닿지 않는다** → C 를 `changeGroup` 의 PUT·PATCH 로 좁혔다.
