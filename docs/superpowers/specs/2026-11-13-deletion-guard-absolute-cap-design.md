# 삭제 가드의 절대 수 상한 설계 (2026-11-13)

회수 수렴 설계(2026-10-20) §14 가 "회수 수렴과 다른 질문"으로 넘긴 "절대 수 상한"을 다룬다(온보딩 13 §3.3, 15 "삭제 가드"의 넷째 행). 같은 줄의 "부여 쪽 가드"는 이 슬라이드 밖이다.
사용자 결정: "추천대로"(2026-11-13) — 아래 결정은 모두 그 추천이다.

## 1. 문제

- 삭제 가드(`DeletionGuard`)는 **지울 튜플 줄 수 ÷ 기준 수**가 `threshold-ratio`(기본 0.3)를 넘으면 회차를 멈춘다. 기준 수가 `min-baseline`(10) 미만이면 보지 않는다.
  - 기준 수는 비교 경로에서 |B| + |U|(기준 스냅샷), 장부 맞추기·재적재에서 훑은 장부의 줄 수다.
  - LDAP 스냅샷 비교(`FullSyncUseCase.비교해_맞춘다`), 멈춘 뒤의 장부 맞추기와 재적재(`LedgerAlignment.가드로_본다`)가 같은 판정을 쓴다. SCIM 에는 가드가 없다.
- 비율만 보면 큰 배포에서 막는 양이 커진다. 실제 규모는 10만 명 이상이고(직원마다 `direct_member` 하나 이상, 조직 연결 `child` 가 더해져) 기준이 대략 10만~20만 줄이다.
  30% 면 한 회차에 3만~6만 줄이 지워져도 통과한다.
- 가드가 막으려는 것은 잘못 읽은 디렉터리다 — 검색 베이스·필터를 잘못 바꾸거나 서비스 계정 권한이 줄어 한 본부가 통째로 안 보이는 경우. 10만 명 회사의 본부는
  수천~2만 명이라, 그 빠짐이 비율 아래로 들어온다. 그 사람들의 권한은 다음 정각 회차에 조용히 사라지고, 신호는 `sync.tuples.deleted` 의 급변뿐이다.
- 사람 소속이 하나도 없는 그림은 가드 앞에서 데이터 오류로 멈춘다(설계 2026-10-27 §13). 문제는 "일부가 크게 빠진" 그림이다.

## 2. 결정

| # | 결정 | 이유 |
|---|---|---|
| G1 | **지울 줄 수에 절대 상한을 더한다.** 지울 줄이 `sync.deletion-guard.max-deletes` 를 **넘으면**(같으면 통과) 걸린다. 비율과 상한 가운데 하나라도 넘으면 걸린다 | 지금 가드와 같은 단위(줄)라 판정 하나만 바뀐다. 운영자가 "한 회차에 몇 줄까지는 사람 확인 없이" 를 수로 정할 수 있다 |
| G2 | **기본값은 5,000 이다(켜짐).** `0` 이하면 상한을 보지 않는다 | 배포 전이라 기본값을 바꾸는 비용이 없다. 10만 명 규모의 평소 변동(퇴사·이동은 시간당 수십~수백 줄)보다 훨씬 크고 비율 30%(3만 줄 이상)보다 훨씬 작다. 앞선 예: Microsoft Entra Connect 의 실수 삭제 방지도 기본이 켜짐·절대 수(내보내기 한 번에 지울 개체 500)다 |
| G3 | **상한은 `min-baseline` 과 상관없이 본다.** 가드가 꺼졌으면(`enabled=false`) 상한도 보지 않는다 | `min-baseline` 은 "작은 기준에서는 비율이 무의미하다"는 이유로 있다. 절대 수에는 그 이유가 없다. 지울 줄은 늘 기준 안의 줄이라(비교 경로: B ∪ U, 장부 맞추기: 훑은 장부) 기준이 상한보다 작으면 상한이 걸릴 일도 없다 |
| G4 | **같은 판정을 가드가 쓰이는 모든 곳에 똑같이 건다** — 비교 경로, 장부 맞추기, 재적재, 그리고 비활성 회수만 떼어 다시 보는 판정(설계 2026-10-20 §5.2). `force=true`·`FORCED` 는 지금처럼 가드 전체를 건너뛴다 | 한 규칙이다. 비활성 회수의 재판정이 상한을 빼면, 시계 오류·잘못된 정책으로 생긴 대량 비활성이 상한을 지나간다 — 그 재판정이 같은 가드인 까닭(§5.2)과 같다 |
| G5 | **문구는 넘은 한도를 적는다.** 지금 문구의 틀("삭제 대상 N건(기준 이름 M건의 X%)이 … 를 초과했습니다. 강제 실행하려면 force=true 로 재요청하세요")을 지키고, "…" 자리에 넘은 것을 적는다 — `임계치 30.0%`, `상한 5000건`, 둘 다면 `임계치 30.0%와 상한 5000건`. 비율은 `min-baseline` 이상일 때만 "넘은 것"이 된다 | 운영자가 무엇 때문에 멈췄는지, 어느 설정을 볼지 문구로 안다. 비율만 넘은 경우의 문구는 지금과 같다 |
| G6 | **새 지표를 두지 않는다.** `sync.guard.aborted` 는 그대로 걸린 회차를 센다 | 걸린 뒤의 대응(실행 기록을 보고 `force` 로 넘기거나 디렉터리를 고친다)이 같다. 어느 한도인지는 문구에 있다 |
| G7 | **설정과 문서.** `SyncProperties.DeletionGuardConfig.maxDeletes`(기본 5000)를 `DeletionGuardPolicy` 로 넘긴다. app-ldap 의 `application.yml` 과 시험 프로필 `application-test.yml` 에도 같은 값을 적는다(`sync.deletion-guard.*` 셋을 두 yml 에 적는 지금 관례, 온보딩 11). README 와 온보딩(02·05·11·12·13·15, 그 밖에 "30%" 만 적은 곳)을 코드대로 고친다 | 온보딩은 늘 현재 동작이다 |

**고치지 않기로 한 것.**
- **잃는 직원 수로 세기.** §7.
- **`child` 한 줄이 지우는 롤업.** 하위 조직 연결 하나를 지우면 그 아래 모든 직원의 상위 조직 권한(롤업)이 빠진다. 줄 수 가드는 그것을 한 줄로 센다. 비율로도 상한으로도 보이지 않는다.
  영향을 재려면 하위 트리를 걸어야 해 10만 명 규모에서 읽기가 크게 는다. 디렉터리에서 상위 연결만 빠지는 오독(DIT 의 부모 이동, 중첩 그룹 멤버 하나 빠짐)이 실제로 보이면 따로 다룬다(§10).
- **부여 쪽 가드.** 같은 리뷰 줄의 다른 질문이다. 무엇을 "이상한 부여"로 볼지부터 정해야 한다(§10).
- **SCIM 의 대량 회수 상한.** SCIM 은 의도된 단건 삭제라 가드가 없고(설계 2026-09-30 §4.3), 시간 창으로 막는 것은 정당한 회수를 늦춰 버렸다(운영 준비 설계 §17.4).
- **설정 검사.** 음수는 0 과 같이 "보지 않음"이다. 기동 검사를 새로 두지 않는다 — 지금 `threshold-ratio`·`min-baseline` 도 검사하지 않는다.

## 3. 동작

### 3.1 판정

```
가드 꺼짐                               → 진행
상한 > 0 이고 지울 수 > 상한             → 걸림(상한 넘음)
기준 수 ≥ min-baseline 이고 비율 > 임계치 → 걸림(임계치 넘음)
둘 다 아니면                            → 진행
```

- 걸리면 지금처럼 지울 줄 가운데 비활성 직원의 `direct_member` 줄만 떼어 **같은 판정**(같은 기준 수, 같은 임계치, 같은 상한)으로 다시 본다. 비어 있지 않고 통과하면 비활성 회수만 반영,
  아니면 전부 보류다(설계 2026-10-20 §5.2~§5.4, 온보딩 05 §6.4·§7.2).
- 걸린 회차의 결론·이력·현재상태·스냅샷은 지금과 같다(`ABORTED`, 전부 보류면 아무것도 쓰지 않음, 일부 반영이면 그 지우기만).
- 문구의 예.
  - 상한만: `삭제 대상 6200건(기준 스냅샷 150000건의 4.1%)이 상한 5000건을 초과했습니다. 강제 실행하려면 force=true 로 재요청하세요`
  - 둘 다: `삭제 대상 52000건(기준 스냅샷 150000건의 34.7%)이 임계치 30.0%와 상한 5000건을 초과했습니다. 강제 실행하려면 force=true 로 재요청하세요`
  - 일부 반영의 문구는 지금처럼 앞에 "삭제 가드 발동 — 비활성 회수 N건만 반영하고 …" 가 붙고 " / " 뒤가 위 문구다.

### 3.2 운영자가 보는 것

| 상황 | 지금 | 바뀐 뒤(기본값) |
|---|---|---|
| 10만 명, 한 본부 8,000명이 디렉터리에서 안 보임(지울 줄 약 8,000, 기준 15만) | 5.3% — 통과, 8,000명의 권한이 사라진다 | 상한을 넘어 걸린다. 비활성 직원이 아니므로 전부 보류, `ABORTED` |
| 10만 명, 3,000명 이동하는 개편(지울 줄 약 3,000) | 통과 | 통과 |
| 10만 명, 7,000명 이동하는 개편 | 통과 | 걸린다. 확인한 뒤 `POST /admin/sync/full?force=true` |
| 10만 명, 6,000명 퇴사를 디렉터리가 비활성으로 표시 | 통과 | 걸린다. 비활성 부분(6,000)도 상한을 넘어 전부 보류 — 확인한 뒤 `force` |
| 1,000명 배포(기준 약 1,500줄) | 비율 30% 가 먼저 걸린다 | 같다 — 지울 줄이 5,000 을 넘을 수 없다 |

- 큰 개편·대량 퇴사를 앞둔 운영자는 그 회차를 `force=true` 로 넘기거나, 그 기간만 `max-deletes` 를 올린다. 영구히 끄려면 `0` 이다.
- 걸린 회차는 매시 같은 판정을 되풀이한다(지금과 같다). `sync.guard.aborted` 경보(온보딩 11 §3.6)가 두 번째 회차부터 잡는다.

### 3.3 장부 맞추기에서 달라지는 것

장부 맞추기(재적재, 기준선 없음·기록 중 회차)의 기준 수는 훑은 장부(옛 장부 ∪ D)라, D 에 새 줄이 많으면 비율이 낮아진다(온보딩 13 §3.4). 상한은 분모를 보지 않으므로 이 경로에서 더 자주 걸린다.

- **약한 분모를 큰 변경에서는 메운다.** 13 §3.4 의 예(11만 줄 중 40% 가 새 id 로 바뀌어 44k/154k ≈ 28.6%)는 지금 통과하지만, 바뀐 뒤에는 44k 가 상한을 넘어 걸린다.
  상한 아래의 변경(예: 4천 줄)은 지금처럼 비율만으로 본다.
- **걸린 장부 맞추기는 비싸게 되풀이된다(지금과 같은 모양).** 전부 보류는 스냅샷을 남기지 않아 기록 중 표시가 남는다. 그래서 `force` 전까지 매시 D 전체를 다시 쓰고 장부를 훑는다
  (10만 명 규모 쓰기 약 1,100 배치·훑기 약 1,100 호출, 온보딩 05 §7.2·11). 상한 때문에 이 상태에 드는 일이 10만 명 규모에서 늘어난다.
- **`force` 로 넘긴 큰 회차가 기록 전에 끊기면 다음 회차에 다시 `force` 가 필요하다.** 다음 정각은 장부 맞추기이고, 아직 지우지 못한 줄이 상한을 넘으면 걸린다. 비율만 볼 때는 분모가
  커서 지나갈 수 있었다. 운영자는 끊긴 회차 뒤 실행 기록을 보고 다시 `force` 한다(온보딩 12 의 끊긴 회차 절에 적는다).

## 4. 시험

각 시험에 "이 시험을 깨뜨릴 운영 코드 변경"을 적는다.

### 4.1 core — `DeletionGuardTest`

| 시험 | 단언 | 깨뜨릴 변경 |
|---|---|---|
| 상한과 같으면 통과, 하나 넘으면 걸린다(비율은 임계치 아래) | 경계 둘, 걸린 쪽 문구에 `상한 N건` | 상한 비교를 `>=` 로 바꾸거나 빼기 |
| 기준이 `min-baseline` 미만이어도 상한은 본다 | 기준 9, 상한 3, 지울 4 → 걸림 | 상한을 `min-baseline` 확인 뒤로 옮기기 |
| 상한 0 이면 상한을 보지 않는다 | 비율 아래·지울 수 큼 → 진행 | 0 을 "모두 막음"으로 다루기 |
| 가드가 꺼지면 상한도 보지 않는다 | `enabled=false` → 진행 | 상한을 `enabled` 확인 앞으로 옮기기 |
| 둘 다 넘으면 문구에 둘 다 | `임계치 30.0%와 상한 N건` | 첫 한도에서 문구를 끝내기 |
| 비율만 넘으면 문구가 지금과 같다 | 지금 문구 그대로(상한 언급 없음) | 문구에 늘 상한을 넣기 |
| 비활성 회수의 재판정도 상한을 본다 | 전체가 상한을 넘고, 비활성 부분이 비율 아래지만 상한 위 → 전부 보류 | 재판정에서 상한을 빼기 |
| 비활성 부분이 상한 아래면 그것만 반영 | `revokeOnly` | 재판정을 아예 빼기 |

### 4.2 core — 경로마다 하나

- `FullSyncUseCaseTest`(비교 경로): 비율 아래·상한 위의 델타 → `ABORTED`, 쓰기 없음, 메시지에 `상한`. `force`(`FORCED`)면 반영.
- `RebuildUseCaseTest` 또는 장부 맞추기 시험: 훑은 장부 기준, 비율 아래·상한 위의 지울 후보 → 전부 보류(`held`), 메시지에 `상한`, 기준 이름 `훑은 장부`.
- 깨뜨릴 변경: 그 경로가 정책을 다른 길로 만들거나(상한을 잃음) 다른 판정 함수를 부름.

### 4.3 app-ldap — 설정 결선

- `sync.deletion-guard.max-deletes` 를 주면 가드가 그 값을 쓰고, 주지 않으면 5000 이다. 시험 방식(속성 바인딩 시험 또는 가드 빈을 꺼내 판정)은 계획이 정한다.
  스프링 문맥으로 시험하면 5000 은 속성 클래스 기본값이 아니라 yml 에서 온다 — 속성 클래스 기본값은 문맥 없는 단위 시험으로 본다.
- 깨뜨릴 변경: `UseCaseConfig.deletionGuard` 가 새 값을 넘기지 않음, 기본값을 0 으로 둠.
- 규모 시험은 더하지 않는다. 판정은 수 하나를 더 비교할 뿐이라 읽기·쓰기가 늘지 않는다. 기존 `LdapDeletionGuardScaleTest`(5천 명, 비율 경계 L12·L13)는 그대로 통과해야 한다 —
  5천 명의 기준(약 수천~1만여 줄)에서는 30% 가 상한 5000 보다 먼저 닿는다. 그렇지 않은 규모 시험이 있으면 계획이 그 시험의 설정에 상한을 적는다(§11).

  - 3인자 생성자를 부르는 지금 시험은 `DeletionGuardTest` 의 가드 끔 시험 하나다. 나머지(`FullSyncUseCaseTest`·`RebuildUseCaseTest`·`LdapSyncAuditTest`·`SyncSchedulerTest`·`SyncSchedulerCronTest`)는
    `DeletionGuardPolicy.defaults()` 라 고치지 않아도 상한 5000 을 받는다.
  - §4.2 의 경로별 시험은 상한 5000 을 넘기려면 가짜 저장소에 수천 줄이 필요하므로, 작은 상한의 정책으로 유스케이스를 만든다. `FullSyncUseCaseTest` 의 `유스케이스()` 는 지금 인자가 없어 정책을 받는 길을 더한다(모양은 계획이 정한다).
- 문서: README(가드 절, "30%" 를 적은 곳 — 약 548·879·1014행 등), 온보딩 02·05·11·12·13(§3.3·§3.4 — 13 §3.4 의 예에는 "30%" 글자가 없어 grep 으로 안 잡힌다)·15(+ grep 으로 찾은 곳), 이 설계 §9.
- 바뀌지 않는 곳: `GuardDecision`, 두 경로의 가드 호출(`FullSyncUseCase`·`LedgerAlignment`), SCIM.

## 6. 이 설계가 말할 수 없는 것

- **기본값 5,000 이 맞는 수인지는 실제 배포의 변동으로만 안다.** 10만 명 규모의 시간당 지울 줄 수를 잰 적이 없다. "평소 수십~수백 줄"은 이직률·이동률로 어림한 것이다.
  큰 개편이 잦은 배포는 사람 확인이 늘고, 작은 배포에서는 비율이 먼저 닿아 이 설정이 의미가 없다.
- **줄 수는 사람 수가 아니다.** 소속이 여럿인 직원은 여러 줄이고, 이동은 지우기 한 줄 + 쓰기 한 줄이다. Entra Connect 의 500 은 개체 수라 같은 수로 비교할 수 없다.
- **`child` 줄이 지우는 롤업은 보이지 않는다**(§2). 상한은 "줄이 많이 빠지는" 오독만 막는다.
- **실제 디렉터리에서 일부가 빠지는 오독을 재현한 시험은 없다.** 시험은 임베디드 LDAP·가짜 저장소에서 엔트리를 지워 만든다(지금 L12·L13 과 같다).

## 7. 왜 다른 길을 안 갔나

| 길 | 버린 까닭 |
|---|---|
| 지금 그대로(비율만) | 큰 배포에서 막는 양이 수만 줄이다(§1). 문서의 우회는 `sync.tuples.deleted` 경보뿐이고, 경보는 이미 지운 뒤에 울린다 |
| 잃는 직원 수로 센다 | 운영자 감각에는 맞지만 `child` 한 줄이 수천 명의 롤업을 지우는 것을 세려면 하위 트리를 걸어야 한다(10만 명 규모 읽기). `direct_member` 만 세면 줄 수와 거의 같아 이득이 없다 |
| 규모에 따라 비율을 낮춘다(기준이 크면 임계치를 줄임) | 새 설정은 없지만 언제 걸리는지 운영자가 예측하기 어렵다. 경계를 설명할 문장이 길어진다 |
| 상한을 두되 기본은 끔(0) | 지금 동작이 그대로라 안전하지만, 큰 배포의 구멍은 운영자가 설정을 알 때만 닫힌다. 배포 전이라 기본값을 바꾸는 비용이 없다 |
| 상한을 비활성 회수의 재판정에서 뺀다 | 대량 퇴사의 회수가 상한에 막히지 않는다. 그러나 시계 오류·잘못된 정책으로 생긴 대량 비활성이 상한을 지나간다 — 재판정이 같은 가드인 까닭(설계 2026-10-20 §5.2) |
| 상한을 장부 맞추기에서는 보지 않는다(걸린 장부 맞추기의 비싼 되풀이를 피함) | 장부 맞추기는 분모가 커서 비율이 가장 약한 경로다(13 §3.4). 재적재와 기록 중 회차가 모두 여기를 탄다. 거기서 상한을 빼면 큰 오독이 가장 쉽게 지나가는 길이 남는다 |
| 상한을 넘으면 상한까지만 지운다(나머지는 다음 회차) | 잘못 읽은 그림이면 상한만큼은 틀린 권한 회수가 반영된다. 가드의 뜻(사람이 보기 전에는 쓰지 않는다)과 어긋난다 |

### 9.3 구현 중 판정

- **§11 을 이렇게 정했다.** 가드 끔 시험은 정책 `(false, 0.3, 10, 5)` 로 바꿔 상한도 보지 않음을 함께 본다. 문구를 단언하는 지금 시험은 모두 비율만 넘는 경우이고 `contains(...)` 라 그대로 통과했다.
- **장부 맞추기 쪽 경로 시험은 `FullSyncUseCaseTest` 의 기준선 없는 회차로 본다**(§4.2 의 "또는"). 재적재도 같은 `LedgerAlignment.가드로_본다` 를 타고, `RebuildUseCaseTest` 의 지금 가드 시험이 재적재가 가드를 부르는 것을 이미 지킨다.
- **결선 시험은 스프링 문맥 없이 한다**(§4.3 "계획이 정한다"). `Binder` 로 `sync` 를 바인딩하고 `UseCaseConfig.deletionGuard` 를 직접 불러 가드로 판정한다. 기준 9 로 비율을 빼고 상한만 본다 — 결선이 `maxDeletes` 자리에 다른 값을 넘기는 실수도 잡는다.
- **판정 앞의 이른 반환(기준 수 < `min-baseline` 이면 진행)을 없앴다.** 상한은 그 앞에서도 봐야 한다. 덧붙은 결과: 예전에는 `min-baseline: 0` 에 기준 수 0 이면 0/0 = NaN 이 `ratio <= 임계치` 를 거짓으로 만들어 "NaN%" 문구로 멈췄다. 이제는 진행한다(지울 줄이 0 이다).

### 9.4 최종 리뷰와 수정

- **최종 리뷰(브랜치 전체, `acc394d..0d1dcc8`) 판정은 "고치면 머지".** 코드는 G1~G7 과 계획에 맞고, 가드를 보는 세 자리(비교 경로·장부 맞추기·비활성 회수 재판정)가 모두 한 판정을 거친다는 것, 기존 e2e·규모 시험이 상한 5000 에서도 그대로라는 것을 확인했다.
- 막은 것은 문서 셋이었다 — README 의 재판정 설명 둘("같은 기준 수·임계치", "남은 비율이 임계 아래로")과 온보딩 입구(`docs/onboarding/README.md`)의 "30% 를 넘으면" 이 비율만 말했다. 사소한 것 다섯 가운데 넷(05 의 링크 대상, 12 §6.1 의 끝까지 못 간 `force` 회차, 11 의 `threshold-ratio` "바꿀 때", 05 의 문장 둘)을 같은 수정에 넣었다.
- 수정 물결 `3c5bfa9` 하나, 범위를 좁힌 재리뷰는 여덟 건 모두 반영·새 문제 없음이었다.

### 9.5 남긴 것

- **비율만 말하는 코드 주석.** `RebuildUseCase`(약 31~32행)·`AdminSyncController`(약 64~65행)의 "훑은 장부의 임계치를 넘으면", `LedgerAlignment`(약 37~38행)의 "남은 비율이 임계 아래로", connector-ldap 의 "삭제 가드(30%)"(`IncompleteAttributeReadException`·`UnmatchedMemberGuard`·`MemberMatchingFailedException`). 논지는 지금도 맞고, 주석만 고쳐도 코드 커밋이라 온보딩 기준 커밋 줄이 모두 움직여 이 슬라이드에서는 두었다. 그 파일을 다음에 고치는 슬라이드가 함께 고친다.
- **끝까지 못 간 `force` 회차가 다시 걸린다(§3.3 의 넓힘).** §3.3 은 "기록 전에 끊김" 만 적었다. 쓰기 차단기·기한 초과·서버 종료·리스 상실로 지우기를 다 보내지 못해도 남은 지우기가 다음 회차에 같은 판정을 받는다(예: 44k 를 `force` 로 넘겼는데 10k 에서 멈추면 남은 34k 가 상한에 걸린다 — 비율만이면 34k/140k ≈ 24% 로 지나갔다). 운영 문서(12 §6.1)에 적었고, 대응은 12 §4.4(확인한 뒤 `force`)다. 결과를 모르는 지우기(U)가 쌓여 평소 회차가 상한을 넘는 일도 같은 모양이다.
- **G4 의 대가.** 디렉터리가 정당하게 막은 대량 비활성(예: 계약직 계정 일괄 만료로 5,000줄 넘음)은 이제 `force` 전까지 전부 보류된다. 예전에는 30% 아래면 나갔다. §7 이 따져 버린 길("재판정에서 상한을 뺀다")의 반대편이다.
- **07 "전부 보류" 행의 메시지 칸**이 세 꼴을 괄호로 겹쳐 읽기 어렵다(같은 내용이 02·12 에 있다).
- 그 밖에는 §10 그대로다 — 부여 쪽 가드, `child` 줄의 롤업 영향, SCIM 대량 회수 상한, 가드 판정 미리보기. 어느 한도에 걸렸는지 가르는 지표(G6), 설정 값 검사(§2), `%.1f` 가 JVM 로케일을 따르는 것(예전부터)도 그대로 두었다.

## 12. 구현 전 점검

계획을 세울 사람의 눈으로 이 문서를 코드와 맞댔다(2026-11-13). 계획 전에 사용자께 여쭐 것은 없었다.

- **맞다고 확인한 것.**
  - 가드를 보는 자리와 기준 수: 비교 경로 `FullSyncUseCase` 의 |B|+|U|("기준 스냅샷", `FORCED` 가 아닐 때만), 장부 맞추기 `LedgerAlignment` 의 훑은 수("훑은 장부", force 면 `DeleteCheck.NONE`).
    재적재와 기준선 없는 회차도 `LedgerAlignment` 를 탄다. SCIM 은 `DeletionGuard` 를 쓰지 않는다.
  - 지울 줄은 늘 기준 안이다(G3): 비교 경로는 (B−D) ∪ (U−D) 이고 B·U 는 겹치지 않는다. 장부 맞추기는 읽은 줄마다 세고 stale 아니면 present 로 가르므로 |stale| ≤ 훑은 수다.
  - 비활성 회수 재판정은 같은 `evaluate(int, int, String)` 을 부른다 — 그 함수에 상한을 넣으면 G4 가 저절로 지켜진다. `GuardDecision` 과 두 호출 자리는 바꾸지 않는다.
  - force 없이 5000 줄을 넘게 지우고 진행을 기대하는 지금 시험은 없다. 앱 규모 시험은 모두 `OrgChartFixture.오천명()`(튜플 약 6.6천 줄)이라 5000 줄을 넘게 지우면 30% 가 먼저 걸린다.
    `LdapDeletionGuardScaleTest` 의 L12-a 는 약 1,990줄, L12-b 는 비율만 넘고, L13 은 force 다.
  - 문구를 파싱하는 운영 코드는 없다. `sync.guard.aborted` 는 결론이 `ABORTED` 인지로 센다.
- **고친 것.**
  - §5 의 "정책 생성자를 부르는 시험" 목록이 틀렸다 — 3인자 생성자는 `DeletionGuardTest` 하나이고 나머지는 `defaults()` 다. §5·§11 을 고쳤다. 경로별 시험이 작은 상한의 정책을 받을 길이 필요하다는 것을 §5 에 적었다.
