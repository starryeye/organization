# 큰 변경도 락을 지키며 끝까지 — 리스 갱신, 커밋 직전 확인, 싼 삭제 (점검 ③-1)

2026-10-02. 점검 권고 슬라이드 ③(큰 변경과 락)을 둘로 나눈 것 중 **③-1** 이다. ③-2 는 읽기 비용과 조직 그래프(P1·P2·M1·S4·S28)다.

근거: `docs/superpowers/specs/2026-09-28-full-audit.md` §4(C6·M8·P8·S3·S14), §7 권고 ③,
`docs/superpowers/specs/2026-09-28-scim-write-lock-design.md` §11(큰 변경의 리스 갱신, BatchGet 재시도 상한·백오프),
`docs/superpowers/specs/2026-09-30-cluster-jobs-baseline-design.md` §12(쓰기 병렬화는 ③).

## 1. 문제

모든 SCIM 쓰기는 앱의 전역 락(`LOCK#MUTATION`, TTL 30초) 하나를 거친다. 10만 명 규모에서 이 락이 다음과 같이 깨진다.

- **C6 — 큰 조직 삭제가 락을 TTL 보다 오래 쥔다.** 10만 명 조직 `DELETE` 가 락 안에서 조직 파티션 전체를 두 번 읽고, 상위 조직 파티션도 통째로 읽고,
  멤버 직원 10만 명을 GetItem 으로 읽고, 후보 10만 줄을 BatchCheck(50줄씩) 2,000번 차례로 묻는다. **DynamoDB Local 에서 58.9초**(점검 측정).
  리스 확인은 OpenFGA 쓰기 직전 한 번뿐이고 갱신은 없다. 경쟁이 있으면 30초에 다른 인스턴스가 락을 가져가 이 삭제는 503 → IdP 재시도 → 또 실패를 되풀이한다.
  리스 확인을 통과해도 뒤의 OpenFGA 쓰기 약 1,000 배치와 DynamoDB 삭제 약 20만 건은 갱신 없이 돈다. "멤버 전원 빼기"·빈 `replace`·큰 PUT 도 같은 길이다.
- **M8 — 커밋이 리스를 다시 확인하지 않는다.** 바뀐 튜플이 없으면 확인 없이 바로 커밋하고, OpenFGA 쓰기 뒤의 커밋도 확인하지 않는다. 커밋은 조건 없는 덮어쓰기다.
  30초 넘게 멈춘 요청이 다른 인스턴스가 저장한 비활성화를 되돌릴 수 있다(점검 예 1·2).
- **P8 — SCIM 재적재가 튜플 스냅샷 저장까지 락 안에서 한다.** 10만 명이면 BatchWrite 약 4,400번(추정 45~110초) 동안 모든 IdP 쓰기가 503 이다.
  SCIM 쓰기 경로는 이 스냅샷을 읽지 않는다.
- **S3 — IdP 가 연결을 끊으면 락을 곧바로 반납한다.** 이미 보낸 OpenFGA 쓰기가 다음 요청의 Check 뒤에 떨어지면 다음 요청의 기준선이 틀린다. 락을 잡는 도중에
  끊기면 리스가 TTL 까지 샌다.
- **S14 — 락 획득 응답이 유실되면 자기 락에 막힌다.** 서버에서 성공한 PutItem 의 응답을 못 받아 SDK 가 같은 요청을 다시 보내면 조건에 걸려 실패 → 30초 동안 모든 SCIM 쓰기 503.
- **백로그 — BatchGet 재시도에 상한이 없다.** `DynamoDbDirectoryStateRepository.batchGet` 은 처리 못 한 키를 50ms 간격으로 끝없이 다시 묻는다.
  스냅샷 쪽 BatchWrite 는 5번·지수 백오프·오류로 이미 정해져 있다.

## 2. 결정 (사용자 확인, 2026-10-02)

- **③ 을 둘로 나눈다.** ③-1 = 락을 짧게·안전하게(이 문서), ③-2 = 읽기 비용·조직 그래프.
- **큰 변경은 끝까지 한 번에, 안전하게.** 나눠 처리하며 락을 사이사이 놓지 않는다. 큰 변경을 최대한 싸게 만들고, 도는 동안 리스를 갱신해 끝까지 끝낸다.
  그동안 다른 SCIM 쓰기는 지금처럼 503 이고 IdP 가 재시도한다.
- **M8 은 "갱신 + 커밋 직전 확인" 수준으로 막는다.** 상태 쓰기를 락 토큰 조건으로 묶는 펜싱(`TransactWriteItems`)은 하지 않는다(§10).

## 3. 리스 지키기 — 모든 SCIM 쓰기 (C6·M8·S3·S14)

### 3.1 하트비트 — 리스를 쥔 채 일 돌리기

- SCIM 쓰기(`IncrementalSyncUseCase#withLock` 을 타는 여덟 입구)는 락을 쥔 동안 `dynamodb.lock-renew-interval`(기본 10초)마다 리스를 갱신한다.
  갱신이 실패하면(=남이 가져갔거나 DynamoDB 가 답하지 않음) 하던 일을 멈추고 503 이다(`LockUnavailableException` "리스를 잃었다").
- ②-2 의 `SyncJobs` 에도 같은 하트비트가 있다(`리스를_갱신한다`). 둘을 core 의 작은 부품 하나로 합친다 — "리스를 쥔 채 일을 돌리고, 리스를 잃으면 그 일을 멈춘다".
  `SyncJobs` 와 `IncrementalSyncUseCase` 가 함께 쓴다. 리스 상실은 `LockObserver#leaseLost` 로 알린다.
- SCIM 쓰기 대부분은 1초 안에 끝나 갱신이 한 번도 일어나지 않는다. 평소 비용은 없다.

### 3.2 커밋 직전 확인 (M8)

- DynamoDB 커밋 직전에 **늘** 리스를 확인(갱신)한다 — 바뀐 튜플이 없을 때도. 확인이 실패하면 커밋하지 않고 503 이다.
- OpenFGA 쓰기 직전 확인은 그대로 둔다. 바뀐 튜플이 있는 요청은 확인이 두 번(쓰기 직전·커밋 직전), 없는 요청은 한 번이다(요청당 UpdateItem 1~2번).
- 큰 커밋(조직 삭제의 BatchWrite 수천 번)은 시작 전에 한 번 확인하고, 도는 동안은 하트비트가 지킨다.
- 남는 틈: "확인"과 "커밋 쓰기" 사이(밀리초)에 30초 넘게 멈추는 경우(§11).

### 3.3 요청이 끊겨도 끝까지 (S3)

- 쓰기 작업(락 잡기부터 반납까지)을 요청의 구독과 떼어 돌린다. IdP 가 연결을 끊어도 커밋까지 마치고 그다음 반납한다.
  요청 쪽은 결과를 기다리다 취소되면 그냥 떠난다(`SyncJobs` 가 작업을 요청과 떼는 것과 같은 방식). 요청의 Reactor Context(traceId)는 이어받는다.
- 이로써 "이미 보낸 OpenFGA 쓰기가 다음 요청의 Check 뒤에 떨어짐"과 "락을 잡는 도중 취소돼 리스가 샘"이 함께 없어진다.
- IdP 의 재시도는 이미 반영된 상태를 본다 — 멤버 추가는 같은 결과(변경 없음), 직원 POST 는 409. 지금도 반쯤 반영된 상태에서 같은 일이 생긴다.
- 앱이 내려가면 떼어 낸 쓰기는 DynamoDB 클라이언트가 닫히며 실패할 수 있다 — 락은 TTL(30초) 뒤 풀리고, 튜플·상태의 어긋남은 다음 같은 대상 쓰기의 Check 가 고친다
  (SCIM 쓰기는 OpenFGA 를 기준선으로 쓴다).

### 3.4 같은 토큰이면 획득 성공 (S14)

- 락 획득 조건을 `attribute_not_exists(#pk) OR #expiresAt < :now OR #token = :token` 으로 넓힌다. SDK 재시도는 같은 요청(같은 토큰)을 다시 보내므로
  "서버에선 성공했는데 응답만 잃은" 경우가 성공으로 끝난다. 앱 쪽 재시도(획득 대기 3초 동안 200ms 간격)는 매번 새 토큰이라 영향이 없다.

## 4. 큰 변경을 싸게 (C6)

### 4.1 조직 삭제는 전용 경로

삭제 뒤의 모습은 "이 조직을 언급하는 줄이 하나도 없음"으로 정해져 있다. 계산(직원 읽기·Check·diff)이 필요 없다.

1. 조직 파티션을 **한 번** 읽어 멤버 키를 얻는다. 상위 조직은 **아이디만** 읽는다(`findGroupIdsContaining(그 조직)` — 소속 줄). 직원은 읽지 않는다.
   지금은 상위 조직 파티션을 통째로 읽는다(`parentsOf`) — 10만 명 본부 밑의 작은 팀을 지울 때도 본부 10만 줄을 읽었다.
2. 지울 튜플을 바로 만든다 — 직원→조직(`direct_member`), 하위 조직→조직(`child`), 조직→상위 조직(`child`). **Check 없이** "없으면 무시"(`onMissing IGNORE`)로 지운다.
   후보에 없는 엉뚱한 튜플은 지금도 Check 대상이 아니므로 놓치는 범위는 같다.
3. DynamoDB 는 BatchWrite(25개씩, §4.4 재시도 규칙)로 지운다. 순서: 멤버 줄(상위 조직들의 "이 조직" 줄, 이 조직의 멤버 줄) → 소속 줄(이 조직의 소속 줄, 멤버들의 소속 줄) →
   **조직 META 맨 마지막**(소속 줄이 멤버 줄보다 늘 많거나 같게 — 강한 소속 조회 설계 §5). 중간에 멈추면(리스 상실·오류) META 가 남아 IdP 의 DELETE 재시도가 남은 것을 마저 지운다.
   지금은 파티션 아이템을 병렬로 지워 META 가 먼저 사라질 수 있다 — 그러면 재시도는 404 이고 멤버·소속 줄이 고아로 남는다.
4. 튜플 삭제가 일부 실패하면 지금 규칙을 지킨다 — 조직을 지우지 않고, 지우지 못한 튜플의 멤버만 남겨 저장한 뒤 5xx(IdP 재시도).
5. 드리프트 지표는 이 경로에서 재지 않는다(전부 지우므로 어긋남을 셀 대상이 없다).

### 4.2 멤버 대량 빼기도 같은 원리

- "멤버 전원 빼기"(값 없는 `remove members`), 빈 `replace members`, 큰 PUT 에서 **빠지는 멤버의 튜플**은 Check·직원 읽기 없이 "없으면 무시"로 지운다.
- **들어오는(남는) 멤버**는 지금처럼 Check 로 확인하고, 활성 여부를 위해 직원을 읽는다. 그 읽기를 묶음으로 바꾸는 것은 ③-2.
- 드리프트 지표는 들어오는 쪽만 잰다.

### 4.3 OpenFGA 요청을 동시에 여러 개

- 새 설정 `openfga.request-concurrency`(기본 4). Check 묶음(50줄)과 Write 묶음(`openfga.write-batch-size`, 100줄)을 이만큼 동시에 보낸다. 지금은 하나씩이다.
- 차단기(②-2: 한 줄도 못 살린 묶음 3번 연속이면 멈춤)는 결과를 **보낸 순서대로** 받아 지금과 같이 센다. 멈출 때 이미 나간 묶음(최대 동시 수 − 1)은 결과를 기다리지 않고
  "보내지 않음(실패)"으로 센다 — 실제로 반영됐더라도 다음 회차(LDAP)·다음 같은 대상 쓰기(SCIM)가 같은 결과로 다시 쓰거나 지우므로 안전하다(쓰기·지우기 모두 멱등).
- 한 델타 안의 쓰기와 지우기는 서로 겹치지 않으므로(diff 결과) 동시에 보내도 결과가 같다.
- LDAP 동기화·재적재, SCIM 재적재, 장부 훑기 뒤의 지우기도 같은 writer 를 타 함께 빨라진다.

### 4.4 DynamoDB 묶음 재시도에 상한

- BatchGet·BatchWrite 의 "처리 못 한 키"는 같은 규칙으로 재시도한다: **최대 5번, 100ms 부터 두 배씩, 다 쓰면 남은 수를 담은 오류.** 스냅샷 저장소의 규칙을 storage 의
  작은 부품 하나로 옮겨 상태 저장소(BatchGet, 조직 삭제 BatchWrite)와 스냅샷 저장소가 함께 쓴다.
- 지금 BatchGet 은 상한 없이 50ms 마다 다시 묻는다 — 스로틀이 계속되면 요청이 락을 쥔 채 끝나지 않는다.

### 4.5 예상

10만 명 조직 삭제: 조직 파티션 Query 2번 → **1번**, 직원 GetItem 10만 → **0**, Check 10만 줄 → **0**, OpenFGA 삭제 약 1,000 묶음(동시 4), DynamoDB BatchWrite 약 8,000번.
AWS 에서는 조직 파티션 하나의 쓰기 한도(초당 약 1,000 WCU) 때문에 멤버 줄 10만 개 삭제만 약 100초 걸릴 수 있다(추정). §3 의 갱신으로 끝까지 끝나고, 그동안 다른 쓰기는 503 이다.

## 5. SCIM 재적재의 스냅샷은 락을 반납한 뒤에 (P8)

- `SyncJobs#startLocked` 에 "반납 뒤 할 일" 단계를 둔다. 순서: **작업 → 반납 → 반납 뒤 할 일 → 기록.** 반납 뒤 할 일은 작업의 결론을 받아 결론을 돌려준다.
- SCIM 재적재(`tuples`·`wipe`)는 튜플 스냅샷 저장을 이 단계로 옮긴다. `wipe` 의 조직도 지우기는 SCIM 쓰기가 읽는 상태라 락 안에 남긴다.
- 반납 뒤 저장이 실패하면 지금처럼 FAILED 다. 사유에 "장부는 맞췄다 — 스냅샷 저장 실패"를 남긴다.
- 반납 뒤 저장하는 사이 다른 재적재가 락을 잡으면, 그 작업이 아직 RUNNING 인 이 기록을 "비정상 종료로 중단"으로 닫을 수 있다(②-2 §3.3 조건부 닫기).
  이 기록의 마지막 쓰기(`finish`)는 조건 없는 덮어쓰기라 결과는 결국 맞게 남는다.
- LDAP 동기화·재적재는 그대로 둔다 — LDAP 락은 IdP 쓰기를 막지 않고, ②-2 의 "기록 중" 표시가 스냅샷 저장에 기댄다.

## 7. 운영자가 보는 것

- 큰 조직 삭제·대량 빼기가 TTL 보다 오래 걸려도 끝난다. 그동안 다른 SCIM 쓰기는 503 이고 IdP 가 재시도한다.
- 리스를 잃은 쓰기는 503 "리스를 잃었다"이고 `LockObserver` 지표(리스 상실)가 오른다.
- 새 설정 `openfga.request-concurrency`(기본 4). OpenFGA 가 버거우면 낮춘다.

| 대상 | 확인할 것 | 모듈 |
|---|---|---|
| 리스 지키기 | SCIM 쓰기가 갱신 주기보다 오래 걸리면 리스를 갱신한다. 갱신이 실패하면 멈추고 503, 커밋하지 않는다 | core |
| 커밋 직전 확인 | 바뀐 튜플이 없어도 커밋 전에 확인한다. 확인이 실패하면 저장하지 않는다(M8 예 1 의 덮어쓰기가 막힌다) | core |
| 끊겨도 끝까지 | 요청이 중간에 취소돼도 커밋까지 하고 그다음 반납한다(S3). 락을 잡는 도중 취소돼도 리스가 새지 않는다 | core |
| 같은 토큰 | 같은 토큰으로 다시 잡으면 성공, 다른 토큰은 막힌다(S14) | storage |
| 조직 삭제 | 직원 GetItem 0, Check 0, 조직 파티션 Query 1, 상위 조직 파티션은 읽지 않는다. 튜플은 "없으면 무시"로 다 지운다. META 는 맨 마지막 — 중간에 실패한 뒤 다시 지우면 끝난다 | core·storage |
| 멤버 대량 빼기 | 빠지는 멤버는 Check·직원 읽기 없이 지운다. 들어오는 멤버는 지금처럼 Check | core |
| 동시 요청 | 동시에 나가는 요청이 설정값을 넘지 않는다. 차단기는 순서대로 세어 3묶음 뒤 멈춘다. 400 쪼개기(②-2)는 그대로 | authz-openfga |
| 묶음 재시도 상한 | BatchGet·BatchWrite 가 처리 못 한 키를 5번 넘게 받으면 오류다 | storage |
| P8 | SCIM 재적재 스냅샷은 락이 풀린 뒤 저장된다. 저장 실패는 FAILED | core |
| 규모 | 10만 명 조직 삭제 실측(시간·호출 수). 삭제 도중 다른 SCIM 쓰기는 503, 끝난 뒤에는 받아진다 | app-scim scaleTest |

머지 전 컨트롤러가 `./gradlew cleanTest test` 와 `./gradlew cleanScaleTest scaleTest` 를 한 번에 하나씩 돌리고, 결과를 §9 에 적는다.

## 9. 결과 (구현 후 기록)

머지 전 `test`·`scaleTest` 시간과 결과, 10만 명 조직 삭제 실측을 구현이 끝나면 여기에 적는다.

## 10. 왜 다른 길을 안 갔나

- **나눠 처리하며 락을 사이사이 놓기.** 다른 쓰기의 503 을 몇 초로 줄일 수 있지만, "지우는 중" 같은 중간 상태가 생기고 그 사이 같은 조직을 다시 만들거나 멤버를 넣는 요청을
  따로 다뤄야 한다. 설계·테스트가 크다. 사용자가 "끝까지 쥐되 안전하게"를 골랐다.
- **상태 쓰기 펜싱(`TransactWriteItems` + 락 토큰 조건).** 커밋 틈을 완전히 닫지만 모든 SCIM 쓰기의 DynamoDB 쓰기 비용이 두 배이고 저장소 쓰기 메서드를 전부 고쳐야 한다.
  OpenFGA 쓰기는 어차피 펜싱이 안 된다. 사용자가 A(갱신 + 커밋 직전 확인)를 골랐다.
- **큰 삭제를 202 로 받고 뒤에서 하기.** SCIM 표준에 비동기 응답이 없다(DELETE 는 204). IdP 가 끝났다고 믿은 뒤에도 권한이 남는다.
- **TTL 을 길게.** 죽은 인스턴스의 락이 그만큼 오래 남아 모든 쓰기가 503 이 된다. 갱신이 표준 리스 패턴이다.
- **Check 를 아예 없애고 늘 "있으면 무시·없으면 무시"로 쓰기.** 들어오는 쪽까지 그렇게 하면 드리프트 지표(Check 기준선 설계의 이유)가 사라진다. 빠지는 쪽만 생략한다.

## 11. 이 설계가 말할 수 없는 것

- **커밋 틈.** 커밋 직전 확인과 커밋 쓰기 사이에 30초 넘게 멈추면(GC 정지 등) 다른 인스턴스의 저장을 덮을 수 있다(펜싱 없음, §10). OpenFGA 쓰기도 펜싱되지 않는다.
- **큰 변경의 503 시간.** AWS 에서 10만 명 조직 삭제는 1~2분 동안 다른 SCIM 쓰기를 503 으로 만들 수 있다(추정, §4.5). 실측은 DynamoDB Local 기준이다.
- **동시 요청은 OpenFGA 부하를 늘린다.** 기본 4 로 시작하고 실연동에서 조정한다.
- **떼어 낸 쓰기와 앱 종료.** 종료 때 떼어 낸 SCIM 쓰기는 끝을 기다리지 않는다 — 락은 TTL 뒤 풀리고 어긋남은 다음 같은 대상 쓰기가 고친다(§3.3).
- **인스턴스 시계 차이(S15)는 다루지 않는다.** 30초 넘게 어긋나면 남의 락을 가져갈 수 있다(NTP 환경이면 드묾).
- **들어오는 멤버가 많은 변경**(큰 PUT, 대량 추가)은 직원 읽기(멤버당 GetItem)가 남아 여전히 느리다 — ③-2.
- **중간에 멈춘 조직 삭제는 소속 줄 몇 개를 남길 수 있다.** 이미 멤버 줄을 지운 멤버의 소속 줄은 재시도가 찾지 못한다(조직 → 멤버는 멤버 줄로만 안다). 소속 줄만 남는 안전한 방향이라 역참조와 권한에는 영향이 없고 저장 공간만 남는다.
