# 정리 묶음 (⑤) — 설계

> 브랜치 `cleanup-bundle` (origin/main `52a500c` 에서 분기).
> 출처: [`2026-09-11-e2e-branch-review.md`](2026-09-11-e2e-branch-review.md) §5, 슬라이드 E·①·③ 의 이월 항목.

## 1. 무엇을 하는가

리뷰와 앞선 슬라이드들이 "기록만" 해 둔 항목을 한 번에 치운다. 대부분 동작을 바꾸지 않는 다듬기지만,
몇 건은 **운영 코드의 결함**이거나 **테스트가 덜 증명하거나 느리게 실패하는** 문제다.

**범위를 정한 과정:** 처음 제안은 운영 코드(§2)만이었다. 사용자가 전부 하기로 정했다(2026-09-25).

### 이 묶음에서 떼어 낸 것 — ⑥ LDAP 비활성 계정

리뷰 문서는 "LDAP 쪽 `active` 가 늘 참이라 퇴사자 권한 생존은 SCIM 으로만 검증된다" 를 **테스트 공백(Minor)**
으로 적었다. 따라가 보니 **동작 결함**이다.

- 두 LDAP 전략 모두 직원을 `active = true` 로만 만든다.
- `TupleMapper` 는 비활성 직원의 튜플을 만들지 않는다. SCIM 은 이 경로로 퇴사자 권한을 지운다.
- 그래서 AD 에서 계정을 **비활성화만 하고 그룹에서 빼지 않으면 권한이 그대로 남는다.**

새 동작(AD `userAccountControl` 의 ACCOUNTDISABLE 비트 읽기 등)을 설계해야 하므로 정리 묶음에 섞지 않고
**⑥ 으로 뗐다**(사용자 확정: ⑤ 바로 다음, S-1 보다 먼저). 이 묶음은 `OrgChartEditor` 의 비활성화 연산(§3)까지만
하고, LDAP 이 비활성을 표현하는 일은 ⑥ 의 몫이다.

## 2. 운영 코드 (`connector-ldap`)

| 항목 | 지금 | 고친 뒤 |
|---|---|---|
| `DitStrategy` 의 DN 처리 | `parentDn` 이 첫 `,` 에서 자르고 `normalize` 가 문자열을 다듬는다. `ou=R\,D` 처럼 이스케이프된 쉼표가 든 RDN 이면 부모를 못 찾아 **그 아래 전원이 소속을 조용히 잃는다** — ③ 과 같은 종류의 결함 | `LdapDns` 로 부모 DN 과 대조 키를 만든다. 부모 DN 을 구하는 도우미를 `LdapDns` 에 더한다 |
| `GroupOfNamesStrategy.values()` | 호출자가 없는데, 읽기 실패를 삼키고 읽은 만큼을 돌려준다 — 이 커넥터가 지운 바로 그 모양이다 | 삭제 |
| 이어받기 다음 위치 | 받은 값의 **개수**로 센다 | **표준(MS-ADTS)대로 `high + 1`**. `Chunk` 가 범위 상한을 들고 다닌다. 방향은 원래도 안전했지만(짧은 조각이면 중복만 생긴다) 표준이 정한 값이 따로 있다 |
| 템플릿 설정 | `EmbeddedLdapSupport`·`LdifRendererTest` 가 `LdapTemplate` 설정을 한 벌씩 더 적는다 — `LdapTemplates` 자바독이 경고하는 표류가 운영과 검증 사이에서 난다 | 두 곳 모두 `LdapTemplates.configured()` 를 부른다 |
| `RangedAttributeReader` 자바독 | `{@link LdapTemplates#...}` 가 다른 패키지라 풀리지 않는다 | 전체 이름으로 |

`DitStrategy` 수정은 **RED 부터** 한다 — 이스케이프된 쉼표가 든 OU 아래 직원이 소속을 유지하는 테스트를 먼저 쓴다.

## 3. 테스트 하네스

| 항목 | 문제 | 고치는 방법 |

## 4. 규모 시나리오

### 깨질 수 있는 단언 — 이 절의 핵심

| 자리 | 문제 | 고치는 방법 |
|---|---|---|
| `ScimRebuildLockScaleTest` S18-b | `Thread.sleep(700)` 으로 재적재가 락을 잡기를 **바라고**, "2초보다 오래 걸렸다" 를 **벽시계로** 단언해 "리스 갱신이 일했다" 를 대신한다. 빠른 머신에서는 이유 없이 깨진다 | **결정 1** 참조 |
| `ScimLimitsAndRecoveryScaleTest` | `runs.get(0)` 이 이력 목록의 순서에 묶여 있다 | 트리거로 찾는다 |
| L4 | 겸직 직원을 빼지 않는다. 지금은 산술적으로 우연히 맞는다 | 명시적으로 뺀다 |

**결정 1 — 락 테스트는 테스트 안에서 확인한다.** 리뷰는 "리스 갱신 카운터 지표로 대체" 를 제안했지만 그런 지표는
운영 코드에 **없다.** 테스트만을 위해 운영 지표를 더하지 않는다. 대신 테스트가 락 빈(`MutationLock`)을
`@SpyBean` 으로 감싸서 (a) 재적재가 락을 잡을 때까지 **기다리고**(`sleep` 대신), (b) `renew` 가 한 번 이상 불렸음을
**직접** 확인한다(벽시계 대신).

| 접근 | 판단 |
|---|---|
| **테스트에서 `@SpyBean` 으로 확인 — 채택** | 운영 코드가 그대로다. 확인하려는 사실("락을 잡았다", "갱신했다")을 그대로 묻는다 |
| 운영 코드에 갱신 카운터 지표 추가 | 테스트 때문에 운영 표면이 는다. 지금 그 지표를 볼 사람이 없다 |
| 벽시계 단언 유지, 임계값만 조정 | 머신 속도에 묶인 채로 남는다 |

| `AdminQueryScaleTest` | 두지 않는다 — 조회 API 를 검증한다 |

### 하드코딩과 낡은 숫자

- `"DEV5_0"` → `Landmarks.대상팀`, `isGreaterThan(5_000)` → 픽스처에서 유도.
- 낡은 주석 숫자 — `LdapPagingScaleTest:113` 의 "나머지 4,024명", `AdminQueryScaleTest:49` 의 "500명짜리 조직":
  픽스처와 맞지 않는다. **유도할 수 없는 숫자는 주석에서 지운다.** 적어 두면 픽스처가 바뀔 때 또 낡는다.
  (리뷰가 함께 적은 `LdapDeletionGuardScaleTest` 의 "3,879" 는 이미 없다.)

## 6. 검증

- **운영 코드(§2)는 RED 부터.** `DitStrategy` 이스케이프 테스트, `high + 1` 테스트.
- **하네스 수정(§3)은 각자 자기가 잡아야 할 것을 잡는지 확인한다** — 순환 가드는 순환이 든 조직도에서 즉시 던지는지,
  결정성은 정렬 전 코드에서 기대값과 어긋나는지.
- **교차 검증을 붙인 세 클래스는 프로브가 실제로 묻는지** 확인한다(쓴 것을 하나 지워 프로브가 잡는지).
- **머지 전:** `./gradlew cleanTest test` 와 `./gradlew cleanScaleTest scaleTest` 를 둘 다 돌린다. 규모 테스트 소요
  시간을 측정해 §8 에 적는다(교차 검증 3곳 추가로 늘어난다).

## 7. 이 설계가 말할 수 없는 것

- **LDAP 비활성 계정은 여전히 권한을 유지한다.** ⑥ 에서 고친다.
- `DitStrategy` 수정도 ③ 처럼 **임베디드 UnboundID 서버로만** 검증된다. 실제 AD 의 DN 표기는 인증 슬라이드 이후에 확인한다.
- 중복 제거는 **테스트 코드의 구조**를 바꾼다. 규모 테스트가 모두 통과하는 것이 동작이 그대로라는 증거의 전부다.
