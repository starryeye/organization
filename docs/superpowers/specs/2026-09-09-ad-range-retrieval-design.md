# Active Directory 범위 검색 지원 설계

**작성일:** 2026-09-09
**상태:** 구현 완료. **실제 AD 로는 검증하지 못했다** (§5)
**발단:** `2026-09-09-idp-conformance-audit.md` L-1
**바꾼 것:** `RangedAttributeReader`(신규), `GroupOfNamesStrategy`, `LdapTemplates`,
`PagedLdapSearch`, `OrgChartFixture`

---

## 1. 문제

Active Directory 는 다중값 속성 하나에서 한 번에 돌려주는 값의 개수를 `MaxValRange` 정책으로
제한한다. 버전·정책에 따라 1,000 / 1,500 / 5,000 이다.

그 수를 넘으면 **속성 이름 자체를 바꿔서** 돌려준다. MS-ADTS 명세는 이렇게 규정한다:

> 요청에 범위 옵션이 없는데 그 속성의 값이 한 번에 돌려주기에 너무 많으면, 서버는
> **(1) 범위 옵션 없는 속성을 값 없이** 그리고 **(2) 범위 옵션이 붙은 속성을 그 범위의 값과
> 함께** 담아 돌려준다.

```
member                 →  (값 없음)
member;range=0-1499    →  1,500개
```

우리 코드는 `member` 를 정확한 이름으로 읽었다. 그래서 **빈 쪽**을 읽고 끝냈다.

### 왜 심각한가

6,000명짜리 그룹이 **멤버 0명**으로 읽히면, 그 6,000개의 `direct_member` 튜플이 삭제 대상이
된다. 삭제 가드(30%)가 잡을 수도 있지만 전체가 10만이면 6% 라 **그냥 지워진다.**

**그리고 어디에도 오류가 남지 않는다.** 서버는 정상 응답했고 우리는 정상적으로 읽었다고
믿는다. 로그도 메트릭도 조용하다.

### 왜 우리 테스트가 못 잡았나

두 가지가 겹쳤다. 픽스처의 최대 조직이 **500명**으로 한계선의 3분의 1이었고, 임베디드
UnboundID 서버는 **범위 검색을 하지 않는다.**

임베디드 서버가 실제 서버보다 관대했던 **세 번째** 사례다 — 앞서 빈 조직의 `groupOfNames`
스키마 위반, 페이징 쿠키의 커넥션 귀속에서 같은 종류를 겪었다.

## 2. 접근안 비교

다음에 이 자리를 보는 사람이 "더 간단한 길이 있는데" 하고 되돌리지 않도록 적어 둔다.

### 2.1 범위 검색을 이어받는다 — **선택**

명세대로 `member;range=<다음>-*` 로 끝까지 받는다.

- 변경이 **멤버를 읽는 지점 하나**에 갇힌다
- 범위 검색을 안 하는 서버(OpenLDAP, UnboundID)에서는 **동작이 그대로다**

### 2.2 질의를 뒤집는다 — `memberOf` 로 사용자를 찾는다

그룹의 `member` 를 읽는 대신 `(memberOf=<그룹DN>)` 으로 사용자를 검색하면 다중값 속성을
아예 안 읽으므로 범위 문제가 사라진다. **그런데:**

- `memberOf` 는 **primary group 을 포함하지 않는다.** AD 에서 사용자의 기본 그룹(보통
  Domain Users)은 `primaryGroupID` 로만 표현되고 `memberOf` 에 안 나온다. 그 그룹을 쓰는
  조직이 있으면 통째로 비어 보인다 — **고치려던 것과 같은 종류의 조용한 결함이다.**
- `groupOfNames` 전략을 통째로 재구성해야 한다. 그러면 "그룹의 멤버 목록을 읽는다" 라는 이
  전략의 정체성이 사라지고 DIT 전략과 구조가 같아져, 전략을 둘 두는 의미가 옅어진다.
- OpenLDAP 은 `memberOf` 를 기본으로 안 켠다(오버레이 설정이 필요하다). 지금 붙는 서버가
  못 쓰게 된다.

### 2.3 지원하지 않고 한계로만 적는다

AD 를 안 쓸 것이면 유효하다. 그러나 LDAP 원천의 대다수가 AD 이고, 결함의 모양이 **조용한
대량 권한 삭제**라 감수할 수 없다.

## 3. 설계

### 3.1 `RangedAttributeReader`

```java
record Chunk(List<String> values, boolean 완료)

static Chunk 읽는다(Attributes attributes, String 속성명)
static List<String> 전부_읽는다(LdapOperations 한커넥션, String dn, String 속성명)
```

- `읽는다` — 범위 옵션이 붙은 쪽이 **있으면 그쪽을 쓴다.** 범위가 걸린 응답에는 원래 이름의
  속성도 함께 오지만 값이 비어 있기 때문이다. 상한이 `*` 면 마지막 조각이다.
- `전부_읽는다` — 완료까지 이어받는다. 값이 안 늘어나는데 완료 표시도 없으면 멈추고 경고를
  남긴다(서버가 예상 밖으로 동작할 때 무한 루프로 도는 것보다 낫다).

### 3.2 커넥션 하나로 묶는다

명세는 값의 순서를 이렇게만 보장한다:

> 임의지만 **같은 LDAP 커넥션에서는** 일관된다.

조각을 서로 다른 커넥션에서 받으면 어떤 값은 두 번 오고 어떤 값은 아예 안 온다.

**페이징 쿠키와 같은 제약이다.** 그래서 `PagedLdapSearch` 안에 인라인으로 있던 것을
`LdapTemplates.한_커넥션에서` 로 빼서 둘이 같은 것을 쓴다. 같은 성질의 요구가 두 곳에
따로 적혀 있으면 한쪽만 고쳐진다.

**첫 조각은 버리고 범위 0 부터 다시 읽는다.** 그것은 검색을 돌린 다른 커넥션에서 온
것이므로, 이어붙이면 순서 보장이 성립하지 않는다.

### 3.3 조직 검색을 `ContextMapper` 로

재요청하려면 그 엔트리를 **다시 지목**해야 하고, 그러려면 서버가 알려준 진짜 DN 이 필요하다.
기존의 `dnOf()` 재구성은 조직이 검색 베이스 **바로 아래** 있다고 가정하므로 트리가 깊으면
틀린 DN 이 된다.

**`externalId` 는 지금 형태를 유지한다.** 진짜 DN 이 더 정확하지만 저장된 값이 전부 바뀌는
데이터 변경이라 별건이다. 진짜 DN 은 재요청에만 쓴다.

### 3.4 끝까지 못 읽으면 던진다 — 읽은 만큼을 돌려주지 않는다

처음 구현은 포기 지점 네 곳에서 **읽은 만큼을 돌려주고 경고를 남겼다.** 그리고
`GroupOfNamesStrategy` 가 그 결과를 `membersComplete = true` 로 못박았다.

**그것은 고치려던 결함을 오류 경로로 되살린 것이다.** 전체 동기화는 델타를 디렉터리 전체를
놓고 계산한다 — `TupleDiff.between(baseline, target)` 의 `toDelete = baseline − target` 이라
**목표에 없으면 지워진다.** 삭제는 "지우라는 신호" 로 일어나지 않고 **"없으면"** 일어난다.
그래서 멤버를 덜 읽은 것이 그대로 "그 사람들이 빠졌다" 가 되고, 삭제 가드(30%)는 전체가
10만이면 6% 라 안 걸린다. 남는 것은 `log.warn` 한 줄뿐이다.

**그래서 `IncompleteAttributeReadException` 을 던진다.** 그 회차가 `FAILED` 로 끝나고
`FullSyncUseCase` 는 **아무것도 쓰지 않는다.** 이전 상태가 그대로 남고 다음 회차가
재시도한다 — LDAP 은 매일 전체 재계산이므로 그렇게 수렴한다(설계 §1.1).

#### "못 읽음" 과 "진짜 삭제" 는 구분된다 — 짐작이 아니다

이 선택이 성립하는 전제다. 서버가 **프로토콜로** 알려준다:

| 상황 | 응답 | 완료 |
|---|---|---|
| 진짜로 멤버가 지워짐 | `member` (값 0개, range 옵션 없음) | **참** — 삭제가 정상 전파 |
| 1,500개만 보냄 | `member;range=0-`**`1499`** (상한이 숫자) | **거짓** — "더 있다" |
| 마지막 조각 | `member;range=1500-`**`*`** | **참** |

**진짜 삭제는 예외에 걸리지 않는다.** 던지는 네 자리는 전부 "서버가 아직 안 끝났다고
했는데 우리가 끝내지 못한" 경우다. 이 구분을 `RangedAttributeReaderTest` 가 못으로 박아
둔다("진짜로 멤버가 0명인 것과 못 읽은 것을 구분한다").

**구분 못 하는 경우도 있다.** 서버가 거짓말을 하면 — range 옵션 없이 값 0개를 주면서
실제로는 멤버가 있으면 — 어떤 클라이언트도 못 잡는다. 그건 `DeletionGuard` 의 몫이고,
무딘 그물이다.

#### 검토했지만 안 간 길

**그 조직만 얼리고 나머지는 동기화한다** — 못 읽은 조직의 튜플만 baseline 에서 이어받는다
(`target ∪ {baseline 중 그 조직 것}`). 조직 하나 때문에 그날 전체가 밀리지 않는다.
그러나 `DirectorySnapshot` 에 "불완전한 조직" 개념이 새로 생겨 core 까지 배선이 올라가고,
얼어붙은 조직을 알아채기 위한 지표·경보가 따라붙는다. **서버가 명세를 어겼을 때만 밟히는
드문 경로 때문에 core 모델에 상설 개념을 들이는 것은 비싸다**고 보고 접었다. 하루 지연이
실제로 아픈 것으로 드러나면 그때 다시 꺼낸다 — 지금의 예외 지점이 그대로 감지 지점이 된다.

### 3.5 DIT 전략은 손대지 않는다

dn 경로로 소속을 도출하므로 다중값 속성을 읽지 않는다. `groupOfNames` 전략만 해당한다.

## 4. 픽스처 변경

최대 조직을 **500명 → 1,600명**으로 키우고 이름을 바로잡았다.

| | 전 | 후 |
|---|---|---|
| 최대 조직 | 전사공통TF 500명 | **제1공장 1,600명** |
| 직원 | 5,024 | **6,124** |
| 튜플 | 5,541 | **6,641** |

**이름을 바꾼 이유:** "전사공통TF" 는 여러 부서에서 차출돼 **겸직**하는 조직으로 읽히는데,
여기 붙은 직원은 이 조직에만 속한 **전속**이다. 공장·콜센터처럼 하위 조직 없이 직속만 많은
단위가 현실의 이 모양이고, 그것이 `member` 속성에 값을 몰아 범위 검색을 밟는 자리다.

**모두가 멤버인 "전 임직원" 같은 평평한 명단은 이 픽스처에 없다.** 그것은 수천 명을 겸직으로
만들어 랜드마크의 "소속이 하나" 전제와 DIT 의 주소속 선택을 흔든다. AD 범위 검색은 두 모양
다 때리므로 결함 재현에는 전속 모양으로 충분하다.

**1,600 인 이유:** 한계선 1,000·1,500 을 넘긴다. 5,000 까지 넘기려면 직원이 4,500명 더 필요해
전체 테스트가 두 배로 느려진다. **실제 AD 로 검증할 때는 픽스처를 키우는 대신 서버의
`MaxValRange` 를 낮춘다** — 그쪽이 LDAP 정책 한 줄이다.

**하드코딩된 숫자를 픽스처에서 유도하도록 바꿨다.** 이번에 픽스처를 키우면서 `5_541` 하나를
놓쳤고 그것이 엉뚱한 테스트 실패로 나타났다.

## 5. 검증과 그 한계

**실제 AD 로는 검증하지 못했다.** AD 인스턴스가 없고 임베디드 서버는 이 동작을 흉내내지
않는다.

`RangedAttributeReaderTest` 가 **응답을 합성해서** 검증한다 — 명세를 그대로 옮긴 모양으로,
특히 "범위가 걸리면 원래 이름의 속성이 값 없이 함께 온다" 를 모든 케이스에 넣는다.

| | |
|---|---|
| 범위 응답 **해석** | 검증함 |
| **이어받는 반복** (6,000명을 1,500씩 네 조각) | 검증함 |
| 경계·대소문자·다른 속성 간섭 | 검증함 |
| **못 읽으면 던진다** (포기 지점 네 곳) | 검증함 |
| **진짜 삭제는 안 던진다** — 삭제가 정상 전파 | 검증함 |
| 범위를 안 쓰는 서버에서 동작이 안 바뀜 | 규모 E2E 회귀로 확인 |
| **실제 AD 가 정말 이렇게 동작하는가** | **못 함 — 문서만 믿는다** |

즉 **"MS-ADTS 명세대로라면 맞게 동작한다"** 까지가 이 작업이 말할 수 있는 전부다.

> 테스트 하나를 고친 기록: "이 결함의 핵심" 이라 이름 붙인 테스트가 원래 버그로 되돌려도
> 통과했다. `BasicAttributes` 의 순회 순서가 임의라 빈 속성과 범위 속성 중 어느 것을 먼저
> 만나는지가 실행마다 달랐기 때문이다. 두 순서를 모두 만들어 검증하도록 고쳤다.

---

## 6. 남은 것

- **실제 AD 연동 검증** — 인증 슬라이드가 선행 조건이다(공개 엔드포인트에 토큰 없이 노출할
  수 없다). 그때 `MaxValRange` 를 낮춰 범위 검색을 강제하고 확인한다.
- **`externalId` 를 진짜 DN 으로** — 정확하지만 저장값이 전부 바뀌는 데이터 변경이라 별건.
- **`primaryGroupID` 로만 표현되는 소속** — `member` 에도 `memberOf` 에도 안 나온다.
  2.2 를 검토하며 알게 된 것으로, 지금 전략은 그 소속을 못 본다. AD 를 붙일 때 실제로
  문제가 되는지 확인할 것.

## 7. 절차에 대한 기록

이 작업은 **바운디드로 분류해 시작했다가 실제로는 그 범위를 넘었다.** 운영 코드 5파일,
공용 픽스처 변경이 테스트 10파일로 파급, 문서 2건. 브레인스토밍 스킬의 규칙대로라면
파급이 드러난 시점에 멈추고 아키텍처 경로로 올렸어야 했다.

되돌려 다시 하지 않기로 한 근거: 접근안(§2)을 따져 보면 **절차를 밟았어도 설계가 달라지지
않는다.** 대신 이 문서를 뒤늦게 써서 기록을 채운다.

**남은 항목(인증, SCIM 목록·필터 조회, 도메인 모델의 `name` 칸)은 전부 아키텍처 경로다.**
바운디드로 분류할 여지가 없으므로 처음부터 스펙을 쓰고 시작한다.
