# 작업 견고성 — 리스 갱신의 다시 시도(S13), SCIM 재적재의 강한 열거 보강(S17)

- 날짜: 2026-10-13
- 근거: 전체 점검(`docs/superpowers/specs/2026-09-28-full-audit.md`) 의 사소 항목 중 미룬 것 — S13, S15, S17, S18, S26.
- 전제:
  - 실제 규모는 직원 10만 명 이상이다.
  - 운영 배포 전이라 저장 형식을 바꿔도 이관 코드를 만들지 않는다(이번에는 저장 형식이 바뀌지 않는다).
  - 배포 하나는 LDAP 아니면 SCIM 이다.
  - 표준이 정한 신호만 받고, 나머지는 한 규칙으로 다룬다.

## 1. 문제

### 1.1 S13 — 리스 갱신이 한 번 실패하면 작업 전체가 멈춘다

- 리스 유지기(`LeaseKeeper`)는 갱신 주기(기본 10초)마다 리스를 갱신한다. 리스 TTL 은 30초다.
- 갱신이 오류로 끝나면 그 자리에서 일을 취소하고 "리스를 잃었다" 로 끝낸다.
  - 남이 락을 가져간 것(토큰 조건 실패)인지, 스로틀·네트워크 오류인지 가리지 않는다.
  - 그래서 리스가 20초 남아 있어도 일시 오류 한 번에 멈춘다.
- 이 유지기를 함께 쓰는 곳:
  - SCIM 재적재: 장부를 반쯤 채운 채 FAILED 가 되고, 락을 반납한다.
  - LDAP 동기화·재적재(`SyncJobs`).
  - 갱신 주기를 넘기는 큰 SCIM 쓰기. 예를 들어 10만 명 조직 삭제는 27초 걸린다. META 를 맨 끝에 쓰므로 IdP 의 재시도로 회복되지만 그동안 503 이다.

### 1.2 S17 — SCIM 재적재가 최종 일관성 GSI 로 대상을 훑는다

- `tuples` 모드는 `loadAll` 로 조직도를 읽는다.
  - 직원·조직 아이디는 GSI1 로 훑는다(최종 일관성).
  - 직원 본문은 BatchGet 으로, 조직은 파티션으로 읽는다. 둘 다 강한 일관성이다.
- 락을 잡기 직전(약 1초 안)에 커밋된 SCIM 쓰기가 아직 GSI1 에 없으면 그 대상이 열거에서 빠진다. 결과는 점검 문서가 적은 것("튜플을 안 쓴다")보다 아프다.
  - 막 만든 직원 kim 이 조직 DEV 의 멤버라고 하자. DEV 파티션(강한 일관성)에는 kim 이 멤버로 보이지만 직원 목록에는 없다.
  - 그러면 `TupleMapper` 가 kim 을 "스냅샷에 없어 건너뛴다". kim 의 `direct_member` 줄은 있어야 할 줄이 아니게 된다.
  - 장부를 훑을 때 그 줄이 "지울 줄" 로 판정돼 **지워진다**. kim 은 다음 쓰기가 닿을 때까지 권한이 없다.
  - 막 만든 조직도 같다. 그 조직의 멤버 줄과 상위 조직 연결이 지워진다.
- `wipe` 는 `replaceWith(빈 조직도)` 가 GSI1 로 대상을 훑으므로, 빠진 대상이 지워지지 않고 남는다. 튜플은 장부를 훑어 지우므로 권한은 없다.
- LDAP 앱은 해당이 없다. 동시 쓰기가 없어 이전 회차가 오래전에 끝났고, GSI 는 이미 맞춰져 있다(`replaceWith` 의 전제).

### 1.3 S15·S18·S26

- **S15.** 락 만료를 각 서버의 시계로 판단한다. 시계가 30초 넘게 어긋나면 남의 락을 가져간다. 리스 방식 락의 표준 전제(시계 어긋남이 작음)다.
- **S18.** 스냅샷 포인터와 스냅샷 Query 가 최종 일관성이라는 지적이었다. 지금은 둘 다 강한 일관성으로 읽는다(`DynamoDbTupleSnapshotRepository`). 이미 해소됐다.
- **S26.** 만료 스냅샷 정리 잡의 설명이 "0건" 이라 실제(TTL 보다 먼저 지움)와 어긋난다는 지적이었다.
  - ①(C1)에서 스냅샷이 테이블 TTL 을 쓰지 않게 바뀌었다. 정리 잡은 이제 유일한 삭제 경로이고, 주석도 그렇게 말한다.
  - 이미 해소됐다.

## 3. S13 — 리스 갱신의 다시 시도

### 3.1 규칙

- **즉시 멈춤.** 갱신이 `LockUnavailableException` 으로 끝나면 지금처럼 바로 일을 취소하고 "리스를 잃었다" 로 끝낸다.
  - 이 예외는 저장소가 토큰 조건 실패(남이 가져감)를 옮긴 것이다(`DynamoDbMutationLock.renew`).
  - "잃었다" 를 아는 표준 신호는 이것 하나다.
- **다시 시도.** 그 밖의 결과는 잃었다고 단정하지 않는다. 스로틀, 네트워크, SDK 오류, 한 번 시도의 시간 초과가 여기에 든다.
  - 짧게 쉬며 다시 갱신한다. 쉬는 시간은 갱신 주기의 1/50 에서 시작해 두 배씩 늘고, 최대 주기의 1/5 다(기본 10초면 200ms~2초). 지터는 없다.
  - 한 번 시도는 갱신 주기의 절반(기본 5초) 안에 답해야 한다. 매달린 연결 하나가 한도를 다 쓰지 않게 하기 위해서다.
- **한도.** 마지막으로 갱신에 성공한 때부터 갱신 주기 두 번(기본 20초) 안에 성공하지 못하면, 잃은 것으로 보고 멈춘다. 처음에는 일을 시작한 때부터 잰다.
  - 지금의 한도("주기 안에 답하지 않으면 잃은 것 — 마지막 성공 + 2×주기")와 같다. 그래서 리스 TTL(30초)보다 먼저 멈춘다는 안전 여유는 줄지 않는다.
  - 바뀌는 것은 그 한도 안에서 한 번이 아니라 여러 번 시도한다는 것뿐이다.
- **시간.** Reactor 스케줄러의 시계로 잰다. 가상 시간 테스트가 그대로 된다.

### 3.2 알림

- 다시 시도할 때마다 WARN 로그를 한 줄 남긴다. 무슨 오류였고, 한도까지 얼마 남았는지 적는다.
- 끝내 잃으면 지금처럼 ERROR 로그와 `LockObserver.leaseLost`(지표)를 남긴다.

### 3.3 범위

- 리스 유지기 하나만 고친다. 그래서 SCIM 재적재, LDAP 동기화·재적재, 갱신 주기를 넘기는 큰 SCIM 쓰기가 함께 낫는다.
- **SCIM 쓰기 한 건의 리스 확인은 그대로다.** 쓰기 직전·커밋 직전에 리스를 확인하는데(`IncrementalSyncUseCase.리스를_확인한다`), 일시 오류면 지금처럼 503 이고 IdP 가 다시 보낸다.
  - 이것이 표준 신호이고, 요청 하나라 다시 보내는 비용이 작다.

## 4. S17 — SCIM 재적재가 장부로 열거를 보강한다

### 4.1 원칙

- **재적재는 현재상태에 있는 대상의 권한을 지우지 않는다.**
- GSI 열거가 빠뜨린 대상이 있으면 장부가 알려 준다. 장부에 나온 대상만 본 테이블에서 강한 일관성으로 다시 확인한다.
- 장부에 줄이 하나도 없는 대상은 권한이 없다. 그래서 빠져도 권한은 바뀌지 않는다(§7).

### 4.2 튜플의 대상

- core 에 튜플에서 대상 아이디를 꺼내는 도우미를 하나 둔다.
  - user 쪽: `user:kim` 은 직원 kim, `group:TEAM` 은 조직 TEAM.
  - object 쪽: `group:DEV` 는 조직 DEV.
  - `#관계` 가 붙은 user 쪽과 다른 종류는 대상이 아니다.
- 변경 이력의 `AuditChanges` 가 user 쪽 대상을 꺼내는 코드도 이 도우미를 쓴다.

### 4.3 `tuples` 모드

장부 맞추기(`TupleReconciler`)에 "지우기 전에 있어야 할 줄을 다시 정하는" 자리를 더한다. LDAP 장부 맞추기(`LedgerAlignment`)는 이 자리를 쓰지 않는다.

1. 지금처럼 GSI 로 읽은 조직도에서 있어야 할 줄(D)을 정하고, D 를 쓰고, 장부를 훑어 지울 후보를 가른다.
2. 지울 후보의 대상 중 조직도에 없는 것만 모은다. 평소에는 0개다.
3. 모은 대상을 본 테이블에서 강한 일관성으로 다시 읽는다.
   - 직원은 `findUsers`(BatchGet 100개씩)로 읽는다.
   - 조직은 `findGroup`(파티션 읽기)으로 읽는다.
   - 다시 읽은 조직의 멤버 중 조직도에 없는 직원도 함께 읽는다. 장부에 아직 줄이 없는 새 멤버까지 잡기 위해서다.
4. 찾은 것을 조직도에 넣고 있어야 할 줄을 다시 계산한다(D').
   - D' 에서 D 에 없던 줄을 쓴다.
   - 지울 후보에서 D' 에 있는 줄을 뺀다.
   - 보류 목록(순환 때문에 버린 연결)도 다시 계산한 조직도로 정한다.
5. 그다음 지금처럼 "빈 조직도면 멈춘다" 확인을 거쳐 지운다. 스냅샷에는 장부에 실제로 있다고 볼 줄을 담는다.

- 다시 읽어도 없는 대상(찌꺼기 줄의 주인)은 그대로 지울 후보다.
- 이력(변경 이력 설계 2026-10-10 §3.5)은 지금처럼 지운 줄만 남긴다. 다시 계산해 쓴 줄은 재적재가 쓴 줄이라 남기지 않는다.

### 4.4 `wipe`

1. 지금처럼 장부를 비운 뒤 `replaceWith(빈 조직도)` 로 조직도를 지운다.
2. 지운 튜플의 대상 중 방금 지운 직원·조직에 없는 것을 모은다.
3. 그것을 본 테이블에서 강한 일관성으로 다시 확인한다(`findUsers`, `findGroup`).
4. 아직 있으면 지운다. 순서는 `replaceWith` 와 같이 조직 먼저(`deleteGroup`, 그때의 멤버로), 그다음 직원(`deleteUser`)이다.
5. 변경 이력에도 삭제로 남긴다. 직원은 이전 값, 조직은 이름표와 그때의 멤버를 담는다.

### 4.5 비용

- 평소에는 추가 읽기가 0이다. 지울 후보의 대상이 모두 조직도에 있기 때문이다.
- 장부에 찌꺼기 줄이 있으면 그 주인 수만큼 강한 읽기가 는다. BatchGet 100개씩, 조직은 하나씩이다.
- `wipe` 에서 확인할 대상도 평소 0개다.

## 7. 이 설계가 말할 수 없는 것

- **장부에 줄이 없는 새 대상은 여전히 빠질 수 있다.** 비활성이거나 어느 조직에도 없는 직원, 멤버 없는 조직이다.
  - 권한이 없으므로 `tuples` 결과는 바뀌지 않는다.
  - `wipe` 뒤에는 그런 직원·조직이 남을 수 있다. IdP 가 다시 보낼 때 같은 `userName`·`externalId` 로 찾아 이어 붙인다.
- **GSI 지연은 DynamoDB Local 로 재현할 수 없다.** 로컬은 GSI 가 즉시 반영된다. 그래서 검증은 core 의 가짜 저장소(열거에서만 숨김)로 한다.
- **SCIM 쓰기 한 건의 리스 확인은 그대로 503 이다**(§3.3).
- **다시 시도도 한도 안에서만이다.** 스로틀이 20초 넘게 이어지면 지금처럼 멈춘다. 멈춘 뒤의 회복은 전과 같다: 재적재는 다시 실행하고, LDAP 은 "기록 중" 표시로 다음 회차가 장부를 훑어 맞춘다.
- **S15** 는 코드로 막지 않는다. 서버 시계를 NTP 로 맞춘다는 운영 전제다.

## 8. 왜 다른 길을 안 갔나

- **락을 잡은 뒤 잠깐(약 2초) 기다렸다가 훑기.** 코드가 몇 줄이라 가장 단순하다. 그러나 보장이 아니다. GSI 전파는 평소 1초 안이지만 부하가 크면 더 걸릴 수 있다. 재적재도 늘 그만큼 느려진다.
- **기다림과 확인을 둘 다.** 늦을 때는 확인이 잡으므로 기다림이 보태는 것이 없다. 느려지기만 한다.
- **본 테이블 Scan(강한 일관성)으로 열거.** 직원·조직 META 외에 멤버 줄, 소속 줄, 스냅샷 묶음, 변경 이력까지 테이블 전체를 읽는다. 10만 명 규모에서 재적재마다 그렇게 읽을 까닭이 없다(처음 설계 2026-08-14 §6.1 이 열거에 Scan 을 쓰지 않기로 정했다).
- **리스 갱신에서 일시 오류만 골라 다시 시도.** 어댑터의 일시 장애 인식기를 core 의 리스 유지기로 들여와야 한다. 분류에서 빠진 오류는 지금처럼 일시 오류 한 번에 멈춘다. "잃었다" 를 아는 신호는 조건 실패 하나뿐이므로, 그것만 받고 나머지는 한 규칙(한도 안 다시 시도)으로 다루는 것이 표준대로다.
- **SCIM 쓰기 한 건의 리스 확인도 다시 시도.** 그동안 IdP 는 기다린다. 503 과 다시 보내기가 표준 신호이고 요청 하나라 비용이 작다.
