# GSI1 쏠림 — 바뀐 것만 쓴다 — 설계

> 브랜치 `gsi1-hot-partition` (origin/main `735d921` 에서 분기).
> 발단: S-1 설계 [`2026-09-25-scim-list-filter-design.md`](2026-09-25-scim-list-filter-design.md) §12 "범위 밖 — GSI1 쏠림".

## 1. 문제 — 아무도 안 바뀐 날에도 직원 10만 건이 GSI1 한 파티션키로 쓰인다

GSI1 은 직원 전원을 파티션키 `USER_INDEX` 하나에, 조직 전원을 `GROUP_INDEX` 하나에 모은다. 파티션키 하나의 쓰기
처리량에는 한계가 있고(초당 약 1,000건), GSI 쓰기가 막히면 본 테이블 쓰기까지 막힌다(AWS 문서, "Provisioned throughput
considerations for Global Secondary Indexes"). 실제 운영 규모는 직원 10만 명 이상이다.

따라가 보면 **쏠림의 원인은 키 구조가 아니라 쓰기 경로다.**

1. LDAP 전체 동기화는 **변경이 없어도 매 회차** `state.replaceWith(directory)` 를 부른다(`FullSyncUseCase` 의 변경 없음
   경로와 커밋 경로 둘 다). `replaceWith` 는 직원 전원에 `saveUser`, 조직 전원에 `saveGroup` 을 부른다.
2. 두 메서드는 META 에 `updatedAt = 지금` 을 넣어 **무조건** PutItem 한다. `updatedAt` 을 읽는 곳은 저장소 밖에 한 군데도 없다.
3. GSI1 은 `ALL` 프로젝션이라 `updatedAt` 도 담는다. AWS 문서의 규칙 — "인덱스 키나 인덱스에 담긴 속성이 바뀌지 않으면 인덱스
   쓰기는 없다", "담긴 속성만 바뀌어도 인덱스 쓰기 한 번" — 에 따라 **매 회차 10만 건의 GSI1 쓰기가 `USER_INDEX` 로 몰린다.**
   GSI2(`INCLUDE userName, active`)와 GSI3(`KEYS_ONLY`)는 `updatedAt` 을 담지 않아 변경이 없으면 쓰지 않는다.

하루에 실제로 바뀌는 직원은 입사·퇴사·이동 정도다. 키 구조가 문제가 되는 것은 대량으로 바뀌는 순간(최초 적재, 대규모 개편)뿐이다.

**`updatedAt` 의 뜻도 어긋나 있다.** 첫 설계(`2026-08-14-organization-sync-design.md`)의 속성 표에 들어왔지만 쓰임은 적혀 있지
않았고, 매 동기화가 덮어써 실제로는 "마지막 변경 시각" 이 아니라 "마지막 전체 동기화 시각" 이다. 같은 이유로 멤버 줄의
`addedAt` 은 덮어쓰지 않게 막아 두었는데(`saveGroup` 주석), META 의 `updatedAt` 은 빠졌다.

## 2. 결정 — 사용자와 정한 것 (2026-09-25)

| 주제 | 결정 | 버린 안 (§8 에 이유) |
|---|---|---|
| 접근 | **바뀐 것만 쓴다** — 저장소가 직원·조직 META 를 저장된 것과 비교해 다를 때만 쓴다 | GSI1 쓰기 샤딩, 둘 다 |
| `updatedAt` | **진짜 변경 시각** — 새로 생기거나 바뀐 때만 넣는다 | 빼기, 지금 SCIM 응답으로 내보내기 |

## 3. 규칙

**저장소는 바뀐 직원·조직 META 만 쓰고, 그때만 `updatedAt` 을 넣는다.**

- **"바뀌었다" 는 쓰려는 아이템 전체를 저장된 아이템과 비교해 정한다** — `updatedAt` 을 뺀 모든 속성, 인덱스 키(GSI1PK·GSI1SK)
  포함. 도메인 필드만 비교하면 키 규칙이 바뀌었을 때(S-1 의 소문자 키처럼) 값은 같은데 키가 옛 모양으로 남는다. 아이템 전체를
  비교하면 파생 속성이 달라져도 다시 쓰인다.
- 저장된 것이 없으면 새로 생긴 것이다 — 쓰고 `updatedAt` 을 넣는다.
- 같으면 **PutItem 을 하지 않는다.** 본 테이블 쓰기도 GSI 쓰기도 없고 `updatedAt` 도 그대로다.
- **조직의 변경은 META 의 변경 또는 멤버 구성의 변경이다.** SCIM 의 Group 리소스는 `members` 를 담으므로 멤버만 바뀌어도 조직은
  바뀐 것이다. 멤버 구성에 차이가 있으면 META 도 다시 쓰고 `updatedAt` 을 넣는다.
- **직원의 소속 변경은 직원의 변경이 아니다.** 우리는 User 의 `groups` 를 내보내지 않는다.

## 4. 두 쓰기 경로

| 경로 | 지금 | 바뀐 뒤 |
|---|---|---|
| `saveUser`·`saveGroup` 을 직접 부르는 경로 (SCIM 요청 하나 — 쓰기 락 안) | 무조건 PutItem | 저장된 META 를 **강한 일관성**으로 한 건 읽어 비교 → 다를 때만 PutItem. 요청당 GetItem 1번이 더해진다 |
| `replaceWith` (LDAP 전체 동기화·재적재) | GSI1 을 훑어 **id 만** 뽑아 삭제를 판단하고, 전원에 PutItem | **같은 조회에서 아이템 전체를** 받아(GSI1 은 `ALL` 이라 더 읽지 않는다) 비교 → 새로 생기거나 바뀐 것만 PutItem. 조직 멤버 줄은 지금처럼 차이만 쓴다 |

**`replaceWith` 가 GSI1(최종 일관성)을 비교 기준으로 쓰는 전제.** LDAP 앱에서 직원·조직을 쓰는 것은 이 동기화 자신뿐이고 이전
회차는 오래전에 끝났다 — 인덱스는 이미 맞춰져 있다. 인덱스가 늦어 생길 수 있는 일은 두 방향이다.

- "다르다" 로 잘못 보고 한 번 더 쓴다 — 무해하다.
- "같다" 로 잘못 보고 안 쓴다 — GSI1 에 아직 반영되지 않은 쓰기가 있어야 생긴다. `replaceWith` 에 내용을 넣어 부르는 것은
  LDAP 의 전체 동기화(`FullSyncUseCase`)와 재적재(`RebuildUseCase`)뿐이고, LDAP 앱에는 그와 동시에 직원·조직을 쓰는 경로가
  없다. SCIM 재적재(`ScimRebuildUseCase`)는 `replaceWith` 를 빈 스냅샷(전부 지우기)으로만 불러 비교할 것이 없다.

## 5. 효과 (10만 명, 하루 변경 100명 가정)

| | 지금 | 바뀐 뒤 |
|---|---|---|
| 매일 동기화의 본 테이블 PutItem | 약 10만 + 조직 수 | 약 100 + 멤버가 바뀐 조직 수 |
| 매일 GSI1 쓰기(`USER_INDEX` 한 곳) | 약 10만 | 약 100 |
| SCIM 요청 하나 | PutItem 1 | GetItem 1 + (바뀌었으면) PutItem 1 |
| 최초 적재 | 10만 | 10만 — 한 번. 파티션키당 한계로 100초 이상 걸릴 수 있고, 한계를 넘는 쓰기는 AWS SDK 가 재시도한다 |

## 6. 검증

테스트 규칙은 기존과 같다 — Lombok, AssertJ, BDD(given/when/then), 한글 `@DisplayName`.

1. **저장소 단위 (storage-dynamodb, DynamoDB Local, 시각을 조종할 수 있는 시계)**
   - 같은 직원을 두 번 저장하면 `updatedAt` 은 첫 시각 그대로이고 두 번째 PutItem 은 없다.
   - 속성이 바뀌면 `updatedAt` 이 그 시각이 된다.
   - 조직: META·멤버가 같으면 그대로, 멤버만 바뀌어도 `updatedAt` 이 갱신된다.
   - `replaceWith` 에 같은 스냅샷을 다시 넣으면 PutItem 0번, 일부만 바꾸면 그 수만큼.
   - 키 규칙이 다른 옛 아이템(GSI1 정렬키가 원문 대소문자)은 값이 같아도 다시 쓰여 키가 고쳐진다.
   - 요청 수는 클라이언트를 감싸 세는 계측(S-1 의 `DynamoDbReadCounter` 와 같은 방식)으로 센다.
2. **규모 (`@ScaleTest`, 저장소 수준)** — 직원 10만 명을 `replaceWith` 로 적재한 뒤, 같은 스냅샷으로 한 번 더 돌리면 PutItem
   0번, 100명을 바꾸면 PutItem 100번. 변경이 저장소 한 곳에 있어 저장소 수준에서 본다 — 10만 명 LDAP 서버를 띄우는 것은 무겁기만
   하고 더 증명하는 것이 없다.
3. **기존 테스트** — LDAP 5천 명 규모 테스트와 E2E 가 그대로 통과한다.

## 7. 결과 (구현 후 기록)

규모 테스트의 PutItem 수와 소요 시간, 머지 전 `test`·`scaleTest` 시간을 구현이 끝나면 여기에 적는다.

## 8. 왜 다른 길을 안 갔나

**GSI1 쓰기 샤딩(`USER_INDEX#00~15`).** 쓰기를 16곳으로 나누지만, GSI1 을 읽는 모든 곳 — admin 접두사 검색과 커서, SCIM
필터·정렬 목록·책갈피·COUNT·건너뛰기, 전체 열거 — 이 16번 묻고 순서대로 합쳐야 한다. S-1 의 책갈피도 16조각이 된다. 매일의
쏠림은 "바뀐 것만 쓰기" 로 원인에서 사라지므로, 샤딩이 더 해 주는 것은 최초 적재·대규모 개편이라는 드문 순간의 속도뿐이다.

**둘 다.** 위 복잡도를 그대로 진다.

**`updatedAt` 빼기.** 가장 단순하지만, "바뀐 것만 쓰기" 를 하면 이 값을 진짜 변경 시각으로 만드는 비용이 거의 없다. SCIM 의
`meta.lastModified` 로 내보낼 수 있는 값이 된다(내보내기는 범위 밖).

**조건부 쓰기(ConditionExpression 으로 "다르면 쓴다").** 추가 GetItem 없이 한 번에 끝나지만, 속성이 없을 수 있는 여러 칸을
"하나라도 다르면" 으로 표현하는 식이 길고 틀리기 쉽다. 조건 실패는 본 테이블 쓰기 용량도 쓴다. 전체 동기화에서는 어차피 GSI1 을
훑으니 비교가 공짜고, SCIM 요청 하나의 GetItem 은 싸다.

## 9. 이 설계가 말할 수 없는 것

- **DynamoDB Local 은 GSI 쓰기 용량을 보여 주지 않는다.** 테스트가 증명하는 것은 "PutItem 이 일어나지 않는다" 까지다. "그래서
  GSI 쓰기도 없다" 는 AWS 문서의 규칙에 기댄다. 실제 AWS 에서의 파티션키당 한계도 재현하지 못한다.
- **`replaceWith` 의 비교는 최종 일관성 인덱스를 기준으로 한다**(§4 의 전제).
- **최초 적재와 대규모 개편은 여전히 `USER_INDEX` 한 곳으로 몰린다.** 느려질 뿐 실패하지 않는다(SDK 재시도).

## 10. 범위 밖 (백로그에 올림)

- **튜플 스냅샷의 쏠림** — 변경이 있는 동기화마다 튜플 전체(10만+ 건)를 새 `SNAPSHOT#id` 한 파티션키에 쓴다. 본 테이블이라
  DynamoDB 가 정렬키 범위로 자동 분할해 주지만 같은 부류의 대량 쓰기다.
- **`loadAll` 의 직원 한 명당 GetItem** — 스냅샷 보관(`SnapshotArchiveUseCase`)과 SCIM 재적재가 쓰고, 10만 명이면 10만 번 읽는다.
- **`updatedAt` 내보내기** — SCIM `meta.lastModified`/`created`.
