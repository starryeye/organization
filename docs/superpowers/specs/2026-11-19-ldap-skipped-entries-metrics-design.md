# 건너뛴 엔트리 지표와 입구의 길이 검사 설계 (2026-11-19)

온보딩 13 의 두 남김을 함께 닫는다 — §4.7 "건너뛴 엔트리는 로그로만 보인다"(설계 2026-10-05 §12)와 §4.1 "긴 DN·식별 값은 미리 막지 않는다"(입구의 id 길이 검사, 설계 2026-09-30 §12).
DC 넘김 설계(2026-11-14) §9.5 가 남긴 "빈 호스트 주소 `ldap://:389` 가 기동 검사를 지난다" 도 같은 connector-ldap 이라 함께 고친다.
사용자 결정: "추천대로"(2026-11-19), 설계 요지 "진행"(2026-11-19) — 아래 결정은 모두 그 추천이다.

## 1. 문제

- **건너뛴 엔트리가 경보에 잡히지 않는다.** 자리를 정할 수 없는 엔트리는 빼고 계속한다(설계 2026-10-05 §3.4, `SkippedEntries`). 사유는 넷이다 —
  식별 속성 없음, 아이디 겹침, 부모 조직 없음(DIT), 대조되지 않은 `member` 값(groupOfNames). 검색마다 사유별 건수와 예시를 **경고 한 줄**로 남길 뿐이다.
  - 빠진 직원은 그 회차에 없는 것과 같아 권한이 조용히 사라진다. 빠짐이 30% 이하이고 5,000줄 이하면 삭제 가드도 막지 않는다. 첫 적재에서는 경고 한 줄이 유일한 신호다(13 §3.7).
  - 지금 할 수 있는 것은 로그 수집기에서 그 문장을 세는 것뿐이다.
- **긴 값 하나가 매 회차 뒤 단계를 막는다.** LDAP 에서 온 id 와 DN 의 길이는 쓰기 전에 보지 않는다(13 §4.1, 04 "막지 않는 것").
  - id 가 OpenFGA 튜플 칸의 한도를 넘으면 그 줄이 영구히 거절된다. [앞 단계 실패 규칙](../../onboarding/02-용어집.md#앞-단계-실패-규칙) 때문에 그 뒤 단계의 부여가 데이터를 고칠 때까지 매 회차 멈춘다.
    첫 적재라면 하위 조직 연결 쓰기 전부, 곧 롤업 전체다(13 §3.6). 회차는 매번 `PARTIAL` 인데 `sync.last.success` 는 `PARTIAL` 도 세므로 신선도 경보가 울리지 않는다.
  - id·DN 이 DynamoDB 키 한도를 넘으면 그 아이템 쓰기가 거절되어 고칠 때까지 매 회차 현재상태 교체가 실패한다.
  - 기본 식별 속성(`entryUUID`, `objectGUID`)은 36자라 해당하지 않는다. 이름 기반 속성(`uid`·`cn`·`ou`·사번 등)을 식별 속성으로 쓴 배포의 문제다.
- **한도는 칸마다 다르다.** OpenFGA 튜플의 `user` 칸은 512**바이트**(실제 OpenFGA 로 확인, 설계 2026-10-17 §7), `object` 칸은 정규식 `^[^\s]{2,256}$` 로 256**자**다
  (openfga/api `openfga/v1/openfga.proto` 의 `TupleKey`·`TupleKeyWithoutCondition` 검증 규칙, 2026-11-19 에 읽음). 이 서버의 튜플에서 직원 id 는 `user:<id>` 로 `user` 칸에만,
  조직 id 는 `group:<id>` 로 `object` 칸(두 튜플 모두)과 `user` 칸(`child` 의 하위)에 들어간다. 그러므로 **조직 id 의 한도가 직원 id 보다 좁다** — `object` 칸에서 250자다.
  DynamoDB 는 정렬키 1024바이트(멤버 줄·소속 줄), 파티션키 2048바이트(`USER#<id>`, GSI3 의 `externalId`)다(04 §6).
- **빈 호스트.** 기동 검사(설계 2026-11-14 F4)가 권한부를 직접 보는데(밑줄 든 호스트 때문에 `getHost()` 를 쓰지 않는다), `ldap://:389` 는 권한부 `:389` 가 비어 있지 않아 지난다.
  JNDI 는 빈 호스트를 `localhost` 로 읽는다 — 설정 실수가 기동 때가 아니라 첫 회차의 접속 실패나 엉뚱한 서버로 드러난다.

## 2. 결정

| # | 결정 | 이유 |
|---|---|---|
| S1 | **한도를 넘는 엔트리는 새 사유 `한도_넘음` 으로 건너뛴다.** 다른 사유와 같은 규칙이다 — 빼고 계속하되, 받은 것이 있는데 하나도 남지 않으면 멈춘다(`아무도_남지_않으면_멈춘다`). 경고 한 줄에도 같은 모양으로 실린다 | 자리를 정할 수 없는 엔트리다 — 쓰면 거절될 것을 알고 있다. 회차 전체를 막던 한 줄이 그 한 사람(조직)만 빠지는 일로 줄고, S5 의 지표에 함께 잡힌다 |
| S2 | **한도.** 모두 UTF-8 바이트다. 직원 id **500**(`KeyValueLimits.MAX_MEMBER_ID_BYTES` — SCIM 이 넣는 멤버 id 에 쓰는 같은 상수), 조직 id **250**(새 상수 `KeyValueLimits.MAX_GROUP_ID_BYTES`), DN **1024**(`KeyValueLimits.MAX_INDEXED_BYTES` — SCIM 이 `externalId` 에 쓰는 같은 상수). id 는 **정규화한 뒤**의 값, DN 은 저장될 **절대 DN**(`externalId`)을 잰다. 같으면 통과, 넘으면 건너뛴다 | 쓰기 전에 잴 것은 실제로 쓰일 값이다. 한도는 그 값이 들어가는 모든 자리 가운데 가장 좁은 곳에서 온다. 직원 id: `user` 칸 507바이트, 멤버 줄 정렬키 1012바이트 → SCIM 과 같이 500. 조직 id: `object` 칸 250자, `user` 칸 506바이트 → 바이트로 250 이면 둘 다 지킨다(1자는 1바이트 이상). DN: GSI3 파티션키 2048바이트지만 같은 `externalId` 를 SCIM 이 1024 로 막는다 — 한 값에 한 한도. 한도는 `KeyValueLimits` 한 곳에 둔다 |
| S3 | **판정은 매퍼에서, 식별 값을 정규화한 직후에 한다.** 식별 속성이 없을 때처럼 나머지 속성(계정 상태, `primaryGroupID`·`objectSid`, 범위가 잘린 `member`)은 읽지 않는다. 순서는 식별 속성 없음 → 한도 넘음 → 겹침이다. id 를 먼저, 그다음 DN 을 재고 먼저 넘은 하나를 적는다 | 건너뛸 엔트리의 다른 값이 표준 밖이라고 회차가 실패하면 안 된다 — 식별 속성 없는 엔트리가 이미 그렇게 한다(05 §3.10). 한도를 넘은 id 는 겹침 색인(`DuplicateIdGuard`)에 들어가지 않는다 — 넣으면 같은 id 의 짧은 쪽은 없으니 해가 없지만, 쓰지 않을 값을 색인에 둘 까닭이 없다 |
| S4 | **예시 문구.** id 가 넘으면 `dn='<DN>'(id 612바이트, 한도 500)`, DN 이 넘으면 `dn='<DN 앞 100자>…'(DN 1100바이트, 한도 1024)`. 사유의 설명은 "값이 저장 한도를 넘음" | 운영자가 어느 값을 얼마나 줄일지 문구로 안다. 넘은 DN 을 그대로 실으면 예시 다섯 개로 경고 한 줄이 5KB 를 넘는다 — 앞부분이면 엔트리를 찾기에 충분하다 |
| S5 | **건너뛴 수를 관찰자로 알린다.** connector-ldap 에 공개 관찰자 인터페이스(검색 종류·사유·건수)와 `NOOP` 를 둔다. `SkippedEntries` 가 경고 한 줄을 남기는 그 자리에서, 건수가 있는 사유마다 한 번 부른다. 관찰자가 던지면 WARN 한 줄을 남기고 삼킨다 — 읽기는 계속된다 | 지표의 뜻이 경고 한 줄과 같다 — "경고에 N건이면 지표가 N 오른다". connector 가 Micrometer 를 모르게 하는 것은 core 의 관찰자들(`RevocationObserver`·`UnsourcedGrantObserver`)과 같은 이유, 같은 모양이다. 지표 때문에 회차가 실패하면 안 된다(같은 관례) |
| S6 | **app-ldap 의 Micrometer 구현.** 카운터 `sync.entries.skipped`, 태그 `search`(`user`·`group`·`member`)와 `reason`(`missing_id`·`duplicate_id`·`over_limit`·`parent_not_found`·`unmatched_member`). 일어날 수 있는 여덟 계열을 **기동 때 0 으로 만들어 둔다** — `user`×{`missing_id`, `duplicate_id`, `over_limit`, `parent_not_found`}, `group`×{`missing_id`, `duplicate_id`, `over_limit`}, `member`×{`unmatched_member`}. 전략과 상관없이 여덟 다 | 카운터는 여러 인스턴스를 더해도 맞다 — 회차는 한 인스턴스가 돌고 다음 회차는 다른 인스턴스일 수 있다. 0 으로 만들어 두는 까닭은 `scim.revocations` 와 같다 — Prometheus `increase()` 는 새 계열의 첫 값을 증가로 세지 않는다. 태그 값은 사유 열거 이름이 아니라 고정한 영문이다 — 경보 식이 코드의 이름 바꾸기에 깨지지 않게. 전략에 없는 계열(DIT 의 `member`)은 늘 0 이고, 0 은 참이다 |
| S7 | **결선.** `LdapConfig.ldapMappingStrategy` 가 관찰자 빈을 있으면 받고 없으면 `NOOP` 를 쓴다. 두 전략은 관찰자를 받는 생성자를 더하고 지금 생성자는 `NOOP` 로 둔다 | connector-ldap 만 쓰는 시험과 전략을 직접 만드는 시험 수십 개가 그대로다. 재적재의 읽기도 같은 전략을 타므로 따로 결선하지 않는다 |
| S8 | **빈 호스트를 기동 때 막는다.** 권한부가 `:` 로 시작하면(`ldap://:389`) 모양이 틀린 주소다 — 지금 문구 "ldap.urls 의 주소는 ldap://호스트[:포트] …" 그대로 | 사용자 정보(`@`)는 이미 막으므로 권한부는 `호스트[:포트]` 다. 호스트가 비는 것은 권한부가 `:` 로 시작하는 경우뿐이다(`ldap://` 처럼 권한부가 없는 것은 지금도 막는다) |
| S9 | **문서.** README(건너뛰는 엔트리 목록, 지표·경보), 온보딩 04(튜플 칸의 길이에 `object` 칸, "막지 않는 것" → 입구에서 막는 것), 05(§3.11 사유 표·경고 모양·흐름의 단계), 11(지표 표, 기동 때 0 으로 만드는 계열, 경보 예), 13(§3.6·§3.7 의 신호, §4.1·§4.7 을 고친 항목으로, 8 한눈에), 15(결정 행과 설계 목록), 그 밖에 grep 으로 찾은 곳. 고친 문서의 기준 커밋 줄 | 온보딩은 늘 현재 동작이다 |

**바꾸지 않는 것.**
- 표시명·계정명(`displayName`·`userName`)의 길이. 색인 정렬키만 1024바이트로 잘라 쓰고 원래 값은 그대로다(설계 2026-10-20 §7). 조직 표시명의 기본 속성이 자유 서술인 `description` 이라, 막으면 지금 들어가는 조직이 빠진다.
- SCIM. SCIM 의 id 는 서버가 정하는 UUID 이고, 받는 값의 한도는 `KeyValueLimits` 가 이미 400 으로 막는다.
- 지금 사유 넷의 뜻과 문구, 멈추는 규칙. 로그는 그대로 남는다 — 지표는 경고를 대신하지 않고 곁에 선다.
- 실행 기록·관리 API. 건너뛴 수를 실행 기록에 싣지 않는다(§7).

## 3. 동작

### 3.1 길이 검사 (두 전략)

| 엔트리 | 재는 값 | 한도 | 넘으면 |
|---|---|---|---|
| 직원(두 전략) | 정규화한 id, 그다음 절대 DN | 500 / 1024 | 직원 검색의 `한도_넘음` 으로 뺀다 |
| 조직 — groupOfNames 의 그룹, DIT 의 OU | 정규화한 id, 그다음 절대 DN | 250 / 1024 | 조직 검색의 `한도_넘음` 으로 뺀다 |

뺀 뒤는 지금 다른 사유로 뺀 것과 같다.

- **groupOfNames.** 뺀 직원·조직을 가리키는 `member` 값은 대조되지 않아 `읽지_않은_member` 로 세인다. 뺀 그룹의 `member` 는 읽지 않는다.
- **DIT.** 뺀 OU 의 DN 은 색인에 넣지 않으므로 그 아래 직원은 `부모_조직_없음`(소속 없이 적재), 하위 OU 는 상위 연결 없는 조직이 된다 — 아이디 겹침으로 뺀 OU 와 같다(05 §3.11).
- **이미 장부에 있던 엔트리.** 한도를 넘는 값은 지금도 쓰기가 거절되므로 OpenFGA 에는 그 줄이 없다. DynamoDB 에 직원·조직 아이템이 있었다면(조직 id 251~500바이트처럼 DynamoDB 는 받고 OpenFGA 만 거절한 경우) 다음 회차의 현재상태 교체가 지운다.
  지울 튜플 줄이 많으면 삭제 가드가 본다. 배포 전이라 옮길 데이터는 없다.
- **모두 넘으면** — 식별 속성을 이름 기반의 긴 속성으로 잘못 고른 설정 — 받은 것이 있는데 하나도 남지 않으므로 데이터 오류로 멈춘다(재시도 없음).

### 3.2 지표

- `SkippedEntries.요약을_남긴다()` 가 경고를 남길 때, 건수가 0 이 아닌 사유마다 관찰자를 한 번 부른다(검색 종류, 사유, 건수). 경고를 남기지 않으면(건너뛴 것이 없으면) 부르지 않는다.
- 검색 종류는 셋이다 — 직원 검색, 조직 검색, `member` 값 집계. 태그 `search` 는 각각 `user`·`group`·`member` 다.
- **읽기마다 센다.** 읽기 재시도가 요약을 남긴 뒤에 돌면(groupOfNames 는 직원 요약을 남긴 뒤 그룹 검색을 한다) 그 사유는 다시 센다. 재적재의 읽기도 센다. 그러므로 회차당 수가 아니라 "읽어 본 엔트리 가운데 뺀 수의 합" 이다.
- 한 회차는 한 인스턴스가 돌므로 그 인스턴스의 계열만 오른다. 모든 인스턴스를 긁어 더한다(11 의 `sync.tuples.*` 와 같다).
- 경고의 예시는 지표에 싣지 않는다. 무엇이 빠졌는지는 경고 한 줄을 본다.

### 3.3 운영자가 보는 것

경고(직원 하나의 id 가 넘은 경우):

```
직원 검색에서 엔트리 1건을 건너뛰었다 — 값이 저장 한도를 넘음 1건(예: dn='uid=…,ou=people,dc=example,dc=com'(id 612바이트, 한도 500))
```

지표(Prometheus 이름, 11 §3.1 의 규칙):

```
sync_entries_skipped_total{search="user",reason="over_limit"} 1
```

경보 예(문서에 적되 시험하지 않는다):

```promql
# 직원·조직이 회차에서 빠졌다 — 그 사람(조직)의 권한이 지금 없다. 매시 되풀이되므로 고칠 때까지 울린다
sum(increase(sync_entries_skipped_total{reason=~"missing_id|duplicate_id|over_limit"}[2h])) > 0

# 소속 없이 적재된 직원(DIT) — 조직 권한이 없다
sum(increase(sync_entries_skipped_total{reason="parent_not_found"}[2h])) > 0
```

- `unmatched_member` 는 AD 에서 그룹에 컴퓨터·연락처가 들어 있으면 늘 0 이 아니다 — 위 예에서 뺐다. 평소 수를 본 뒤 그보다 크게 늘 때 거는 것이 맞다.
- 영구히 빠지는 엔트리(식별 속성이 없는 서비스 계정 등)가 있는 배포는 첫 식이 늘 울린다. 그런 엔트리는 직원 검색 필터에서 빼는 것이 맞다 — 빠질 것을 아는 엔트리는 읽지 않는 것이 신호를 살린다.

### 3.4 빈 호스트

`ldap.urls` 에 `ldap://:389` 가 있으면 기동이 멈춘다. 문구는 지금 모양 오류와 같다 — `ldap.urls 의 주소는 ldap://호스트[:포트] 또는 ldaps://호스트[:포트] 다 — 검색 베이스는 ldap.base-dn 에 준다(받은 값: ldap://:389)`.
`ldap://dc1:389`·`ldap://dc_1.corp:389`·`ldap://[::1]:389` 는 지금처럼 지난다.

## 4. 시험

각 시험에 "이 시험을 깨뜨릴 운영 코드 변경" 을 적는다. 이름 기반의 긴 식별 값은 임베디드 LDAP 에 직접 만든다(식별 속성을 `uid`·`ou`·`description` 같은 문자열 속성으로 설정).

### 4.1 connector-ldap — `SkippedEntriesTest`

| 시험 | 단언 | 깨뜨릴 변경 |
|---|---|---|
| 요약을 남기면 사유마다 건수로 관찰자를 부른다 | 두 사유(2건·1건) → 호출 둘, 검색 종류·사유·건수 | 사유를 합쳐 한 번만 부르기, 건수 대신 1 |

### 4.2 connector-ldap — 전략 (임베디드 LDAP)

두 전략 각각:

| 시험 | 단언 | 깨뜨릴 변경 |
|---|---|---|
| 직원 id 가 정확히 500바이트면 남고 501바이트면 빠진다 | 그림의 직원, 경고의 `한도_넘음` 1건과 바이트 수 | 비교를 `>=` 로, 한도를 다른 상수로 |

| 바이트로 잰다 — 한글 id 는 글자 수가 한도 아래여도 바이트로 넘으면 빠진다 | 예: 조직 id 한글 84자(252바이트) → 빠짐 | `length()` 로 재기 |

- DIT: 한도를 넘어 빠진 OU 아래 직원이 `부모_조직_없음` 으로 소속 없이 적재된다.

### 4.4 app-ldap — 지표

| 시험 | 단언 | 깨뜨릴 변경 |
|---|---|---|
| 기동 때 여덟 계열이 0 으로 있다 | `SimpleMeterRegistry` 에서 여덟 (search, reason) 가 0 | 처음 오를 때 만들기 |
| 사유를 받으면 그 계열이 건수만큼 오른다 | 다른 계열은 0 | 태그 매핑을 틀리게 |

## 6. 이 설계가 말할 수 없는 것

- **`object` 칸 256자는 OpenFGA 의 검증 규칙을 읽어 정했다.** 실제 OpenFGA 로 257자를 보내 보지 않았다. 규칙이 Go 정규식이라 바이트가 아니라 글자(룬)로 센다고 읽었다 — 그래서 한도를 바이트 250 으로 두면 어느 쪽으로 세든 들어간다.
  `user` 칸 512바이트는 앞 설계가 실제 OpenFGA 로 확인했다. OpenFGA 를 올리면 두 값을 다시 확인한다(`KeyValueLimits` 자바독).
- **조직 id 250바이트는 한글 조직 코드를 83자에서 자른다.** 실제 한도(`user` 칸)로는 168자까지 들어간다. 83자를 넘는 조직 코드가 실제로 있는지는 모른다 — 있으면 그 조직이 빠지고 경고와 지표에 보인다.
- **지표는 사람 수가 아니다.** 읽기마다 세므로 재시도·재적재가 다시 센다(§3.2). `member` 는 엔트리가 아니라 값을 센다.
- **경보 예는 시험하지 않았다.** Prometheus 이름은 11 §3.1 의 규칙에서 따른 것이다.
- **실제 AD 의 긴 값으로 보지 않았다.** 임베디드 UnboundID 로만 본다.
- **DN 1024바이트는 실제 한도(2048)보다 좁다.** 같은 값을 SCIM 이 1024 로 막아 맞췄다. 1024바이트를 넘는 DN 이 실제로 있는지는 모른다.

## 7. 왜 다른 길을 안 갔나

| 길 | 버린 까닭 |
|---|---|
| 건너뛴 수를 디렉터리 그림에 실어 실행 기록 → `SyncMetrics` 로 | 실행 기록·관리 API 에도 보이지만 core 모델(`DirectorySnapshot`·`SyncRun`)과 저장 모양까지 바뀐다. 무엇이 빠졌는지는 경고 한 줄이 이미 주고, 경보에 필요한 것은 수뿐이다 |
| connector-ldap 이 `MeterRegistry` 를 직접 받는다 | 결선이 짧지만 connector 가 Micrometer 에 묶이고, core 의 관찰자 관례와 어긋난다. 전략을 직접 만드는 시험마다 레지스트리가 필요해진다 |
| 게이지(마지막 읽기의 수) | "지금 몇 명이 빠져 있나" 에 바로 답하지만, 회차를 돈 인스턴스만 갱신해 다른 인스턴스가 낡은 값을 쥔다 — 아카이빙 게이지가 이미 가진 문제다(13 §6.7). 카운터는 더하면 맞다 |
| 처음 오를 때 카운터를 만든다(`sync.tuples.*` 처럼) | 계열이 없을 때를 경보 식이 따로 다뤄야 하고, 기동 직후 첫 빠짐이 `increase()` 에 잡히지 않는다(`scim.revocations` 가 0 으로 만드는 까닭) |
| 긴 값이 있으면 회차를 멈춘다(`FAILED`) | 한 사람의 데이터 탓에 전원의 갱신이 멈춘다 — 지금의 문제(뒤 단계 부여가 멈춤)를 모양만 바꿔 되풀이한다 |
| 긴 값을 해시해 줄인다 | 어떤 길이든 받지만 id 형식이 둘이 되고, 권한을 묻는 앱이 아는 값과 어긋난다. 이름 기반 id 를 쓰는 까닭(사람이 읽는 id)도 잃는다 |
| 쓰기 직전(저장소·OpenFGA 어댑터)에서 막는다 | 마지막 그물은 되지만 그때는 이미 그림이 정해져 회차가 부분 실패한다. 입구에서 빼야 "그 엔트리만 없는 그림" 이 된다 |
| 직원·조직 id 모두 250바이트 한 수 | 수 하나라 설명이 짧지만 직원 id 는 `object` 칸에 들어가지 않는다 — 들어갈 수 있는 직원을 까닭 없이 뺀다. 직원 쪽은 SCIM 과 같은 500 이 이미 있다 |
| 조직 id 를 글자 250 과 바이트 500 둘로 잰다 | 실제 한도에 가장 가깝지만 한 값에 두 기준이라 문구·문서가 길어진다. 83자 넘는 한글 코드가 나오면 그때 바꾼다 |
| 표시명·계정명도 막는다(`KeyValueLimits.over` 를 그대로 쓴다) | LDAP 은 색인 키만 잘라 받아들이기로 했다(설계 2026-10-20 §7). 막으면 `description` 이 긴 조직이 빠진다 |

## 11. 확인할 것 (구현 때 사실로 정한다)

- **정규화는 바이트 수를 바꾸지 않는다(읽어서 확인, 2026-11-19).** `IdNormalizer` 의 금지 문자는 모두 ASCII 한 바이트(`\s` 는 플래그 없이 ASCII 공백만, `:`·`#`·`*`·`,`·`\`·`|`)이고 한 바이트 `_` 로 바뀐다.
  그래서 "정규화한 뒤에 잰다"(S2)는 쓰일 값을 잰다는 뜻일 뿐 결과가 같다 — 이것을 가르는 시험은 두지 않는다. 금지 목록이 바뀌면 이 사실을 다시 본다.
- **임베디드 LDAP 이 1024바이트 넘는 DN 을 받는지.** 받지 않으면 DN 시험은 단위 수준(매퍼에 긴 DN 을 넘기는 길)으로 내린다.
- **임베디드 LDAP 이 1024바이트 넘는 DN 을 받는지.** 받지 않으면 DN 시험을 매퍼 수준으로 내린다 — 계획의 시험 도우미가 그 길을 남겨 둔다.
- **app-ldap 의 기존 문맥 시험이 `MeterRegistry` 를 갖는지** — 결선 시험을 어디에 더할지.

## 12. 구현 전 점검

계획을 세울 사람의 눈으로 이 문서를 코드와 맞댔다(2026-11-19). 계획 전에 사용자께 여쭐 것은 없었다.

- **맞다고 확인한 것.**
  - 두 전략의 생성자는 `(properties, clock)`(롬복)과 `(properties)` 둘이고, `LdapConfig.ldapMappingStrategy` 가 앞의 것으로 만든다. 전략을 직접 만드는 시험은 약 120곳이다 — 지금 생성자를 `NOOP` 로 두면(S7) 그대로다.
  - `SkippedEntries.요약을_남긴다()` 는 건수가 있을 때만 경고를 남긴다 — 그 자리에서 사유마다 부르면 §3.2 와 같다. `사유` 열거는 패키지 안에 있고 `member값()` 집계는 별개 인스턴스다.
  - 식별 값을 정규화하는 줄은 두 전략의 매퍼에 있다. DIT 매퍼의 DN 은 베이스에 상대적이라 절대 DN 은 `LdapDns.절대로(dn, baseDn)` 로 만든다 — `externalId` 가 이미 그 값이다.
  - `IdNormalizer` 의 금지 문자는 모두 ASCII 한 바이트다(§11).
  - `ldap://:389` 는 권한부 `:389` 로 지금 기동 검사를 지난다(§1).
  - 재적재는 같은 전략 빈을 탄다. app-ldap 은 connector-ldap 에 의존하므로 공개 관찰자를 구현할 수 있다. 0 으로 만드는 계열과 관찰자의 관례는 `ScimSyncMetrics`·core 관찰자에 있다.
- **정한 것(점검이 짚은 것).**
  - **한도 넘은 그룹의 범위 이어받기.** groupOfNames 는 요약 줄 앞에서 `member;range=` 로 잘린 그룹의 멤버를 이어 읽는다. 한도를 넘은 그룹은 식별 속성 없는 그룹(`RawEntry.식별_속성_없음`)처럼
    멤버를 비우고 완료로 돌려준다 — 뺄 그룹의 멤버를 더 읽는 질의를 보내지 않는다(S3 의 "범위가 잘린 `member` 는 읽지 않는다").
