# 재활성 가드의 읽기 오류 가르기 설계 (2026-11-25)

재활성 가드 설계(2026-11-24) §9.5 의 첫 항목, R8 의 빈틈을 닫는다. 작은 변경이라 짧은 설계다(빌더 점검 없음).

사용자 결정은 "추천대로"(2026-11-25)다. 아래 결정은 모두 그 추천이다.

## 1. 문제

- **기록 중 회차와 재적재는 직전 스냅샷을 읽다 실패하면, 원인과 상관없이 재활성 가드 없이 지나간다.**
  - `FullSyncUseCase.직전_I_를_읽어_본다` 가 모든 오류를 WARN 하나로 삼키고 빈 I 를 돌려준다(R8).
  - R8 이 건너뛰려던 것은 **깨진 스냅샷**이다. 재적재는 깨진 스냅샷을 고치는 통로라, 깨진 스냅샷 때문에 막히면 안 된다.
  - 그런데 DynamoDB 일시 오류(스로틀, 연결 끊김)도 같은 길로 빠진다.
- **겹치면 기억이 영영 사라진다.**
  - 계정 상태 속성을 못 읽는 사고와 일시 오류가 같은 회차에 겹치면, 막혀 있던 직원이 가드 없이 활성이 된다.
  - 그 회차는 새 스냅샷을 커밋한다. 새 I 에는 그 직원들이 없다(이번 그림에서 활성이므로). 그래서 "직전에 막혀 있던 직원"이라는 기억이 그 뒤로 없다.
  - 겹침은 드물다. 그러나 이 가드가 막으려는 사고에서 가드를 끄는 길이 오류 하나로 열린다.
- **비교 경로는 이미 다르다.** 스냅샷을 못 읽으면 회차가 실패한다(`기준_스냅샷()`). 세 길이 서로 다른 규칙을 쓴다.

## 2. 접근안

| 안 | 내용 | 판단 |
|---|---|---|
| **A (고름)** | 깨짐(`SnapshotIntegrityException`)만 판정 없이 넘긴다. 그 밖의 오류는 회차를 실패시킨다. 저장소는 "읽어 온 아이템을 푸는 동안의 실패"를 모두 그 예외로 묶는다 | 깨짐과 일시 장애를 저장소 경계 한 곳에서 가른다. 일시 장애는 다음 정각이 다시 본다. 회차는 쓰기 전에 멈춰 잃는 것이 없다 |
| B | 분류기(`TemporaryFailureClassifier`)로 일시 장애만 실패시키고, 나머지는 넘긴다 | 모르는 오류(권한 거절, 코드 버그)가 계속 가드를 끈다 — 닫으려는 것이 바로 그 fail-open 이다. HTTP 층에서 쓰던 분류기를 유스케이스에 결선해야 한다 |
| C | 읽기를 몇 번 다시 시도하고, 그래도 실패하면 넘긴다 | 재시도가 다 실패하면 여전히 가드가 꺼진다. SDK 가 이미 재시도한다 |
| D | 비교 경로처럼 모든 오류에 실패한다(깨짐 포함) | 깨진 스냅샷이 재적재까지 막는다. 고칠 길이 초기화(`wipe`)뿐이 된다 |

## 3. 결정

| # | 결정 | 이유 |
|---|---|---|
| E1 | **기록 중 회차와 재적재의 직전 I 읽기는 `SnapshotIntegrityException` 일 때만 판정 없이 넘긴다.** 그 밖의 오류는 그대로 올린다. 회차는 `FAILED`, 메시지는 그 오류의 메시지다 — 비교 경로와 같다. 스냅샷이 없을 때(빈 Mono)는 지금처럼 판정 없이 간다 | 깨짐은 재적재가 고칠 일이고, 일시 장애는 기다리면 풀린다. 읽기는 LDAP 을 다 읽은 뒤·매핑과 쓰기 전이다. 그래서 실패한 회차는 장부·현재상태·스냅샷에 아무것도 내보내지 않는다. 기록 중 표시는 그대로 남아 다음 정각이 다시 본다 |
| E2 | **넘길 때의 WARN 문구를 `직전 스냅샷이 온전하지 않아 재활성 가드를 보지 않는다: {}` 로 바꾼다.** `{}` 는 예외 메시지다(스냅샷 id 와 사정, 재적재 안내 — id 는 싣지 않는다) | 이제 이 줄은 깨진 스냅샷에만 나온다. "읽지 못해"는 일시 장애로 읽힌다 |
| E3 | **저장소는 읽어 온 아이템을 스냅샷으로 푸는 동안의 실패를 모두 `SnapshotIntegrityException` 으로 묶는다.** 메타의 수 칸이 수가 아님, `createdAt` 이 시각이 아님, `source` 가 모르는 값, 칸이 빠져 생성자가 거절함 등이다. 아이템을 **가져오는** 동안의 실패(SDK 오류)는 묶지 않는다. 사정 문구는 `메타를 풀 수 없다: <예외 이름>` 이다 | 깨짐과 아닌 것의 경계가 "가져왔나, 풀었나" 한 줄이 된다. 묶지 않으면 메타 칸 하나가 깨진 스냅샷이 E1 에서 재적재를 영영 막는다. 비교 경로도 이 덕에 같은 재적재 안내로 실패한다 |
| E4 | **새 지표·새 설정은 없다.** 실패한 회차는 `FAILED` 라 기존 신호(`sync.last.success` 경보)가 잡는다 | 일시 장애가 길게 가면 매시 실패가 쌓여 그 경보가 울린다 — fail-closed 쪽이다 |
| E5 | **SCIM 은 범위 밖이다.** SCIM 은 직전 I 를 읽지 않는다 | 재활성 가드 R13 그대로다 |

## 4. 시험

- **core `FullSyncUseCaseTest`.**
  - 기록 중 회차에서 `findLatest` 가 깨짐이 아닌 오류(예: `RuntimeException("DynamoDB 일시 장애")`)로 실패하면 회차는 `FAILED`, 메시지는 그 오류 메시지다. 장부에 쓴 줄이 없고, 새 스냅샷이 없고, 기록 중 표시가 남고, 현재상태가 그대로다.
  - 기존 `기록_중_회차가_스냅샷을_못_읽으면_판정_없이_맞춘다`(깨짐 → 판정 없이 성공)는 그대로 둔다. 이름과 표시 이름만 "깨져 있으면"으로 바꾼다.
- **core `RebuildUseCaseTest`.** 같은 짝이다 — 깨짐이 아닌 오류면 재적재가 `FAILED` 이고 아무것도 쓰지 않는다. 깨짐이면 지금처럼 판정 없이 끝낸다.
- **storage-dynamodb `DynamoDbTupleSnapshotRepositoryTest`.**
  - 메타의 튜플 수 칸이 수가 아닐 때, `createdAt` 이 시각이 아닐 때, `source` 가 모르는 값일 때 `findLatest`·`findById` 가 `SnapshotIntegrityException` 이다(메타를 직접 고쳐 쓴다).
  - 경계의 반대쪽: 아이템을 가져오다 실패하면(없는 테이블을 가리킨 저장소) `SnapshotIntegrityException` 이 **아니다**.
- 규모 시험은 바꾸지 않는다(정상 읽기 경로는 그대로다).

## 6. 이 설계가 말할 수 없는 것

- **실제 AWS 의 일시 오류는 재현하지 않았다.** core 시험은 가짜 저장소가 던지는 예외로, 저장소 시험은 없는 테이블로 "가져오기 실패"를 흉내 낸다. 실제 스로틀에서 SDK 재시도가 다 실패한 뒤의 예외 모양은 보지 않았다 — E1 은 모양과 상관없이 "깨짐이 아니면 실패"라 결과는 같다고 본다.
- **일시 장애가 길면 기록 중 회차가 매시 실패한다.** 그동안 회수도 늦어진다. 이전에는 판정 없이 장부를 맞췄으므로, 이 변경은 가용성을 조금 내주고 재활성 가드를 지킨다. 그 회차는 어차피 같은 테이블에 현재상태와 스냅샷을 써야 해 DynamoDB 가 흔들리면 다른 곳에서도 실패하기 쉽다(재지 않았다).
- **"풀기 실패 = 깨짐"은 코드 버그도 깨짐으로 본다.** 푸는 코드에 버그가 생기면 기록 중 회차와 재적재는 재활성 가드 없이 지나간다(WARN 은 남는다). 비교 경로는 실패해 드러난다.
- 재활성 가드 설계 §9.5 의 나머지(스냅샷 통째 읽기, 정적 도우미 여섯, 차단기 끝 문구, 사소한 시험·문서)는 이 슬라이드에서 다루지 않는다.

### 8.3 구현 중 판정

- **가져오기 실패 시험은 바꾸기 전에도 통과한다.** 경계를 못박는 시험이라 받아들였다 — 가져오기 실패까지 묶는 변경이 이 시험을 깨뜨린다.
- **§4 의 "없는 테이블" 대신 `Query` 를 스로틀하는 프록시로 가져오기 실패를 흉내 냈다.** 없는 테이블이면 포인터 `GetItem` 에서 먼저 실패해 `Query` 를 지나지 않는다. 최종 리뷰가 더 낫다고 보았다.
- **감싸면서 원래 예외를 원인(cause)으로 달지 않았다.** B∩U 겹침의 메시지에는 직원 id 가 든 튜플이 있고, 비교 경로의 실패는 예외 사슬 전체를 ERROR 로 남긴다. 예외 이름만 사정에 싣는다 — 이전에는 그 메시지가 실행 기록과 ERROR 로그에 그대로 들어갔으니 덤으로 노출이 줄었다.

### 8.4 최종 리뷰와 수정

최종 리뷰(브랜치 전체)는 "고치면 머지"였다. Critical 0. Important 1 — 온보딩의 끝 표(05 §11.2, 07 재적재 실패 표, 12 §3.1·§3.5·§8.2)에 새 `FAILED` 끝이 없었다. Minor 가운데 포트 계약, 15 의 시험 방법·R8 표기, 13 §3.12 의 한계, README 문장을 함께 고쳤다(`5ac17b4`). 재검토는 열 가지 모두 반영, 새로 깨진 것 없음이었다.

### 8.5 남긴 것

- **재활성 가드를 꺼도 직전 I 를 읽는다.** 그 읽기의 일시 오류로 기록 중 회차·재적재가 실패한다. 기본은 켜짐이고 다음 정각이 다시 본다. 13 §3.12 에 한계로 적었다. 고르는 가드가 꺼져 있으면 읽지 않게 하려면 분기 하나와 시험이 는다.
- **사정 문구 `메타를 풀 수 없다` 는 메타가 아닌 깨짐에도 붙는다** — B∩U 겹침, 본문의 깨진 튜플 줄. 처방(재적재)은 같다.
- **목록 읽기(`snapshotMetas`·`listRecent`)의 메타 풀기는 감싸지 않았다** — 범위 밖. 정리·목록이 깨진 메타에서 날것 예외로 실패한다(이전과 같다).
- 사소한 것: core 시험의 import 순서, 재적재 깨짐 시험에 WARN 단언 없음(같은 도우미라 FullSync 시험이 못박는다), 저장소 메타 시험 셋의 같은 몸통, 15 E1 의 긴 "버린 길" 칸, 05 의 빽빽한 문장 하나.
- 재활성 가드 설계 §9.5 의 나머지(스냅샷 통째 읽기, 정적 도우미 여섯, 차단기 끝 문구, 사소한 것들)는 그대로 남는다.
