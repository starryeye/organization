## 1. 문제

점검 문서의 네 발견이다. 자세한 시나리오·위치는 그 문서 §4.1 에 있다.

| ID | 무엇 | 점검 때 증거 |
|---|---|---|
| C1 | LDAP 비교 기준(최신 튜플 스냅샷)이 7일 뒤 정리 잡·TTL 로 지워진다. 다음 회차는 빈 기준선으로 돌아 그 회차의 삭제를 하나도 안 한다 — 퇴사자 권한이 영구히 남고 삭제 가드도 꺼진다 | 재현(`spike-full-audit` `a90ab10`) |
| C4 | 아이디에 작은따옴표가 든 직원(`o'brien@corp.com`)은 `members[value eq "…"]` 로 조직에서 뺄 수 없다(400 `invalidPath`) — 소속·권한이 남는다 | 재현(`9bcc4fa`) |
| C8 | 쓰기 경로의 Check 가 OpenFGA 캐시를 우회하지 않는다. 캐시를 켜면 넣고 10초 안에 빼는 멤버의 튜플이 안 지워진다 | 코드·문서 |
| C5 | LDAP 연결·읽기 타임아웃이 없다. 응답 없는 연결 하나에 물리면 회차가 끝나지 않아 실행 가드가 안 풀리고 이후 매일 동기화가 건너뛰어진다 | 코드 |

C1 의 "최신 스냅샷이 7일 넘게 안 바뀌는" 경우는 변경 없는 연휴만이 아니다. 새 스냅샷은 **변경이 있고 끝까지 간 회차**만 만들므로
삭제 가드 중단(ABORTED)이 7일 넘게 방치되거나, LDAP 장애·데이터 오류(M11)로 7일 넘게 매일 실패하거나, C5 로 동기화가 멈춰도 같다.
가장 위험한 것은 가드 중단이다 — 가드가 멈췄다는 것은 지울 것이 많다는 뜻인데, 기준선이 사라지면 그 삭제가 한 건도 안 나간 채 SUCCEEDED 가 된다.

## 2. 결정 — 사용자와 정한 것 (2026-09-29)

- **C1: 최신은 안 지우기 + 감지.** 최신이 아닌 스냅샷만 보존 기간(7일) 뒤 지운다. 지우는 일은 DynamoDB TTL 이 아니라 이미 있는 매일 정리 작업이
  하고, 정리 작업은 최신을 건너뛴다. 스냅샷은 목차(메타) → 튜플 → 포인터 순서로 쓴다. 기준선이 깨졌으면 회차를 실패시킨다.
- **C4: 큰따옴표만.** 멤버 빼기 필터 값은 RFC 대로 큰따옴표 JSON 문자열만 받는다. 작은따옴표로 감싼 `'kim'` 은 거절한다.
- C8·C5 는 설계 제안 그대로 승인.

## 3. C1 — 최신 스냅샷은 지우지 않고, 기준이 깨지면 알린다

### 3.1 스냅샷에서 TTL 을 뗀다

- 지금은 스냅샷의 튜플 아이템과 메타 아이템 모두 테이블 TTL 속성 `expiresAt` 을 갖는다(`DynamoDbTupleSnapshotRepository.java:68-104`).
- 바뀐 뒤: 스냅샷 아이템(메타·튜플)에 `expiresAt` 을 쓰지 않는다. 메타에만 보관 기한 `retainUntil`(epoch 초, **TTL 속성 아님**)을 적는다
  = 스냅샷 `createdAt` + `dynamodb.snapshot-retention-days`.
- 락·책갈피·실행 이력 등 다른 아이템은 지금처럼 `expiresAt` TTL 을 쓴다.

**왜 TTL 을 최신에서만 빼지 않나.** TTL 은 아이템마다 붙은 시각만 보고 지운다 — 최신인지 모른다. 최신만 빼려면 최신이 바뀔 때마다
새 최신 10만 줄에서 시각을 빼고, 밀려난 옛 최신 10만 줄에 시각을 붙여야 한다(매번 쓰기 약 10만 번 추가). 정리 작업은 이미 스냅샷
단위로 지우고 있으므로 "최신이면 건너뛴다" 한 줄이면 같은 결과를 추가 비용 없이 얻는다.

### 3.2 정리 작업은 최신을 건너뛴다

- `purgeExpired`: 포인터(`SNAPSHOT_POINTER`/`LATEST`)를 **강한 일관성**으로 읽어 최신 id 를 얻는다. 목차 목록(GSI1 `SNAPSHOT_INDEX`)에서
  `retainUntil <= 지금` 인 스냅샷을 지우되 **최신 id 는 건너뛴다.** 포인터가 없으면 건너뛸 것도 없다.
- 결과: 최신이 아닌 스냅샷은 보존 기간이 지나면 다음 정리(app-ldap 04:00 · app-scim 아카이브 뒤)에 지워진다. 최신은 며칠이 지나도 남는다.
- 예: 가드 중단이 20일 이어져도 최신 S0 는 남는다. 21일째 개편 삭제를 승인(`force`)하면 S0 를 기준으로 정확히 지운다.

### 3.3 목차를 먼저 쓴다

- 저장 순서를 **메타 → 튜플 → 포인터** 로 바꾼다(지금은 튜플 → 메타 → 포인터).
- 이유: 정리 작업은 목차(메타) 목록으로 스냅샷을 찾는다. 튜플을 쓰다 프로세스가 죽으면 지금 순서로는 메타 없는 튜플 조각이 남고,
  TTL 을 뗀 뒤에는 아무도 그 조각을 치우지 못한다. 메타를 먼저 쓰면 조각도 목차가 있어 보존 기간 뒤 정리된다.
- 포인터는 마지막에만 바뀌므로 반쪽 스냅샷이 기준선이 되는 일은 없다.

### 3.4 기준선이 깨졌으면 회차를 실패시킨다(안전망)

- `findLatest`:
  - 포인터가 **없으면** 빈 결과 — 처음 설치·재적재 직후. 지금처럼 빈 기준선으로 첫 적재를 한다(정상 흐름).
  - 포인터가 **있는데** 그 스냅샷의 메타가 없거나, 읽은 튜플 수가 메타의 `tupleCount` 와 다르면 **오류.**
    메시지에 스냅샷 id 와 복구 방법을 적는다(예: "기준선 스냅샷 20260806T030000-LDAP 을 온전히 읽지 못했습니다(메타 튜플 100,000 · 읽음 30,000)
    — `POST /admin/sync/rebuild?mode=store` 로 복구하세요").
- `findById` 도 같은 튜플 수 확인을 한다(반쪽 조각을 직접 읽는 경우).
- LDAP 전체 동기화(`FullSyncUseCase`)는 이 오류를 받으면 OpenFGA·스냅샷·상태를 건드리지 않고 FAILED 로 끝난다(기존 `onErrorResume` 경로).
- 재적재 `mode=snapshot`(`RebuildUseCase`)도 같은 오류로 멈춘다 — 메시지가 `mode=store` 를 안내한다.
- 3.2·3.3 이 있으면 평소에는 걸리지 않는다. 테이블을 손으로 건드리는 것 같은 예상 밖의 일에 조용히 삭제를 놓치지 않게 하는 장치다.

## 4. C4 — 멤버 빼기 필터를 표준 해석기로 읽는다

- `ScimPatchApplier` 의 정규식(`members\[\s*value\s+eq\s+["'](?<value>[^"']+)["']\s*]`, `:35-36`)을 걷어낸다.
- `members[ … ]`(속성 이름 대소문자 무시)의 **대괄호 안**을 목록 조회 필터가 쓰는 `ScimFilter` 해석기로 읽는다.
  이 해석기는 RFC 8259 JSON 문자열 규칙(큰따옴표만 구분자, `\"`·`\\`·`\uXXXX` 이스케이프)을 이미 구현한다(`ScimFilter.java:139-167`).
- 대괄호 안은 정확히 한 항 `value eq "<문자열>"` 만 받는다.

| path | 결과 |
|---|---|
| `members[value eq "kim"]` | 204, kim 을 뺀다(지금과 같음) |
| `members[value eq "o'brien@corp.com"]` | 204, o'brien 을 뺀다(**지금은 400**) |
| `members[value eq "a\"b"]` | 204, `a"b` 를 뺀다(지금은 400) |
| `members[value eq 'kim']` | 400 `invalidFilter` — 큰따옴표만(결정) |
| `members[ value eq "kim" ]`(대괄호 안 앞뒤 공백·두 칸 공백) | 400 `invalidFilter` — RFC 7644 ABNF 는 한 칸(SP)만 정한다. 목록 조회 필터와 같은 규칙(옛 정규식은 받았다) |
| `members[value eq "kim" and …]`, `members[display eq "x"]`, 값이 문자열이 아님 | 400 `invalidPath` — 지원하지 않는 모양(지금과 같음) |

- 뺀 값은 지금처럼 `IdNormalizer.normalize` 를 거쳐 아이디가 된다.
- 기존 테스트 "작은따옴표로 감싼 필터 값도 인식한다"는 "400 으로 거절한다"로 바꾼다.

## 5. C8 — 우리가 부르는 Check 는 모두 캐시를 우회한다

- `OpenFgaRelationTupleChecker` 의 두 호출에 `ConsistencyPreference.HIGHER_CONSISTENCY` 를 넘긴다(SDK 0.9.11 에 있음 — `javap` 로 확인).
  - `existing`(BatchCheck, `:99-102`) — `ClientBatchCheckOptions().consistency(...)`. 쓰기 전 기준선, 아카이빙이 쓴다.
  - `check`(Check, `:46-51`) — `ClientCheckOptions().consistency(...)`. 관리 조회의 "있어야 함/실제" 비교가 쓴다.
- 둘 다 붙이는 이유: 한 규칙. 관리 조회·아카이빙도 "실제"를 보여 주는 자리라 캐시 값이면 거짓 어긋남이 나온다.
- 영향 범위는 **이 서버가 부르는 Check 뿐**이다. 권한을 묻는 다른 앱은 계속 캐시를 쓸 수 있다.
- 서버 요구: OpenFGA v1.5.7 이상(우리는 이미 v1.10.0 이상 요구 — 멱등 쓰기 옵션).

## 6. C5 — LDAP 연결·읽기 타임아웃

- `LdapProperties` 에 둘을 더한다.

| 설정 | 기본값 | 뜻 |
|---|---|---|
| `ldap.connect-timeout` | 10초 | 접속이 이보다 오래 걸리면 실패 |
| `ldap.read-timeout` | 150초 | 요청 뒤 응답을 이보다 오래 못 받으면 실패 |

- `LdapConfig` 가 `LdapContextSource` 의 기본 환경에 JNDI `com.sun.jndi.ldap.connect.timeout`·`com.sun.jndi.ldap.read.timeout`(밀리초)을 싣는다.
  페이징용 `SingleContextSource`(`LdapTemplates.한_커넥션에서`)는 같은 컨텍스트 소스에서 커넥션을 얻으므로 같은 설정을 탄다 — 테스트로 확인했다.
- 두 설정은 이름과 달리 경계가 나뉜다: 인증(bind) 응답 대기는 `connect-timeout` 이 재고, 인증 이후(페이징 등) 응답 대기만 `read-timeout` 이
  잰다(JDK-8194264) — 각각을 별도 테스트로 고정했다.
- 읽기 기본값 150초: AD 가 검색 하나를 최대 120초(`MaxQueryDuration`)까지 허용하므로, 서버가 정상적으로 오래 일하는 경우를 우리가 먼저 끊지 않게
  그보다 길게. 평소 한 페이지(500명) 응답은 1초 안쪽이라 150초는 사실상 "연결이 죽었다"는 뜻이다.
- 걸리면: 읽기 타임아웃 예외는 `DirectoryDataException` 이 아니라 일시 장애로 분류돼 기존 재시도(`ldap.max-retries`, 처음부터 다시 읽기)를 탄다.
  그래도 안 되면 FAILED, 실행 가드가 풀려 다음 cron·수동 `/full` 이 정상으로 돈다.

**하지 않는 것 — 회차 전체 타임아웃.** 점검 문서는 회차 전체 백스톱도 권했지만 넣지 않는다. LDAP 읽기는 `boundedElastic` 스레드가 JNDI 응답을
기다리며 막히는 구조라, 바깥 Mono 에 `.timeout` 을 걸어도 그 스레드는 깨어나지 않는다. 막힌 스레드는 남고 재시도가 새 읽기를 시작해 읽기가 겹친다.
스레드를 실제로 깨우는 것은 JNDI 읽기 타임아웃뿐이다.

    그 클래스만(1분 23초), app-ldap 규모 전체만(33개, 3분 35초), 전체 규모를 다시 돌리면 모두 통과 — 재현되지 않았다.
  - 두 번 모두 요청이 우리 앱이 아닌 다른 리스너에 닿은 모양이라, 테스트 서버의 임의 포트가 Testcontainers 가 잡은 호스트 포트와 겹친 것으로 **추정**한다
    (확인 못 함). 이 슬라이드의 변경과는 무관하다고 본다 — 실패한 경로(관리 조회 부팅, 수동 동기화 라우팅)는 이번에 바뀌지 않았다.
  - 규모 수치는 그대로다(멤버 10만 명 조직): 한 명 넣기 233ms·GetItem 3·Check 1, 한 명 빼기 34ms, 전체 교체 1,064ms·Query 7·훑은 100,000,
    소속 직원 삭제 32ms·Query 2·Check 1.
- **리뷰.** 과제별 리뷰에서 과제 1(스냅샷 삭제 순서 — 메타를 먼저 지우면 중간 실패가 영구 조각을 남김)과 과제 4(검색 대기의 read-timeout 을
  증명하는 테스트가 없었음 — JDK 는 bind 응답 대기를 connect-timeout 으로 잰다)를 고쳤다. 브랜치 전체 최종 리뷰(판정 "With fixes", Critical 0)가
  두 가지를 더 요구해 고쳤다: 재적재 초기화(`reset`)는 포인터를 먼저 지운다(중간 실패가 "기준선 깨짐"으로 굳지 않게), 스냅샷 TTL 을 말하던 낡은
  주석 세 곳. 멤버 필터의 "공백은 한 칸" 규칙도 §4 표와 README 에 적었다.

## 9. 왜 다른 길을 안 갔나

**C1**
- **오래되면 다시 저장.** TTL 은 두고, 최신 스냅샷이 며칠 묵으면 같은 내용을 새 스냅샷으로 다시 쓴다. 10만 명이면 며칠에 한 번 BatchWrite 약 4,400번이고,
  변경 없음·가드 중단·실패 회차마다 "다시 쓸지" 규칙이 따로 붙는다. 정리 작업에서 최신을 건너뛰는 쪽이 한 줄이고 비용이 없다.
- **감지만.** 기준선이 사라지면 실패시키고 사람이 재적재로 복구한다. 변경 없는 연휴처럼 정상적인 7일에도 매번 사람이 개입해야 한다.
- **TTL 을 최신에서만 떼기.** §3.1 — 최신이 바뀔 때마다 약 10만 번 쓰기가 더 붙는다.
- **보존 기간을 늘리기(예: 30일).** 창을 넓힐 뿐 없애지 않는다.

**C4 — 작은따옴표도 계속 받기.** RFC 7644 는 큰따옴표 JSON 문자열만 정한다. 조사한 IdP 중 작은따옴표로 보내는 곳이 없고, SCIMple·Goldfish·UnboundID 도 큰따옴표만 받으며,
우리 목록 조회 필터도 이미 큰따옴표만 받는다. 표준 밖을 받으려던 관용이 표준 안의 값(`"o'brien"`)을 깨뜨린 것이 이 결함이다.

**C5 — 회차 전체 타임아웃.** §6 — 막힌 JNDI 스레드를 깨우지 못하고 읽기를 겹치게 한다.

## 10. 이 설계가 말할 수 없는 것

- **C8 은 캐시를 켠 OpenFGA 컨테이너로만 확인한다.** 운영 OpenFGA(Postgres 엔진, 캐시 설정)에서의 동작은 같은 옵션이 같은 뜻이라고 문서로만 믿는다.
- **C5 의 기본값(10초·150초)은 AD 기본 정책을 근거로 잡은 값이다.** 실제 AD·OpenLDAP 에서 한 페이지 응답 시간은 재 보지 못했다(인증 슬라이드 뒤 실연동에서 확인).
  읽기 타임아웃보다 긴 정상 응답이 있는 디렉터리라면 설정을 늘려야 한다.
- **C5 가 막는 것은 "응답이 오지 않는" 경우다.** 아주 느리게 조금씩 응답하는 서버는 각 응답이 제때 오므로 타임아웃에 걸리지 않는다.
- **JNDI 는 bind 응답 대기를 connect-timeout 으로 잰다(JDK-8194264) — 두 설정의 경계는 이름과 다르다.** 두 경로를 각각 테스트로 고정했다.
- **C1 의 감지(§3.4)는 튜플 수로만 본다.** 수는 같은데 내용이 바뀐 경우(손으로 아이템을 바꿔치기)는 못 잡는다.
- **C1 로 이미 사라진 기준선은 이 변경이 되살리지 못한다.** 운영 배포 전이라 해당 없다고 본다. 배포 뒤라면 `rebuild?mode=store` 한 번이 필요하다.
