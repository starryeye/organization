# 실행 기록 단건 조회를 보관 기간 전체로 설계 (2026-11-25)

온보딩 13 §6.6 "실행 기록은 이번 달과 지난달만 읽는다"를 닫는다. 작은 변경이라 짧은 설계다(빌더 점검 없음).

사용자 결정은 "추천대로"(2026-11-25)다. 아래 결정은 모두 그 추천이다.

## 1. 문제

- **단건 조회가 실행 id 로 바로 찾지 못한다.** `DynamoDbSyncRunRepository.findById` 는 이번 달과 지난달 파티션(`SYNCRUN#<yyyy-MM>`)을 최신부터 훑어 `runId` 가 같은 기록을 고른다. 실행 id 가 무작위 UUID 라 id 만으로는 어느 달 파티션인지 모른다.
- **설정 안내를 따르면 바로 걸린다.** 두 앱의 `application.yml` 은 "변경 이력 보관을 늘리려면 `syncrun-retention-days` 와 함께 늘린다 — 이력의 원인 회차가 먼저 사라지면 거슬러 갈 곳이 없다"고 적는다. 감사 때문에 둘 다 1년으로 늘리면, 두 달이 지난 실행 기록은 테이블에 남아 있는데 `GET /admin/sync/runs/{runId}` 가 404 다. 감사 이력의 `cause.id`(= `runId`)를 따라 그 회차의 멈춤 내역·보류 내역·강제 허용 수를 볼 수 없다.
- **읽는 양도 id 와 상관없다.** 지난달 끝의 기록을 찾으면 이번 달 파티션을 다 읽고 지난달로 넘어간다. 없는 id 는 두 파티션을 다 읽고 404 다.

## 2. 접근안

| 안 | 내용 | 판단 |
|---|---|---|
| **A (고름)** | 실행 id 에 시작 시각(UTC, 밀리초)을 싣는다. 단건 조회는 id 에서 키(PK 의 달, SK 의 시작 시각)를 다시 만들어 GetItem 한 번으로 읽는다 | 보관 기간과 상관없이 아이템 하나만 읽는다. 테이블 모양·쓰기가 그대로다. 운영 배포 전이라 옛 id 를 옮길 일이 없다 |
| A′ | id 에 달만 싣고 그 달 파티션을 훑는다 | A 와 바꾸는 곳이 같은데 한 달치를 읽는다 |
| B | UUID 를 두고 `runId → 키` 색인 아이템을 따로 쓴다 | 쓰기가 하나 늘고, 두 쓰기 사이에 실패하면 색인이 없다. 읽기가 둘이다 |
| C | `runId` 로 GSI 를 둔다 | 테이블 모양이 바뀌어 기동 검사와 생성이 바뀌고, 실행 기록을 쓸 때마다 인덱스 쓰기가 붙는다 |
| D | UUID 를 두고 보관 기간만큼 달을 거슬러 훑는다 | 코드는 작지만 없는 id 의 404 가 보관 기간만큼 읽는다(1년이면 13 파티션) |
| E | `syncrun-retention-days` 를 30일로 막는다(기동 검사) | 감사 이력을 더 오래 두는 배포가 원인 회차를 잃는다. yml 안내와 반대다 |

## 3. 결정

| # | 결정 | 이유 |
|---|---|---|
| I1 | **실행 id 는 `<시작 시각>-<UUID>` 다.** 시작 시각은 UTC 의 `yyyyMMdd'T'HHmmss.SSS'Z'`(예 `20261125T135329.645Z-3f2a9c1e-…`)다. 기록의 `startedAt` 과 같은 `Instant` 에서 만든다 — `start` 가 시계를 한 번 읽어 둘에 쓴다 | 기록의 SK 가 이미 `<시작 시각 밀리초>#<runId>` 라, id 에서 키 전체를 다시 만들 수 있다. URL 경로에 그대로 쓸 수 있는 글자만 쓴다(`#`·`:` 없음). 같은 밀리초에 두 회차가 시작해도 UUID 가 가른다 |
| I2 | **단건 조회는 id 의 모양을 엄격히 본다.** `^\d{8}T\d{6}\.\d{3}Z-<소문자 UUID>$` 이고 날짜·시각으로 풀리면 PK(`SYNCRUN#<그 달>`)·SK(`<시작 시각 밀리초>#<runId>`)로 GetItem 한 번. 모양이 다르거나 풀리지 않으면 DynamoDB 를 부르지 않고 빈 결과(관리 API 404)다. 읽기는 지금처럼 최종 일관성이다 | 보관 기간 안의 기록은 몇 달 전 것이든 찾는다. 이상한 id(긴 문자열 포함)가 키 길이 한도로 DynamoDB 오류가 되지 않는다. 모양 검사는 "받는 신호는 하나, 나머지는 404" 한 규칙이다 |
| I3 | **목록(`findRecent`)과 실행 중(`findRunning`)은 그대로 이번 달·지난달이다** | 목록은 "최근" 이고 상한이 있다(`MAX_RUNS_LIMIT`). 죽은 기록은 지금 근처에만 있다. 오래된 기록은 id 로 찾는다 |
| I4 | **옛 모양(UUID 만)의 id 는 받지 않는다** | 운영 배포 전이라 옛 기록을 옮길 일이 없다 |
| I5 | **id 형식은 저장소 안의 일이다.** 만들기·풀기는 storage-dynamodb 의 `Keys` 에 둔다. core 는 `runId` 를 불투명한 문자열로 다룬다 | 키 모양을 아는 곳이 한 곳이다. 가짜 저장소를 쓰는 core 시험은 바뀌지 않는다 |
| I6 | **새 지표·새 설정은 없다.** 두 앱이 같은 저장소라 app-ldap·app-scim 의 실행 id 가 함께 바뀐다 | — |

## 4. 시험

- **storage-dynamodb `DynamoDbSyncRunRepositoryTest`.**
  - `start` 가 준 id 가 I1 의 모양이고, 시각 부분이 기록의 `startedAt`(밀리초)과 같다.
  - 석 달 전 시계로 `start`·`finish` 한 기록을 지금 시계의 저장소가 `findById` 로 찾는다 — 이 슬라이드의 핵심이다.
  - `findById` 가 `query` 없이 `getItem` 한 번만 부른다(호출을 세는 프록시).
  - UUID 만인 id, 모양은 맞지만 풀리지 않는 시각(예 `20261340T…`), 1,000자 넘는 문자열은 빈 결과이고 DynamoDB 를 부르지 않는다.
  - 기존 시험(찾기·목록·실행 중·닫기)은 그대로 통과한다.
- **관리 API.** 두 앱의 `GET /admin/sync/runs/{runId}` 는 저장소가 빈 결과면 404 — 지금 시험 그대로다. 새 시험은 두지 않는다.
- 규모 시험은 바꾸지 않는다.

## 5. 바뀌는 곳

- `storage-dynamodb/.../Keys.java` — 실행 id 만들기(`Instant`, `UUID` → 문자열)와 풀기(문자열 → 시작 시각, 없으면 빈 값).
- `storage-dynamodb/.../DynamoDbSyncRunRepository.java` — `start` 가 시계를 한 번 읽어 id 와 `startedAt` 에 쓴다. `findById` 를 GetItem 으로. Javadoc(두 달 이야기)을 고친다.
- `core/.../port/SyncRunRepository.java` — `findById` Javadoc 에 "보관 기간 안이면 몇 달 전 것도 찾는다".
- 두 앱 `AdminSyncController` 의 404 주석("보관 기간(30일)")을 "보관 기간(`syncrun-retention-days`)"으로.
- 문서: 온보딩 04(실행 기록 id 표 `UUID` → 새 모양, 실행 기록 절), 09(`runId` 칸), 13 §6.6(고친 항목 표로 옮기고, 목록은 두 달이라는 남은 것을 적는다), 15(결정 색인 I1~I6), 루트 README 에 실행 id 가 UUID 라고 적힌 곳이 있으면 고친다. 고친 온보딩 문서의 기준 커밋은 이 슬라이드의 마지막 코드 커밋으로 올린다.

## 6. 이 설계가 말할 수 없는 것

- **실제 AWS 로 보지 않았다.** DynamoDB Local 로만 본다. TTL(`expiresAt`)이 지운 뒤의 404 는 Local 에서 재현하지 않는다(지금도 같다).
- **목록은 여전히 두 달이다.** 석 달 전 회차를 목록에서 훑어 찾을 수는 없다. 감사 이력의 `cause.id` 나 로그의 `[runId]` 로 찾는다.
- **id 가 길어진다**(57자). 로그·감사 이력·관리 API 응답에 그대로 실린다. 시작 시각이 id 에 드러나지만 기록에 이미 있는 값이다.
- **202 직후의 조회는 지금처럼 잠깐 404 일 수 있다**(최종 일관성 읽기). 바꾸지 않았다.
