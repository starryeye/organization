# SCIM 조직 계층 설계 (2026-11-04)

이 슬라이드는 외부 리뷰(2026-10-19)의 N5 를 고친다. 계획된 슬라이드는 인증으로 모두 끝났고, 이것이 남은 마지막 항목이다.
- **외부 리뷰 N5(IAM 리더 H6).** SCIM 배포에서 조직 계층을 어디서 받는지 정해져 있지 않다. 근거: `docs/superpowers/specs/2026-10-19-outsider-review/0-종합.md` 48·112줄, `4-iam-platform-lead.md` H6.
- **온보딩 13 §2.2.** 같은 내용을 "제품 범위의 결정이 먼저" 로 남겨 두었다.

사용자는 "N5 진행" 다음 "추천대로" 라고 했다. **이 문서의 결정은 모두 내 추천이다.** 질문 없이 정했고, 이 문서를 승인하는 것이 §2 의 결정을 승인하는 것이다.

코드 사실은 이 브랜치의 기준(main `8d3759e`)에서 읽은 것이다. 파일:줄은 구현 때 다시 확인한다(§17).

## 1. 문제

### 1.1 SCIM 배포에서는 롤업이 생기지 않는다

- `child` 튜플은 조직 멤버 가운데 GROUP 타입에서만 나온다(`TupleMapper.collectChildEdges`, `candidateTuples`). 곧 IdP 가 그룹 안에 그룹을 넣어 보내야 계층이 생긴다.
- **Entra ID 는 그룹 안의 그룹을 보내지 않는다.** 앱에 할당한 그룹의 직속 멤버(사용자)만 읽어 프로비저닝한다. 근거는 Microsoft Learn 의 Databricks SCIM 문서("can only read and provision users that are immediate members of the explicitly assigned group")와 Snowflake 문서다.
- **Okta 도 보내지 않는다.** Okta 그룹에는 중첩이 없고, Group Push 는 평평한 멤버십만 보낸다. AD 의 중첩 그룹도 가져오지 않는다(Snowflake·Stalwart 문서).
- 그래서 Entra·Okta 로 붙인 배포에서는 `child` 튜플이 하나도 없다. README 의 핵심 약속인 "하위 조직 소속이면 상위 조직의 member" 가 거짓이 된다. 상위 조직 Check 가 늘 false 라 권한을 묻는 앱이 롤업을 따로 만든다.

### 1.2 IdP 가 가진 조직 정보는 계층이 아니다

- 사용자에게 붙는 enterprise 확장(`department`·`division`·`organization`)은 **이름**이고(RFC 7643 §4.3), 위아래 관계가 없다. 지금은 받아서 버린다(`ScimRfcAttributes`, README "받아서 버리는 속성").
- 회사의 조직도(본부 → 실 → 팀)는 보통 인사 시스템(HRIS)에 있다. IdP 에는 팀 단위 그룹이 평평하게 있다.

## 2. 결정

| # | 결정 | 이유 |
|---|---|---|
| H1 | **운영자가 조직마다 상위 조직 하나를 지정하는 관리 API 를 app-scim 에 둔다.** `PUT /admin/organizations/{orgCode}/parent` (본문 `{"parentOrgCode": "<orgCode>"}`)와 `DELETE /admin/organizations/{orgCode}/parent`. 이 연결을 **지정 연결**이라 부른다 | 리뷰가 낸 길 가운데 표준을 어기지 않고, 이 서버 안에서 시험할 수 있고, 어떤 HRIS·IdP 와도 붙는 유일한 길이다(§13). 계층은 드물게 바뀌므로(개편) 운영 도구 한 번 호출로 충분하다 |
| H2 | **계층 = IdP 가 보낸 하위 조직 멤버 ∪ 지정 연결.** 둘 다 같은 `child(하위, 상위)` 튜플이 된다. 같은 쌍이면 튜플 한 줄이고, 한쪽이 빠져도 다른 쪽이 남아 있으면 튜플이 남는다 | 규칙 하나로 섞인다. 사용자 SCIM 클라이언트가 표준대로 중첩 그룹을 보내는 배포도 그대로 돈다 |
| H3 | **소유를 가른다.** 지정 연결은 SCIM 표현(`GET /Groups` 의 `members`, `meta`)에 나오지 않는다. IdP 의 PUT·PATCH 는 이것을 바꾸지 못한다. 저장도 멤버 행(`MEMBER#`)과 따로 한다(§4) | IdP 가 자기 그룹을 다시 쓰면(멤버 전체 교체) 섞어 둔 연결이 조용히 사라진다. IdP 가 모르는 멤버를 보여 주면 IdP 가 그것을 지우려 할 수 있다 |
| H4 | **한 조직의 지정 상위는 하나다.** PUT 은 바꾸기이고, 이전 지정 연결 지우기와 새 연결 쓰기가 한 요청이다 | 조직도는 나무다. 개편의 "팀을 다른 본부로 옮긴다" 가 호출 하나이고, 중간 상태(두 본부 소속, 어디에도 없음)가 없다 |
| H5 | **순환은 지금 규칙 하나로 판정한다 — 먼저 저장된 연결이 이긴다.** 관리 API 는 순환을 닫는 지정을 **409 로 거절**하고 아무것도 바꾸지 않는다. 자기 자신을 상위로 지정하는 것도 순환이다. 이미 같은 상위로 지정돼 있지만 보류 중인 연결(H6)도 409 다 — 409 는 늘 "이 요청 뒤에도 그 상위가 순환 때문에 반영되지 않는다" 이다. IdP 가 나중에 보낸 연결이 지정 연결과 순환을 닫으면 지금처럼 보류한다 | IdP 는 거절을 다룰 수 없어 보류하지만(설계 2026-10-03), 운영자는 사람·스크립트라 거절이 가장 분명한 답이다. 매일 전체를 다시 거는 스크립트가 반영되지 않은 지정을 409 로 알아챈다. 판정 코드(`OrgGraph`)는 같다 |
| H6 | **지정 연결도 보류 목록의 원천이다.** 재적재의 DFS 는 지정 연결을 자를 수 있다. 자른 지정 연결은 IdP 연결과 똑같이 보류 목록에 들어가고, 순환이 풀리면 돌아온다. 보류 줄을 다시 볼 때 "원천이 아직 있는가" 는 멤버 행 **또는** 지정 연결이다 | 재적재는 처음부터 다시 판정한다(지금 동작). 지정 연결만 예외로 두면 DFS 를 바꿔야 하고 LDAP 결과까지 흔든다. 불변식 "튜플 그래프 = 원천 연결 − 보류 목록" 하나를 지킨다 |
| H7 | **SCIM 쓰기와 같은 길로 반영한다.** 같은 변경 락, OpenFGA Check 기준선, diff, 감사다. 감사 원인은 새 종류(관리 API 의 지정 요청)이고 행위자는 토큰의 `client:<sub>` 다. 기록은 지정 대상(하위 조직)의 이력에 남는다 | 동시 SCIM 쓰기와 순서가 섞이지 않는다. 실패하면 커밋하지 않으므로 다시 보내면 된다 |
| H8 | **새 범위 `admin.hierarchy`.** 두 경로(PUT·DELETE `…/parent`)에 묶는다. 개발용 클라이언트 `org-chart`(`admin.read`, `admin.hierarchy`)를 더한다 | 계층을 바꾸면 하위 조직 전체의 롤업 권한이 생기거나 사라진다. 읽기·동기화 범위와 가른다. 스크립트는 조직을 찾으려고 `admin.read` 가 필요하다 |
| H9 | **IdP 가 조직을 지우면 그 조직이 끼인 지정 연결을 모두 지운다** — 그 조직의 지정 상위, 그리고 그 조직을 상위로 지정한 하위 조직들의 연결. 하위 조직들은 지정 상위가 없어진다 | 없는 조직을 가리키는 연결을 남기지 않는다. 다시 붙이는 것은 운영자의 다음 지정이다 |
| H10 | **`mode=wipe` 는 지정 연결을 모두 지운다.** `mode=tuples` 재적재는 유지하고 튜플에 싣는다 | wipe 뒤 IdP 가 다시 보내면 orgCode(서버가 발급한 UUID)가 바뀐다. 옛 id 의 연결은 뜻이 없다. 운영자는 IdP 재프로비저닝 뒤 지정을 다시 건다 |
| H11 | **조회.** 조직 상세에 `assignedParentOrgCode`(없으면 null)를 싣는다. 상위 계층·직속 하위 조직·직원 상세의 롤업 경로는 합집합(H2)으로 보여 준다 | 운영자가 무엇을 지정했는지, 실제 판정이 어떤지를 한 화면에서 본다 |
| H12 | **LDAP 배포는 그대로다.** 계층은 LDAP 에서 온다. 엔드포인트는 app-scim 에만 있다 | 배포 하나엔 커넥터 하나다. LDAP(AD)은 중첩 그룹·DIT 로 계층을 이미 준다 |
| H13 | **문서.** 루트 README(SCIM 절, 관리 API, 인증 범위 표)와 온보딩(13 §2.2 고침 외)을 코드대로 고친다. 기준 커밋은 이 브랜치의 마지막 코드 커밋 | 온보딩은 늘 현재 동작이다 |

**고치지 않기로 한 것.**
- **일괄 지정(조직도 파일 한 번에 바꾸기).** 개편 스크립트가 조직마다 PUT 을 부르면 된다. PUT 은 멱등이라 매일 전체를 다시 걸어도 상태는 바뀐 것만 움직인다(비용은 요청마다 든다 — §15.3).
- **HRIS 커넥터, enterprise 속성으로 조직 만들기.** §13.
- **한 조직에 지정 상위 여럿.** 매트릭스 조직은 IdP 의 중첩 그룹(사용자 SCIM 클라이언트)으로는 여전히 표현된다.
- **지정 연결 목록 API.** 조직 상세가 보여 준다. 필요가 확인되면 더한다.

## 3. API (H1·H4·H5)

### 3.1 요청과 응답

| 요청 | 결과 |
|---|---|
| `PUT /admin/organizations/{orgCode}/parent` `{"parentOrgCode": "P"}` | 204. 지정 상위를 P 로 둔다 |
| 같은 P 로 다시 PUT | 204. 지정은 그대로다. 줄이 OpenFGA 에 없으면(어긋남) 쓴다 — SCIM 이 요청에 나온 멤버의 어긋남을 고치는 것과 같다. 바뀐 것이 없으면 감사 기록이 없다 |
| `DELETE /admin/organizations/{orgCode}/parent` | 204. 지정 상위를 없앤다. 없었으면 아무것도 하지 않고 204 |
| 본문이 없거나 `parentOrgCode` 가 문자열이 아니거나 비었다 | 400 |
| `orgCode` 나 `parentOrgCode` 의 조직이 없다 | 404 — 상세에 어느 쪽인지 적는다 |
| 지정이 순환을 닫는다(P 가 이 조직 자신이거나 그 하위), 또는 같은 P 의 지정이 보류 중이다 | 409 — 상세에 P 와 이 조직을 적는다. 아무것도 바꾸지 않는다(H5) |
| 순환을 판정하다 걷기 예산(`MAX_EXPANSIONS`)을 넘었다 | 400 — SCIM 이 같은 예외(`GroupGraphTooLargeException`)를 400 으로 내는 것과 같다 |
| 락을 제때 못 잡았다, 리스를 잃었다, OpenFGA·DynamoDB 가 일시 실패했다 | 503 + `Retry-After` — SCIM 쓰기와 같다 |
| 토큰 없음 / 범위 없음 | 401 / 403 (인증 슬라이드의 problem details) |

- 본문은 관리 API 의 다른 오류처럼 problem details 다.
- 판정은 락 안에서 한다. 존재 확인·순환 판정·쓰기 사이에 다른 SCIM 쓰기가 끼지 않는다.
- **락 경합이 409 가 아니라 503 인 까닭.** 관리 API 의 처리기(`AdminExceptionHandler`)는 `LockUnavailableException` 을 409 로 낸다 — 동기화·재적재 같은 **작업 시작**에서 "이미 다른 작업이 돈다" 는 뜻이다. 지정은 SCIM 쓰기와 같은 `withLock` 을 거치는 **쓰기 요청**이고, 거기서 이 예외는 대기 초과·리스 상실·획득 중 저장소 오류를 모두 감싼 "잠시 뒤 다시" 다. 409(순환, 영구 거절)와 섞이면 스크립트가 재시도 여부를 가를 수 없다. 그래서 새 컨트롤러가 이 예외를 `ResponseStatusException(503)` + `Retry-After` 로 감싼다 — 처리기는 그 상태와 머리를 그대로 낸다. 규칙은 "쓰기 요청은 503, 작업 시작은 409" 하나다.

### 3.2 운영자가 쓰는 법

1. 조직도의 원천(HRIS 내보내기 등)에서 (하위, 상위) 쌍을 얻는다.
2. 각 조직의 orgCode 를 찾는다 — `GET /admin/organizations/lookup?externalId=`(Entra 는 `objectId` 를 `externalId` 로 보낸다), 또는 `GET /admin/organizations?displayName=`(Okta 는 조직에 `externalId` 를 보내지 않는다).
3. 조직마다 `PUT …/parent` 를 부른다. 뿌리 조직은 `DELETE …/parent`.
4. 멱등이라 매일 전체를 다시 걸어도 된다. wipe 뒤에는 IdP 재프로비저닝이 끝난 다음 다시 건다(H10).

README 에 이 순서와 curl 예를 싣는다. 스크립트 자체는 제공하지 않는다(원천이 회사마다 다르다).

## 4. 저장 (H3·H4)

- **정본 — 하위 조직 파티션의 아이템 하나.** `GROUP#<하위>` / `ASSIGNED_PARENT`, 속성 `parent`. 정렬키가 하나라 지정 상위가 하나임(H4)을 저장소가 지킨다.
- **역색인 — 상위 조직 파티션.** `GROUP#<상위>` / `ASSIGNED_CHILD#<하위>`. "이 조직을 상위로 지정한 하위 조직들" 을 찾는다(H9 조직 지우기, H11 직속 하위 조직). 읽을 때 정본과 맞춰 본다 — 지금의 `BELONGS_TO#`(역색인)와 `MEMBER#`(정본)의 관계와 같다.
- **쓰는 순서.** 지정·바꾸기는 새 역색인 → 정본 → 옛 역색인 지우기. 없애기는 정본 → 역색인. 중간에 멈추면 남는 것은 정본과 맞지 않는 역색인뿐이고, 읽을 때 걸러진다.
- **META·멤버 행은 건드리지 않는다.** META 에 속성을 더하면 `sameContent` 비교 때문에 SCIM 저장마다 META 를 다시 쓴다. 멤버 행에 섞으면 SCIM `GET` 에 나오고 IdP 의 멤버 교체가 지운다(H3).
- **SCIM 이 보는 상태는 바뀌지 않는다.** 지정은 조직의 `updatedAt`(SCIM `meta.lastModified`)을 움직이지 않는다.
- **조직 지우기(`deleteGroup`).** 지금은 키를 하나씩 지운다. 지운 조직의 정본·그 역색인, 지운 조직 파티션의 `ASSIGNED_CHILD#*` 와 그 하위 조직들의 정본을 함께 지운다(H9). 줄을 다 지웠을 때만 불린다 — 일부만 지운 경우는 §5.6.
- **읽기.** `findGroup` 은 조직 파티션 전체를 한 번에 읽는다. 그래서 그 조직의 정본·역색인이 같은 조회에 딸려 온다 — 재적재·아카이빙의 `loadAll`(조직마다 `findGroup`)은 읽기를 더하지 않고 지정 연결을 싣는다(§5.6). 역색인을 정본과 맞춰 보는 것만 하위 조직마다 읽기 하나다.
- **wipe.** `replaceWith(empty)` 가 조직을 `deleteGroup` 으로 지우므로 지정 아이템도 함께 비워진다(H10).

## 5. 튜플과 순환 (H2·H5·H6)

### 5.1 원천 연결

- **원천 연결 = 멤버 행의 하위 조직 연결 ∪ 지정 연결.** 지금 저장소 포트가 적어 둔 불변식 "튜플 그래프 = 멤버 행의 하위 조직 연결 − 보류 목록" 을 "원천 연결 − 보류 목록" 으로 넓힌다.
- 같은 쌍은 한 줄이다(`GroupEdge` 가 같다).

### 5.2 그림과 변환

- `DirectorySnapshot` 에 지정 연결 집합을 더한다(기존 생성자는 빈 집합으로 남긴다 — 호출처가 수백 곳이다). `DirectoryGroup` 은 바꾸지 않는다.
- `TupleMapper` 의 하위 조직 연결 모으기와 `candidateTuples` 가 지정 연결을 더한다. 양끝이 그림에 없으면 지금 규칙처럼 경고하고 건너뛴다. 보류 빼기와 순환 DFS 는 그대로다.
- LDAP 그림은 늘 빈 집합이다. LDAP 결과는 바뀌지 않는다.

### 5.3 SCIM 순증 쓰기

- **IdP 가 조직 P 에서 하위 조직 C 를 빼고(PATCH remove, PUT 멤버 전체 교체), C 의 지정 상위가 P 일 때.** 결과는 이렇다.
  - 멤버 행은 지운다. SCIM `GET` 에서 C 가 빠진다 — IdP 가 본 상태와 같다.
  - `child(C, P)` 는 남긴다. 지정 연결이 받치고 있다.
  - 회수로 기록하지 않는다. 튜플이 그대로이기 때문이다.
- **지금 코드로는 그림만 바꿔서 될 일이 아니다.** `changeGroupInternal` 은 빠지는 멤버를 그림에 싣지 않고 "확인 없이 지울 줄"(`확인없이_지울것`)로 조건 없이 지운다. 그다음 멤버 정리(`reconcileGroupMembers`)는 "있던 줄이 지워지지 않았다" 를 지우기 실패로 읽고 멤버 행을 되살린다. 그래서 둘을 고친다.
  - 락 안에서 빠지는 하위 조직들의 지정 상위를 읽는다. 지정 상위가 이 조직(P)인 하위 조직의 줄을 "확인 없이 지울 줄" 에서 뺀다.
  - 멤버 정리가 그 멤버를 "지움 성공" 으로 본다. 멤버 행이 남으면 IdP 가 같은 빼기를 계속 되풀이한다.
- IdP 가 C 를 P 의 하위로 넣는데 지정 연결로 이미 튜플이 있으면 Check 기준선이 있다고 보므로 쓰지 않는다(지금 동작).
- **관리 API 가 지정을 바꾸거나 없앨 때 IdP 멤버 행이 같은 쌍을 받치고 있으면 줄을 남긴다.** 지정 요청의 그림은 이 조직(C)과 옛·새 상위만 담는다. 각 상위의 멤버로는 "그 상위에 C 의 멤버 행이 있으면 C 하나" 만 싣는다(지금 `findMembers` 로 읽는 것과 같다). 전·후 그림 모두에 그 멤버 연결이 있으므로 diff 가 지우지 않는다.
- 조직 만들기(`upsertGroupInternal`)는 바꾸지 않는다. 새 조직에는 지정 연결이 있을 수 없다.

### 5.4 순환 판정

- `OrgGraph` 가 위로 걸을 때의 부모 = IdP 부모(멤버 행) ∪ 지정 상위 − 보류 목록.
- 관리 API 의 지정은 새 연결 하나가 초점이다(지금의 "초점 하나" 가정과 맞는다). 판정은 지금의 diff 가 한다. 그림 전·후에 그 연결이 있고 Check 로 줄이 없으면 쓸 대상이 되며, 쓸 줄은 순환 판정(`OrgGraph.거른다`)을 거친다. 판정이 보류로 보내는 연결이면 관리 API 는 아무것도 쓰지 않고 거절한다(H5). 같은 P 의 보류 중인 지정도 이 길로 409 가 된다.
- 판정이 쓰기로 결정한 줄이 보류 목록에 있었으면 지금처럼 커밋 뒤 목록에서 뺀다.
- 걷기 예산(`MAX_EXPANSIONS`)을 넘기면 `OrgGraph` 는 `GroupGraphTooLargeException` 을 던진다. SCIM 은 이것을 400 `invalidValue` 로 낸다. 관리 API 도 400 이다(§3.1).

### 5.5 보류 다시 보기

- 하위 조직 연결이 빠지는 요청 뒤 보류 목록을 다시 보는 지금 동작에, 지정 연결이 빠지는 요청(지정 바꾸기·없애기, H9 의 조직 지우기)을 더한다.
- 보류 줄을 버리는 조건은 "멤버 행도 지정 연결도 없다" 다(H6).

### 5.6 재적재·아카이빙·조직 지우기

- **재적재(`mode=tuples`).** 그림에 지정 연결이 실리므로 목표 튜플·장부 훑기·보류 목록 다시 쓰기에 그대로 들어간다.
- **아카이빙.** `candidateTuples` 가 지정 연결을 싣는다. 싣지 않으면 Check 대상에서 빠져 "빠짐" 으로 센다.
- **조직 지우기 — 지울 줄에 지정 연결을 더한다.** 지금 `removeGroupInternal` 은 OpenFGA 를 읽지 않는다. 지울 줄(`조직을_언급하는_튜플`)을 멤버 행과 IdP 상위(`findGroupIdsContaining`)만으로 만든다. 그대로 두면 지정 연결의 `child(G, 지정상위)` 와 `child(지정하위, G)` 가 남는다. G 가 사라진 뒤에도 지정하위의 직원이 G 를 거쳐 지정상위의 member 가 된다 — 권한이 샌다. 그래서 G 의 지정 상위와 G 를 상위로 지정한 하위 조직들(역색인을 정본과 맞춘 것)의 줄을 지울 줄에 더한다.
- **줄을 다 지웠으면** `deleteGroup` 이 지정 아이템을 양방향으로 정리한다(§4).
- **일부만 지웠으면(503, META 를 남기는 지금 길)** 지금 멤버 행과 같은 규칙을 따른다. 줄이 지워진 지정 연결의 아이템만 지우고, 못 지운 것은 남긴다. 조직(META)이 남으므로 IdP 의 재시도가 그 아이템을 다시 읽어 남은 줄을 지운다. 아이템을 먼저 지우면 재시도가 남은 줄을 찾을 길이 없다.
- 지정 연결이 빠지면 끝에서 보류 목록을 다시 본다(§5.5).

## 6. 감사 (H7)

- 원인: `AuditCause` 의 새 종류(관리 API 의 지정 요청). 원천은 SCIM, 행위자는 `client:<sub>`. 아이디는 SCIM 요청과 같은 추적 아이디.
- 하위 조직의 이력에 "지정 상위 P0 → P"(없앰은 P0 → 없음)를 남긴다. 튜플 부여·회수는 지금처럼 함께 남는다.
- IdP 가 조직을 지워 지정 연결이 사라지는 것은 그 SCIM 요청의 기록에 남는다(하위 조직 이력의 "지정 상위 P → 없음").
- 바뀐 것이 없는 요청은 기록하지 않는다.

## 7. 조회 API (H11)

- `GET /admin/organizations/{orgCode}` 에 `assignedParentOrgCode` 를 더한다. 상위 계층(`ancestorsOf`)과 직속 하위 조직(`childrenOf`)은 합집합이다.
- `GET /admin/employees/{employeeId}` 의 상위 계층도 합집합으로 올라간다. 줄마다 실제 판정(Check)은 지금처럼 싣는다 — 재적재가 자른 지정 연결은 판정이 false 로 보인다.
- admin-api 는 두 앱이 함께 쓴다. LDAP 배포에서는 지정 연결이 없으므로 결과가 같다. 비용은 노드마다 읽기 하나 이내로 늘어난다.

## 8. 보안 (H8)

- `ResourceServerSecurityConfig` 에 `PUT /admin/organizations/*/parent`, `DELETE /admin/organizations/*/parent` → `admin.hierarchy` 를 더한다. 지금은 그 밖의 쓰기가 모두 `denyAll` 이다.
- `Scopes` 에 상수를 더하고, 시험용 기본 토큰(`TestAuthAutoConfiguration`)의 범위에 넣는다.
- `app-auth` 개발 클라이언트 `org-chart` 를 더한다. 운영 설정 예시도 같다.
- app-ldap 은 같은 규칙을 받지만 처리기가 없어 범위가 있으면 404 다.

## 9. 시험

- **변환(core).** 지정 연결이 `child` 가 된다. 멤버 연결과 겹치면 한 줄이다. 양끝이 없으면 경고하고 건너뛴다. 보류에 있으면 빠진다. 순환이면 DFS 가 자른다. `candidateTuples` 에 실린다.
- **유스케이스(core, 가짜 저장소·OpenFGA).**
  - 지정 → `child` 쓰기. 같은 지정 다시 → 아무것도 안 함, 기록 없음. 같은 지정인데 줄이 없음 → 쓴다.
  - 바꾸기 → 옛 줄 지우기·새 줄 쓰기. IdP 멤버 연결이 옛 쌍을 받치고 있으면 옛 줄은 남는다.
  - 없애기. 없앤 뒤 보류 줄이 돌아온다.
  - 순환·자기 자신 → 거절, 아무것도 쓰지 않는다. 같은 P 의 보류 중인 지정 → 거절. IdP 연결이 지정 연결과 순환을 닫으면 보류한다.
  - 걷기 예산 초과 → `GroupGraphTooLargeException`.
  - IdP 가 하위 조직 멤버를 빼도(PATCH remove, PUT 전체 교체) 지정 연결이 있으면 줄이 남고, 멤버 행은 지워지며, 회수로 세지 않는다.
  - IdP 가 조직을 지우면 양방향 지정 연결의 줄과 아이템이 지워진다. 지정상위의 member Check 가 지정하위의 직원에게 거짓이 된다.
  - 조직 지우기가 일부만 성공하면 못 지운 지정 연결의 아이템이 남고, 재시도가 마저 지운다.
  - 감사 원인·행위자·이력 항목.
- **저장소(DynamoDB 컨테이너).** 정본·역색인 쓰기 순서, 정본과 맞지 않는 역색인 거르기, `deleteGroup` 의 양방향 정리, `loadAll` 이 지정 연결을 싣는 것, wipe 가 비우는 것, 지정이 META·`updatedAt`·SCIM 멤버를 건드리지 않는 것.
- **종단(app-scim, Testcontainers OpenFGA·DynamoDB).**
  - Entra 처럼 평평한 그룹만 보낸 뒤 지정하면 상위 조직 Check 가 참이다. 이것이 이 슬라이드의 목표다.
  - IdP 의 멤버 전체 교체(PUT)가 지정을 지우지 않는다.
  - `GET /scim/v2/Groups/{id}` 에 지정 연결이 나오지 않는다.
  - 재적재(`mode=tuples`) 뒤 롤업이 남는다. `mode=wipe` 뒤 지정이 없다.
  - 관리 API 의 400·404·409, 락 경합의 503 + `Retry-After`.
- **범위.** 범위×경로 행렬 시험에 두 경로를 더한다. `admin.hierarchy` 없이 403, 토큰 없이 401.
- **규모.** 바뀌는 비용은 요청당 몇 번의 읽기(노드마다)와 재적재의 조직당 읽기 하나 이내다. 새 규모 시험은 두지 않는다. 기존 `scaleTest` 가 그대로 통과하는지만 본다.

## 12. 이 설계가 말할 수 없는 것

- **벤더 동작은 문서 근거다.** Entra·Okta 가 중첩 그룹을 보내지 않는다는 것은 Microsoft Learn(Databricks)·Snowflake·Stalwart·WorkOS 문서에서 왔다. 실제 테넌트로 확인하지 않았다.
- **실제 IdP 와 함께 돌려 보지 않는다.** 종단 시험의 IdP 는 시험이 보내는 SCIM 요청이다.
- **운영자의 원천(HRIS)과의 대응은 이 서버 밖이다.** 조직도와 IdP 그룹을 짝짓는 것은 운영자의 몫이다. 짝이 틀리면 권한이 틀린다.
- **지정 연결의 크기.** 조직 수(수천~수만)만큼이다. 규모 시험으로 재지 않는다(§9).

## 13. 왜 다른 길을 안 갔나

| 길 | 버린 이유 |
|---|---|
| **문서에만 한계를 적는다** | 가장 싸지만 Entra·Okta 배포에서 이 서버가 있는 이유(롤업)가 빠진 채로 남는다. 적는 것은 이 설계에도 들어 있다(H13) |
| **enterprise 속성(`department`·`division`·`organization`)으로 조직을 만든다** | 값이 이름이다 — "불변 id 는 이름에서 만들지 않는다" 를 어긴다. 단계가 셋으로 고정이고, 위아래 관계는 여전히 없다. 그룹 멤버십과 속성이라는 소속의 원천이 둘이 된다 |
| **HRIS(Workday 등) 커넥터** | 배포에 원천이 둘이 된다(SCIM + HRIS). 벤더마다 다르고 여기서 시험할 수 없다. 규모가 슬라이드 하나를 넘는다 |
| **운영자가 SCIM PATCH 로 그룹 안에 그룹을 넣는다(코드 없음)** | 표준이고 지금도 받는다. 그러나 IdP 의 그룹에 IdP 가 모르는 멤버를 섞는다 — 멤버 전체 교체가 조용히 지우고, `GET /Groups` 를 읽는 IdP 가 지우려 할 수 있다. 롤업이 소리 없이 사라진다 |
| **지정 연결을 멤버 행에 표시를 달아 섞는다** | SCIM 멤버를 다루는 모든 길(표현, 교체, PATCH, 스트림)에 예외가 생긴다. 따로 두면 SCIM 쪽은 하나도 바뀌지 않는다 |
| **지정을 META 의 속성으로 둔다** | 역방향(하위 조직들) 찾기가 없고, SCIM 저장마다 META 를 다시 쓴다(§4) |
| **조직도 파일을 한 번에 바꾸는 API** | 전체 비교·부분 실패 처리 코드가 더 든다. 조직마다 PUT 이 멱등이라 스크립트 반복으로 같은 결과다. 필요가 확인되면 그 위에 얹는다 |
| **orgCode 대신 externalId 로 가리킨다** | wipe 뒤에도 남지만 Okta 는 조직에 `externalId` 를 보내지 않는다. 가리키는 값이 둘이면 경우가 나뉜다 |
| **한 조직에 지정 상위 여럿(더하기·빼기 API)** | 옮기기가 두 호출이 되고 중간 상태가 생긴다(H4) |
| **순환을 닫는 지정도 보류한다(거절하지 않고)** | 효과 없는 연결이 저장된 채 204 로 끝난다. 운영자가 알아차리기 어렵다. 재적재가 자른 지정 연결만 보류로 간다(H6) |
| **재적재의 DFS 가 지정 연결을 자르지 않게 한다** | DFS 를 바꿔야 하고 LDAP 의 결과(어느 연결을 자르는지)까지 바뀐다. 지정과 IdP 중첩이 서로 순환을 만드는 배포에서만 드러나는 차이다 |

## 14. 검증

- 머지 전에 전체 `test` 와 `scaleTest` 를 모두 돌린다(메인 세션이, 한 번에 하나씩).
- 종단 시험이 "평평한 그룹 + 지정 → 상위 조직 Check 참" 을 고정한다.

### 15.2 구현 중 판정

- **계획을 쓰며 바로잡은 설계 가정.** 자바는 17 이다(21 아님). `ResponseStatusException` 은 머리를 싣지 못해 `Retry-After` 를 싣는 하위 클래스(`RetryLaterStatusException`)를 두었다. `withLock` 이 원인을 SCIM 요청으로 고정해 만들어 원인 만들기를 인자로 받게 했다. IdP 의 하위 조직 빼기는 지정이 받치는 줄을 "확인 없이 지울 줄" 에서 빼기만 한다 — 그림에 실으면 Check 기준선이 그 줄을 담아 멤버 정리가 멤버 행을 되살린다.
- **`deleteGroup` 의 지정 정리는 정본 → 상위 역색인 순서를 유지했다(과제 2).** 중간에 멈추면 상위 파티션에 낡은 역색인만 남고, 읽을 때 걸러지며 상위를 지울 때 정리된다. 틀렸을 때 비용: 낡은 아이템 몇 개.
- **IdP 가 조직 G 를 지우면 G 자신의 지정 상위도 G 의 이력 줄에 "`assignedParent` P → 없음" 으로 남긴다(과제 4).** 계획은 지정 하위의 줄만 적었다. §6 "하위 조직 이력" 그대로이고, 일부만 지운 경우 살아 있는 G 의 지정이 이력 없이 사라지지 않는다. 틀렸을 때 비용: 이력 줄 하나.
- **저장된 지정 상위의 조직 헤더가 없으면 "지정 없음" 으로 친다(과제 4).** `deleteGroup` 이 META 를 맨 마지막에 지워 계약상 생기지 않는 상태다. 틀렸을 때 비용: 낡은 정본·역색인이 남는다.
- **재적재 보강이 다시 읽은 조직 자신의 지정 상위도 싣는다(과제 5, 리뷰가 찾음).** GSI 에 늦게 잡힌 조직 H 는 `findGroup`(멤버만)으로 다시 읽혀 H 의 지정 상위가 그림에서 빠지고 `child(H,P)` 가 그 재적재에서 지워졌다(회수 쪽, 좁은 창). 보강한 조직마다 `findAssignedParent` 를 더했다.
- **종단 시험 ③ 을 다시 썼다(과제 8, 리뷰가 찾음).** 처음 모양(IdP 멤버가 없는 조직에 빈 PUT)은 §5.3 보호 코드를 지워도 통과했다. IdP 가 같은 쌍을 넣은 뒤 비우게 바꾸고, 보호 코드를 빼면 실패하는 것을 확인했다. 이력 시험이 맨 위 줄을 보므로 둘의 순서를 바꿨다.
- **지정 API 는 원인 사슬에 든 락 경합도 503 으로 낸다(최종 리뷰).** 직접 던진 `LockUnavailableException` 만 바꾸면, 감싸 온 것은 관리 API 처리기가 사슬에서 찾아 409(순환과 같은 코드)로 낸다. 거절 사유 → 상태는 switch 식으로 바꿔 사유가 늘면 컴파일러가 잡는다.

### 15.3 남긴 것

- **벤더 동작은 문서 근거다.** Entra·Okta 가 중첩 그룹을 보내지 않는다는 것을 실제 테넌트로 확인하지 않았다(§12).
- **503 뒤 다른 값으로 바꾸면 줄이 남을 수 있다.** OpenFGA 에 반영한 뒤 저장이 실패하면(503) 장부가 저장된 지정보다 앞선다. 그 상태에서 다른 값으로 바꾸거나 없애면 전 그림이 저장된 옛 값을 실어 503 이전 요청이 쓴 줄이 후보에서 빠지고 남는다 — 아카이빙도 저장 상태로 후보를 만들어 못 잡고, 재적재(`mode=tuples`)만 지운다. 문서(README, 온보딩 09·12)에 "503 이면 다른 값을 걸기 전에 같은 요청을 성공할 때까지 다시 보낸다 — 끝내 안 되면 `mode=tuples`" 를 적었다. 코드로 막지는 않았다.
- **매일 전체를 다시 거는 운용의 비용.** 바뀐 것이 없는 PUT 도 전역 쓰기 락·읽기 몇 번·Check 를 거친다 — 조직 수만큼 IdP 쓰기와 줄을 선다. 문서는 속도 조절이나 조직 상세(`assignedParentOrgCode`)로 먼저 비교하기를 권한다. 다만 먼저 비교해 같은 값을 건너뛰면 "같은 P 로 다시 PUT 하면 빠진 줄을 쓴다" 는 어긋남 복구도 건너뛴다. 정본이 P 이고 Check 가 참이면 락 없이 끝내는 길은 다음 후보다.
- **재적재 DFS 가 지정 연결을 자를 수 있다(H6).** 지정과 IdP 중첩이 서로 순환을 만드는 배포에서만 생긴다. 자른 지정은 보류로 가고, 조직 상세의 판정이 거짓으로 보인다.
- **늘어난 읽기.** 순환 판정은 노드마다 GetItem 하나, `deleteGroup` 은 조직마다 Query 하나와 GetItem 하나, 관리 조회는 노드마다 GetItem 하나(LDAP 배포에서도 빈 읽기)를 더한다. 하위 조직을 빼는 IdP 요청은 빠지는 하위 조직마다 GetItem 하나다. 요청마다 전원을 읽는 곳은 없다.
- **리뷰가 미룬 작은 것.** 시험 단언 보강(중복 제거·잘린 연결 고정·쓰기 순서 실패 주입·키 한도 읽기 등), 비교자 중복, 헤더 조직의 지정 상위 두 번 읽기, 보강 경로의 GetItem 중복, 지정이 받치는 하위만 빠져도 보류 목록을 한 번 읽는 것, README 오류 표의 415 줄, 온보딩 표현 몇 곳(02·09 "유일한 경로", 15 H 표의 출처, 12 §3.7 의 문장·인용 위치, 13 §2.1 PITR 우회).

## 17. 확인할 것 (구현 때 사실로 정한다)

- 관리 API 요청의 추적 아이디가 어디서 오는가(SCIM 요청과 같은 출처인가).
  - **답: 같은 출처다.** `withLock` 이 요청의 Reactor Context 에서 `TraceIds`(app-scim 이 관측 컨텍스트로 현재 span 의 traceId 를 읽게 묶음)로 읽어 `AuditCause.hierarchyRequest(traceId, actor)` 를 만든다. 종단 시험이 `traceparent` 머리의 traceId 가 이력의 `cause.id` 로 나오는 것을 본다.
- 감사 이력 응답(`AuditHistoryItem`)에 지정 변경을 싣는 모양.
  - **답: 기존 `attributes` 칸이다.** `[{"name": "assignedParent", "before": <옛 orgCode|null>, "after": <새 orgCode|null>}]` 이고 다른 속성 뒤에 붙는다. 저장 형식·응답 레코드는 바뀌지 않았다. 원인은 `cause.kind` = `HIERARCHY_REQUEST`, `cause.source` = `SCIM`.
- 일부만 지운 조직 지우기에서 "줄이 지워졌다" 를 지금처럼 `result.deleted()` 로 판정해도 되는가(없는 줄 지우기를 무시하는 옵션의 결과가 deleted 에 들어오는가).
  - **답: 된다.** OpenFGA 쓰기 묶음이 성공하면 요청한 지우기 전부가 `deleted` 에 든다(없는 줄은 `onMissing(IGNORE)` 로 성공). 곧 `deleted().contains(t)` 는 "그 지우기 요청이 실패하지 않았다" 이고, 멤버 행과 같은 판정이다.

**구현 전 점검에서 확인한 것.** 처음 보는 리뷰어가 이 문서만으로 계획을 세워 보며 코드와 맞댔다. 다음은 그 결과로 고친 것이다.
- 조직 지우기가 지정 연결의 줄을 지우지 않는다(§5.6).
- IdP 의 하위 조직 빼기가 지정 줄을 조건 없이 지운다(§5.3).
- 락 경합이 409 로 나가 순환 409 와 섞인다(§3.1).
- 같은 P 의 PUT 이 보류·어긋남을 감춘다(H5, §3.1).
- 걷기 예산 초과가 순환이 아니라 예외다(§5.4).

같은 점검에서 확인된 사실도 있다.
- `findGroup` 은 조직 파티션 전체를 읽는다.
- wipe 는 `replaceWith(empty)` → `deleteGroup` 으로 조직을 지운다.
- 관리 API·SCIM 쓰기·재적재는 같은 락 아이템(`LOCK#MUTATION`)을 쓴다.
