**M2 예시.** 월요일 스냅샷에 park 이 없다 → 화요일 동기화가 park 의 권한을 쓰고 스냅샷 저장 전에 멈춘다 → 수요일 park 입사 취소 → 목요일 동기화는
월요일 스냅샷과 지금 LDAP 을 비교한다. 둘 다 park 이 없으니 지울 게 없다고 본다 → **park 의 권한이 영원히 남는다.** 지운 뒤 멈췄다가 사람이
되살아나면 반대로 권한이 영원히 빠진다.

## 2. 결정 — 사용자와 정한 것 (2026-09-30)

- **app-ldap 은 여러 대도 안전하게 만든다.** 한 대만으로 못 박지 않는다.
- **M2 는 "기록 중" 표시 + 다음 동기화는 장부를 훑어 맞추기로 고친다.** OpenFGA Read(장부 목록 읽기)를 재적재에 더해 **"멈춘 뒤 첫 LDAP 동기화"** 에도
  쓴다. 평소 동기화·SCIM 판단·관리 조회는 여전히 Read 를 쓰지 않는다. 검토한 대안(쓰기 전에 의도를 기록해 기준선을 넓히기 — Read 없음)은 §10.
- 1~5절 설계는 제안대로 승인.

## 3. 작업은 클러스터 전체에서 한 번에 하나 (M14)

### 3.1 app-ldap 도 DynamoDB 락을 쓴다

- app-ldap 의 실행 가드(`SyncExecutionGuard`)를 없앤다. 정기 동기화·수동 동기화·재적재가 모두 **이미 있는 DynamoDB 리스 락**(`MutationLock`)을 잡는다.
  테이블이 앱마다 다르므로 락도 앱마다 따로다. 락 아이템 키 이름 `LOCK#SCIM_WRITE` 는 두 앱이 함께 쓰는 것이라 `LOCK#MUTATION` 으로 바꾼다(운영 배포 전).
- `LockPurpose` 에 LDAP 동기화용 `SYNC` 를 더한다(재적재는 기존 `REBUILD`).
- 못 잡으면: 관리 API 는 곧바로 **409**, 정기 동기화는 "다른 인스턴스가 작업 중이라 건너뛴다" 로그만 남긴다(기록 없음). 재시도하지 않는다.
- 리스는 30초, 작업 동안 10초마다 갱신한다(`dynamodb.lock-renew-interval`). 갱신이 실패하면(=남이 가져갔으면) 작업을 멈추고 FAILED 로 기록한다
  — 지금 SCIM 재적재와 같은 동작이다.

### 3.2 락 작업은 `SyncJobs` 가 한 곳에서 다룬다

- 지금은 SCIM 재적재가 락 잡기·하트비트·리스 상실 시 중단·반납을 직접 한다. 이것을 ②-1 의 `SyncJobs` 로 옮겨 **"락을 잡고 작업 띄우기"** 하나로 만든다:
  락 획득(재시도 없음, 못 잡으면 `LockUnavailableException`) → 실행 기록 열기 → 작업을 요청과 떼어 띄움 → 하트비트 → 리스 상실·기한·서버 종료와 경주 →
  반납 → 기록. SCIM 재적재, LDAP 동기화, LDAP 재적재가 같은 코드를 탄다.
- ②-1 의 "바깥에서 반납 수단을 넘기는" 시작 방식은 바깥에서 쓰는 곳이 없어지므로 공개 API 에서 뺀다(패키지 안에서 "락을 잡고 띄우기"가 쓰는 기본 단위로 남긴다).

### 3.3 끝나지 못한 기록은 락을 잡은 다음 작업이 닫는다

- ②-1 의 앱 시작 때 정리(`InterruptedRunCleanup`)를 없앤다. 여러 대면 다른 대가 돌리는 중인 기록을 닫는다.
- 대신 **락을 잡은 작업이 시작할 때** 같은 앱의 락 작업 기록 중 RUNNING 인 것을 FAILED("비정상 종료로 중단")로 닫는다. 락을 쥐었으니 그것들은 반드시
  죽은 작업이다(강제 종료·정전·다른 대의 비정상 종료). 락 작업 트리거: app-ldap 은 `SCHEDULED`·`MANUAL`·`FORCED`·`REBUILD`, app-scim 은
  `REBUILD`·`RESET`. SCIM 아카이빙(`ARCHIVE`) 기록은 건드리지 않는다.
- 닫기는 "아직 RUNNING 일 때만" 조건부 쓰기다. 앞 작업이 반납한 뒤·결과를 쓰기 전의 틈에 다음 작업이 락을 잡으면, 막 끝난 기록이 RUNNING 으로 보일 수 있다(읽기는 최종 일관성). 조건이 있으면 어느 쪽 쓰기가 먼저 닿든 결과가 맞다.

## 4. 쓰기 시작 뒤 기록 전에 멈췄으면, 다음 동기화는 장부를 훑어 맞춘다 (M2)

### 4.1 "기록 중" 표시

- 최신 스냅샷을 가리키는 포인터 줄에 "기록 중" 칸(`writingSince`, 쓰기를 시작한 시각)을 둔다. LDAP 동기화가 **OpenFGA 에 쓰기 직전** 이 칸을 붙인다(쓸 게 없는 회차는
  붙이지 않는다). 스냅샷 저장의 마지막 단계가 포인터를 통째로 새로 쓰면서 칸이 저절로 없어진다.
- 그래서 칸이 남아 있다는 것 = "OpenFGA 에 쓰기 시작했는데 기록을 끝내지 못했다". 스냅샷 저장 실패·강제 종료·기한 초과·서버 종료·리스 상실이 모두
  여기에 걸린다. 차단기로 멈춘 동기화는 ②-1 대로 나간 쓰기로 스냅샷을 남기므로 칸이 사라진다(기준선이 정확하다).
- LDAP 재적재도 쓰기 전에 칸을 붙인다. 재적재가 중간에 멈추면 다음 동기화가 맞춘다.
- 포인터가 아직 없는 첫 설치에서도 칸을 붙일 수 있다 — 칸만 있고 스냅샷 번호가 없는 포인터는 "기준선 없음"으로 읽는다.
- SCIM 은 판단을 Check 로 하고 스냅샷을 비교 기준으로 쓰지 않으므로 표시를 쓰지 않는다.

### 4.2 다음 동기화

- 정기·수동 동기화가 칸을 보면 스냅샷 비교(diff) 대신 **재적재와 같은 청소**(`TupleReconciler`: 있어야 할 줄 D 를 쓰고 → 장부를 Read 로 훑어 →
  D 에 없는 줄을 지우고 → 스냅샷 = 쓴 줄 ∪ 지우지 못한 줄)를 한 번 한다. 스냅샷을 새로 저장하므로 칸이 사라진다. 이어서 현재상태를 LDAP 대로 바꾼다.
- 실행 기록의 트리거는 원래대로(`SCHEDULED`·`MANUAL`·`FORCED`)이고, 메시지에 "기준선 의심 — 장부를 훑어 맞췄다"를 남긴다.
- 비용: 멈춘 뒤 첫 회차만 재적재 수준(10만 명 약 1분, ②-1 §9 추정). 평소에는 포인터 줄 쓰기(UpdateItem) 한 번이 는다.

### 4.3 삭제 가드를 훑어 맞추기와 재적재에도 건다 (빈 D 가드 포함)

- 청소는 D 를 쓰고 장부를 훑은 뒤, **지우기 전에** 가드를 본다: "지울 줄 수 / 훑은 줄 수"가 동기화와 같은 임계치(`sync.deletion-guard`, 기본 30%,
  최소 기준 10줄)를 넘으면 지우지 않고 ABORTED 로 끝낸다. 스냅샷을 새로 저장하지 않으므로 "기록 중" 칸이 남아 다음 회차도 다시 확인한다.
- `FORCED`(수동 동기화 `force=true`)는 가드를 건너뛴다(지금과 같다).
- **수동 재적재에도 같은 가드를 건다.** 지금은 재적재가 가드를 건너뛰어 LDAP 이 0명을 돌려주면 장부 전체를 지운다. `POST /admin/sync/rebuild?force=true`
  를 더해 사람이 확인한 뒤 넘기게 한다.
- SCIM `tuples` 는 가드 설정이 없으므로 한 규칙만: 조직도가 비었는데(D = ∅) 장부에 지울 줄이 있으면 지우지 않고 FAILED("조직도가 비어 있다 — 장부를
  비우려면 mode=wipe"). `wipe` 는 가드가 없다(확인값으로 이미 확인했다).
- 가드 판정은 `DeletionGuard` 가 한다 — "지울 수 / 기준 수" 로 판정하는 입구를 하나 더해 diff 와 청소가 같은 규칙을 쓴다.

### 4.4 정리

- ②-1 뒤로 아무도 부르지 않는 `TupleSnapshotRepository#reset()`(재적재 전용이던 전체 삭제)과 그 구현·테스트를 지운다.

## 5. 하루 한 번 작업은 클러스터 전체에서 한 번만 (M15)

### 5.1 하루 1회 표지

- DynamoDB 에 `DAILY#<작업>#<날짜>` 한 줄을 조건부 쓰기(`attribute_not_exists`)로 먼저 잡는다. 잡은 인스턴스만 그날 작업을 돌리고, 다른 대는 "오늘은
  다른 인스턴스가 이미 했다" 로그만 남기고 건너뛴다. 표지는 사흘 뒤 테이블 TTL 로 사라진다. 날짜는 앱 시계의 UTC 날짜다.
- 대상: app-scim 아카이빙(03:00), app-scim 만료 스냅샷 정리(04:00), app-ldap 만료 스냅샷 정리(04:00). 매일 동기화는 §3 의 락이 막는다.
- 새 core 포트 하나(`DailyJobClaims#claim(job, day)`)와 DynamoDB 구현. 표지를 잡는 일은 스케줄러가 하고, 잡지 못하면 작업을 부르지 않는다.

### 5.2 재적재와 겹치면 아카이빙은 건너뛴다

- 아카이빙은 표지를 잡은 뒤, 시작 전에 SCIM 락을 **들여다본다**(`MutationLock#peek` — 지금 쥔 목적, 없거나 만료면 빈 값). 재적재(`REBUILD`)가 쥐고 있으면
  그날 아카이빙을 하지 않고 실행 기록에 ABORTED("재적재 중이라 건너뜀")를 남긴다. 표지를 먼저 잡으므로 이 기록은 하루 하나다.
- 락을 잡지는 않는다 — 아카이빙이 락을 잡으면 몇 분 동안 SCIM 쓰기가 전부 503 이다.
- 재적재가 아카이빙 도중에 시작되는 경우는 막지 않는다(드물고, ②-1 뒤로 장부가 비는 일은 없다).

## 6. 잘못된 줄 하나가 묶음 전체를 끌고 가지 않게 (M16)

### 6.1 오류를 둘로 나눈다

- **400(`FgaApiValidationError` — OpenFGA 가 요청 내용을 거절: 없는 타입, 너무 긴 아이디 등)**: 다시 보내도 같다. 재시도하지 않는다.
- **그 밖**(연결 실패·타임아웃·5xx·429 등): 지금처럼 `openfga.max-retries`(3)번 200ms 부터 늘려 가며 다시 보낸다.

### 6.2 400 을 받은 묶음은 반씩 쪼개 다시 보낸다

- 거절된 묶음을 반으로 나눠 각각 보내고, 거절된 쪽을 또 반으로 나눈다. 한 줄까지 좁혀도 거절되면 그 줄만 실패로 남기고, 사유에 OpenFGA 가 준 거절 이유를 적는다.
- 100줄에 나쁜 줄 하나면 호출이 약 14번 늘고 나머지 99줄은 반영된다. 다음 회차도 같은 식이라 "같은 99명이 매번 빠지는" 일이 없다.

### 6.3 연속 실패 차단기는 "한 줄도 못 살린 묶음"만 센다

- 묶음 안에서 **한 줄도 반영되지 못했을 때만**(일시 오류로 다 실패했거나, 쪼개도 전부 거절됐거나) 연속 실패로 센다. 쪼개서 일부라도 살렸으면 셈을 처음부터
  다시 한다. 나쁜 줄이 여기저기 있어도 끝까지 보내고 PARTIAL 로 끝난다.
- 인가 모델이 통째로 없어 모든 줄이 거절되는 경우는 세 묶음 뒤에 멈춘다(쪼개는 비용으로 묶음당 최대 약 200번 호출, 멈추기까지 약 600번).

### 6.4 장부 훑기도 같은 분류

- 장부 훑기(Read)도 일시 오류만 다시 시도한다. 재시도를 다 쓰면 원래 오류를 그대로 던져 실행 기록에 진짜 원인이 남게 한다
  (`onRetryExhaustedThrow` — ②-1 최종 리뷰에서 남긴 한 줄).

## 7. README

- "app-ldap 여러 대 띄우기" 절: 동기화·재적재는 DynamoDB 락으로 클러스터 전체에서 하나, 못 잡으면 409·정기 동기화는 건너뜀, 리스 갱신·상실.
- 재적재·수동 동기화 절: "기록 중" 표시와 멈춘 뒤 첫 동기화의 훑어 맞추기, 삭제 가드가 훑어 맞추기·재적재에도 걸림, `rebuild?force=true`,
  SCIM `tuples` 의 빈 조직도 규칙, 끝나지 못한 기록은 다음 락 작업이 "비정상 종료로 중단"으로 닫음.
- 하루 1회 작업(아카이빙·정리)은 클러스터 전체에서 한 번, 재적재 중이면 아카이빙 건너뜀.
- OpenFGA 쓰기: 400 은 재시도 없이 반씩 쪼개 나쁜 줄만 실패, 차단기는 한 줄도 못 살린 묶음만 셈.
- "Read 는 재적재에서만" 문장을 "재적재와 멈춘 뒤 첫 동기화에서만"으로 고친다.

## 8. 검증

테스트 규칙은 기존과 같다(Lombok, AssertJ, BDD, 한글 `@DisplayName`). 각 테스트는 먼저 지금 코드로 실패하는 것을 본 뒤 고친다.

| 대상 | 확인할 것 | 모듈 |
|---|---|---|
| 클러스터 락 | 같은 테이블을 쓰는 두 인스턴스가 동시에 동기화를 걸면 한쪽만 돈다. 관리 API 는 409, 정기 동기화는 건너뛴다. 작업 도중 리스를 뺏으면 멈추고 FAILED | core·app-ldap |
| 죽은 기록 정리 | 락을 잡은 작업이 시작할 때 같은 앱의 RUNNING 락 작업 기록을 "비정상 종료로 중단"으로 닫는다. SCIM 아카이빙 기록은 그대로다 | core |
| 기준선 의심 | 쓰기 뒤·스냅샷 저장 전에 멈추면(저장 실패·기한·종료) 칸이 남는다. 다음 회차는 훑어 맞추고, §1 의 park 예시에서 권한이 남지 않는다(빠지는 쪽도). 가드를 넘으면 ABORTED 이고 칸이 남는다. `force` 면 진행한다. 칸만 있고 스냅샷 번호가 없는 포인터는 "기준선 없음"이다 | core·storage·app-ldap E2E |
| 재적재 가드 | LDAP 이 0명을 돌려주면 재적재가 장부를 지우지 않고 ABORTED, `force=true` 면 진행. SCIM `tuples` 에 빈 조직도 + 장부에 줄이 있으면 FAILED | core·app |
| 하루 1회 | 같은 날 두 번 잡으면 두 번째는 못 잡는다. 재적재가 락을 쥐고 있으면 아카이빙은 ABORTED("재적재 중이라 건너뜀") | core·storage·app-scim |

## 10. 왜 다른 길을 안 갔나

- **M14 — "한 대만"을 문서·시작 검사로 못 박기.** 락 코드가 필요 없지만 두 대를 띄우면 막지 못한다. 사용자가 여러 대를 원했다.
- **M14 — 리더 선출(한 대만 스케줄러를 돌림).** 수동 API 겹침은 여전히 막아야 해서 락이 어차피 필요하다. 락 하나로 둘 다 막는다.
- **M2 — 쓰기 전에 "이번에 쓸 것"(의도)을 기록하고 다음 회차가 기준선을 넓히기.** 지울 판단은 "스냅샷 + 의도한 쓰기", 쓸 판단은 "스냅샷 − 의도한 지우기"로.
  Read 를 쓰지 않지만 매 회차 DynamoDB 쓰기가 늘고(첫 적재 11만 줄), 비교 규칙이 복잡해지며, 멈춘 재적재(의도 = D 전체)는 따로 다뤄야 한다.
- **M2 — 직전 델타만 BatchCheck 로 관찰.** 델타를 어딘가 저장해야 하는 것은 위와 같고, 관찰은 기준선을 고칠 뿐 스냅샷에 없는 찌꺼기는 못 찾는다.
- **M2 — 한계로 두고 알리기만.** 코드는 거의 안 바뀌지만 아무도 안 보면 어긋난 채 남는다.
- **M15 — 아카이빙이 SCIM 락을 잡기.** 한 번만 돌고 재적재와도 안 겹치지만, 아카이빙(몇 분) 동안 SCIM 쓰기가 전부 503 이다.
- **M15 — RUNNING 재적재 기록을 보고 건너뛰기.** 강제 종료로 RUNNING 이 남으면 아카이빙이 영영 건너뛰어진다. 락을 들여다보는 쪽은 TTL 이 지나면 풀린다.
- **M16 — 입구에서 아이디 길이만 검사.** 나쁜 줄이 들어오는 길이 길이 하나가 아니다(모델 변경 등). 쪼개 보내기는 원인과 상관없이 나머지를 살린다.
  입구 검사는 식별자를 다루는 권고 ④에서 더한다.
- **M16 — 처음부터 한 줄씩 쓰기.** 10만 줄이면 호출이 100배다.

## 11. 이 설계가 말할 수 없는 것

- **락은 완벽한 상호 배제가 아니다.** GC 정지 등으로 살아 있는데 리스가 만료되면 늦은 쓰기가 새어 나갈 수 있다(SCIM 과 같은 한계, OpenFGA 에 펜싱 토큰이 없다).
- **"기록 중" 칸을 붙이는 쓰기가 실패하면 그 회차는 OpenFGA 에 쓰지 않고 FAILED 다** — 칸 없이 쓰기 시작하는 일은 없다. 반대로 칸을 붙인 뒤 OpenFGA 에 아무것도
  못 쓰고 멈춰도 다음 회차는 훑어 맞춘다(불필요하지만 안전하다).
- **훑어 맞추기는 장부를 이 서버만 쓴다는 전제다**(②-1 §11 과 같다). 다른 앱이 직접 쓴 줄은 지워진다.
- **아카이빙은 한 시점의 사진이 아니다.** 읽는 도중 SCIM 쓰기가 끼면 거짓 어긋남이 나올 수 있다(범위 밖).
- **쪼개 보내기는 나쁜 줄이 많을수록 호출이 는다**(나쁜 줄 k 개면 대략 2k·log₂100). 모델이 통째로 없으면 차단기가 멈춘다.
- **하루 1회 날짜는 UTC 다.** 스케줄 시각(서버 시간대)과 날짜 경계가 다를 수 있지만 "하루 한 번"은 지켜진다.
- **첫 전체 동기화가 기한(30분)을 넘길 만큼 느리면** 멈출 때마다 칸이 남고 다음 회차가 다시 훑어 맞춘다 — 진행은 되지만 매번 처음부터 쓴다. ②-1 §9 추정은 약 2.5분이라
  여유가 있다. 실연동에서 기한에 가까우면 진행분을 나눠 남기는 방식을 따로 설계한다.
