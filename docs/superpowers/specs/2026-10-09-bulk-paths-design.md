# 대량 경로 비용 — 튜플 스냅샷은 압축 묶음으로, `loadAll` 의 직원 읽기는 BatchGet 으로

- 날짜: 2026-10-09
- 근거: 기존 백로그 둘. `docs/superpowers/specs/2026-09-25-gsi1-hot-partition-design.md` §10 에서 처음 찾았다.
  - 튜플 스냅샷의 쏠림
  - `loadAll` 의 직원 한 명당 GetItem
- 전제:
  - 실제 규모는 10만 명 이상이고, 튜플은 약 15만 줄로 잡는다(직원 1인당 소속 약 1.5).
  - 운영 배포 전이라 저장 형식을 바꿔도 이관 코드를 만들지 않는다.
  - 표준이 정한 신호만 받는다.
  - 배포 하나는 LDAP 아니면 SCIM 이다.

## 1. 문제

| 항목 | 지금 | 결과 |
|---|---|---|
| 튜플 스냅샷 | 튜플 한 줄이 아이템 하나다. 모두 `SNAPSHOT#id` 파티션 하나에 쓴다(`DynamoDbTupleSnapshotRepository.writeTuples`). 읽기·지우기는 늘 통째로 하고, 무결성은 메타의 `tupleCount` 로 본다 | 변경이 있는 LDAP 동기화마다, 그리고 SCIM 아카이빙·재적재·장부 맞추기마다 아이템 약 15만 개를 쓴다. 약 15만 WCU, 약 6천 요청이 한 파티션에 몰린다. 한 파티션의 쓰기 한도는 초당 1,000번이라 자동 분할 전까지 최소 2~3분이고 스로틀을 맞는다 |
| `loadAll` | 직원 아이디를 GSI1 로 훑은 뒤 직원마다 GetItem(강한 일관성)을 한다. 조직은 조직마다 파티션 전체를 Query 한다(`DynamoDbDirectoryStateRepository.loadAll`) | 직원 10만 명이면 GetItem 10만 번 — 수십 초의 왕복이다. 쓰는 곳은 SCIM 스냅샷 아카이빙(매일)과 SCIM 재적재다. RCU(약 10만)는 온디맨드 요금으로 미미하다 |

## 2. 결정 (사용자 확인, 2026-10-09)

- **스냅샷은 압축 묶음으로 저장한다.** 튜플 목록을 gzip 으로 압축해 350KB 이하 묶음 아이템 몇 개로 나눈다.
  - 고르지 않은 안: 파티션 나누기, 바뀐 것만 저장하기(§9).
- **`loadAll` 의 직원은 GSI1 로 아이디를 훑고 BatchGet(100개씩, 강한 일관성)으로 읽는다.** 기존 `findUsers` 를 쓴다.
  - 고르지 않은 안: GSI1 내용을 그대로 쓰기(§9).

## 3. 튜플 스냅샷 — 압축 묶음

### 3.1 저장 모양

- 튜플을 지금 쓰는 문자열 표기(`Keys.tupleSk`, `TUPLE#<user>#<relation>#<object>`)로 한 줄에 하나씩 적는다. 줄 사이는 `\n` 이다.
- 목록 전체를 UTF-8 로 바꿔 gzip 으로 압축한다.
- 압축한 바이트를 350,000바이트 이하 조각으로 나눈다. 아이템 한도는 400KB 이고, 키와 속성 이름이 들어갈 자리를 남긴다.
- 조각 하나가 묶음 아이템 하나다.
  - `PK = SNAPSHOT#<id>`, `SK = CHUNK#0000`, `CHUNK#0001`, …
  - 번호는 네 자리라 정렬 순서가 곧 이어 붙일 순서다. 조각이 1만 개를 넘을 일은 없다(3.5GB).
  - 본문은 이진 속성 `data` 하나다.
- 튜플이 0개여도 묶음은 하나다(빈 목록의 압축본). 그래야 "묶음이 없다" 를 늘 무결성 오류로 볼 수 있다.
- 메타:
  - 지금 있는 것(`createdAt`, `source`, `tupleCount`, `retainUntil`, GSI1 `SNAPSHOT_INDEX` 키)은 그대로 둔다.
  - `chunkCount` 를 더한다.

### 3.2 순서와 무결성 (지금 규칙 그대로)

- **쓰기:** 메타 → 묶음 → 포인터.
  - 메타가 먼저라 묶음을 쓰다 죽어도 정리가 그 조각을 찾아 지운다.
  - 포인터가 마지막이라 반쪽 스냅샷이 기준선이 되지 않는다.
  - 묶음은 하나씩 차례로 PutItem 으로 보낸다(3.3).
- **읽기(`findById`·`findLatest`):** 파티션을 강한 일관성으로 Query 한다.
  - 메타가 없으면 빈 결과다(지금과 같다).
  - 다음 넷은 모두 `SnapshotIntegrityException` 이다. 복구는 지금처럼 재적재다.
    - 묶음 수가 `chunkCount` 와 다르다(메타에 `chunkCount` 가 없는 옛 형식 포함).
    - 번호가 0부터 이어지지 않는다.
    - 압축을 풀 수 없다.
    - 풀어서 센 튜플 수가 `tupleCount` 와 다르다.
- **지우기(`purgeExpired`):** 묶음 먼저(하나씩 DeleteItem), 메타 마지막.
  - 지금 코드는 "파티션에서 메타가 아닌 줄 전부" 를 지우므로 옛 형식의 튜플 줄도 함께 지워진다.
- **옛 형식:** 튜플 줄만 있고 묶음이 없는 스냅샷은 무결성 오류다. 지금 깨진 스냅샷과 같은 길로 재적재가 고친다. 운영 배포 전이라 이관 코드는 없다.

### 3.3 효과(추정, 튜플 15만 줄)

- 원본 약 12MB 는 압축하면 약 4~6MB 다. 아이디가 UUID 라 압축률은 2~3배로 잡았다. 묶음은 15개 남짓이다.
- 쓰기: 약 15만 WCU → 약 5천 WCU, 요청 약 6천 번 → 약 15번.
- 한 파티션에 몰리는 쓰기가 약 30분의 1 로 준다. 0 은 아니다.
  - 묶음 하나는 최대 350 WCU 다. 15개면 한 파티션의 쓰기 한도(초당 1,000)로 약 5초다.
  - 그래서 묶음은 하나씩 차례로 PutItem 으로 보낸다. 여러 개를 BatchWriteItem 에 담으면 일부만 처리되고, `BatchRequests` 의 재시도 예산(약 1.5초)이 모자랄 수 있다.
  - 하나씩이면 스로틀이 요청 전체의 오류로 온다. 그것은 SDK 재시도(이 클라이언트의 DynamoDB 기본값: 최대 9번, 지수 백오프 — SDK 2.28.29 `DynamoDbRetryPolicy`)가 받는다.
- 읽기 비용은 약 절반이다(Query 는 읽은 바이트로 센다).

### 3.4 그대로인 것

- `TupleSnapshotRepository` 포트, 포인터, "기록 중" 표시(`markWriting`·`isWriting`), 보관 기한(`retainUntil`)과 최신을 건너뛰는 정리, `listRecent`(메타만 읽는다).
- 부르는 쪽(LDAP 동기화, 장부 맞추기, SCIM 아카이빙·재적재)은 고치지 않는다.

## 4. `loadAll` — 직원은 BatchGet 으로

- 직원 아이디는 지금처럼 GSI1 `USER_INDEX` 파티션을 훑어 얻는다.
- 읽기는 100개씩 묶어 기존 `findUsers` 로 한다.
  - 강한 일관성 BatchGet 이고, 동시 8이다.
  - `BatchRequests` 가 처리되지 않은 키를 최대 5번, 100ms 부터 두 배로 늘려 다시 보낸다.
- 훑은 뒤 읽기 전에 지워진 직원은 결과에 없다(지금 `findUser` 가 빈 값일 때와 같다).
- 조직은 지금처럼 조직마다 파티션을 읽는다(`findGroup`). 멤버 목록이 필요해 피할 수 없다.
- 효과: GetItem 10만 번이 BatchGet 약 1천 번이 된다. 왕복이 100분의 1 이다. RCU 는 그대로다.
- 그대로인 것:
  - 포트, 결과(`DirectorySnapshot`), 부르는 두 곳.
  - GSI 로 훑는 탓에 방금 만든 직원이 빠질 수 있는 성질(점검 S17). 이미 받아들였고 범위 밖이다.

## 8. 이 설계가 말할 수 없는 것

- **압축률은 추정이다.** UUID 아이디는 잘 압축되지 않는다. 규모 테스트의 실측을 §10 에 적는다.
- **스냅샷 하나를 메모리에 통째로 든다.** 지금도 `TupleSnapshot` 이 튜플 집합을 통째로 든다. 압축본 몇 MB 가 잠깐 더해진다.
- **`loadAll` 은 GSI 로 훑는다.** 방금 만든 직원이 빠질 수 있는 창(점검 S17)은 그대로다.
- **DynamoDB Local 의 시간은 AWS 와 다르다.** 요청 수와 바이트만 믿는다.
- **AWS 의 스로틀은 확인하지 못한다.** 한 파티션에 약 5초 걸릴 쓰기를 묶음마다 SDK 재시도가 받는다고 본 것(3.3)은 DynamoDB Local 로 확인할 수 없다.
  - 저장이 실패하면 지금 규칙대로다. LDAP 은 "기록 중" 표시가 남아 다음 회차가 장부를 훑어 맞춘다. SCIM 재적재·아카이빙은 `FAILED` 로 남는다.
- **정리도 한 파티션에 몰린다.** 묶음을 지우는 것도 묶음 크기만큼 WCU 를 쓴다.
  - 정리도 묶음을 하나씩 DeleteItem 으로 지운다(쓰기와 같은 까닭, 3.3). 옛 형식 튜플 줄은 지금처럼 묶음 요청으로 지운다.
  - 스로틀로 끝내 실패하면 메타가 남아 다음 정리가 남은 것을 이어 지운다.
- **줄바꿈이 든 튜플은 저장하지 않는다.** 아이디에는 줄바꿈이 없다(`IdNormalizer` 가 공백류를 걸러낸다). 그래도 섞이면 조용히 다른 튜플로 되읽히지 않게 저장을 실패시킨다.

## 9. 왜 다른 길을 안 갔나

- **스냅샷 파티션 나누기(`SNAPSHOT#id#0..15`).** 쏠림은 풀리지만 쓰기 양(15만 WCU)과 요청 수는 그대로다.
- **바뀐 것만 저장하기.** 쓰기 양이 가장 적다. 그러나 읽을 때 조각을 이어 붙여야 하고 합치기·정리·무결성이 복잡해진다. 기준선은 통째로 쓰는 물건이라 이득이 작다.
- **`loadAll` 이 GSI1 내용을 그대로 쓰기.** 가장 싸다(Query 약 50쪽, RCU 약 6천). 그러나 재적재 직전(1초 안)의 변경이 반영되지 않을 수 있다. 재적재는 장부를 바로잡는 권위 있는 연산이라, 들어오자마자의 비활성화를 놓쳐 퇴사자 권한이 남는 틈을 두지 않는다.

### 10.2 구현 중 판정

- **정리도 묶음을 하나씩 DeleteItem 으로 지운다(§3.2·§8 고침).** 과제 2 리뷰가 찾았다.
  - DeleteItem 도 지우는 아이템 크기만큼 WCU 를 쓴다.
  - 묶음 요청 하나에 묶음 18개를 담으면 쓰기와 같은 한 파티션 한도에 걸린다. 그러면 `BatchRequests` 의 재시도 예산(약 1.5초)이 모자란다.
  - 그 실패가 `purgeExpired` 의 `flatMap(…, 4)` 에서 함께 돌던 다른 스냅샷 정리까지 끊는다.
  - 옛 형식 튜플 줄만 묶음 요청으로 지운다.
- **S18-b(`ScimRebuildLockScaleTest`)의 전제를 속도와 무관하게 바꿨다.**
  - 이 테스트는 리스 TTL 2초, 갱신 주기 500ms 를 두고 갱신 5번 이상을 요구한다. "재적재가 리스 TTL 보다 오래 락을 쥔다" 가 전제다.
  - `loadAll` 이 빨라져 5천 명 재적재가 1.7초가 되자 갱신이 4번에 그쳤다. 재적재는 성공했고 쓰기는 503 이었으니 제품은 맞다.
  - 그래서 테스트에서만 락 안의 읽기 단계(`loadAll`)를 스파이로 TTL + 1초 늦춘다. 단언은 그대로다.
  - TTL 을 줄이는 길은 버렸다. 다음 속도 개선 때 또 깨지고 리스 여유가 준다.
  - 지연 동안에도 쓰기를 두드리므로 시도 상한을 넉넉히 올렸다. 상한에 먼저 닿으면 장부를 고치는 뒷부분을 두드리지 못한다.
