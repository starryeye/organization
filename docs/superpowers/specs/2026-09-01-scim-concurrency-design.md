# SCIM 쓰기 경로 동시성 설계

**작성일:** 2026-09-01
**상태:** 승인됨
**선행 기록:** `docs/superpowers/plans/2026-08-15-follow-ups.md` §6 (의도적으로 미룬 설계 결정)

---

## 1. 왜 지금인가

app-scim 을 **가용성 목적**으로 여러 대 띄운다. 한 대가 죽어도 IdP 의 프로비저닝
push 가 유실되지 않아야 한다.

그 순간 follow-ups §6 이 기록해 둔 문제가 실제 문제가 된다. 두 요청이 각자 자기
시점에서 올바르게 동작하고 **둘 다 200 을 반환하는데 결과가 틀린다**:

```
        A: upsertUser(kim, 비활성)          B: upsertGroup(DEV001 + kim)
 t1  읽기: kim 활성
 t2                                      읽기: kim 활성, DEV001 에 kim 없음
 t3  계산: 지울 튜플 없음
 t4                                      계산: dm(kim,DEV001) 추가
 t5  커밋: kim 비활성                        200
 t6                                      OpenFGA: dm(kim,DEV001) 씀
 t7                                      커밋: DEV001 에 kim         200
```

최종 상태("kim 비활성 + DEV001 이 kim 포함")가 요구하는 튜플은 없음인데 OpenFGA 에는
`dm(kim,DEV001)` 이 남는다. **퇴사자 권한이 살아남는 방향이다.**

가용성 목적이라는 점이 설계를 크게 좌우한다. 동시 쓰기는 드물다 — 따라서 **직렬화
비용을 거의 치르지 않는다.**

---

## 2. 두 가지 문제, 두 가지 장치

follow-ups §6 은 서로 다른 두 문제를 담고 있다.

| | 문제 | 장치 |
|---|---|---|
| **A** | 동시 쓰기가 서로를 덮어쓴다 | 분산 락 — 경합 자체를 없앤다 |
| **B** | 어긋나도 스스로 모르고 스스로 못 고친다 | Check 기준선 — 만질 때마다 대조한다 |

### B 를 다시 설명하면

LDAP 은 매일 전체를 다시 계산해 자가 치유가 된다. SCIM 은 델타만 적용하므로 전체를
다시 보는 순간이 오지 않는다. 그리고 더 중요한 것:

**diff 의 양쪽 재료가 모두 DynamoDB 다.**

```
before = TupleMapper(변경 전 DynamoDB 상태)
after  = TupleMapper(변경 후 DynamoDB 상태)
```

"OpenFGA 에 실제로 무엇이 있나" 를 한 번도 묻지 않는다. 그래서 위 경합으로 남은
`dm(kim,DEV001)` 은 이후 어떤 연산도 발견하지 못한다 — 계산은 매번 정확하고, 틀린
곳을 볼 방법이 구조적으로 없을 뿐이다.

**락만으로는 B 가 남는다.** OpenFGA 쓰기 성공 직후 DynamoDB 커밋 전에 프로세스가
죽고 IdP 가 재시도하지 않으면 같은 결과가 된다. follow-ups §6 의 "장애는 이미 안전하다" 는
IdP 가 재시도한다는 전제 위에 있었다.

## 3. 전체 흐름

```
SCIM 쓰기 요청
     │
     ▼
┌─────────────────────────────────────────┐
│ ① 분산 락 획득 (DynamoDB 조건부 쓰기)      │  인스턴스 전체에서 한 번에 하나
└─────────────────────────────────────────┘
     │
     ▼
  후보     = 이번 연산이 건드릴 수 있는 튜플 (active·순환 필터 적용 전)
  원하는것 = TupleMapper(변경 후 상태)          (필터 적용)
  실제     = BatchCheck(후보)                  ② OpenFGA 의 실제 상태
  델타     = 원하는것 - 실제 / 실제 - 원하는것
     │
     ▼
  리스 재확인 → OpenFGA 쓰기 → DynamoDB 커밋   순서는 기존 그대로
     │
     ▼
┌─────────────────────────────────────────┐
│ 락 반납 (성공·실패·취소 어느 경로든)         │
└─────────────────────────────────────────┘
```

**OpenFGA → DynamoDB 순서는 바꾸지 않는다.** 반대로 하면 중간 실패가 영구 어긋남이
된다 — 상태는 "됐다" 는데 OpenFGA 엔 없고, 다음 델타는 상태 기준이라 이미 반영된
것으로 본다.

### 구성 요소

| | 변경 |
|---|---|
| `core` | `MutationLock` 포트 추가, `RelationTupleChecker` 에 배치 메서드 추가 |
| `core` | **`MutationGate` 삭제** — 분산 락이 흡수 |
| `core` | `IncrementalSyncUseCase` 의 기준선 출처 변경, 락 획득 |
| `core` | `ScimRebuildUseCase` 가 같은 락을 잡음 |
| `storage-dynamodb` | `MutationLock` 의 DynamoDB 구현 |
| `authz-openfga` | `OpenFgaRelationTupleChecker` 에 BatchCheck 구현 |

새 인프라는 없다. 락은 **기존 단일 테이블에 아이템 하나**로 얹는다.

## 4. 분산 락

### 4.1 왜 전역 락인가

엔티티별 락도 검토했으나 전역 락을 택한다.

엔티티별 락의 근본 난점은 **무엇을 잠글지 정하는 것 자체가 읽기**라는 것이다.
`upsertUser(kim)` 이 잠가야 할 것은 kim 만이 아니라 kim 이 속한 조직들인데, 그
목록은 DynamoDB 를 읽어야 안다. 반대로 `PUT /Groups/DEV001 {members:[park]}` 는
요청에 kim 이 적혀 있지 않은데 kim 의 튜플을 지운다(기존 멤버였으므로).

요청에 적힌 이름만 잠그면 이런 구멍이 남는다:

```
C: PUT /Groups/DEV001 {members:[park]}    A: PUT /Users/kim {active:true}
   잠금: {DEV001, park}                       잠금: {kim}
   계산: dm(kim,DEV001) 삭제                  계산: dm(kim,DEV001) 추가
                                              ↑ 겹치는 락이 없어 둘 다 진행
```

닫으려면 "락 없이 읽어 영향 집합 계산 → 전역 정렬 순서로 전부 획득 → 집합이
그대로인지 재확인 → 바뀌었으면 전부 반납하고 재시도" 라는 2단계 획득이 필요하다.

**가용성 목적의 배포에서는 그 복잡도를 살 이유가 없다.** 동시 쓰기가 드물어
직렬화 비용을 거의 치르지 않는다. 대량 온보딩 때만 느려진다.

> 처리량 때문에 스케일 아웃하게 되면 이 결정을 다시 열어야 한다. 그때의 후보가
> 위 2단계 획득이다.

### 4.2 아이템 모양

```
PK: LOCK#SCIM_WRITE
SK: META
    token      : <UUID>          이번 점유를 식별
    holder     : <인스턴스 id>     진단용
    purpose    : WRITE | REBUILD  진단용
    expiresAt  : <epoch seconds>  이때까지만 유효
```

app-ldap 과 app-scim 은 서로 다른 테이블을 쓰므로 락도 자연히 분리된다.

### 4.3 세 가지 연산 — 전부 조건부 쓰기

```
획득   PutItem      조건: attribute_not_exists(PK) OR expiresAt < :now
반납   DeleteItem   조건: token = :myToken
갱신   UpdateItem   조건: token = :myToken     SET expiresAt = :new
```

**`token` 조건이 핵심이다.** 내 리스가 만료돼 남이 가져간 뒤에 내가 반납하면 남의
락을 풀어버린다. 토큰을 확인하면 그 일이 없다. 반납이 조건 위반으로 실패하면
"내가 만료됐었다" 는 뜻이므로 경고를 남긴다 — TTL 이 짧다는 신호다.

### 4.4 TTL 과 대기

| | 값 | 근거 |
|---|---|---|
| 락 TTL | 30초 | SCIM 쓰기 p99 보다 한참 길게. 짧으면 살아있는데 만료된다 |
| 재적재 갱신 주기 | 10초 | 몇 분을 쥐지만 TTL 은 짧게 유지 |
| 획득 대기 한도 | 3초 | 넘으면 503 |

**대기 규칙은 하나다.** 3초 안에 못 잡으면 503. 재적재를 특별 취급하지 않는다 —
재적재 중이면 어차피 3초 안에 안 풀리니 503 이 나가고, 이는 **기존
`MutationGate` 와 정확히 같은 동작**이다. IdP 는 503 을 재시도 신호로 읽는다.

### 4.5 MutationGate 를 흡수하는 이유

`MutationGate` 는 재적재 중 쓰기를 막는 인메모리 `AtomicBoolean` 이다. 인스턴스가
둘이면 **막고 있다고 믿지만 안 막힌다** — 인스턴스 2 는 재적재가 도는 사실 자체를
모르고 자기 게이트는 열려 있다.

재적재가 같은 분산 락을 잡으면 문이 하나가 되고 인스턴스를 넘어 제대로 배제된다.
`MutationGate` 는 할 일이 없어져 삭제한다.

### 4.6 크래시

| 죽은 주체 | 결과 |
|---|---|
| 쓰기 중 인스턴스 | 30초 뒤 리스 만료 → 다음 요청이 획득. OpenFGA 에 반쯤 쓰였을 수 있으나 Check 기준선이 다음 터치에 걷어낸다 |
| 재적재 중 인스턴스 | 갱신이 멈춰 30초 뒤 만료 → 쓰기 재개. OpenFGA 는 반쯤 재적재된 상태 |

두 번째는 **오늘 재적재가 실패했을 때와 같은 상태**다(`mode=tuples` 한 번 더
실행하면 복구, PR #4). 새로운 위험이 아니라 기존 위험으로 수렴시킨다.

### 4.7 한계 — 락은 완벽하지 않다

분산 락의 고전적 구멍이 여기도 있다:

```
t1  A 가 락 획득 (TTL 30초)
t2  A 가 GC 정지 등으로 35초 멈춤
t3  리스 만료 → B 가 획득
t4  A 가 깨어나 OpenFGA 에 씀      ← B 와 동시에 쓰는 중
```

OpenFGA 는 **펜싱 토큰을 지원하지 않아** 원천 차단이 불가능하다. 세 겹으로 좁힌다:

1. TTL 을 작업 시간보다 훨씬 길게 — 살아있는데 만료되는 일 자체를 드물게
2. OpenFGA 쓰기 직전 리스 재확인 — 창을 사실상 밀리초로 축소
3. Check 기준선 — 그래도 새어나간 것은 다음 터치에 걷어냄

**이 한계를 문서에 남기는 이유**: "락을 걸었으니 안전하다" 고 믿는 것이 락이 없는
것보다 위험할 수 있다.

## 5. Check 기준선

### 5.1 후보 집합 — 설계의 핵심

단순히 `TupleMapper(이전 상태)` 를 Check 하면 **§1 의 잘못된 튜플을 못 잡는다.**
그 튜플은 어떤 상태로부터도 유도되지 않기 때문이다.

§1 최종 상태를 다시 보면 *"kim 비활성 + DEV001 이 kim 포함"* — DynamoDB 에는
**kim 이 DEV001 의 멤버로 들어 있다.** 비활성이라 튜플이 안 나올 뿐이다.

그래서 후보를 **`active`·순환 필터를 적용하기 전의 멤버십**에서 뽑는다.

```
후보     = 이번 연산이 건드릴 수 있는 튜플 전부 (필터 적용 안 함)
원하는것 = TupleMapper(변경 후 상태)             (필터 적용)
실제     = BatchCheck(후보)

쓸것   = 원하는것 - 실제
지울것 = 실제 - 원하는것
```

이제 잡힌다:

```
누가 DEV001 을 건드림
  후보     = { dm(kim,DEV001), dm(park,DEV001), ... }   kim 은 멤버니까 후보
  원하는것 = { dm(park,DEV001) }                         kim 은 비활성이라 빠짐
  실제     = { dm(kim,DEV001), dm(park,DEV001) }         Check 결과
  지울것   = { dm(kim,DEV001) }                          걷어냄
```

### 5.2 연산별 후보

후보는 **그 연산이 쓰거나 지울 수 있는 것**으로 좁힌다. 무관한 튜플까지 확인하면
비용만 늘고 삭제 범위만 위험해진다.

| 연산 | 후보 | 크기 |
|---|---|---|
| `upsertUser(kim)` | kim 이 속한 각 조직 g 에 대해 `dm(kim,g)` | kim 의 소속 수 |
| `removeUser(kim)` | 동일 | 동일 |
| `upsertGroup(DEV001)` | 현재·요청 멤버 m 에 대해 `dm(m,DEV001)` / `child(m,DEV001)`, 상위 p 에 대해 `child(DEV001,p)` | 멤버 수 |
| `removeGroup(DEV001)` | 동일 | 동일 |

`upsertUser` 가 **소속 조직의 전체 멤버**를 확인하지 않는 것이 중요하다 — 5000명
조직에 속해 있어도 후보는 kim 의 소속 수뿐이다.

### 5.3 포트

새 포트를 만들지 않는다. 조회 API 슬라이드에서 만든 `RelationTupleChecker` 에 배치
메서드를 얹는다 — 같은 일(OpenFGA 에 묻기)을 하는 포트가 둘이 되면 어느 쪽을 쓸지가
매번 판단거리가 된다.

```java
// core — 기존 포트에 추가
public interface RelationTupleChecker {

    Mono<Boolean> check(RelationTuple tuple);              // 기존

    /** 후보 중 OpenFGA 에 실제로 있는 것만 돌려준다. */
    Mono<Set<RelationTuple>> existing(Set<RelationTuple> candidates);
}
```

`OpenFgaRelationTupleChecker` 가 `OpenFgaClient.batchCheck` 로 채운다. 서버 기본
상한(배치당 50건)이 있어 청크로 나눠 보낸다.

`direct_member` 와 `child` 는 모델에서 직접 관계이므로 Check 가 "그 튜플이
존재하는가" 를 그대로 답한다.

### 5.4 한계 — 잡히지 않는 것

후보가 **DynamoDB 멤버십에 매여 있어서**, 멤버십 자체가 사라진 잘못된 튜플은 후보에
들어오지 않는다.

```
DynamoDB:  DEV001 멤버에 kim 없음
OpenFGA:   dm(kim,DEV001) 있음      ← 후보에 안 들어옴 → 못 잡음
```

사람이 손으로 넣었거나, 멤버십을 지우는 커밋 직전에 크래시한 경우가 이렇다. 열거
API 없이는 발견할 방법이 없고 **재적재(`mode=tuples`)가 유일한 해결책**이다.

### 5.5 범위 밖 — 스냅샷 의미 불일치

follow-ups §6 은 SCIM 스냅샷이 "의도한 튜플" 이고 LDAP 스냅샷이 "실제 반영된 튜플" 이라는
불일치를 지적한다. **이번 변경은 그것을 해소하지 않는다.**

스냅샷을 쓰는 곳은 쓰기 경로가 아니라 일일 아카이빙(`SnapshotArchiveUseCase`)이고,
그것을 "실제 반영된 튜플" 로 만들려면 조직 전체를 Check 해야 한다. 별개 문제이며
이번 범위에서 뺀다.

## 6. 에러 처리

| 어디서 | 어떻게 | 왜 |
|---|---|---|
| 락 획득 3초 초과 | 503 | 기존 `MutationGate` 와 같은 응답. IdP 가 재시도 |
| 락 획득이 예외 (DynamoDB 장애) | 503 | 어차피 커밋도 못 한다 |
| **BatchCheck 실패** | **503, 폴백 없음** | 아래 |
| OpenFGA 쓰기 직전 리스 재확인 실패 | 503 | 상태 안 바뀜 → 재시도가 같은 델타 재계산 |
| 반납이 토큰 불일치로 실패 | 경고 로그, 응답은 성공 | 일은 이미 끝났다. TTL 이 짧다는 신호로 남긴다 |
| 재적재가 리스를 잃음 | 재적재 중단, FAILED 기록 | §4.6 두 번째 행과 같은 상태 |

**BatchCheck 실패 시 폴백하지 않는다.** "OpenFGA 를 못 읽으니 예전처럼 상태에서
유도하자" 로 넘어가면 조용히 옛 동작으로 돌아가고, 그게 하필 어긋남이 생기는
순간이다. 실패시켜 IdP 가 재시도하게 둔다.

## 7. 관측

Check 기준선을 넣으면 **상태에서 유도한 기준선**과 **실제 기준선**을 둘 다 갖게
된다. 둘이 다르면 그것이 곧 어긋남이다. 별도 스캔 없이 쓰기 경로가 지나가면서
알려준다 — follow-ups §6 이 원한 감지의 상당 부분이 여기서 나온다.

| 지표 | 종류 | 태그 |
|---|---|---|
| `scim.drift.detected` | Counter | `kind` = extra / missing |
| `scim.lock.wait` | Timer | – |
| `scim.lock.contended` | Counter | – |
| `scim.lock.lease_lost` | Counter | – |

`scim.drift.detected` 가 지속적으로 오르면 재적재 시점을 판단할 근거가 된다.

로그는 조직 동기화 설계 §12.4 의 `traceId` 를 그대로 탄다. 락 대기·경합·리스 상실은 요청 하나 안에서
일어나므로 같은 trace 로 묶인다.

## 8. 테스트 전략

### 8.1 락

DynamoDB Local(Testcontainers) 위에서:

- 쥐고 있는 동안 두 번째 획득이 실패한다
- 리스가 만료되면 다른 쪽이 가져간다
- **남의 토큰으로 반납하면 거부된다** — 없으면 만료 뒤 남의 락을 푼다
- 남의 토큰으로 갱신하면 거부된다
- 갱신하면 만료가 미뤄진다

### 8.2 상호 배제

두 스레드가 동시에 쓰기를 시도할 때 실제로 직렬화되는지. 락이 있으면 겹치는 구간이
없고, 없으면 겹친다.

### 8.3 Check 기준선 — 가장 강한 테스트

경합을 재현하는 테스트는 타이밍에 기대서 잘 흔들린다. 대신 **결과를 직접 심는다.**

```
1. OpenFGA 에 dm(kim,DEV001) 을 직접 심는다   경합이 남겼을 바로 그 상태
2. DynamoDB 에서 kim 은 DEV001 멤버지만 비활성
3. 아무 SCIM 쓰기로 DEV001 을 건드린다
4. dm(kim,DEV001) 이 사라졌는지 Check 로 확인
```

완전히 결정적이고, §1 이 말한 위험(퇴사자 권한 생존)을 그대로 못박는다.

### 8.4 변이 검증

| 되돌리는 것 | 깨져야 하는 테스트 |
|---|---|
| 락 획득 제거 | 상호 배제 |
| 토큰 조건 제거 | 남의 락 반납 거부 |
| Check 기준선 → 상태 기준선 | 잘못된 튜플 제거 |

### 8.5 기존 테스트 영향

`MutationGate` 를 지우므로 재적재 중 503, `wipe` 뒤 쓰기가 열리는지 확인하는 E2E 가
새 락 위에서 그대로 통과해야 한다.

## 9. 이 설계가 하지 않는 것

- **주기적 대조·표본 검증** — 아무도 다시 건드리지 않는 튜플의 어긋남은 여전히
  발견되지 않는다. `scim.drift.detected` 가 부분적인 신호를 주지만, 만지는
  것에 한한다
- **자동 수렴** — 어긋남을 발견하면 그 연산 범위에서 고치지만, 전체를 훑어 고치는
  것은 사람이 재적재를 실행할 때뿐이다
- **스냅샷 의미 통일** — §5.5
- **처리량 스케일 아웃** — §4.1
