# 소속 역참조를 강한 일관성으로 — 설계

> 브랜치 `strong-membership-lookup` (origin/main `cdc6c88` 에서 분기).
> 발단: [`2026-09-11-harness-independent-expectation-design.md`](2026-09-11-harness-independent-expectation-design.md) §9 의 의심을 스파이크로 재현했다.

## 1. 문제 — 삭제가 권한을 남긴다

`removeUser`·`removeGroup` 은 "이 직원(조직)이 어디에 속했나" 를 GSI1 역참조
(`findGroupIdsContaining`)로 찾는다. GSI 는 최종 일관성이라 **막 추가된 멤버십을 아직 모를 수 있다.**

```
1. IdP: "kim 을 A팀에 넣어"   → A팀 파티션에 MEMBER#USER#kim 기록 (GSI 반영 전)
2. IdP: "kim 을 지워"         → 역참조가 A팀을 보고하지 않음
3. 앱: "속한 조직 없음" 으로 판단 → A팀 멤버 줄도, dm(kim,A팀) 튜플도 안 지움
4. 직원 레코드만 삭제 → 결과는 fullyApplied=true (성공)
```

### 스파이크로 확인한 것 (2026-09-16)

`FakeStateRepository` 의 역참조가 특정 조직을 숨기게 하고 `core` 단위 테스트로 재현했다
(로컬 브랜치 `spike-gsi-missed-membership`, 커밋 `358056a`, **버릴 코드**).

| 확인 | 결과 |
|---|---|
| 직원 삭제 | `fullyApplied=true`. `direct_member(kim, TEAM_A)` 와 멤버 줄이 남고 직원 레코드만 사라짐 |
| 조직 삭제 | 같은 모양. `child(C, P)` 와 P 의 멤버 줄이 남음 |
| 이후 그 조직의 PUT·PATCH | 남은 튜플을 지운다. PATCH 는 멤버 줄을 남긴다 |
| SCIM 재적재 `mode=tuples` | 튜플은 치운다. 멤버 줄은 남는다 |
| **같은 아이디로 직원 재생성** | **옛 소속 권한이 되살아난다** — 남은 멤버 줄을 보고 튜플을 만든다 |

`DynamoDbDirectoryStateRepository` 자바독의 "잔여 위험은 빠짐 방향뿐" 은 **틀렸다.** 삭제 경로에서는
남김 방향이다.

### 같은 뿌리의 두 번째 결함

`upsertGroup` 은 `parentsOf`(같은 역참조)로 상위 조직을 찾는다. 상위 P 가 "C 는 내 하위" 로 저장된
직후 C 가 도착하면 P 를 못 찾아 **`child(C, P)` 를 영원히 쓰지 못한다.** 이쪽은 빠짐 방향이지만
P 가 다시 바뀔 때까지 복구되지 않는다.

## 2. 목표와 비목표

**목표**

- 쓰기 경로 네 곳(`upsertUser`·`upsertGroup`·`removeUser`·`removeGroup`)이 소속을 **항상 최신으로** 찾는다.
- 역참조 결과가 **정확하다** — 많지도 적지도 않다.
- OpenFGA 에 쓰는 튜플 규칙은 바뀌지 않는다.

**비목표**

- LDAP 전체 동기화의 계산 방식은 바꾸지 않는다(역참조를 쓰지 않는다).
- 기존 데이터 이관·하위 호환은 고려하지 않는다 — **배포 전이라 초기화한다**(사용자 확인, 2026-09-16).

## 3. 접근안 — 왜 다른 길을 안 갔나

| | 내용 | 판단 |
|---|---|---|
| **A. 소속을 멤버 쪽 파티션에도 적는다 — 채택** | 조직 파티션의 `MEMBER#...` 줄과 짝을 이루는 `BELONGS_TO#GROUP#<gid>` 줄을 직원(또는 하위조직) 파티션에 함께 쓴다. 역참조는 그 줄을 강한 일관성으로 읽는다 | 시간 가정 없이 정확하다. 초기화가 가능하므로 이관·병행 조회가 필요 없다 |
| D. 최근 추가만 TTL 로 기록 | 최근에 추가한 소속만 만료 시각을 붙여 기록하고, 역참조는 GSI 와 합쳐 본다 | 이관이 없다는 것이 유일한 장점이었는데 초기화가 가능해 그 장점이 사라졌다. "GSI 반영이 TTL 안에 끝난다" 는 시간 가정이 남는다 |
| 직원 레코드 안에 소속 목록 칸 | 한 아이템에 Set 으로 | 조직이 먼저 도착하면 **칸만 가진 가짜 직원 레코드**가 생긴다. `saveUser` 의 `PutItem` 이 목록을 통째로 덮는다. 새 결함이 둘 생긴다 |
| 조직 쪽을 없애고 멤버 쪽만 진실로 | 역참조를 본문으로 | "이 조직에 누가 있나" 가 최종 일관성이 된다. SCIM 델타 계산이 그 목록에 의존하므로 더 나쁘다 |
| DynamoDB Streams 로 역참조 유지 | 비동기 복제 | Streams 도 지연된다. 같은 문제가 남는다 |
| 삭제를 미뤘다가 재시도 | 1~2초 뒤 한 번 더 찾기 | 틈을 줄일 뿐이다. 락을 쥔 채 기다리면 503 이 늘고, 인스턴스 간 예약 상태가 새로 필요하다 |
| OpenFGA 에서 그 직원의 튜플을 찾아 지우기 | 열거 API | `Read`/`ListObjects` 는 이 프로젝트에서 금지다 |

**두 곳에 쓰는 일은 저장소가 맡는다.** 유스케이스가 직접 쓰면 순서 규칙이 밖으로 새고, LDAP 전체 교체
경로(`replaceWith` → `saveGroup`)를 따로 챙겨야 한다. 저장소 안에 두면 네 경로와 조회 API 가 한꺼번에 덮인다.

## 4. 저장 구조

SCIM 테이블(`organization-scim`), LDAP 테이블(`organization`) 모두 같은 코드라 같은 구조다.

```
[GROUP#A팀]
  META
  MEMBER#USER#kim            ← 기존. GSI1 키를 뗀다
  MEMBER#GROUP#C팀           ← 기존. GSI1 키를 뗀다
[USER#kim]
  META
  BELONGS_TO#GROUP#A팀       ← 신규
[GROUP#C팀]
  META
  BELONGS_TO#GROUP#A팀       ← 신규
```

| 규칙 | 이유 |
|---|---|
| 새 줄의 SK 는 `BELONGS_TO#` 로 시작한다 | 조직 파티션을 읽는 `toGroup`·`existingMemberSks` 가 `META` 와 `MEMBER#` 만 고른다. 접두사가 겹치면 하위 조직의 소속 줄이 그 조직의 **멤버로 오인**된다 |
| 새 줄에는 GSI 키를 넣지 않는다 | `USER_INDEX`·`GROUP_INDEX` 열거와 조회 API 결과에 섞이지 않는다 |
| 멤버 줄에서 GSI1 키를 뗀다 | 그 키를 쓰던 곳은 역참조 하나뿐이었다(`memberGsi1Pk` 사용처 확인). 색인 쓰기가 사라져 추가 쓰기와 상쇄된다 |
| 새 줄은 `addedAt` 만 갖는다 | 조직 이름 같은 값을 복제하지 않는다 — 복제하면 이름이 바뀔 때마다 양쪽을 맞춰야 한다 |

## 5. 쓰는 순서 — 소속 줄이 항상 많거나 같게

두 줄을 한 번에 쓸 수 없으므로(트랜잭션은 §7 참고) 실패 시 어긋난다. **어긋나는 방향을 고정한다.**

| 어긋난 모양 | 결과 |
|---|---|
| 멤버 줄 있음 / 소속 줄 없음 | 삭제할 때 그 조직을 못 찾는다 — **지금 결함과 같다** ❌ |
| 소속 줄 있음 / 멤버 줄 없음 | 역참조가 걸러 낸다(§6) — 무해하다 ✅ |

- **넣을 때:** 소속 줄 먼저 → 멤버 줄 나중
- **뺄 때:** 멤버 줄 먼저 → 소속 줄 나중

### 연산별 변경

| 연산 | 바뀌는 것 |
|---|---|
| `saveGroup` | 새 멤버는 위 순서로 두 줄을 쓴다. 빠진 멤버는 위 순서로 두 줄을 지운다. 기존 멤버는 지금처럼 건드리지 않는다(`addedAt` 보존) |
| `deleteGroup` | 멤버 목록을 먼저 읽어 두고 → 조직 파티션을 지우고 → **그 멤버들의 소속 줄**을 지운다 |
| `deleteUser` | 직원 파티션의 모든 줄을 지운다(지금은 `META` 만) |
| `findGroupIdsContaining` | 색인 대신 `PK = USER#<id> AND begins_with(SK, "BELONGS_TO#")` 를 강한 일관성으로 읽는다 |
| `replaceWith` | 바뀌지 않는다 — `saveGroup`·`deleteGroup`·`deleteUser` 를 그대로 쓴다 |

### 동시 실행

SCIM 의 모든 변경은 인스턴스 전체에 하나뿐인 분산 락 안에서 돈다. 두 요청이 같은 소속을 동시에 쓰는
경우는 없다. 순서 규칙은 **한 요청이 중간에 실패했을 때**를 위한 것이다.

## 6. 역참조는 확인까지 해서 정확한 값을 준다

`findGroupIdsContaining` 은 소속 줄을 읽은 뒤 **각 조직에 그 멤버 줄이 실제로 있는지**(`containsMember`
와 같은 `GetItem`) 확인하고, 확인된 것만 돌려준다.

**왜 부르는 쪽에 맡기지 않나.** 관리자 조회(`AdminQueryUseCase.directGroupsOf`)는 역참조 결과를 그대로
화면에 올린다 — 조직 레코드 존재만 보고 멤버십은 확인하지 않는다. 걸러 주지 않으면 실패로 남은 소속 줄이
**"속하지 않은 조직" 으로 계속 보인다.** 지금도 GSI 지연으로 같은 일이 생기지만 1초 안에 사라지는 반면,
남은 줄은 저절로 사라지지 않는다.

- 유스케이스의 `containsMember` 호출(`affectedGroupHeadersOf`)은 저장소로 흡수된다. 읽기 총량은 그대로다.
- 포트 `containsMember` 는 **없앤다** — 유일한 호출자가 사라진다. 저장소 내부 도우미로 남는다.
- 남은 소속 줄은 그 조직이 다음에 저장될 때 정리된다. 별도 청소 잡을 두지 않는다.

## 7. 성능

| | 지금 | 바뀐 뒤 |
|---|---|---|
| 과금 쓰기량(멤버십 1건) | 본문 1 + GSI1 복제 1 | 본문 2 (GSI 없음) — **비슷하다** |
| 앱이 보내는 쓰기 요청 수 | 1 | **2** — 락 보유 시간이 늘 수 있다 |
| 역참조 읽기 | GSI Query 1 + (쓰기 경로) 확인 GetItem N | Query 1(강한 일관성) + 확인 GetItem N — **비슷하다** |
| 관리자 조회 | Query 1 | Query 1 + 확인 GetItem N(소속 수, 보통 1~3) |
| 저장 용량 | — | 멤버십 1건당 작은 아이템 1개 추가(5,000명 규모에서 수 MB 이하) |

**트랜잭션(`TransactWriteItems`)은 쓰지 않는다.** 쓰기 비용이 2배이고 한 번에 100개 제한이라 1,600명
조직은 어차피 여러 트랜잭션으로 쪼개져 원자성이 깨진다. §5 의 순서 규칙이 같은 안전을 더 싸게 준다.

**배치(`BatchWriteItem`)는 실측 후 판단한다.** 최초 적재에서 락 보유 시간이 크게 늘면 25건 묶음 쓰기를
검토한다 — 다만 배치는 순서 보장이 없으므로, 쓰면 "소속 줄 배치 전부" → "멤버 줄 배치 전부" 순으로 나눠야
§5 가 유지된다.

## 8. 검증

### 핵심 증명 — "역참조가 색인을 쓰지 않는다"

DynamoDB Local 은 GSI 를 즉시 반영해 **지연 자체를 재현할 수 없다.** 그래서 지연을 흉내 내는 대신 보낸
요청을 검사한다. AWS SDK 의 `ExecutionInterceptor` 로 요청을 기록하고 단언한다.

- 역참조가 보낸 `QueryRequest` 에 `indexName` 이 없다
- 그 요청의 `consistentRead` 가 `true` 다

### 저장소 테스트 (DynamoDB Local, Testcontainers)

| 테스트 | 확인 |
|---|---|
| 소속 줄 생성 | 조직 저장 후 직원·하위조직 파티션에 `BELONGS_TO#` 줄이 있고 역참조가 그 조직을 돌려준다 |
| **찌꺼기 필터** | 소속 줄만 남기고 멤버 줄을 지우면 역참조가 그 조직을 **안** 돌려준다 |
| **쓰기 순서** | 가로챈 요청 순서로: 추가는 소속 줄이 먼저, 제거는 멤버 줄 삭제가 먼저 |
| 삭제 정리 | `deleteGroup` 이 멤버들의 소속 줄까지 지운다. `deleteUser` 가 파티션을 비운다 |
| 색인 키 제거 | 멤버 줄이 GSI1 조회에 잡히지 않는다 |
| 아직 없는 직원 | 소속 줄만 있고 `META` 가 없으면 `findUser` 는 여전히 빈 결과다 |

### 변이로 확인

| 변이 | 실패해야 하는 테스트 |
|---|---|
| 쓰기 순서를 뒤집는다 | 쓰기 순서 |
| 확인 단계를 뺀다 | 찌꺼기 필터 |
| 역참조를 GSI 조회로 되돌린다 | 색인 미사용 |
| `deleteGroup` 의 소속 줄 정리를 뺀다 | 삭제 정리 |

### 규모·성능 측정

`cdc6c88` 을 기준으로 전후를 잰다 — LDAP 최초 적재, SCIM 최초 싱크, 대형 조직(1,600명) 멤버 교체,
S3 경합의 503 비율. 결과는 이 문서 §11 에 표로 추가한다.

### 기존 테스트 중 바꿔야 하는 것

| 대상 | 이유 |
|---|---|
| `FakeStateRepository` | 역참조가 정확해진다. `staleGroupIdsContaining` 과 `containsMember` 를 없앤다 |
| `IncrementalSyncUseCaseTest` 의 낡은 히트 테스트 | 같은 성격의 테스트가 저장소 쪽으로 옮겨진다 |
| `IncrementalSyncReadScopeTest` | `containsMemberCalls` 로 읽기 범위를 재던 단언을 다른 계측으로 바꾼다 |
| `DynamoDbDirectoryStateRepositoryTest` | 역참조·삭제 동작이 바뀐다 |
| `KeysTest` | `memberGsi1Pk` 가 없어진다 |
| `LdapInterruptedSyncScaleTest` 의 저장소 대역 | 포트에서 `containsMember` 가 빠진다 |

### 데이터 초기화

키 규칙이 바뀌므로 로컬·개발 테이블을 지우고 다시 만든다. 자동화 테스트는 매번 새 컨테이너를 띄우므로
영향이 없다.

## 9. 범위 밖

- LDAP 커넥터의 H(`dnOf` 평면 트리)와 범위 검색 응답 구멍 — 다음 슬라이드들이다.
- 이미 쌓인 끊긴 멤버 줄 정리 — 초기화로 없어진다.

## 10. 이 설계가 말할 수 없는 것

- **실제 AWS 의 GSI 지연 시간.** 우리는 "색인을 쓰지 않는다" 를 증명할 뿐이다.
- **두 줄 쓰기 중간 실패를 실제 장애로 재현하는 것.** 요청을 실패시키는 대역으로만 확인한다.
- **`BELONGS_TO#` 줄이 조회 API 결과에 섞이지 않는다는 것**은 GSI 키를 넣지 않는다는 구현 사실로만
  보장된다. 실수로 넣으면 색인 조회에 섞인다 — 그 경우를 잡는 테스트를 §8 에 넣었다.

## 11. 실측

구현 마지막 태스크에서 §8 의 규모 측정 결과와 변이 결과를 이 절에 표로 추가한다.
