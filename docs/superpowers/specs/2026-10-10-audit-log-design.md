# 변경 이력(감사 로그) — 직원·조직별 조직도 변경과 권한 변경

- 날짜: 2026-10-10
- 근거:
  - 기존 백로그 7번(2026-09-26 사용자가 별도 슬라이드로 정함).
  - 변경 시각 내보내기(`docs/superpowers/specs/2026-10-09-updated-at-export-design.md` §2·§9·§11)가 관리 API 노출을 이 슬라이드로 넘겼다.
- 전제:
  - 실제 규모는 직원 10만 명 이상이다. 요청 하나가 전원을 읽지 않는다.
  - 운영 배포 전이라 저장 형식을 바꿔도 이관 코드를 만들지 않는다.
  - 배포 하나는 LDAP 아니면 SCIM 이다.
  - 표준이 정한 신호만 받는다.

## 1. 문제

지금은 직원·조직 변경 한 건마다의 이력이 없다.

| 기록 | 담는 것 | 보관 | 빠진 것 |
|---|---|---|---|
| 동기화 이력(`SYNCRUN#`, `/admin/sync/runs`) | 회차마다 언제, 무엇이(LDAP·SCIM·재적재·아카이빙), 몇 건을 쓰고 지웠는지, 성공했는지 | 30일(`dynamodb.syncrun-retention-days`) | 누구의 무엇이 바뀌었는지 |
| 튜플 스냅샷 | 그 시점의 권한 전체 | 7일(최신은 기간과 무관하게 남음) | "언제 바뀌었나" — 두 스냅샷을 비교해야 하고, 7일 뒤 사라진다 |
| 직원·조직 META 의 `createdAt`·`updatedAt` | 생성 시각·마지막 변경 시각 하나 | 아이템이 있는 동안 | 무엇이 바뀌었는지 |
| SCIM 요청 | 로그·메트릭(traceId) | 로그 보관 정책 | 구조화된 변경 내용 |

그래서 "kim 이 언제, 무엇 때문에 개발본부 권한을 잃었나", "kim 의 표시명이 언제 바뀌었나" 에 답할 수 없다.

## 2. 결정 (사용자 확인, 2026-10-10)

| 주제 | 결정 | 고르지 않은 안(§11) |
|---|---|---|
| 무엇을 남기나 | **둘 다** — 조직도 변경(속성 이전 → 이후, 생성·삭제, 소속 들어옴·나감)과 권한 변경(쓴·지운 튜플)을 같은 사건에 묶는다 | 권한만, 조직도만, SCIM 요청 원문 |
| 어떻게 찾나 | **대상별** — 직원·조직마다 최신순. 줄마다 원인(회차 id·SCIM traceId)을 적어 동기화 이력·로그로 거슬러 간다 | 사건별, 기간별 |
| 얼마나 남기나 | **동기화 이력과 같은 30일, 설정값**(`dynamodb.audit-retention-days`) — 원인 회차 기록과 기한이 같아 거슬러 갈 곳이 끝까지 있다 | 감사만 더 길게(1년), 지우지 않음 |
| 어디서 쓰나 | **유스케이스가 커밋 뒤 대상별로 쓴다** — 원인을 아는 곳에서 쓴다 | 사건 단위 기록 + 대상 색인, DynamoDB Streams |

## 3. 기록 모양

### 3.1 한 줄 = 대상 하나 × 사건 하나

- 대상 하나(직원 또는 조직)가 사건 하나(동기화 회차 또는 SCIM 요청)에서 겪은 변경을 한 아이템에 모은다.
  - 예: "10월 10일 03:00 LDAP 동기화 회차 R1 에서 kim 은 표시명이 바뀌었고, 개발본부에 들어왔고, 개발본부 권한을 얻었다."
- 사건마다 한 줄이라, 초기 적재에서도 직원 한 명당 한 줄이다.

### 3.2 키

- 파티션키: `AUDIT#USER#<직원 id>` / `AUDIT#GROUP#<조직 id>`.
- 정렬키: `<시각>#<원인 id>`.
  - 시각은 `Keys.sortableTimestamp`(밀리초 3자리 고정)다.
  - 최신순은 역순 Query 다.
- 직원·조직의 본 파티션(`USER#`·`GROUP#`)과 따로 둔다.
  - 직원·조직을 지워도(`deleteUser`·`deleteGroup`) 이력은 남는다.
  - SCIM `wipe` 도 이력을 지우지 않는다. 이력은 GSI 키가 없어 `replaceWith` 의 열거에 걸리지 않는다. 기존 원칙("감사 이력은 지우지 않는다", `ScimRebuildUseCase` 자바독)과 같다.

### 3.3 한 줄에 담는 것

- **원인**
  - 출처: `LDAP` · `SCIM`.
  - 종류: 동기화 · 재적재 · 장부 맞추기 · SCIM 요청.
  - 원인 id: 회차 id(동기화 이력 `runId` 와 같은 값) 또는 SCIM 요청의 traceId(로그와 같은 값).
- **조직도 변경**
  - 생성 · 삭제.
  - 바뀐 속성만 이전 값 → 이후 값. 직원은 externalId, userName, displayName, email, active, 이름 여섯이고, 조직은 externalId, displayName 이다.
  - 직원 줄: 소속 들어옴 · 나감(조직 id).
  - 조직 줄: 멤버 들어옴 · 나감(멤버 종류·id 목록과 수).
- **권한 변경** — 이 대상이 user 쪽인 튜플 중 그 사건이 실제로 쓴 것 · 지운 것.
  - 예: 직원 줄에 `user:kim direct_member group:DEV`, 하위 조직 줄에 `group:TEAM child group:HQ`.
- **보관** — `expiresAt` = 기록 시각 + `dynamodb.audit-retention-days`(기본 30). 테이블의 단 하나뿐인 TTL 속성을 함께 쓴다(`Keys.EXPIRES_AT`).

### 3.4 큰 조직의 멤버 목록

- 10만 명 조직이 한 회차에 통째로 바뀌면(초기 적재, 대개편, `wipe`) 조직 줄의 멤버 목록이 아이템 한도(400KB)를 넘는다.
- 넘으면 같은 정렬키에 조각 번호(`#0000`, `#0001`, …)를 붙여 몇 줄로 나눈다. 조회는 조각을 합쳐 한 줄로 돌려준다.
- 한 회차에 조직 하나는 많아야 몇 줄이다. 그래서 큰 조직 파티션 하나에 수만 줄이 몰리지 않는다. GSI1·튜플 스냅샷 쏠림의 교훈이다.

### 3.5 남기지 않는 것

- **재적재가 "쓴" 튜플.** OpenFGA 에 중복 무시(`OnDuplicate.IGNORE`)로 쓰므로, 이미 있던 줄과 새로 생긴 줄을 가를 수 없다.
- 재적재가 지운 찌꺼기 줄은 남긴다. 재적재 자체는 동기화 이력에 회차로 남아 있다.
- 아카이빙은 상태를 바꾸지 않으므로 남길 것이 없다.

### 3.6 규모

- 대량 변경(초기 적재·`wipe`·대개편): 직원 10만 줄 + 조직 수만큼, 약 10만 쓰기다. 직원마다 파티션이 달라 흩어진다.
- 평소: 바뀐 직원·조직 수만큼만 쓴다.
- 같은 조직도를 다시 동기화하면 이력 쓰기가 0번이다(바뀐 것이 없다).

## 4. 쓰는 흐름

### 4.1 포트

- core 에 이력 포트 `AuditLog` 하나를 둔다. 사건 하나와 그 사건의 대상별 변경 목록을 받아 기록하고, 대상 하나의 이력을 최신순으로 한 쪽씩 읽는다.
- 저장소 구현은 대상별 줄을 묶음 쓰기(25개씩, `BatchRequests` 의 재시도 규칙 — 5번, 100ms 부터 두 배)로 쓴다.

### 4.2 흐름별로 넘기는 것

| 흐름 | 조직도 변경 | 권한 변경 | 원인 |
|---|---|---|---|
| LDAP 동기화(`FullSyncUseCase` 비교해 맞추기, 변경 없는 회차 포함) | 전체 교체의 비교 결과(§4.3) | 이번 회차가 쓰고 지운 튜플(`TupleWriteResult.written`·`deleted`) | 회차 id |
| LDAP 재적재·멈춘 회차 뒤 첫 동기화(`LedgerAlignment`) | 전체 교체의 비교 결과 | 지운 찌꺼기 줄만 | 회차 id |
| SCIM 쓰기(`IncrementalSyncUseCase` 직원·조직 생성·변경·삭제) | 유스케이스가 락 안에서 이미 쥔 이전·이후 값, 넣고 뺀 멤버 | 그 요청의 결과 | 요청 traceId(앱이 core 에 넘긴다) |
| SCIM 재적재 `tuples` | 없음(상태를 바꾸지 않는다) | 지운 찌꺼기 줄만 | 회차 id |
| SCIM 재적재 `wipe` | 전체 교체(빈 조직도)의 비교 결과 — 전원 삭제 | 지운 줄 전부 | 회차 id |
| 아카이빙 | 없음 | 없음 | — |

### 4.3 전체 교체가 비교 결과를 돌려준다

- `DirectoryStateRepository.replaceWith` 는 이미 저장본과 비교해 바뀐 것만 쓴다(GSI1 쏠림 설계 §3). 그 비교 결과를 돌려주게 바꾼다. 지금은 `Mono<Void>` 라 포트 모양이 바뀐다.
- 비교 결과에 담는 것:
  - 직원: 생성, 바뀐 속성의 이전·이후, 삭제.
  - 조직: 생성, 이름표의 이전·이후, 삭제, 멤버 들어옴·나감.
- 저장본은 이미 손에 있다(`Stored<T>` 의 도메인 값). 새로 읽는 것은 없다.

### 4.4 쓰는 시점

- **상태(현재상태·스냅샷)를 커밋한 뒤에 쓴다.** 커밋되지 않은 변경을 이력에 남기지 않는다.
- **락을 푼 뒤에 쓴다.** 락을 쥔 시간을 늘리지 않는다.
  - 작업(동기화·재적재)은 `SyncJobs.startLockedThen` 의 "반납 뒤 할 일" 자리다. 재적재의 스냅샷 저장이 이미 그 자리를 쓴다.
  - LDAP 동기화도 그 자리로 옮긴다(지금은 `startLocked`).
  - SCIM 쓰기는 락을 푼 뒤, 응답 전에 쓴다.
- **시각**은 기록을 만든 시각이다(사건의 커밋 직후, 서버 시계).

### 4.5 실패 — 빠질 수는 있어도 틀린 줄은 남기지 않는다

- 재시도 끝에 이력 쓰기가 실패해도 그 동기화·SCIM 쓰기를 실패시키지 않는다. 까닭은 셋이다.
  - 변경은 이미 커밋됐다.
  - 실패시켜도 재시도(IdP 의 다시 보내기, 다음 회차)는 "바뀐 것 없음" 을 보고 이력을 다시 만들지 못한다.
  - 실패시키면 장애만 늘고 이력은 돌아오지 않는다.
- 대신 크게 알린다.
  - ERROR 로그(원인 id, 빠진 줄 수).
  - 지표 `audit.write.failures`.
  - 동기화·재적재 회차면 회차 메시지에 "감사 기록 N건 실패" 를 붙인다.

## 5. 조회 API

- admin-api 라 LDAP·SCIM 배포 둘 다에 들어간다.
  - `GET /admin/employees/{employeeId}/history?limit=20&cursor=…`
  - `GET /admin/organizations/{orgCode}/history?limit=20&cursor=…`
- 최신순이다. 커서는 지금 관리 API 의 멤버 목록처럼 불투명 커서이고, 위조하면 400 이다(점검 S16 과 같은 시작 키 검사).
- 지워진 직원·조직도 30일 동안은 이력이 보인다. 기록이 없는 아이디는 404 가 아니라 빈 목록으로 답한다.
- 한 줄의 응답:
  - 시각.
  - 원인: 출처, 종류, 회차 id 또는 traceId.
  - 생성·삭제.
  - 바뀐 속성(이름, 이전, 이후).
  - 소속 들어옴·나감.
  - 권한 얻음·잃음(튜플).
  - 조직 줄이면 멤버 들어옴·나감 목록과 수.
- 조각으로 나뉜 조직 줄은 하나로 합친다. 쪽 경계가 조각 사이에 걸리지 않게 읽는다.

## 6. 보관

- 줄마다 `expiresAt` 을 넣고 테이블 TTL 이 지운다(§3.3).
- TTL 은 며칠 늦게 지울 수 있다. 기한이 막 지난 줄이 잠시 보일 수 있다.
- 동기화 이력과 기한을 맞춘다. 운영에서 늘리려면 두 설정을 함께 늘린다(`dynamodb.syncrun-retention-days`, `dynamodb.audit-retention-days`).

## 9. 검증

| 무엇 | 어떻게 | 어디 |
|---|---|---|
| 저장·조회 | 최신순, 커서 이어 읽기와 위조 400, 큰 조직 줄 나누기·합치기(작은 한도로), `expiresAt`, 직원을 지워도 이력이 남음, `wipe` 가 이력을 지우지 않음 | storage(DynamoDB Local) |

| 끝단 | SCIM PATCH 뒤 이력 API 에 그 요청의 traceId 와 이전·이후 값이 나온다. LDAP 동기화 뒤 이력 API 에 회차 id 가 나온다 | app-scim, app-ldap |
| 규모 | 직원 10만 명 초기 적재의 이력 쓰기 수(약 10만 + 조직 수)와 시간. 같은 조직도 재동기화의 이력 쓰기 0 | storage 규모 테스트 |
| 전체 | 머지 전 `test`·`scaleTest` 둘 다 | 전체 |

## 10. 이 설계가 말할 수 없는 것

- **이력은 빠질 수 있다.** 커밋 뒤 이력 쓰기가 재시도 끝에 실패하면 그 사건의 줄이 없다(§4.5). 틀린 줄은 남기지 않는다.
- **재적재가 새로 채운 권한은 이력에 없다**(§3.5). 재적재 회차는 동기화 이력에 있다.
- **큰 조직이 한 회차에 통째로 바뀐 줄은 응답 하나가 클 수 있다.** 멤버 10만 명이면 약 4MB 다. 초기 적재·`wipe` 때뿐이다.
- **관리 API 는 아직 인증이 없다**(인증은 마지막 슬라이드). 이력에는 이전 값(이름·이메일 등)이 담기므로, 지금 관리 API 와 같은 노출 수준이다.
- **서버 시계.** 여러 대면 각자의 시계로 찍는다. 시계가 어긋나면 순서가 아주 조금 뒤바뀔 수 있다.
- **TTL 지연**(§6).

## 11. 왜 다른 길을 안 갔나

- **권한만 또는 조직도만.** 비활성화는 소속은 남기고 권한만 거둔다. 표시명 변경은 권한과 무관하다. 둘 중 하나로는 "왜 권한이 사라졌나" 와 "언제 무엇이 바뀌었나" 중 하나에 답하지 못한다.
- **SCIM 요청 원문 기록.** IdP 디버깅에는 좋지만 LDAP 배포에 해당이 없고, 저장한 상태가 실제로 어떻게 바뀌었는지는 보이지 않는다.
- **사건별·기간별 조회.** 한 회차·하루치를 한 파티션에 모아야 한다. 초기 적재·대개편 회차는 수십만 줄을 한 번에 쓴다. 그러면 GSI1·튜플 스냅샷에서 두 번 고친 쏠림이 다시 생긴다. 사건별은 줄의 원인 id 로 동기화 이력에 거슬러 간다.
- **감사만 더 길게(1년)·지우지 않음.** 원인 회차 기록이 30일 뒤 사라져 거슬러 갈 곳이 없어진다. 지우지 않으면 이전 값(개인정보)이 끝없이 남는다.
- **사건 단위 기록 + 대상 색인.** 사건별 조회는 공짜지만 색인 쓰기가 결국 대상 수만큼 든다. 한 줄을 보려면 사건 기록을 다시 열어야 해 읽기도 무겁다.
- **DynamoDB Streams 로 자동 수집.** 쓰기 경로에 코드가 들지 않고 손으로 고친 것도 잡는다. 그러나 권한 변경(OpenFGA)은 DynamoDB 에 한 건씩 남지 않아 잡지 못한다. 원인(회차·요청)도 모르고, 앱 밖 인프라(스트림 소비자)가 생긴다.
- **커밋 전에 "예정" 줄을 먼저 쓰고 나중에 확정하기.** 빠짐은 줄지만 커밋이 실패하면 일어나지 않은 변경이 이력에 남는다. 그것을 걸러낼 확정·정리 장치가 따로 필요하다.
