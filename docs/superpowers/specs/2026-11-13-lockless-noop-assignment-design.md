# 바뀐 것 없는 지정을 락 없이 끝내기 설계 (2026-11-13)

조직 계층 설계(2026-11-04) §15.3 이 남긴 "매일 전체를 다시 거는 운용의 비용"과 원천 없는 줄 설계(2026-11-11) §9.5 가 남긴 "커밋 자리 경계 시험 둘"을 한
슬라이드로 묶는다. 사용자 결정: "추천대로"(2026-11-13) — 아래 결정은 모두 그 추천이다. 구현 전 점검(§12)이 2026-11-11 §9.5 의 첫 항목(지정이 받치는 하위 조직의
되지우기)을 범위로 끌어왔다(L8) — 그 구멍이 있으면 락 없는 길의 논증(§3.3)이 깨진다.

## 1. 문제

### 1.1 바뀐 것 없는 지정도 전역 쓰기 락을 잡는다

- 관리 API `PUT /admin/organizations/{orgCode}/parent` 는 멱등이다. 문서는 개편 스크립트가 매일 조직도 전체를 다시 걸어도 된다고 한다(README 지정 절 4, 온보딩 09 §4.4,
  11 §9.8, 13 §2.2 "일괄 지정·지정 목록 API 가 없다").
- 그런데 같은 상위로 다시 건 요청도 `assignParent` 의 `withLock` 을 지난다. 줄이 이미 있어도 이만큼 한다.
  - 같은 인스턴스의 줄 서기와 DynamoDB 전역 쓰기 락 획득(조건부 PutItem, 겨루면 물러서며 다시 시도)
  - DynamoDB 읽기 다섯: S·P 이름표, S 의 지정, `지금_지정` 이 다시 읽는 P 이름표, P 의 멤버 행 S(`지정_그림`)
  - 보류 목록 읽기(순환 판정, `OrgGraph.보류`)
  - Check 한 번(`child(S,P)`)
  - 델타가 비어도 커밋 직전 리스 확인(조건부 갱신, `반영하고_커밋한다`)
  - 반납(DeleteItem)
- 결과는 "바뀐 것 없음"이다. 쓰기도 이력도 없다. 그런데 그동안 같은 락을 기다리는 IdP 의 SCIM 쓰기가 줄을 선다.
- SCIM 쓰기의 획득 한도는 줄과 겨루기를 합쳐 3초다(`dynamodb.lock-acquire-timeout`). 넘으면 IdP 는 503 을 받는다.
- 10만 명 규모면 조직이 수천 개다. 매일 전체를 다시 걸면 수천 번 락을 잡았다 놓는다. 그 대부분이 바뀐 것 없는 요청이다.
- 지금 문서는 스크립트에 "속도를 조절하거나, 조직 상세(`assignedParentOrgCode`)로 먼저 비교해 바뀐 것만 보내라"고 권한다.
  - 먼저 비교해 같은 값을 건너뛰면 어긋남 복구도 건너뛴다. 같은 P 로 다시 걸면 빠진 줄을 쓰는 것이 지금 동작이다(설계 2026-11-04 §15.3).
  - 그래서 운영자는 비용과 복구 가운데 하나를 고르게 된다.
- 같은 모양이 `DELETE …/parent` 에도 있다. 지정이 없는 조직에 보내도 락을 잡고 지정을 읽은 뒤 "바뀐 것 없음"으로 끝난다. 뿌리 조직에 DELETE 를 보내는 스크립트가 그렇다
  (온보딩 12 §5.8).

### 1.2 커밋 자리 경계의 반을 시험이 고정하지 않는다

- 원천 없는 줄 카운터 `scim.writes.unsourced` 는 커밋 자리를 마친 뒤의 끝남을 세지 않는다(설계 2026-11-11 U5).
  - `보류와_함께_커밋한다` 는 앞쪽 보류 쓰기 → 커밋 → 뒤쪽 보류 목록 정리 순이다. 추적기의 `커밋을_마쳤다` 는 커밋 바로 뒤, 뒤쪽 정리 전에 불린다.
  - 그래서 뒤쪽 정리의 실패는 세지 않고, 앞쪽 보류 쓰기의 실패는 센다.
- 이 경계는 코드 모양과 자바독으로만 맞다. `커밋을_마쳤다` 를 앞뒤로 옮겨도 깨지는 시험이 없다(설계 2026-11-11 §9.5).

**고치지 않기로 한 것.**
- **거절도 락 없이.** 상위가 없거나 대상이 없는 요청은 매일 스크립트에서 드물다. 순환 판정은 락 안의 그래프가 있어야 한다. 앞 확인을 넓히면 응답이 지금과 달라질 수 있는 곳이 생긴다(L3).
- **일괄 지정 API.** 조직마다 PUT 이 남는다. 바뀐 것 없는 요청이 싸지면 일괄 API 의 이득은 왕복 수뿐이다. 범위 밖(설계 2026-11-04 §2)이다.
- **전역 쓰기 락의 처리량 자체.** 실제 요구가 확인될 때 한다(남은 슬라이드 순서, 2026-10-14 사용자 결정).
- **L8 과 같은 자리의 거짓 셈 하나(온보딩 13 §2.7).** 장부에 `child(S,G)` 가 이미 빠진 드리프트에서 지정이 받치는 S 를 넣는 G 의 PATCH 가 커밋 전에 끝나면, U5 (a) 가
  한 번 거짓으로 센다 — 커밋 전이라 변경 전 그림(지정을 싣지 않는다)과 비교하기 때문이다. 고치려면 성공 경로에서도 넣는 하위 조직마다 지정을 읽어야 한다. 줄을 남기지는
  않고, 운영 절차의 2단계(같은 요청이 그 뒤 성공했는지 본다)가 대개 끝낸다.

## 3. 동작

### 3.1 PUT `…/{S}/parent` `{"parentOrgCode": P}`

| 지금 상태 | 앞 확인 | 결과(지금과 같다) |
|---|---|---|
| S 있음, 지정 P, P 있음, 장부에 `child(S,P)` 있음 | 참 — **락 없이** 끝 | 204, 쓰기·이력 없음 |
| 위와 같은데 장부에 `child(S,P)` 없음(어긋남, 또는 보류 중) | Check 거짓 → 락 안 | 줄을 쓴다(204). 보류 중이면 409 |
| 지정이 없거나 다른 상위 Q | 지정이 P 아님 → 락 안(Check 안 함) | 바꾼다 |
| 지정 P 인데 P 가 없음 | P 이름표 없음 → 락 안 | 404(상위 없음) |
| S 없음 | 락 안 | 404 |
| S = P | 저장된 지정은 자기 자신일 수 없다 → 락 안 | 409 |
| 앞 확인의 읽기·Check 오류 | 락 안(L5) | 지금처럼 |

### 3.2 DELETE `…/{S}/parent`

| 지금 상태 | 앞 확인 | 결과(지금과 같다) |
|---|---|---|
| S 있음, 지정 없음(또는 가리키는 조직이 없음) | 참 — **락 없이** 끝 | 204 |
| S 있음, 지정 있음 | 락 안 | 지정을 없앤다. 델타가 비어도 커밋한다(온보딩 12 §3.7 의 PITR 복원 절차가 기대는 동작) |
| S 없음 | 락 안 | 404 |
| 앞 확인의 오류 | 락 안 | 지금처럼 |

### 3.3 왜 락 없이 읽어도 되는가

- 락은 **바꾸는 쪽끼리** 차례를 지킨다. 앞 확인은 아무것도 쓰지 않는다. 그래서 락을 쥔 다른 요청의 상태나 장부를 흐트러뜨리지 않는다 — 재적재가 쥐고 있어도 같다.
- 앞 확인이 204 를 낸다는 것은 이것뿐이다: 어느 때 t1 에 저장된 지정이 P 였고(S·P 이름표도 그때 있었다), 그 뒤 t2 에 장부에 `child(S,P)` 가 있었다.
  - **t1~t2 사이에 지정을 바꾼 요청이 없으면** t2 에 "지정 P, 줄 있음"이 함께 성립했다. 그때 락 안의 같은 요청도 아무것도 하지 않았다.
  - **사이에 지정을 바꾼 요청 W 가 있으면** W 는 이 요청과 동시에 돈 것이다. 이 요청이 W 보다 먼저 끝난 것으로 보면 된다. W 는 자기 그림(전: 지정 P)으로 줄을 맞춘다.
    이 요청이 줄을 쓰지 않았어도, W 가 Check 기준선으로 델타를 정하므로 W 가 성공하면 W 가 남기는 장부는 같다. W 가 실패하면 지정은 P 로 남고, 줄이 빠졌으면
    다음 같은 PUT 이 락 안에서 쓴다.
- 끝난 요청 뒤에 보낸 요청은 그 결과를 본다 — 읽기가 모두 강한 일관성이기 때문이다(L4). "PUT Q 성공 → PUT P" 는 지정 Q 를 읽어 락 안으로 간다.
- 실패한 쓰기가 남긴 상태도 같은 규칙을 따른다.
  - 지정을 바꾸다 실패한 요청은 저장하지 않으므로 지정은 P 로 남는다. 옛 줄을 지웠으면 Check 가 거짓이라 락 안으로 가 복구한다.
  - 원천 없는 줄의 되지우기는 저장된 상태가 요구하는 줄을 지우지 않는다(설계 2026-11-11 U4). 지정 P 가 저장돼 있는 동안 `child(S,P)` 는 되지울 대상이 아니다 —
    **L8 뒤에야 참이다.** 지금은 저장하는 조직 커밋이 지정을 빠뜨린다. 그러면 이런 순서가 생긴다.
    1. 장부에서 `child(S,P)` 가 빠져 있고 저장된 지정은 P 다.
    2. IdP 가 P 에 S 를 넣는 PATCH(W)를 보낸다. W 는 그 줄을 쓰는데 응답을 잃는다.
    3. 앞 확인의 Check 가 여기 닿아 참을 보고 204 로 끝난다.
    4. W 는 S 를 저장하지 않고 그 줄을 되지운다. 줄은 다음 PUT 까지 빠진 채다.
    - 락 안의 길에서는 PUT 이 W 앞에 돌든(줄을 써 두어 W 가 쓰지 않는다) 뒤에 돌든(빠진 줄을 쓴다) 줄이 남는다. 직렬 순서로는 나올 수 없는 결과다. L8 이 4 의 되지우기를
      막아 닫는다.
- **이 논증은 코드를 읽고 따진 것이다.** 실제 DynamoDB·OpenFGA 에서 두 요청을 겹쳐 돌리는 시험은 없다(§6).

### 3.4 락 안의 같은 요청과 다른 점

- **보류 목록의 낡은 줄을 덜 걷는다.** 락 안의 길은 순환 판정이 보류 목록을 읽으며, 튜플이 이미 장부에 있는 줄을 목록에서 뺀다(`이미_있던_보류`). 앞 확인은 목록을 읽지 않는다.
  - 그런 줄은 쓰기 뒤 목록 빼기가 실패했을 때만 남고, 목록은 보통 비어 있다.
  - `OrgGraph` 는 그 줄을 늘 "있는 연결"로 다룬다. 하위 조직 연결을 건드리는 다음 요청이나 재적재가 걷는다.
- **락 지표에 남지 않는다.** `scim.lock.wait`·`scim.lock.contended` 가 이 요청을 재지 않는다.
- **재적재 중에도 204 다.** 지금은 재적재가 락을 쥔 동안 바뀐 것 없는 PUT 도 503(`Retry-After` 60)이다. 앞 확인이 참이면 204 가 된다.
  - `mode=tuples` 는 저장된 상태로 장부를 다시 만든다. 앞 확인이 본 줄을 지울 수 있는 것은 그 연결이 순환이라 재적재가 보류할 때뿐이다(재적재는 지정 연결도 끊을
    대상에 넣는다 — `TupleMapper`, 온보딩 15 의 H6). 재적재 직전에 보낸 요청과 같은 결과다.
  - `mode=wipe` 도중에 204 를 받은 지정은 곧 wipe 가 지운다. wipe 직전에 보낸 요청과 같다. wipe 뒤에는 지금처럼 IdP 재프로비저닝이 끝난 다음 새 `orgCode` 로 다시 건다(온보딩 12 §8.4).

### 3.5 운영자가 보는 것

- 응답 코드, 이력, 장부는 지금과 같다(§3.4 의 재적재 중 204 만 다르다).
- 바뀐 것 없는 요청은 읽기 셋(DELETE 는 둘)과 Check 하나다. IdP 쓰기와 줄을 서지 않는다.
- 스크립트가 먼저 비교할 까닭이 없어진다. 그냥 다 보내면 바뀐 것만 락을 잡고, 빠진 줄도 고친다.
- **동시에 많이 보내지 않는다.** 지금은 락이 요청을 한 줄로 세워 저절로 늦췄다. 바뀐 것 없는 요청은 이제 서로 기다리지 않아, 동시에 수천 개를 보내면 그 Check 가 한꺼번에
  OpenFGA 에 간다. IdP 쓰기의 Check 와 같은 OpenFGA 다. 차례로(또는 작은 동시성으로) 보내기를 권한다.

## 4. 시험

각 시험에 "이 시험을 깨뜨릴 운영 코드 변경"을 적는다.

### 4.1 core — `IncrementalSyncParentAssignmentTest`(또는 새 시험 클래스)

| 시험 | 단언 | 깨뜨릴 변경 |
|---|---|---|
| 같은 상위·줄 있음 → 락 없이 끝 | 결과 `fullyApplied`, `lock.acquired` 0, 쓰기·이력·지정 저장 없음, Check 한 번(`child(S,P)`) | 앞 확인을 빼거나 락 뒤로 옮김 |
| 다른 요청이 락을 쥔 동안 같은 상위·줄 있음 → 끝 | 락을 미리 다른 토큰으로 쥐어 두고(획득 한도 0) 부르면 `fullyApplied` 이고 `LockUnavailableException` 이 아니다 | 앞 확인이 락을 기다림 |
| 같은 상위·줄 없음 → 락 안에서 쓴다 | `lock.acquired` 1, `child(S,P)` 를 쓴다(지금 시험 `같은_지정인데_줄이_없으면_쓴다` 에 획득 단언을 더해도 된다) | Check 를 빼고 저장된 지정만 봄(복구가 사라짐) |
| 다른 상위 → 락 안 | `lock.acquired` 1, Check 가 앞 확인에서 불리지 않는다(저장된 지정이 다르면 Check 안 함) | 순서를 Check 먼저로 바꿈 |
| 지정 P 인데 P 이름표 없음 → 지금처럼 거절 | `HierarchyRejectedException(PARENT_NOT_FOUND)`, `lock.acquired` 1 | P 이름표 확인을 뺌 |
| 앞 확인의 Check 가 한 번 실패 → 락 안에서 끝 | 결과 `fullyApplied`, `lock.acquired` 1 | 앞 확인의 오류를 그대로 냄 |
| 앞 확인의 저장소 읽기가 실패 → 락 안 | 같다. 주입은 `FakeStateRepository` 에 읽기 실패를 한 번 더해서 한다(§11) | 같다 |
| DELETE, 지정 없음 → 락 없이 끝 | `fullyApplied`, `lock.acquired` 0 | DELETE 앞 확인을 뺌 |
| DELETE, 지정이 없는 조직을 가리킴 → 락 없이 끝 | `fullyApplied`, `lock.acquired` 0, 지정 지우기 없음(지금과 같음) | "지금 지정"을 저장된 값만으로 봄 |
| DELETE, 지정 있음 → 락 안 | 지금 시험 그대로, `lock.acquired` 1 | — |
| 대상 조직 없음 → 지금처럼 빈 결과 | PUT·DELETE 모두 빈 결과 | S 이름표 확인을 뺌 |

- 지금 시험 가운데 "같은 상위·줄 있음"에서 락을 잡는다고 기대하는 시험(리스·락 관찰자·추적기 시험 등)은 줄이 없는 경우로 바꾸거나 기대를 고친다. 찾는 것은 구현이 한다(§11).

## 6. 이 설계가 말할 수 없는 것

- **동시성 논증(§3.3)은 시험하지 않는다.** 실제 저장소에서 앞 확인의 두 읽기 사이에 다른 요청을 끼우는 시험이 없다. 가짜 저장소로 끼우는 시험도 두지 않는다 — 그 시험은 끼운 순서 하나만 보고, 논증의 "모든 순서"를 보이지 못한다.
- **OpenFGA `HIGHER_CONSISTENCY` 가 "끝난 쓰기를 본다"는 뜻이라는 것은 문서와 지금 포트 계약에 기댄다.** 이 저장소의 다른 판단(Check 기준선)도 같은 전제다.
- **많은 동시 요청이 OpenFGA 에 주는 부하는 재지 않는다.** §3.5 의 권고는 따져서 한 말이다.
- **비용 감소는 재지 않는다.** 어림만 있다 — 바뀐 것 없는 요청 하나가 DynamoDB 쓰기 셋(획득·리스 확인·반납)과 읽기 셋(두 번째 P 이름표·멤버 행·보류 목록)을 덜 하고, 락 줄에 서지 않는다.

## 7. 왜 다른 길을 안 갔나

| 길 | 버린 까닭 |
|---|---|
| 지금 그대로(스크립트가 먼저 비교) | 먼저 비교하면 빠진 줄 복구를 건너뛴다. 모든 운영자가 같은 비교를 다시 짠다 |
| 앞 확인에서 Check 를 빼고 저장된 지정만 본다 | 더 싸지만 "같은 P 로 다시 걸면 빠진 줄을 쓴다"가 사라진다. 매일 다시 거는 운용이 장부를 고치는 길이 없어진다 |
| 읽기 락(공유 락)을 두고 그 안에서 확인 | 지금 락은 하나뿐이다. 읽기 락을 새로 세우면 재적재·회차와의 관계를 다시 정해야 한다. 앞 확인은 쓰지 않으므로 락이 지킬 것이 없다 |
| 지정 쓰기 전체를 락 없이(조건부 쓰기로) | 순환 판정과 보류 목록이 락으로 고정된 그래프를 전제한다(`OrgGraph`). 전역 락 처리량 슬라이드의 일이다 |
| 앞 확인이 바꾸기까지 판정하고 락 안에 넘김 | 락 밖에서 읽은 값으로 락 안을 판정하면 그 사이 바뀐 상태를 놓친다. L3 |
| 일괄 지정 API | 범위 밖(설계 2026-11-04 §2). 바뀐 것 없는 요청이 싸지면 이득이 왕복 수뿐이다 |
| 결과를 캐시 | 캐시는 낡은 값을 낸다(L4 의 "PUT Q 뒤 PUT P"). 읽기 셋·Check 하나는 이미 싸다 |
| L8 없이 앞 확인만 하고 그 경우를 한계로 적기 | 매일 다시 거는 PUT 은 빠진 줄을 고치는 길이다. 앞 확인이 그 복구를 가리는 순서가 하나라도 있으면 "결과는 지금과 같다"가 거짓이 된다. 고치는 길은 이미 있는 도우미를 실패 경로에 거는 것뿐이라 작다 |

### 9.1 머지 전 검증

- 최종 리뷰 수정 뒤의 트리(코드 마지막 `79bb08a`)에서 메인 세션이 차례로 돌렸다.

  - `IncrementalSyncUnsourcedUndoTest` 3건 — L8 의 PATCH·`upsertGroup`, 넣기가 다 저장되면 지정을 읽지 않음.

  - `ScimHierarchyEndToEndTest` 1건 — 재적재가 락을 쥔 동안 바뀐 것 없는 PUT·DELETE 는 204, 바꾸는 PUT 은 503(`Retry-After` 60), 놓은 뒤 204.

- **검증 한계.**
  - §3.3 의 동시성 논증은 코드를 읽고 따졌다. 실제 DynamoDB·OpenFGA 에서 앞 확인의 읽기 사이에 다른 요청을 끼우는 시험은 없다(§6). 최종 리뷰가 `child(S,P)` 를 지우는 길을 모두 다시 따져 L8 뒤에 성립한다고 판정했다.

### 9.3 구현 중 판정

- **§11 을 이렇게 정했다.**
  - "같은 상위·줄 있음" 에서 락을 기대한 지금 시험은 없었다. core 전체가 그대로 통과했고, app-scim 에서 지정을 부르는 다른 시험(`OrganizationHierarchyControllerTest`)은 유스케이스를 목으로 바꾼다.
  - 앞 확인의 저장소 읽기 실패 주입은 `findAssignedParentFailsOnce` 다(과제 1 이 L8 시험과 함께 만들었다).
  - Check 는 `check(tuple)` 을 쓴다. 가짜의 `check` 가 `checked` 에 남긴다.
  - S 이름표와 지정은 `Mono.zip` 으로 함께 읽는다. P 이름표는 지정이 P 일 때만, Check 는 P 이름표가 있을 때만이다.
- **읽기 수를 코드대로 적었다.** §3.5 의 "읽기 셋(DELETE 는 둘)과 Check 하나" 는 느슨하다. 바뀐 것 없는 PUT 은 읽기 셋과 Check 하나, DELETE 는 읽기 둘(지정이 없는 조직을 가리키면 셋)이고 Check 는 없다.
- **T1 의 앞쪽 변이는 `보류와_함께_커밋한다` 앞이어야 한다.** 커밋 람다 첫머리로 옮기는 것은 앞쪽 보류 쓰기 뒤라 앞쪽 시험을 깨지 않는다. 경계가 아니므로 버렸다.
- **설계 §4.3 2행("지정이 다른 하위 조직 넣기는 지금처럼 되지운다")** 은 L8 경로에서 지정이 없는 S 로만 본다(지금 시험 `하위 조직을 넣는 PATCH 가 결과를 모르면 멤버 행을 저장하지 않고 연결 줄을 지운다`). 다른 상위를 가리키는 경우의 거름은 같은 도우미의 빼기 시험(`IncrementalSyncAssignedEdgeTest.지정이_다른_상위를_가리키면_지운다`)이 지킨다.

### 9.5 남긴 것

- **L8 자리의 U5 (a) 거짓 셈**(§2 고치지 않기로 한 것). 그 드리프트에서 L8 의 지정 읽기가 실패해도 센다.
- **L8 의 지정 읽기가 커밋 직전 리스 확인과 저장 사이에 든다.** 실패 경로에서 그 틈이 GetItem 몇 개만큼 넓어진다. 앞쪽 보류 쓰기도 같은 자리이고 리스를 잃으면 LeaseKeeper 가 취소한다.
- **락 없는 길은 보류 목록의 낡은 줄을 걷지 않고, 락 지표에 남지 않는다**(§3.4).

## 11. 확인할 것 (구현 때 사실로 정한다)

- **"같은 상위·줄 있음"에서 락을 기대하는 지금 시험.** core 의 리스·락 관찰자·추적기·감사 시험과 app-scim 의 지정 시험에서 찾는다. 줄이 없는 경우로 바꾸거나 기대를 고친다.
- **앞 확인의 저장소 읽기 실패 주입.** `FakeStateRepository` 에 `findAssignedParent`(또는 `findGroupHeader`)를 한 번 실패시키는 길이 있는지 본다. 없으면 더한다.
- **Check 를 부르는 모양.** 앞 확인이 `check(tuple)` 을 쓸지 `existing(Set.of(tuple))` 을 쓸지 정한다. 가짜의 `checked` 기록이 둘 다 남기는지 본다.
- **읽기의 병렬.** S 이름표와 지정은 함께 읽어도 된다. P 이름표와 Check 는 지정이 P 일 때만이다. 순서만 L4 를 지키면 계획이 정한다.

## 12. 구현 전 점검

계획을 세울 사람의 눈으로 이 문서를 코드와 맞댔다(2026-11-13). 찾은 것과 고친 것:

- **§3.3 의 "되지우기는 저장된 지정이 요구하는 줄을 지우지 않는다"는 지정 쪽에서만 참이었다.** 저장하는 조직 커밋(`changeGroup`·`upsertGroup`)의 되지울 집합은 멤버
  행만 본다. 그래서 앞 확인이 복구를 가리는 순서가 하나 있었다(§3.3 의 1~4) → 미뤄 둔 2026-11-11 §9.5 첫 항목을 L8 로 끌어와 닫았다. 같은 자리의 거짓 셈은 남긴다(§2).

  읽게 하위 조직 연결을 건드리도록 §4.2 를 고쳤다.

- 맞다고 확인한 것: 락 안 길의 읽기 다섯·보류 목록 읽기·빈 델타의 커밋 직전 리스 확인, 줄이 있으면 순환 판정·걷기 예산을 보지 않음(`OrgGraph.거른다`), 이름표·지정의

  저장되는 길이 없음.
