# 실패한 회차·요청의 변경 이력 — 설계

- 날짜: 2026-10-15
- 슬라이드: 운영 견고성 잔여 ②-b (②-a 유일 값 표지판 다음, ②-c 작은 것 앞)
- 출발점: 변경 이력 설계(2026-10-10) §4.4·§10, 작업 견고성 설계(2026-10-13) §10.2.

## 1. 문제

변경 이력은 회차·요청이 **값을 내고 끝나야** 쓴다(이력 설계 §4.4: "커밋되지 않은 변경을 이력에 남기지 않는다"). 그래서 실패하거나 중단된 회차·요청이 그 사이 실제로 한 변경이 모두 사라진다. 사고 조사에 이력이 가장 필요한 때가 바로 이런 회차다.

| 흐름 | 빠지는 경우 | 사라지는 것 |
|---|---|---|
| LDAP 동기화 | 스냅샷 저장 실패, 그 뒤 `replaceWith` 실패, 쓰기 단계 오류 | 쓴·지운 튜플, `replaceWith` 가 이미 쓴 일부 조직도. 스냅샷 뒤 실패면 다음 회차는 기준선이 맞아 "변경 없음" 이 되어 영영 남지 않는다 |
| LDAP 장부 맞추기·재적재 | 스냅샷 저장 뒤 `replaceWith` 실패 | 지운 튜플 |
| SCIM `tuples` | 보류 목록·스냅샷 저장 실패 | 지운 튜플 |
| SCIM `wipe` | 장부 지우기 일부 실패, `replaceWith`·남은 대상·표지판·보류 목록 실패 | 지운 튜플 전부, 지운 직원·조직. 다시 실행해도 장부가 이미 비어 첫 회차 몫은 돌아오지 않는다 |
| SCIM 쓰기 요청 | OpenFGA 를 쓴 뒤 리스 확인·커밋 실패(503) | 쓴 튜플 |
| 모든 회차 | 기한(`sync.job-timeout`)·서버 종료·리스 상실로 취소 | 그때까지 한 모든 변경 |

- `SyncJobs` 는 일이 오류·취소로 끝나면 "반납 뒤 할 일" 을 버리고 `FAILED` 만 적는다. 이력은 반납 뒤 할 일 안에서 쓰므로 0건이다.
- `replaceWith` 는 끝난 변경을 지역 큐에 모아 다 끝나야 돌려준다. 도중에 실패하면 이미 쓴 조직도 변경을 호출자가 알 수 없다.
- SCIM 쓰기 요청은 튜플을 **커밋이 끝난 뒤** 모음에 더한다. OpenFGA 를 쓰고 리스 확인·커밋에서 실패하면 쓴 튜플이 모음에 들어가지 않는다.

## 2. 결정 (사용자 확인, 2026-10-15)

| 무엇 | 고른 것 | 버린 것 |
|---|---|---|
| 원칙 | **실제로 일어난 변경은 일어난 때 모으고, 회차·요청이 어떻게 끝나든 남긴다** | 성공한 회차·요청만 남긴다(지금) |
| 범위 | 회차(LDAP 동기화·장부 맞추기·재적재, SCIM 재적재 `tuples`·`wipe`), SCIM 쓰기 요청, 취소·기한까지 전부 | 손에 값이 있는 실패만 |
| 모으는 방식 | 각 쓰기가 끝나는 즉시 모음에 더하고(포트가 "끝날 때마다" 알린다), 락을 반납한 뒤 한 곳에서 남긴다 | 실패가 부분 결과를 싣고 올라오기, 일어나는 즉시 이력에 쓰기(§9) |

## 3. 회차의 이력을 `SyncJobs` 가 모으고 남긴다

- **회차의 변경 모음 `RunAudit`**(core `audit` 패키지).
  - `AuditChanges` 하나와 이력 종류(`AuditKind`)를 든다.
  - 종류는 부르는 쪽이 기본값을 준다. LDAP 동기화가 장부 맞추기로 가면 일이 `LEDGER_ALIGNMENT` 로 바꾼다.
- **`SyncJobs` 가 회차를 열 때 모음을 만들어 일에 넘긴다.**
  - 이력을 남기는 회차는 새 오버로드를 쓴다: `startLockedThen(source, trigger, purpose, kind, (run, 기록) -> ...)`.
  - 이력이 없는 작업(아카이빙·정리)은 지금의 오버로드 그대로다.
- **일은 쓰기가 끝나는 즉시 모음에 더한다**(§5). 유스케이스는 이력을 직접 쓰지 않는다 — `audit.now()`·`recordRun` 호출과 이력 줄 조립이 빠진다.
- **기록 순서**(`SyncJobs`):
  1. 락 안의 일이 끝나는 순간(값·오류·취소 무엇이든, 반납 전)에 시각을 잡는다. 지금의 "커밋 직후" 와 같은 뜻이다.
  2. 반납한다.
  3. 반납 뒤 할 일(스냅샷 저장 등)을 돌려 결론을 정한다. 일이 실패했으면 결론은 `FAILED` 다.
  4. **모음을 그 결론과 함께 `recordRun` 으로 남긴다.** 빈 모음이면 쓰지 않는다.
  5. 실행 기록을 닫는다.
- **이력 쓰기 실패는 회차를 실패시키지 않는다.** 지금처럼 오류 로그·지표 `audit.write.failures`·회차 메시지 "감사 기록 N건 실패" 로 알린다.
- **`SyncJobs` 생성자가 `AuditRecorder` 를 받는다.** 결선 두 곳(app-ldap·app-scim)이 넘긴다. 테스트용 생성자는 `AuditRecorder.NONE` 이다.

## 4. 포트가 "끝날 때마다" 알린다

- **`RelationTupleWriter.apply(delta, 묶음마다)`**
  - OpenFGA 쓰기는 묶음 단위로 나간다. 묶음 하나가 끝날 때마다 그 묶음의 결과(쓴 줄·지운 줄·실패)를 알린다.
  - OpenFGA 구현은 묶음의 응답이 오는 자리에서 곧바로 알린다. 결과를 모으는 자리(`ResultAccumulator`)는 보낸 순서를 지키느라 먼저 끝난 묶음을 붙들 수 있어, 그 사이 취소되면 끝난 묶음을 놓친다. 차단기로 멈추거나 도중에 취소돼도 끝난 묶음은 이미 알린 뒤다.
  - 지금의 `apply(delta)` 는 알림을 받지 않는 기본 메서드로 남는다.
- **`DirectoryStateRepository.replaceWith(snapshot, 변경마다)`**
  - 직원·조직 하나의 저장·삭제가 끝날 때마다 그 변경(`UserDiff`·`GroupDiff`)을 알린다.
  - 다 끝나면 지금처럼 `DirectoryChanges` 전체도 돌려준다(wipe 가 남은 대상을 찾는 데 쓴다).
  - 지금의 `replaceWith(snapshot)` 은 알림을 받지 않는 기본 메서드로 남는다.
- **`deleteUser`·`deleteGroup` 은 그대로다.** wipe 의 남은 대상 지우기가 하나 지울 때마다 직접 더한다.
- 알림은 여러 스레드에서 올 수 있다. `AuditChanges` 는 이미 동기화돼 있다.

## 5. 흐름별로 더하는 것

지금의 이력 규칙(무엇을 남기나)은 바꾸지 않는다. 언제 더하나만 바뀐다.

| 흐름 | 더하는 것 |
|---|---|
| LDAP 동기화 | OpenFGA 묶음마다 쓴 줄·지운 줄, `replaceWith` 변경마다 |
| 장부 맞추기·LDAP 재적재·SCIM `tuples` | 지우기 묶음마다 지운 줄(쓴 줄은 지금처럼 남기지 않는다 — 중복 무시로 써서 이미 있던 줄과 가를 수 없다) |
| SCIM `wipe` | 지우기 묶음마다 지운 줄, `replaceWith` 변경마다, 남은 대상을 하나 지울 때마다 |

**변경 모음의 규칙 하나를 고친다 — 이름표가 그대로인 조직 결과는 상태를 보지 않는다.**
- 즉시 더하면 순서가 생긴다.
  - `replaceWith` 가 GSI 밖 조직에서 멤버를 뺄 때 내는 "멤버만 빠짐" 결과가 먼저 모음에 들어간다.
  - 그 조직의 삭제는 나중에 들어온다.
- 지금 모음은 처음 본 "이전" 을 붙든다(`상태를_본다`). 이름표가 빈 "멤버만 빠짐" 이 먼저 오면 삭제 줄의 이름표가 사라진다. 작업 견고성 슬라이드에서 같은 문제를 접기로 피했다.
- 그래서 이전과 이후의 이름표가 같은 결과는 **멤버 변화만** 적고 상태(생성·삭제·속성)는 보지 않는다. 그러면 나중에 온 삭제가 이름표를 제대로 남긴다.
- 이름표가 같으면 속성 변화가 없으므로, 한 번만 오는 경우의 결과는 지금과 같다.
- wipe 의 "멤버만 빠짐 접기" 는 이력에는 필요 없어진다. 하지만 `replaceWith` 가 돌려주는 값을 정확하게 두려고 그대로 둔다.

## 6. SCIM 쓰기 요청

요청마다 변경 모음이 이미 있다(`IncrementalSyncUseCase.withLock`). 같은 규칙을 쓴다.

- **튜플은 묶음이 끝날 때마다 더한다**(`apply(delta, 묶음마다)`). 지금은 커밋이 끝난 뒤에 더해, OpenFGA 를 쓴 뒤 리스 확인·커밋이 실패하면 빠진다. 보류 목록을 다시 볼 때 쓰는 튜플도 같다.
- **조직도 변경은 지금처럼 각 저장이 끝난 직후에 더한다.**
- **기록은 어떻게 끝나든 한다.**
  - 값이든 오류든(리스 상실·차단기·커밋 실패) 락 안에서 끝난 순간의 시각으로 모은 것을 남긴다.
  - 순서는 지금처럼 반납 → 차례 넘김 → 이력 → 응답이다. 응답(503 등)은 바뀌지 않는다.
  - 대상이 없어 빈 결과로 끝나면 모은 것도 없어 쓰지 않는다.

## 8. 이 설계가 말할 수 없는 것

- **서버 프로세스가 죽으면 메모리의 모음이 사라진다.** 그 회차의 실행 기록은 지금처럼 RUNNING 으로 남았다가 다음 락 작업이 "비정상 종료로 중단" 으로 닫는다.
- **서버 종료와 큰 회차가 겹치면 이력 쓰기가 종료 대기를 먼저 쓴다.** 종료로 멈춘 회차도 이력을 쓴 뒤에 실행 기록을 닫는다. 종료는 최대 10초만 기다리므로, 10만 줄 같은 큰 모음이면 이력이 일부만 남고 실행 기록은 RUNNING 으로 남는다. 다음 락 작업이 그 기록을 "비정상 종료로 중단" 으로 닫는다. 순서를 종료 때만 바꾸지 않았다 — 한 규칙(이력 → 기록)을 지키고, 전에는 그 회차의 이력을 모두 잃었다.
- **OpenFGA 가 쓰고 응답을 잃은 묶음은 실패로 센다.** 우리는 반영됐는지 모르므로 이력에서 빠진다.
- **거절돼 쪼개 보내는 묶음은 조각을 다 보낸 뒤에 한 번 알린다.** 그 사이 취소되면 이미 반영된 조각은 이력에서 빠진다. 400 거절과 취소가 겹칠 때뿐이다.
- **조직 하나의 저장이 도중에 실패하면 이미 쓴 일부는 알리지 않는다.** 조직 저장은 멤버 지우기 → 이름표 → 멤버 넣기 순이다. 알림은 직원·조직 하나의 저장이 다 끝날 때만 나온다.
- **같은 단계에서 동시에 쓰던 다른 변경이 실패로 취소되면, 이미 쓰였어도 알리지 않을 수 있다.** 전체 교체는 단계 안에서 직원·조직을 동시에 쓴다. 하나가 실패하면 나머지가 취소되는데, 취소된 쓰기가 DynamoDB 에 이미 반영됐을 수 있다 — OpenFGA 가 쓰고 응답을 잃은 묶음과 같은 종류다.
- **회차의 모든 줄은 시각이 하나다** — 락 안의 일이 끝난 때다(지금과 같다).
- **실패한 회차의 이력 쓰기도 실패할 수 있다.** 지금과 같은 경로로 알린다.
- **AWS 실측은 없다.** 비용은 늘지 않는다 — 알림은 메모리 안의 호출이고, 모음은 지금도 10만 명 회차의 변경 전부를 든다.

## 9. 왜 다른 길을 안 갔나

- **실패가 부분 결과를 싣고 올라오기**(`TupleWriteAbortedException.partial()` 을 넓히기).
  - 실패하는 단계마다 그때까지 한 변경을 예외에 싣는다.
  - 그러나 취소(기한·종료·리스 상실)는 예외가 아니라서 다루지 못한다.
  - 단계마다 잡는 코드도 흩어진다.
- **일어나는 즉시 이력에 쓰기(선기록).**
  - 서버가 죽어도 남는다.
  - 그러나 이력 쓰기를 락 밖에 두는 원칙(이력 설계 §4.4)을 깨고, 10만 명 적재 같은 큰 회차에서 이력 쓰기가 SCIM 쓰기를 막는다.
- **손에 값이 있는 실패만 고치기.** 작지만 취소·SCIM 요청이 남고, 경로마다 따로 고쳐 앞으로 경로가 늘면 다시 빠진다.

| 끝단 | LDAP 동기화 중 스냅샷을 저장한 뒤 상태 저장(`replaceWith`)이 실패해도 OpenFGA 에 쓴 권한이 이력에 남고, 다음 회차는 "변경 없음" 이다(L15-a·L15-b). 스냅샷 저장 자체가 실패한 회차는 core 가 본다 | app-ldap |
| 전체 | 머지 전 `test`·`scaleTest` 둘 다 | 전체 |

## 11. 결과 (구현 후 기록)

### 11.1 머지 전 검증

- `./gradlew cleanTest test`: 1,748개 통과(4분 31초, 3581081).
- `./gradlew cleanScaleTest scaleTest`: 89개 통과(16분 38초, 3581081).
  - L15-a 가 상태 저장이 실패한 회차의 이력을 본다. 원인은 그 회차(`LDAP`/`SYNC`)이고, 쓴 권한이 남고, 생성 표시는 없다. L15-b 는 그대로 "변경 없음" 이다.
  - 전체 시간은 앞 슬라이드(17분 14초)보다 짧다. 실행 간 차이 안이다. 알림은 메모리 안의 호출이라 쓰기 수는 같다.
- 실패 경로는 core 가 본다.
  - `SyncJobs`: 값·오류·기한·종료·리스 상실·반납 뒤 할 일 실패에서 모두 남긴다. 시각은 반납 전이다(시계가 반납 때만 가는 락으로 본다).
  - LDAP: 스냅샷 저장 실패, 조직도 교체 도중 실패, 쓰는 도중 리스 상실, 장부 맞추기·재적재 실패.
  - SCIM 재적재: `tuples` 의 보류 목록·스냅샷 실패, `wipe` 의 장부 일부·조직도 교체·표지판·보류 목록·남은 대상 실패.
  - SCIM 요청: 커밋 실패, 커밋 직전 리스 확인 실패, 차단기, 락 못 잡음.
- DynamoDB Local: 단계 사이에서 실패한 전체 교체는 알린 변경과 테이블이 같다. OpenFGA: 차단기로 멈추면 보낸 묶음만, 먼저 끝난 묶음은 순서를 기다리지 않고 알린다.

### 11.2 구현 중 판정

- **계획에서 정한 것(설계를 고친 것).**
  - OpenFGA 는 결과를 모으는 자리가 아니라 묶음의 응답 자리에서 알린다(§4). 모으는 자리는 보낸 순서를 지키느라 먼저 끝난 묶음을 붙들어, 그 사이 취소되면 놓친다.
  - 끝단 시험은 L15-a 다(§10). 다음 회차가 "변경 없음" 인 것은 스냅샷을 저장한 뒤 상태 저장이 실패한 경우다.
  - 두 포트 모두 알림을 받는 2-인자가 추상이고, 지금의 1-인자는 알림 없이 그것을 부르는 기본 메서드다.
- **과제 리뷰에서 정한 것.**
  - 전체 교체의 같은 단계에서 형제가 실패해 취소된 쓰기는 반영됐어도 알리지 않을 수 있다. §8 에 적었다.
- **최종 리뷰에서 고친 것.**
  - **서버 종료와 큰 회차가 겹치는 한계를 §8·자바독·README 에 적었다.** 이력 쓰기가 종료 대기 10초를 먼저 써, 기록이 "비정상 종료로 중단" 으로 닫힐 수 있다. 종료 때만 순서를 바꾸는 갈래는 두지 않았다 — 한 규칙을 지키고, 잃는 것은 사유 문구와 이력 일부다.
  - DynamoDB 쓰기 단계 두 곳의 알림을 안쪽으로 옮겼다. 바깥에서 알리면 형제가 실패할 때 큐에 담긴 끝난 변경을 버렸다.
  - 거절 묶음을 쪼갠 조각의 알림 한계를 §8 에 적었다(코드는 그대로).
  - 이력 기록기의 낡은 "커밋" 문구, 포트 자바독의 응답 잃은 묶음 문구를 고쳤다. `SyncJobs` 가 기록기를 null 검사한다.
- **남긴 것.**
  - `wipe` 의 "멤버만 빠짐 접기" 는 이제 아무도 받지 않는 값에 작용한다. §5 가 댄 이유(돌려주는 값을 정확하게)도 맞지 않는다. 동작 영향이 없어 이번에는 두고 ②-c 에서 없앨지 정한다.
  - 시험하지 않은 것: SCIM 요청의 리스 상실(취소) 경로 시각, 형제 실패 때의 DynamoDB 알림, 앞 단계 실패로 지우기만 보낸 OpenFGA 묶음의 알림, 오류로 끝난 요청에서 이력 쓰기도 실패하는 경우.
  - 실패한 회차의 실행 기록 집계(written·deleted)는 그대로 0 이다. 같은 runId 의 이력에는 실제로 쓴 권한이 보인다.
