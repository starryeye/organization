# 재활성 가드 설계 (2026-11-24)

온보딩 13 §3.3 "부여 쪽에는 가드가 없다"를 좁은 판으로 닫는다. 대상은 12 §4.6 "서비스 계정이 계정 상태 속성을 못 읽음 — 전원 활성"이다. 외부 리뷰 N3 이 짚은 셋(원인별 분리·절대 수 상한·부여 가드) 가운데 마지막 갈래다.

사용자 결정은 "추천대로"(2026-11-23)와 방향 "진행"(2026-11-24)이다. 아래 결정은 모두 그 추천이다.

## 1. 문제

- **막힌 계정이 한꺼번에 활성으로 읽히면 권한이 조용히 돌아온다.**
  - 계정 상태 속성이 없으면 막히지 않은 것으로 읽는다(설계 2026-09-25 ⑥, 사용자 결정). 동기화 계정이 `userAccountControl`·`accountExpires`(OpenLDAP 이면 `pwdAccountLockedTime`)를 못 읽게 되면 막힌 계정이 모두 활성이다.
  - 다음 회차가 그 직원들의 `direct_member` 를 다시 쓴다. 실행 상태는 `SUCCEEDED` 다. 오류가 없고, 루트 README.md 에 이것을 잡는 경보 예도 없다(12 §4.6).
  - 같은 모양이 더 있다. 앱 시계가 뒤로 가면 `accountExpires` 가 지난 계정이 아직 유효하게 읽힌다. 한 OU 의 접근 제어만 바뀌면 그 OU 의 막힌 계정만 활성이 된다.
- **지우는 쪽에는 가드가 있고 부여 쪽에는 없다.** 지우기는 비율·상한, 비활성 회수 떼어 보기, 멈춤 내역, 확인한 수의 `force` 까지 갖췄다(설계 2026-10-20·11-13·11-20). 부여 쪽 가드는 남김이다(13 §3.3, 설계 2026-10-20 §14).
- **지금 코드에는 알아챌 근거가 없다.**
  - 비교의 기준인 스냅샷(`TupleSnapshot`)은 장부에 쓴 줄 B 와 결과를 모르는 줄 U 만 갖는다. 직전에 누가 비활성이었는지는 없다.
  - 그래서 다시 활성이 된 직원의 줄은 쓸 줄(D − B)에 새 입사자의 줄과 섞인다.
  - 현재상태(DynamoDB 직원 META)에는 `active` 가 있다. 하지만 교체(`replaceWith`)는 쓰기 **뒤에** 저장본과 비교한다. 회차 앞에서 그것을 읽으면 10만 명의 META 를 한 번 더 읽는다.

## 3. 동작

### 3.1 비활성 소속 줄 I (스냅샷)

- **모델.** `TupleSnapshot` 에 칸 `inactive`(I, `Set<RelationTuple>`)를 더한다. 비어 있을 수 있다. B·U 와 겹쳐도 된다 — I 는 장부의 상태가 아니라 그 회차 그림의 사실이다(지우다 실패한 비활성 직원의 줄은 B 와 I 에 함께 있다). 지금의 4·5인자 생성자는 빈 I 로 둔다(SCIM 과 기존 호출처).
- **만드는 값.** 그 회차가 반영한 그림(재활성을 보류했으면 그림′)의 `TupleMapper.inactiveMemberTuples` 다. 비활성 직원 u 가 조직 g 의 직원 멤버일 때의 `direct_member(user:u, group:g)` 다.
- **저장하는 회차.** LDAP 이 스냅샷을 저장하는 자리 전부다.
  - 비교 경로: 커밋, 차단기 멈춤(`stopped`), 비활성 회수만 반영.
  - 장부 맞추기: 커밋(일부 반영 포함).
- **저장하지 않는 회차.** 지금도 스냅샷을 남기지 않는 두 경우다. 이때 직전 I 가 그대로 남는다.
  - 변경 없음(델타가 빔). 새로 막힌 직원은 지울 줄을 만들고, 보류한 직원은 그림′ 에서 비활성이라 줄을 만들지 않으므로, 델타가 비면 직원 단위의 I 는 같다. 다른 것은 비활성 직원이 소속만 옮긴 경우와 그림에서 사라진 경우뿐이다 — 둘 다 직전 I 에 남아 있어도 다음 판정을 안전한 쪽(재활성으로 센다)으로만 바꾼다.
  - 비교 경로의 전부 보류(삭제 가드). 아무것도 반영하지 않았다.
  - 장부 맞추기의 전부 보류. 이 길은 가드를 보기 전에 D 를 이미 다 썼다(`TupleReconciler.reconcile` 이 쓴 뒤 `DeleteCheck` 를 부른다). 그래서 이번 회차에 통과한(문턱 아래이거나 강제로 넘긴) 재활성 직원의 줄은 장부에 나갔는데 I 는 옛것 그대로다. 기록 중 표시도 남아 다음 회차는 다시 장부 맞추기로 오고, 같은 직원을 다시 재활성으로 센다. 받아들인 한계다(§6, §12).
- **저장.** `DynamoDbTupleSnapshotRepository` 에 세 번째 묶음 계열을 둔다 — 정렬키 `INACTIVE#`, 메타 칸 `inactiveCount`·`inactiveChunkCount`. U 처럼 비어 있지 않을 때만 메타에 칸을 적고, 칸이 없으면 빈 I 로 읽는다. 무결성 검사(묶음 수·번호·본문·줄 수)는 본문과 같다. 저장 순서는 메타 → 본문 → U → I → 포인터, 지우는 순서(만료 정리)는 그 반대다.
- **크기 어림.** 막힌 계정을 그룹에 둔 채 두는 AD 배포에서 막힌 계정 2만 명, 소속 1.5개면 I 는 3만 줄이다. 본문 15만 줄(10만 명)의 약 20% 다. 변경이 있는 회차마다 스냅샷 한 벌을 새로 쓰므로(13 §5.4) 저장량도 그만큼 는다 — 보관 7일 최대 약 1GB 가 약 1.2GB 가 된다(어림, 재지 않았다). 막힌 계정을 그룹에서 빼거나 검색 범위 밖 OU 로 옮기는 배포는 I 가 작다.

### 3.2 판정 (`ReactivationGuard`)

core `guard` 패키지에 둔다. 삭제 가드와 나란한 모양이다.

```java
public record ReactivationGuardPolicy(boolean enabled, double thresholdRatio, int minBaseline, int maxReactivations) {
    public static ReactivationGuardPolicy defaults() { return new ReactivationGuardPolicy(true, 0.3, 10, 100); }
}

public class ReactivationGuard {
    public ReactivationGuard(ReactivationGuardPolicy policy)
    /** 강제 회차 — 비율을 끄고 상한을 M 으로 본다. 설정에서 꺼 두었어도 켠다 */
    public static ReactivationGuard forced(int maxReactivations)
    /** 직전 I 와 이번 그림으로 판정한다. 보류면 그림′ 과 내역과 문구를 준다 */
    public ReactivationCheck check(Set<RelationTuple> previousInactive, DirectorySnapshot picture)
}

/** held() 가 거짓이면 picture 는 받은 그림 그대로, hold·message 는 null 이다 */
public record ReactivationCheck(DirectorySnapshot picture, ReactivationHold hold, String message) {
    public boolean held() { return hold != null; }
}
```

- **기준.** I 의 줄 가운데 `user` 가 `user:` 로 시작하는 것에서 직원 id 를 뗀다(다른 모양의 줄은 세지 않는다). 서로 다른 id 의 수가 기준 수다.
- **재활성.** 그 id 가운데 이번 그림의 `users` 에 있고 `active` 인 것. 비면 판정하지 않는다(보류 없음).
- **판정.** 가드가 꺼졌으면 보류 없음. 아니면 상한 초과(`maxReactivations > 0` 이고 재활성 수 > 상한, 기준 수와 무관)와 임계치 초과(기준 수 ≥ `minBaseline` 이고 비율 > 임계치)를 따로 보아 하나라도 넘으면 보류다.
- **문구.**(숫자는 쉼표 없이)
  - `재활성 대상 %d명(직전 비활성 소속 직원 %d명의 %.1f%%)이 %s 초과했습니다. 강제 실행하려면 실행 기록의 reactivationHold 를 확인한 뒤 force=true 와 maxReactivations(허용할 재활성 직원 수)로 재요청하세요`
  - 넘은 것: `임계치 30.0%를`(비율만), `상한 100명을`(상한만), `임계치 30.0%와 상한 100명을`(둘 다).
- **그림′.** 재활성 직원 모두를 `withActive(false)` 로 바꾼 그림이다. 나머지 칸(조직·지정 연결)은 그대로다.
- **내역.** `ReactivationHold(int count, List<String> ids)` — 재활성 직원의 수와 사전순 앞 10개(`GuardHold.SAMPLE_SIZE`). core `model` 에 둔다.
- **강제.** `forced(M)` = 정책 `(true, 1.0, Integer.MAX_VALUE, M)` — 삭제 가드의 `forced` 와 같은 꼴이다. M 은 1 이상이다.
- **비용.** 직전 I 를 한 번, 재활성 후보마다 그림 맵 조회 한 번. 보류면 그림의 직원 맵을 한 번 복사한다. 더 읽는 것은 없다.

### 3.3 회차 흐름

```
LDAP 전체 읽기 → 포인터 상태
  ├ 있음(PRESENT): 최신 스냅샷을 한 번 읽는다 → I 로 재활성 판정 → 그림′ → 매핑 → 비교(같은 스냅샷을 기준선으로)
  ├ 기록 중(WRITING): 최신 스냅샷을 읽어 본다(없거나 실패면 판정 없음) → 그림′ → 매핑 → 장부 맞추기
  └ 없음(NONE): 판정 없음 → 매핑 → 장부 맞추기
재적재: LDAP 전체 읽기 → 최신 스냅샷을 읽어 본다(없거나 실패면 판정 없음) → 그림′ → 매핑 → 장부 맞추기
```

- **비교 경로는 스냅샷을 한 번만 읽는다.** 지금 `비교해_맞춘다` 안에서 읽는 기준선(`baseline()`)을 매핑 앞으로 당겨, 같은 스냅샷에서 I 와 B·U 를 함께 쓴다. 스냅샷을 못 읽으면 지금처럼 `SnapshotIntegrityException` 으로 실패한다.
- **기록 중·재적재의 읽기.** 실패하면 WARN `직전 스냅샷을 읽지 못해 재활성 가드를 보지 않는다: {}` 를 남기고 판정 없이 간다. 스냅샷이 없으면 조용히 간다.
- **판정 뒤 할 일.** 보류면 WARN `재활성 가드 발동: {}`(가드 문구 — 수만 담는다). 그 뒤의 매핑·가드·현재상태·스냅샷은 모두 그림′ 이다(R4).
- **결론 붙이기 순서.** 경로의 결론(장부 맞추기의 사정 문구 포함) → 재활성 보류(상태를 R6 대로, 내역, 앞 문구) → 강제 문구(가장 바깥, R11).
  - 예(속성을 못 읽음, 강제 아님): `재활성 가드 발동 — 직원 2000명의 재활성을 보류(비활성 그대로 둠) / 재활성 대상 2000명(직전 비활성 소속 직원 2000명의 100.0%)이 임계치 30.0%와 상한 100명을 초과했습니다. 강제 실행하려면 … 재요청하세요`
  - 변경이 없던 회차면 끝에 ` / 변경 없음` 이 붙는다.
- **예외로 끝난 회차.** 결론이 없어 보류 내역과 문구가 실행 기록에 남지 않는다(강제 허용 수와 같다, 설계 2026-11-20 §6). 현재상태 교체까지 갔다면 보류한 직원은 비활성 그대로 저장된다.
- **감사 이력.** 보류한 직원은 현재상태가 바뀌지 않으므로 이력 줄이 생기지 않는다.

### 3.4 실행 기록과 API

- **모델.** `SyncOutcome` 과 `SyncRun` 에 칸 `reactivationHold`(없으면 null)를 더한다. `SyncOutcome` 에 보류를 적용하는 메서드 하나를 둔다 — 상태(R6), 내역, 앞 문구를 한 번에 바꾼다.
- **저장.** `DynamoDbSyncRunRepository` 의 M 속성 `reactivationHold` — `count`(N), `ids`(L of S). 없으면 칸이 없다.
- **응답.** `GET /admin/sync/runs/{runId}` 에 `reactivationHold: {"count": 2000, "sample": ["…", …]}` — 모양은 `guardHold` 의 갈래(`GuardHoldResponse.Sample`)와 같다. 없으면 칸이 없다. 목록(`SyncRunResponse.listed`)은 `guardHold` 처럼 뺀다.
- **두 내역.** 한 회차에 둘 다 있을 수 있다. `guardHold` 는 지우려던 것, `reactivationHold` 는 보류한 재활성이다.

### 3.5 강제 요청

- **허용 수.** `ForceAllowance(Integer maxDeletes, Integer maxReactivations)` — 둘 다 null 이면, 또는 준 값이 1 미만이면 `IllegalArgumentException`(컨트롤러의 400 과 별개로 core 가 스스로 지킨다). `note()` 는 R11 의 세 꼴이다.
- **가드 고르기.** 동기화·재적재가 회차를 띄울 때 한 번 고른다. 삭제 가드는 `maxDeletes` 가 있으면 `DeletionGuard.forced(maxDeletes)`, 없으면 설정의 가드. 재활성 가드는 `maxReactivations` 가 있으면 `ReactivationGuard.forced(maxReactivations)`, 없으면 설정의 가드. `DeletionGuard.forced` 는 `int` 를 받게 바꾼다.
- **트리거.** 수가 무엇이든 강제면 `FORCED`(재적재는 `FORCED_REBUILD`)다.
- **컨트롤러.** `POST /admin/sync/full`·`POST /admin/sync/rebuild` 가 `maxReactivations` 를 더 받는다. 검사 순서는 R10 이다. 400 문구:
  - `force=true` 인데 수가 없거나 1 미만: `force=true 에는 maxDeletes(허용할 지울 줄 수) 또는 maxReactivations(허용할 재활성 직원 수)가 1 이상으로 함께 와야 합니다`
  - `force` 없이 수: `maxDeletes·maxReactivations 는 force=true 와 함께만 씁니다`
- **로그.** 요청 INFO·WARN 에 `maxReactivations` 를 더한다.

### 3.6 운영자가 하는 일 (12 §4.6 을 고쳐 쓸 내용)

1. `sync.guard.aborted` 경보가 울린다. 실행 기록 단건에 `reactivationHold` 가 있다.
2. 예의 id 를 디렉터리에서 본다.
   - **디렉터리에서는 여전히 막혀 있다** → 읽기 문제다(서비스 계정 권한, 시계). 고치면 다음 회차가 그들을 다시 비활성으로 읽어 재활성이 0 이 되고 저절로 풀린다. 그동안 그들의 권한은 없다 — 맞는 상태다.
   - **정말 다시 켰다**(대량 재고용, 잘못 막은 계정 되돌리기) → `POST /admin/sync/full?force=true&maxReactivations=M`, M 은 `count` 에 작은 여유를 둔다.
   - **같은 회차에 `guardHold` 도 있고 메시지가 장부 맞추기(`기준선 의심 …`·`기준선 없음 …`) 또는 재적재의 전부 보류다** → 두 수를 함께 준다(`force=true&maxDeletes=N&maxReactivations=M`). 재활성만 넘기면 줄은 장부에 나가지만 스냅샷이 남지 않아, 다음 회차가 같은 직원을 다시 재활성으로 세고 보류하면 방금 나간 줄을 비활성 회수로 지운다(§6).
3. 보류가 이어지는 동안 그 회차들은 ABORTED 라 `sync.last.success` 도 멈춘다. 속성을 못 읽는 동안은 새로 막힌 계정도 활성으로 읽혀 회수 신호가 끊긴 것이므로, 마지막 성공 경보가 함께 울리는 것이 사정과 맞다.

## 4. 시험

### 4.1 core — 판정(`ReactivationGuardTest`, 순수 함수)

- 재활성이 없으면 보류 없음(기준이 있어도).
- 비율만 넘음 / 상한만 넘음 / 둘 다 — 세 문구가 정확히 맞는다. 같으면 통과(초과만 걸린다).
- 기준 수가 `min-baseline` 미만이면 비율은 보지 않고 상한은 본다.
- 상한 0 이하면 상한을 보지 않는다. 가드를 끄면 보류 없음.
- `forced(M)`: 재활성 M 명은 통과, M+1 명은 보류. 정책을 꺼도 `forced` 는 본다.
- 그림′: 재활성 직원만 비활성이 되고 다른 직원·조직은 그대로다. 그림에 없는 직원·이미 비활성인 직원은 재활성이 아니다. `user:` 가 아닌 줄은 세지 않는다.
- 내역: 수와 사전순 앞 10개.

### 4.2 core — 유스케이스

- **비교 경로**(`FullSyncUseCaseTest`):
  - 보류 — 그 직원의 `direct_member` 를 쓰지 않는다, 현재상태에 비활성으로 남는다, 새 스냅샷 I 에 그 직원의 줄이 있다, ABORTED·`reactivationHold`·앞 문구가 맞는다. 같은 회차의 새 입사자 줄은 쓴다.
  - 다음 회차가 같은 그림이면 다시 보류한다(스냅샷 I 로 이어진다).
  - 읽기가 돌아와 그들이 다시 비활성으로 읽히면 재활성 0, 지울 줄 0, 보류 없음.
  - 문턱 아래면 그대로 쓴다(SUCCEEDED, I 에서 빠진다).
  - 변경 없음 + 보류 → ABORTED 이고 문구 끝이 ` / 변경 없음`.
  - 삭제 가드와 함께 걸림 — 상태 ABORTED, 두 내역, 문구 순서.
  - 차단기 멈춤(FAILED) + 보류 → FAILED 그대로, 내역은 붙는다.
  - `startForced(new ForceAllowance(null, M))` — 재활성 M 명 통과, 결론 앞 `강제 실행 — 재활성 허용 M명`. 삭제 가드는 설정대로 본다.
  - 기록 중 경로는 최신 스냅샷의 I 로 판정한다. 그 스냅샷 읽기가 실패하면 판정 없이 장부 맞추기를 끝낸다.
  - 기록 중 경로에서 재활성을 강제로 넘기고(`maxReactivations` 만) 삭제 가드가 전부 보류면, 그 직원의 줄은 쓰이고 스냅샷은 남지 않는다. 다음 강제 아닌 회차는 같은 직원을 다시 재활성으로 센다 — §6 의 한계를 고정한다.
  - 포인터 없음은 판정하지 않는다.
- **재적재**(`RebuildUseCaseTest`): 스냅샷이 있으면 보류한다. 없거나 읽기가 실패하면 판정 없이 끝낸다.
- **스냅샷 I 저장**: 비활성 회수만 반영한 회차와 장부 맞추기 커밋도 그림′ 의 I 를 남긴다.
- **허용 수**(`ForceAllowance`): 둘 다 null·1 미만이면 IAE, `note()` 세 꼴.

### 4.3 storage-dynamodb — 왕복

- 스냅샷 I 있음·없음 왕복. I 묶음이 여럿으로 나뉘는 크기에서도 맞다(지금 U 시험과 같은 방식).
- 만료 정리가 I 묶음까지 지운다.
- 실행 기록 `reactivationHold` 왕복. 없으면 칸이 없다.

### 4.4 admin-api·app-ldap

- 컨트롤러(`AdminSyncControllerTest`): `maxReactivations` 만, 둘 다, 둘 다 없음(400), 0(400), force 없이(400), 범위 없음(403 먼저), 재적재의 400 이 `mode` 400 보다 먼저.
- 응답: 단건에 `reactivationHold` 칸, 목록에는 없음.
- 설정 결선: `sync.reactivation-guard.*` 기본값과 덮어쓰기가 가드에 닿는다.
- 종단(`LdapSyncEndToEndTest`, 임베디드 LDAP + 실제 DynamoDB Local·OpenFGA): 시험 설정으로 상한을 낮춘다(예 `max-reactivations: 1`). 막힌 계정 둘의 `userAccountControl` 을 지워 "읽지 못함"을 흉내 내면 회차가 ABORTED, `reactivationHold.count` 2, 두 직원의 OpenFGA `direct_member` Check 가 거짓, 관리 API 직원 상세의 `active` 거짓이다. 속성을 되돌리면 다음 회차는 ABORTED 가 아니다. 정말 켜면(`512`) 다시 보류되고, `force=true&maxReactivations=2` 로 넘기면 권한이 생긴다.

### 4.5 규모

새 규모 시험은 두지 않는다. 규모 픽스처에는 계정 상태 속성이 없다(설계 2026-09-25 ⑥ — 스키마 확장이 필요하다). 기존 규모 시험은 빈 I 로 스냅샷 저장·읽기를 그대로 지난다. §6 에 남긴다.

## 6. 이 설계가 말할 수 없는 것

- **직전 스냅샷에 소속이 없던 비활성 직원은 기억하지 않는다.** I 는 소속 줄에서 나온다. 그런 직원이 한 회차에 다시 활성이 되며 소속도 새로 얻으면 새 입사자처럼 그대로 쓴다.
- **스냅샷이 없으면 보지 않는다.** 첫 적재·새 테이블·초기화 뒤, 그리고 기록 중 회차와 재적재에서 스냅샷을 읽지 못할 때다. 이 슬라이드를 배포한 뒤 첫 회차도 옛 스냅샷에 I 가 없어 보지 않는다(운영 배포 전이라 이관하지 않는다).
- **문턱 아래의 뒤집힘은 지나간다.** 예: 막힌 계정 1,000명 가운데 한 OU 의 30명만 활성으로 읽히면 3%·30명이라 기본 문턱 아래다. 삭제 가드의 "30% 이하·5,000줄 이하는 나간다"와 같은 한계다.
- **보류하는 동안 새로 막힌 계정도 활성으로 읽힌다.** 속성을 못 읽는 사고에서는 회수 신호 자체가 끊긴다. 이 가드가 막는 것은 "이미 막혀 있던 사람의 권한이 돌아오는 것"뿐이다. 새로 막힌 사람은 그 사이 권한을 유지한다 — 마지막 성공 경보가 그 신호다(§3.6).
- **정상적인 대량 재활성도 멈춘다.** 계약 연장으로 만료가 한꺼번에 풀리는 경우 등이다. 사람이 `maxReactivations` 로 넘긴다.
- **현재상태는 디렉터리와 다르게 보인다.** 보류한 직원은 디렉터리에서 활성인데 관리 API 에서는 비활성이다. 장부와는 맞는다.
- **보류는 회차 단위 전부다.** 문턱을 넘으면 그 회차의 재활성을 모두 보류한다. 일부만(문턱까지) 반영하지 않는다 — 어느 쪽을 먼저 반영할지 고를 근거가 없다.
- **장부 맞추기가 전부 보류로 끝나면 통과한 재활성이 기억되지 않는다.**
  - 이 길은 D 를 먼저 다 쓰고 스냅샷을 남기지 않는다(§3.1). 문턱 아래로 통과했거나 강제로 넘긴 재활성 직원의 줄은 장부에 나가지만 I 는 옛것이다.
  - 다음 회차(역시 장부 맞추기)가 같은 직원을 다시 센다. 문턱을 넘으면 보류하고, 방금 나간 줄은 그림′ 에서 비활성 직원의 줄이라 지울 후보의 비활성 회수로 떼어져 삭제 가드 안이면 지워진다 — 강제로 연 권한이 한 회차 뒤 닫힌다. 비활성 회수마저 가드를 넘으면 줄은 장부에 남고 현재상태는 비활성이다(전부 보류는 현재상태를 바꾸지 않는다 — 13 §3.5 와 같은 부류의 틈).
  - 비교 경로의 비활성 회수만 반영은 스냅샷을 남기므로 이 일이 없다. 두 경로가 다르게 동작한다.
  - 막으려면 전부 보류에서도 I 만 따로 남기거나, 전부 보류가 될 회차의 재활성 줄을 D 에서 빼야 한다. 앞의 것은 "기록 중 표시를 남긴 채 스냅샷을 저장"하는 새 상태가, 뒤의 것은 쓰기 전에 지울 판정을 알아야 하는 순서 변경이 필요하다. 둘 다 드문 겹침(장부 맞추기 + 삭제 가드 전부 보류 + 재활성)에 비해 크다. 운영 절차가 두 수를 함께 주게 한다(§3.6).
- **예외로 끝난 회차에는 보류 내역이 남지 않는다.** 결론이 없어서다.
- **기본값(30%·10명·100명)은 실제 배포의 재활성 빈도를 잰 값이 아니다.**
- **10만 명 규모와 실제 AD 로 보지 않았다.** 판정 비용은 I 의 크기에 비례하고 맵 조회뿐이라는 논증뿐이다. I 가 커지는 저장량은 어림이다(§3.1). 실제 AD 에서 서비스 계정의 읽기 권한을 잃었을 때 엔트리가 속성 없이 오는지(가정)도 확인하지 않았다 — 임베디드 LDAP 에서 속성을 지워 흉내 낸다.

## 7. 왜 다른 길을 안 갔나

| 버린 길 | 까닭 |
|---|---|
| 신호만 내기(재활성 카운터 + 경보 예) | 가장 싸다 — 현재상태 교체가 직원마다 `active` false→true 를 이미 안다. 하지만 경보가 울릴 때는 권한이 이미 돌아갔다. 권한이 열리는 구멍이 그대로다 |
| 걸리면 회차를 통째로 멈추기 | 뜻은 단순하다. 하지만 고칠 때까지 회사 전체의 입사·퇴사 반영이 멈춘다. 2026-10-20 의 방향과 어긋난다 |
| 쓸 줄 수에 대는 일반 부여 가드(비율·상한) | 실제 사고는 기준 수에 비해 작다 — 막힌 계정 2천 명이면 약 3천 줄로 15만 줄의 2% 라 지나간다. 반대로 평소의 대량 입사·개편이 걸린다 |
| 계정 상태 속성이 통째로 비었는지 직접 보기 | OpenLDAP 의 잠금 속성은 평소에도 없다. 디렉터리 종류마다 경우를 나열하게 된다. "속성이 없으면 활성" 결정과 부딪힌다 |
| 직전 비활성을 현재상태(DynamoDB)에서 읽기 | 회차마다 10만 명의 META 를 한 번 더 읽는다. 스냅샷은 이미 회차마다 읽는다 |
| 스냅샷에 비활성 직원 id 만 남기기 | 소속 줄로 남기면 기존 묶음 인코딩을 그대로 쓴다. 소속이 없는 비활성 직원은 돌아와도 줄이 생기지 않아 셀 까닭이 적다 |
| 문턱까지만 일부 반영하기 | 누구를 먼저 반영할지 근거가 없다. 결과가 회차마다 달라진다 |
| 새 상태(예: HELD) 만들기 | 실행 상태를 읽는 곳(지표·게이지·API)이 모두 바뀐다. "가드가 걸린 회차는 ABORTED" 한 규칙으로 충분하다 |
| 재활성 보류 전용 지표 | `sync.guard.aborted` 와 실행 기록의 두 내역으로 원인을 가른다 |

## 11. 확인할 것 (구현 때 사실로 정한다)

- 삭제 가드 설정에 값 검사가 있는지. 있으면 재활성 가드 설정도 같은 검사를 둔다. 없으면 두지 않는다.
- `LdapSyncEndToEndTest` 의 순서(`@Order`)에서 시나리오를 넣을 자리와, 시험 설정으로 상한을 낮출 때 다른 순서(재활성 한 명을 다루는 `@Order(9)` 등)가 그대로 통과하는지. 픽스처의 직원은 kim·park 둘이고 `@Order(9)` 뒤 kim 은 활성(`512`), park 은 `@Order(10)` 에서 `accountExpires` 로 막힌다 — 시나리오는 먼저 두 계정을 `userAccountControl` `514` 로 막아 두거나 직원을 더해 전제를 깐다.
- `force=true` 를 적은 문서 문장 가운데 온보딩·README 만 고친다. 옛 설계 문서는 그때의 기록이라 고치지 않는다.
