# userName·조직 externalId 유일성을 표지판 줄로 — 설계

- 날짜: 2026-10-14
- 슬라이드: 운영 견고성 잔여 ②-a (②-b 실패한 회차의 이력, ②-c 작은 것이 뒤따른다)
- 출발점: SCIM 쓰기 락 설계(2026-09-28) §9 의 B 안, §10 의 남은 틈. 불변 식별자 설계(2026-10-04) §3.2·§11.

## 1. 문제

SCIM 직원 `userName`(대소문자 무시)과 조직 `externalId` 의 유일성은 락 안에서 확인한다. 그런데 후보를 **최종 일관성 GSI** 로 찾는다.

- 직원은 GSI1(`USER_INDEX` + 소문자 userName)로 후보를 찾는다. 조직은 GSI3(`externalId`)로 찾는다. 후보는 본 테이블을 강하게 다시 읽어 확인한다(`IncrementalSyncUseCase.userName을_확인한다`·`externalId를_확인한다`).
  - 이 재확인은 GSI 에 잠깐 남은 옛 값 때문에 잘못 거절하는 일만 막는다.
  - **방금 저장돼 GSI 에 아직 없는 리소스**는 후보로 나오지 않아 통과한다.
- 전역 락은 쓰기를 한 줄로 세울 뿐, 앞 쓰기가 GSI 에 보이는 것까지 보장하지 않는다. A 가 커밋하고 반납하면 B 는 수십 ms 안에 락을 얻어 GSI 를 묻는다.
- **④-1 뒤로 틈이 넓어졌다.** 직원·조직 id 는 POST 마다 새 UUID 다. 그래서 같은 직원의 중복을 막는 것은 userName 확인(조직은 externalId 확인) 하나뿐이다.
  - IdP 가 POST 응답을 잃고 곧바로 재시도하면 같은 userName 의 직원이 둘 생긴다(id 는 다르다).
  - 그러면 `filter=userName eq` 와 관리 API 정확 일치가 두 줄을 돌려준다. IdP 매칭이 오류가 나거나 잘못된 쪽을 비활성화할 수 있다.
  - 조직은 멤버가 두 조직으로 갈린다.
- DynamoDB Local 은 GSI 가 곧바로 반영돼 테스트가 이 틈을 보지 못한다. 경합 끝단 테스트(`ScimWriteRaceEndToEndTest`)도 주석으로 이를 인정한다.

## 2. 결정 (사용자 확인, 2026-10-14)

| 무엇 | 고른 것 | 버린 것 |
|---|---|---|
| 방식 | **표지판 줄 + 조건부 쓰기.** 유스케이스가 락 안에서 OpenFGA 쓰기 전에 차지하고, 커밋 뒤에 옛 것을 놓는다 | TransactWriteItems 로 표지판과 META 를 함께 쓰기, "최근 이름" 기록 파티션 + GSI 검사(§8) |
| 범위 | 직원 `userName`, 조직 `externalId` | 직원 `externalId` 는 지금처럼 유일성을 보지 않는다 |
| GSI 이름 조회 | **없앤다** — 검사는 표지판 한 규칙이다 | GSI 검사와 함께 쓰기 |

## 3. 표지판 줄과 포트

### 3.1 줄

| 무엇 | PK | SK | 속성 |
|---|---|---|---|
| 직원 userName | `UNIQUE#USERNAME` | 소문자 userName(`Locale.ROOT`) | `ownerId`, `claimedAt` |
| 조직 externalId | `UNIQUE#GROUP_EXTERNAL_ID` | externalId 그대로(대소문자 구분 — 지금과 같다) | `ownerId`, `claimedAt` |

- **종류마다 파티션 하나다.** 강한 일관성 Query 로 전부 훑을 수 있어 `wipe` 가 비울 수 있다.
  - SCIM 쓰기는 전역 락으로 한 줄이라 한 파티션 쓰기 한도(초당 1000 WCU)에 닿지 않는다.
  - 10만 줄이어도 약 10MB 다.
- **인덱스 키 속성 이름(`externalId`, `GSI1PK`, `displayNameKey`)을 쓰지 않는다.** 그래서 어느 GSI 에도 실리지 않고, 테이블·GSI 정의가 바뀌지 않는다.
- **키를 만드는 규칙은 core 가 정한다.** 대소문자 무시는 SCIM userName 의 규칙(RFC 7643 `caseExact=false`)이라 도메인 몫이다. 저장소는 받은 키를 그대로 쓴다.
- **키 길이.** 포트 계약으로 키는 UTF-8 1024바이트까지다(DynamoDB 정렬키 한도). 넘는 값은 core 가 400 `invalidValue` 로 거절한다.
  - 전용 예외를 두고 라우터가 `GroupGraphTooLargeException` 처럼 바꾼다.
  - 지금은 같은 한도에 걸리는 GSI1SK 쓰기가 500 을 냈다.

### 3.2 포트(`DirectoryStateRepository`)

| 메서드 | DynamoDB | 결과 |
|---|---|---|
| `claimUnique(종류, 키, 주인, 시각)` | 조건부 PutItem — `attribute_not_exists(PK)`, `ReturnValuesOnConditionCheckFailure=ALL_OLD` | 없어서 차지하면 빈 값, 이미 있으면(주인이 나여도) 그 표지판(주인, 차지한 시각) |
| `takeOverUnique(종류, 키, 새_주인, 옛_주인, 시각)` | 조건부 PutItem — `ownerId = :옛_주인` | 넘겨받았는지(참·거짓) |
| `releaseUnique(종류, 키, 주인)` | 조건부 DeleteItem — `ownerId = :주인` | 조건 실패(이미 남의 것·없음)는 조용히 넘어간다 |
| `clearUniqueMarkers()` | 두 파티션을 강하게 Query → 묶음 삭제 | `wipe` 용 |
| `findUniqueOwners(종류)` | 그 파티션을 강하게 Query(`ownerId` 만 투영, 쪽 나눠 읽기) | 주인 아이디들. 같은 주인이 여러 번 나올 수 있다. `wipe` 가 GSI 열거에서 빠진 직원·조직을 찾는 데 쓴다 |

- 시각은 유스케이스가 넘긴다. 쓰는 시각과 비교하는 시각이 같은 시계에서 나와 가상 시간으로 시험할 수 있다.
- `findUserIdsByUserName`(GSI1 이름 조회)은 **없앤다.** `userName을_확인한다` 만 썼다.
  - `findGroupIdsByExternalId` 는 관리 API 조회가 쓰므로 남는다.
- `saveUser`·`saveGroup`·`saveGroupChange`·`deleteUser`·`deleteGroup`·`replaceWith` 는 바뀌지 않는다. TransactWriteItems 는 쓰지 않는다.

## 4. 유스케이스 흐름 (모두 락 안)

### 4.1 차지하기 — 부딪쳤을 때의 판단

직원·조직 공통 규칙 하나다.

1. `claimUnique` 가 성공하면 다음으로 간다.
2. 막혔으면 표지판의 주인을 본 테이블에서 강하게 읽는다(`findUser`·`findGroupHeader`).
   - **주인이 그 값을 지금 쥐고 있으면 409 `uniqueness` 다.** 응답을 잃은 POST 의 재시도가 여기서 막힌다. 문구는 지금과 같다.
     주인이 나여도 그렇다 — 생성에는 자기 자신이 없어, 같은 아이디로 다시 온 생성이 기존 직원·조직을 덮어쓰지 않는다(지금의 규칙).
   - **주인이 나면 차지한 것으로 본다.** 내가 전에 차지하고 놓지 못한 표지판이다(이름 변경이 실패한 뒤의 재시도 등). 차지 조건을
     `attribute_not_exists` 하나로 둔 까닭이 위 한 줄이다 — 조건에 "주인이 나" 를 넣으면 같은 아이디의 생성이 409 없이 덮어쓴다.
     내 표지판이 락 TTL 만큼 지났으면 시각을 새로 쓴다(넘겨받기와 같은 조건부 쓰기, 막히면 503) — 그대로 두면 META 를 저장하기 전에 남이 넘겨받는다.
   - **주인이 그 값을 쥐고 있지 않고 표지판이 락 TTL(`dynamodb.lock-ttl`, 30초)보다 오래됐으면 넘겨받는다.** 주인이 지워졌거나 이름을 바꿨는데 표지판을 못 놓은 경우다. 넘겨받기마저 조건에서 막히면(그 사이 남이 넘겨받았다) 처음부터 다시 판단하지 않고 503 이다.
   - **그 밖이면 503(Retry-After 2초)이다.** 주인 META 에 아직 그 값이 없고 표지판이 30초 안으로 새것인 경우다.
     - 그 주인이 락을 일찍 반납했을 수 있다 — 리스 지킴이가 갱신 주기 두 번에서 멈췄거나, 리스 확인·놓기가 실패해 새 표지판이 남은 경우다. 그때 보내던 META 쓰기가 늦게 닿을 수 있다.
     - core 의 `TemporaryFailureException` 으로 낸다. 30초가 지나면 넘겨받으므로 IdP 의 재시도가 곧 통과한다.
3. 시각은 서버마다 제 시계다. 시계 어긋남이 TTL − 2×갱신 주기(10초)보다 작다는 S15 전제를 그대로 쓴다.

결선(app-scim)이 `dynamodb.lock-ttl` 을 유스케이스에 넘긴다. core 는 저장소 설정을 모른다.

### 4.2 직원

- **생성(POST):** userName 을 새 id 로 차지한다 → OpenFGA → META 저장.
- **변경(PUT·PATCH):** 소문자 키가 바뀔 때만 새 키를 차지한다. 커밋(META 저장) 뒤에 옛 키를 놓는다.
  - `Kim` → `kim` 은 키가 같아 표지판을 건드리지 않는다.
  - 이름을 안 바꾸는 변경(비활성화 등)도 건드리지 않는다. 이미 겹친 직원도 비활성화할 수 있다는 지금의 규칙(`userName을_안_바꾸면_중복을_확인하지_않는다`)이 그대로다.
- **삭제:** `deleteUser` 가 끝난 뒤 그 직원의 userName 을 놓는다. 튜플 삭제가 일부 실패해 `deleteUser` 를 건너뛰면 META 가 남으므로 표지판도 남긴다.
- userName 이 null 이면 표지판이 없다. SCIM 핸들러가 이미 거절하지만 유스케이스도 지금처럼 그냥 지나간다.

### 4.3 조직

직원과 같은 규칙에 `externalId` 를 쓴다.

- 값이 null·빈 값이면 표지판이 없다.
- 생성(POST)은 차지한다. PUT·PATCH 로 바꾸면(`GroupChange.reidentified` 포함) 새 값을 차지하고 커밋 뒤 옛 값을 놓는다. null 로 비우면 커밋 뒤 옛 값만 놓는다.
- 삭제는 `deleteGroup` 뒤에 놓는다. 값은 락 안에서 읽은 조직 이름표에서 온다.

### 4.4 META 를 저장하지 못하고 끝나면 놓는다

- 차지한 뒤 META 를 저장하지 못하고 끝나면 차지한 것을 놓는다.
  - 오류로 끝난 경우가 여기 든다(OpenFGA 일시 장애로 503 등).
  - 생성인데 튜플 쓰기가 일부 실패해 커밋을 건너뛴 경우(`existing.isEmpty() && result.hasFailure()`)도 든다.
  - 깨끗이 끝나지 않았으면(오류·일부 실패) 주인을 한 번 강하게 읽어, 주인이 쥐고 있지 않은 값만 놓는다. 깨끗이 끝났으면 결과를 알므로 읽지 않는다.
- **리스를 잃어 일이 취소되거나, 쓰기·커밋 직전 리스 확인이 실패해 끝나면 놓지 않는다.** 남이 락을 쥐었을 수 있어 락 없이 더 쓰지 않는다 — 같은 요청의 재시도가 다른 서버에서 "주인이 나" 로 차지한 표지판을 지울 수 있다. 그 표지판은 30초 뒤 넘겨받는다(같은 직원·조직의 재시도는 "주인이 나" 로 곧바로 통과한다).
- 놓기는 조건부라 남의 것을 지우지 않는다. 놓기가 실패해도 경고만 남기고 응답은 바꾸지 않는다. 30초 뒤면 넘겨받을 수 있다.
- 그래서 503 은 락을 일찍 반납했거나 놓기가 실패해 새 표지판이 남은 경우에, 그 표지판이 30초가 될 때까지만 난다. 서버가 죽은 경우는 락이 먼저 만료돼야 남이 잡으므로 그때 표지판은 이미 오래돼 곧바로 넘겨받는다.

### 4.5 커밋 뒤 놓기는 응답을 바꾸지 않는다

- 이름 변경·삭제 뒤 옛 값을 놓다가 실패해도 요청은 성공이다.
- 그 표지판은 주인이 쥐고 있지 않은 값이라 30초 뒤에는 넘겨받는다. 그 전에 같은 값을 쓰면 503 이다.

### 4.6 이력

표지판은 조직도가 아니다. 차지·놓기·넘겨받기는 변경 이력(설계 2026-10-10)에 남기지 않는다.

## 5. `wipe` 와 다른 경로

- **SCIM `wipe`:** 순서는 `replaceWith(빈 조직도)` → 남은 대상 지우기 → **`clearUniqueMarkers()`** → 보류 목록 비우기다.
  - 표지판 비우기가 실패하면 보류 목록 비우기 실패와 같이 `FAILED` 다.
  - 남은 표지판은 주인이 없고 오래된 것이라 나중에 넘겨받으므로 해는 없다.
  - 남은 대상 지우기는 지운 튜플의 대상에 더해 **표지판의 주인** 중 `replaceWith` 가 지우지 않은 것도 다시 읽는다 — 표지판은 강한 일관성 열거라 어느 조직에도 없는 새 직원까지 잡는다. 평소에는 표지판 Query 두 번뿐이고 다시 읽기는 없다.
- **SCIM 재적재 `tuples`:** 현재상태를 바꾸지 않는다. 표지판도 그대로다.
- **LDAP:** 바뀌지 않는다. 표지판이 생기지도 읽히지도 않는다(배포 하나엔 커넥터 하나).
- **테스트용 `upsertUser`·`upsertGroup`:** 운영 호출자가 없고 지금도 유일성을 보지 않는다. 그대로 둔다.
- **기존 SCIM 데이터:** 표지판 없이 저장된 직원·조직은 보호받지 못한다. 운영 전이라 이관하지 않는다. README 에 "기존 SCIM 테이블은 비우고 다시 프로비저닝한다" 를 적는다.

## 6. 바뀌는 곳

| 모듈 | 무엇 |
|---|---|
| core | 포트에 표지판 메서드 넷(+ `findUserIdsByUserName` 없앰), 종류·키 규칙(`UniqueKind`), 차지·판단·놓기 흐름(직원·조직), 키 길이 예외, 가짜 저장소의 표지판 지도 |
| storage-dynamodb | 표지판 줄 쓰기·지우기·비우기 |
| connector-scim | 키 길이 예외 → 400 `invalidValue` |
| app-scim | 결선이 `dynamodb.lock-ttl` 을 유스케이스에 넘김, 끝단 테스트 |
| 문서 | README, 이 설계, 쓰기 락 설계 §10·불변 식별자 설계 §11 의 해결 표시 |

테이블·GSI 정의와 LDAP 경로는 바뀌지 않는다.

## 7. 이 설계가 말할 수 없는 것

- **GSI 지연 자체는 DynamoDB Local 로 재현할 수 없다.** 증명은 구조로 한다. 확인 경로에 GSI 읽기가 없다(포트에서 이름 조회를 없앴고, 판단 읽기 수를 세는 테스트가 고정한다).
- **락을 일찍 반납했거나 놓기가 실패해 새 표지판이 남으면, 그 표지판이 30초가 될 때까지 새 직원·조직의 같은 값 쓰기는 503 이다.** 같은 직원·조직의 PUT·PATCH·DELETE 재시도는 "주인이 나" 로 곧바로 통과한다. POST 재시도는 새 UUID 라 기다린다.
- **유일성은 락의 커밋 틈을 물려받는다**(2026-10-02 §10, 펜싱 없음). 멈춘 서버의 리스가 만료돼 다른 서버가 락을 얻을 때 그 서버의 표지판은 이미 TTL 보다 오래돼 넘겨받힌다 — 멈췄던 서버의 META 커밋이 그 뒤에 닿으면 같은 값이 둘이 된다. 막으려면 META 쓰기를 표지판 주인 조건으로 묶어야 하는데(§8 의 트랜잭션 안) 받아들인다. GSI 검사도 같은 틈을 통과시켰으므로 회귀는 아니다.
- **표지판 파티션은 종류마다 하나다.** SCIM 쓰기가 전역 락으로 한 줄이라는 전제 위의 설계다. 그 락을 풀어 처리량을 늘리면 이 파티션도 다시 봐야 한다.
- **직원 `externalId` 는 유일성을 보지 않고, 조직 `externalId` 는 대소문자를 구분한다.** 지금과 같다.
- **표지판 없이 저장된 기존 데이터는 보호받지 못한다**(§5).
- **AWS 실측은 없다.** 조건부 쓰기의 동작은 DynamoDB Local 로 확인한다.

## 8. 왜 다른 길을 안 갔나

- **TransactWriteItems 로 표지판과 META 를 함께 쓰기(AWS 의 유일성 예제).**
  - 원자적이지만 META 를 쓰는 때, 곧 OpenFGA 쓰기 **뒤**에 충돌을 안다. 이미 쓴 튜플을 되돌려야 한다.
  - 트랜잭션 취소 예외(`TransactionCanceledException`)의 이유별 분류(조건 실패·충돌·스로틀)를 새로 만들어야 한다.
  - 멤버가 많은 조직 변경은 어차피 트랜잭션 한도(100개) 밖이라 META 와 표지판만 묶게 된다.
- **"최근 이름" 기록 파티션(TTL) + 지금의 GSI 검사.** GSI 가 늦는 창만 메우지만 검사 규칙이 둘로 갈린다. 조건부 쓰기가 아니라서 락이 겹치는 틈은 막지 못한다.
- **시각 없이 "주인이 쥐고 있지 않으면 넘겨받는다".** 더 단순하다. 그러나 락을 일찍 반납한 쓰기의 늦게 닿는 META 와 부딪친다. 30초 기준이 그 경우를 막는다 — 리스가 만료된 뒤의 늦은 커밋(커밋 틈)은 막지 못한다(§7).
- **표지판을 값마다 다른 PK(`USERNAME#<값>`)에 두기.** 쓰기는 흩어지지만 `wipe` 가 훑을 길이 없다(GSI 를 하나 더 써야 한다). 쓰기는 이미 전역 락으로 한 줄이라 흩을 이득이 없다.
