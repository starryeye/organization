# 규모 E2E 테스트 시나리오 — LDAP / SCIM

**작성일:** 2026-09-06
**목적:** 약 5,000명 규모의 실제 조직도로 두 커넥터를 각각 독립 검증한다.
**관련 설계:** `docs/superpowers/specs/2026-08-14-organization-sync-design.md`,
`docs/superpowers/specs/2026-09-01-scim-concurrency-design.md`

---

## 0. 이 문서가 전제하는 것

**로컬 E2E 의 목표는 운영 처리량 측정이 아니다.** 코드에 박힌 임계값(페이징, 배치, 청크)을
넘겨서 **구조적 동작**을 검증하는 것이다. 처리량은 건당 비용을 재서 외삽한다.

**시간에 의존하는 결함은 데이터가 아니라 설정으로 재현한다.** 로컬 OpenFGA 는 응답이
밀리초라 데이터를 아무리 키워도 락 TTL 근처에 못 간다(§4.3).

## 1. 공통 — 검증 하네스

**모든 시나리오가 매 단계 끝에 같은 검증을 돈다.** 이것이 없으면 "모든 케이스" 를 감당할 수 없다.

구현: `SyncVerifier` (core testFixtures). 포트(`DirectoryStateRepository`,
`RelationTupleChecker`)에만 의존하므로 LDAP·SCIM 양쪽 E2E 가 **같은 것**을 쓴다 — 두 커넥터를
서로 다른 잣대로 재면 "같은 조직도로 같은 결과에 도달하는가" 를 물을 수 없다.

```
검증(기대조직도):
  ① DynamoDB   state.loadAll() 이 기대조직도와 같은가
  ② OpenFGA 양성   기대 튜플이 전부 Check = true 인가
  ③ OpenFGA 음성   후보 − 기대 튜플이 전부 Check = false 인가
  ④ 롤업        각 직원의 조상 체인이 전부 member = true 이고
                형제 가지는 false 인가
```

### ③ 이 가장 중요하다

**"있어야 할 것이 있다" 만 보면 잘못 남은 튜플을 영원히 못 잡는다.** 이 프로젝트가 처음부터
위험하다고 본 것(퇴사자 권한 생존)이 정확히 그 모양이다.

음성 검증의 후보 집합은 `TupleMapper.candidateTuples(기대조직도)` 로 뽑는다 — `active`·순환
필터를 적용하기 전의 멤버십 전체다. 비활성 직원의 잘못 남은 튜플이 여기 들어온다.

> **한계를 알고 쓴다.** 후보가 멤버십에서 나오므로, **멤버십이 아예 사라진 튜플**은 이
> 검증으로도 안 잡힌다(설계 §5.4). 그것을 잡으려면 열거가 필요한데 금지돼 있다.
> 시나리오 L12·S17 이 그 한계 자체를 못박는다.
>
> `SyncVerifierTest` 에 이 사각지대를 통과 케이스로 고정해 뒀다 — 하네스가 잡는 것과
> 못 잡는 것의 경계가 코드에 남아 있어야, 나중에 "왜 이건 안 잡혔지" 를 다시 묻지 않는다.

### ④ 롤업 검증이 별도인 이유

인가 모델은 `member(P) = direct_member(P) ∪ member(자식들)` 이다 — **멤버십은 위로만 흐른다.**
②③ 은 `direct_member`/`child` 튜플의 존재만 보므로, 롤업이 실제로 성립하는지는 `member`
관계로 따로 물어야 한다.

```
L5 팀 직속 김씨   member(L5) = member(L4) = ... = member(L1) = true
L2 부문 직속 박씨 member(L2) = member(L1) = true
                  member(L3) = member(L5) = false      ← 아래로 안 샘
```

---

### 실측 비용

실제 컨테이너(OpenFGA + DynamoDB Local) 위에서 잰 한 회차 비용이다.

| | 싱크 | 하네스 검증 |
|---|---|---|
| LDAP 전체 동기화 | **7.2초** | 2.7초 |
| SCIM 최초 싱크 (요청 5,376건) | **41.6초** (건당 7.7ms) | 1.9초 |

**그래서 시나리오는 최초 싱크를 한 번만 만들고 그 위에 순차로 쌓는다.** 시나리오마다 처음부터
채우면 SCIM 쪽만 19 × 42초 = 13분이다. 이어 붙이면 최초 42초 + 검증 2초 × 19 ≈ 1분 20초다.
실제 운영도 최초 싱크는 한 번뿐이므로, 이어 붙이는 쪽이 더 실제에 가깝기도 하다.

`ScimScaleSyncCostTest` / `LdapScaleSyncCostTest` 가 이 수치를 계속 재고, 동시에 두 커넥터가
**같은 조직도에서 같은 검증을 통과하는지**를 확인한다.

## 2. 픽스처 — 5,024명 / 352개 조직

**부문마다 깊이가 다르다.** 균일 깊이면 롤업 체인이 전부 같은 길이라 짧은 체인이 제대로
끝나는지를 검증하지 못한다.

```
L1 회사                      1개   직속    8명
L2 부문                      5개   직속 각 10명 =    50

A. 개발부문      L6까지
   L3 본부                   4개   직속 각  8명 =    32
   L4 실                    12개   직속 각  6명 =    72
   L5 팀                    40개   직속 각 12명 =   480
   L6 파트                  80개   직속 각  8명 =   640

B. 제조부문      L6까지, 넓음
   L3 본부                   3개   직속 각  5명 =    15
   L4 실                     9개   직속 각  5명 =    45
   L5 팀                    30개   직속 각 20명 =   600
   L6 파트                  90개   직속 각 18명 = 1,620

C. 사업부문      L5까지
   L3 본부                   3개   직속 각  8명 =    24
   L4 실                    10개   직속 각  7명 =    70
   L5 팀                    35개   직속 각 14명 =   490

D. 신사업부문    L4까지
   L3 본부                   2개   직속 각  6명 =    12
   L4 팀                    12개   직속 각 18명 =   216

E. 경영지원부문  L3까지
   L3 팀                    10개   직속 각 15명 =   150

전사 공통 TF     L2 직속      1개   직속    500명
빈 조직          L2 직속      5개   직속      0명
                ────                        ─────
조직 352개                                  5,024명
```

> 이 표의 숫자는 손으로 센 것이 아니라 `OrgChartFixture` 가 실제로 만드는 값이다.
> `OrgChartFixtureTest` 가 형상을, `LdifRendererTest`/`ScimRequestRendererTest` 가
> 그 조직도의 왕복을 검증한다. 표와 코드가 갈라지면 테스트가 먼저 깨진다.

**모든 중간 조직이 직속 직원과 하위 조직을 동시에 갖는다.** L4 실에 직속 6명 + 하위 팀 3개가
같이 있으면 그 조직의 `member` 에 `direct_member` 와 자식 롤업이 둘 다 기여한다 — 한쪽만
있는 조직에선 나오지 않는 경우다.

**이상치**

| | 노리는 것 |
|---|---|
| 전사 공통 TF 500명 직속 | BatchCheck 10청크 (상한 50) |
| 겸직 166명 — 깊이가 다른 두 부문에 걸침 | 다중 경로, 후보 확대 |
| 빈 조직 5개 (L2 직속) | 빈 델타 경로 |

**튜플: `direct_member` 5,190 + `child` 351 = 5,541**

`direct_member` 는 직원 5,024 + 겸직 166. `child` 는 조직 352 − 루트 1.

| 임계값 | 값 | 이 픽스처 |

## 3. LDAP 시나리오

**구현 상태:** L1~L16 구현 완료. L17 은 단위 테스트 중복이라 쓰지 않기로 했다(아래 참조).

| 시나리오 | 테스트 클래스 |
|---|---|
| L1~L11, L16 | `LdapScaleScenarioTest` — 하나의 컨텍스트에서 순차로 이어진다 |
| L12, L13 | `LdapDeletionGuardScaleTest` — 삭제 가드 경계 양쪽 |
| L14 | `LdapPagingScaleTest` — 서버측 상한 + 페이징 해제 |
| L15 | `LdapInterruptedSyncScaleTest` — 상태 저장 직전 중단과 수렴 |

**모델:** pull 기반, 하루 1회 전체 재계산. 기준선은 **스냅샷**(우리가 썼다고 기록한 장부),
목표는 LDAP 읽기 결과다.

**시나리오 형식:** LDIF 를 바꾸고 → `POST /admin/sync/full` → §1 검증 하네스.

각 시나리오는 **직전 시나리오의 결과 위에서 이어진다** — 실제 운영이 그렇기 때문이다.

### L1. 최초 전체 동기화 (cold)

빈 상태에서 5,541 튜플을 만든다.

| 검증 | |
|---|---|
| DynamoDB | 직원 5,024 + 조직 352 + 멤버십 전부 |
| OpenFGA | 5,541 튜플 전부, 그 외 없음 |
| 스냅샷 | `SUCCEEDED`, 튜플 5,541 |
| 롤업 | 깊이 3·4·5·6 각 대표 직원의 조상 체인 |

**측정:** LDAP 읽기(11 페이지) / OpenFGA 쓰기(56 배치) / 스냅샷 저장(222 배치) / 상태 저장
각각의 소요. 어디가 지배하는지가 이 시나리오의 답이다.

### L2. 무변경 재동기화 — 1년에 364번 도는 정상 케이스

LDIF 를 그대로 두고 다시 돌린다.

| 검증 | |
|---|---|
| **OpenFGA 호출 0회** | `"변경 없음. OpenFGA 를 호출하지 않는다"` 로그 |
| 상태 | `state.replaceWith` 는 **호출된다** (빈 델타 경로도 부른다) |
| 이력 | `SUCCEEDED` + 메시지 `"변경 없음"` — 별도 상태값이 아니다 |

**측정:** 기준선(스냅샷 5,541) 읽기 + LDAP 전체 읽기 비용. **변경이 없어도 이만큼은 든다.**

### L3. 직원 추가

L5 팀 하나에 3명 추가.

| 검증 | |
|---|---|
| DynamoDB | 직원 3명 신규, 그 팀 멤버십 +3 |
| OpenFGA | `dm(신규, L5팀)` 3개만 추가. **다른 튜플 변화 없음** |
| 롤업 | 신규 3명이 L5→L4→L3→L2→L1 전부 `member` |
| 델타 | `toWrite` 3건, `toDelete` 0건 |

**핵심:** 델타가 정확히 3건인가. 전체 재계산인데도 변경분만 쓰는지가 이 설계의 전제다.

### L4. 직원 삭제 (엔트리 제거)

L6 파트에서 2명 제거.

| 검증 | |
|---|---|
| DynamoDB | 직원 2명 사라짐, 그 파트 멤버십 −2 |
| OpenFGA | 해당 `dm` 2개 삭제. **음성 검증이 이걸 잡는다** |
| 롤업 | 삭제된 직원은 어느 조직에도 `member` 아님 |

### L5. 직원 속성 변경 — 튜플은 안 바뀌어야 한다

`displayName`, `mail` 만 변경.

| 검증 | |
|---|---|
| DynamoDB | 속성 반영 |
| **OpenFGA** | **델타 0건. 호출 없음** |

**튜플 식별자는 직원 아이디와 조직코드뿐**이라는 설계를 못박는다. 이름이 바뀌었다고 튜플이
다시 쓰이면 안 된다.

### L6. 직원 소속 이동 — 조직 A → B

L5 팀에서 다른 부문의 L6 파트로 1명 이동.

| 검증 | |
|---|---|
| DynamoDB | 옛 조직 멤버십 −1, 새 조직 +1 |
| OpenFGA | `dm(김, 옛팀)` 삭제 + `dm(김, 새파트)` 추가 |
| **롤업** | **옛 조상 체인 전부 `member = false`**, 새 조상 체인 전부 `true` |

**깊이가 다른 부문으로 옮긴다** — 체인 길이가 5홉에서 6홉으로 바뀌는지 본다.

### L7. 겸직 추가·해제

한 직원을 두 번째 조직에도 넣었다가(다른 부문, 다른 깊이) 뺀다.

| 검증 | |
|---|---|
| 추가 시 | 두 경로 모두 `member = true`. 튜플 2개 |
| 해제 시 | 한쪽만 사라지고 **다른 쪽은 유지** |

**해제할 때 남은 쪽이 같이 지워지지 않는지**가 요점이다.

### L8. 조직 추가

L4 실 아래에 L5 팀 신설 + 직원 5명.

| 검증 | |
|---|---|
| DynamoDB | 조직 1개, 직원 5명 |
| OpenFGA | `child(신규팀, L4실)` 1개 + `dm` 5개 |
| 롤업 | 신규 팀 직원이 L4→L3→L2→L1 까지 |

### L9. 조직 이동 — 부모 변경

L5 팀 하나를 다른 L4 실 아래로 옮긴다. **직원은 그대로.**

| 검증 | |
|---|---|
| OpenFGA | `child(팀, 옛실)` 삭제 + `child(팀, 새실)` 추가. **`dm` 은 변화 없음** |
| **롤업** | 그 팀 직원 전원이 **옛 조상 체인에서 `false`**, 새 조상 체인에서 `true` |

**직원을 하나도 안 건드렸는데 그 직원들의 권한 범위가 통째로 바뀐다.** `child` 엣지 하나가
얼마나 큰 영향을 갖는지 확인하는 자리다.

### L10. 중간 조직 삭제 — 계층이 끊긴다

L4 실을 삭제한다. 그 아래 L5 팀들은 LDAP 에 남아 있다.

groupOfNames 에서 부모가 사라지면 그 팀들은 아무에게도 참조되지 않아 **루트가 된다.**

| 검증 | |
|---|---|
| OpenFGA | `child(팀들, 삭제된실)` 전부 삭제. 팀의 `dm` 은 유지 |
| **롤업** | 그 팀 직원들이 **L5 는 `member`, L3·L2·L1 은 `false`** |
| 상태 | 삭제된 실의 직속 직원 처리 확인 |

**계층이 끊겨 고아가 된 조직을 시스템이 어떻게 다루는지** — 이 픽스처의 깊이 다양성이
여기서 값을 한다.

### L11. 조직명 변경 — 코드는 유지

`description`(조직명)만 바꾼다.

| 검증 | |
|---|---|
| DynamoDB | `displayName` 반영 |
| **OpenFGA** | **델타 0건** — 조직코드가 안 바뀌었으므로 |

### L12. 삭제 가드 발동

LDAP 필터를 망가뜨려 70%만 반환하게 한다.

```
삭제 대상 1,662 / 기준선 5,541 = 29.996%  → 통과   (ratio <= 0.3)
삭제 대상 1,663 / 기준선 5,541 = 30.013%  → ABORTED
```

| 검증 | |
|---|---|
| 이력 | `ABORTED`, 사유 메시지 |
| **OpenFGA** | **아무것도 안 지워짐** |
| **DynamoDB** | **상태도 안 바뀜** |
| 다음 회차 | 필터 복구 후 정상 동기화되는가 |

**경계값을 둘 다 돌린다.** 가드는 `ratio <= thresholdRatio` 로 판정하므로 정확히 30%는
통과해야 하는데, 기준선 5,541 에서 정확히 30%가 되는 정수 삭제 건수는 없다. 그래서 30%를
사이에 두고 붙어 있는 두 값으로 경계를 집는다 — 한 건 차이로 판정이 갈리는 것까지 본다.

### L13. 강제 실행으로 가드 우회

L12 상황에서 `force=true`.

| 검증 | 가드를 지나 실제로 삭제되는가. 이력에 `FORCED` 트리거 |

### L14. LDAP 페이징 — 서버측 상한

LDAP 서버에 엔트리 상한 1,000 을 걸고 `page-size: 500` 으로 읽는다.

| 검증 | |
|---|---|
| 정상 | 5,024명 전부 읽힘 (11 페이지) |
| **`page-size: 0`** | `SizeLimitExceededException` 으로 실패. **조용히 잘리지 않음** |

두 번째가 핵심이다 — 잘린 목록이 대량 퇴사처럼 보여 실제 소속을 지우는 것을 막는 방어선이다.

### L15. 동기화 중단 후 다음 회차 복구

`state.replaceWith` 직전에 프로세스를 죽인다.

| 검증 | |
|---|---|
| 죽은 직후 | OpenFGA 는 반영됨, 상태는 낡음 |
| 다음 회차 | 델타는 비지만 **빈 델타 경로가 상태를 다시 씀** → 수렴 |

**설계 §1.1 의 "재시도가 수렴 기제" 전제를 5,000 규모에서 실증한다.**

### L16. 순환 참조 유입

L4 실을 그 손자 L6 파트의 하위로 만든다 (A→B→C→A).

| 검증 | |
|---|---|
| 이력 | `SUCCEEDED` — 동기화가 완주한다 |
| 로그 | `"순환"` 경고 |
| OpenFGA | 순환을 닫는 간선 **하나만** 빠지고 나머지는 유지 |
| 롤업 | 순환 밖 직원들의 권한은 그대로 |

### L17. 정규화 충돌 — 같은 코드로 뭉개지는 두 조직

**규모 E2E 로 쓰지 않기로 했다.** 세 검증이 모두 단위 테스트에 이미 있다 —
`GroupOfNamesDuplicateIdTest`(직원 아이디 충돌: 하나만 생존, 경고에 두 dn, 생존한 쪽이
경고가 "유지" 라고 말한 dn)와 `DitStrategyDuplicateCodeTest`(조직코드 충돌).

충돌 판정은 `DuplicateIdGuard` 한 곳에서 두 엔트리만 보고 내려지므로 **디렉터리 크기와
무관하다.** 5,000명 판을 다시 깔아도 새로 얻는 정보가 없고, 통과하는 E2E 한 건이 늘면
"이것도 검증하고 있다" 는 착시만 커진다.

**다시 열어야 할 때:** 충돌 판정이 전역 정보(예: 전체 엔트리를 훑어 정하는 우선순위)에
의존하도록 바뀌면 규모가 변수가 된다. 그때 이 자리로 돌아온다.

## 4. SCIM 시나리오

**모델:** push 기반, 증분. 전역 락이 쓰기를 직렬화하고, 기준선은 **OpenFGA BatchCheck** 다.

**시나리오 형식:** SCIM 요청을 보내고 → 응답 검증 → §1 검증 하네스.

### 4.1 최초 적재

#### S1. 대량 프로비저닝 — 조직 먼저

조직 352개 → 직원 5,024명 순으로 POST.

| 검증 | |
|---|---|
| 응답 | 전부 201 |
| DynamoDB·OpenFGA | 최종 상태가 픽스처와 일치 |
| **늦게 온 직원** | 조직이 먼저 참조한 직원의 튜플이 **직원 도착 시 만들어지는가** |

**`TupleMapper` 가 "스냅샷에 없어 건너뜁니다" 로 미뤄 둔 것을 나중에 잡는 경로**를 5,000 규모로
탄다.

#### S2. 대량 프로비저닝 — 직원 먼저

순서를 뒤집는다. 직원 5,024명 → 조직 352개. `ScimRequestRenderer.최초싱크` 가 이 순서다.

| 검증 | 최종 상태가 **S1 과 동일** 한가 |

**순서가 결과를 바꾸면 안 된다.** 두 순서 중 하나만 테스트하면 그걸 못 본다.

#### S3. 대량 적재 중 락 경합

S1 을 돌리면서 다른 인스턴스가 동시에 쓰기를 시도한다.

| 검증 | |
|---|---|
| 응답 | 3초 안에 못 잡으면 **503** (500 아님) |
| `scim.lock.wait` | p99 기록 |
| `scim.lock.contended` | 증가 |
| 최종 상태 | 경합에도 정합 |

**측정:** 건당 락 보유 시간. 10만 건 외삽의 근거가 된다.

### 4.2 직원 변경

#### S4. 직원 추가 후 조직 편입

`POST /Users` → `PATCH /Groups add members`.

| 검증 | |
|---|---|
| POST 직후 | 직원 레코드만. **튜플 없음** (아직 어느 조직에도 없음) |
| PATCH 후 | `dm` 1개 + 조상 체인 롤업 |

#### S5. 비활성화 — 멤버십은 남고 권한만 사라진다

`PUT /Users/kim {active: false}`.

| 검증 | |
|---|---|
| **DynamoDB** | **멤버십 유지** — 조직 멤버 목록에 그대로 |
| **OpenFGA** | 그 직원의 `dm` **전부** 삭제 (겸직이면 둘 다) |
| 롤업 | 모든 조상에서 `member = false` |

**겸직 직원으로 돌린다** — 소속이 여럿일 때 전부 지워지는지가 요점이다.

#### S6. 재활성화 — 권한 복원

`PUT /Users/kim {active: true}`.

| 검증 | |
|---|---|
| OpenFGA | 소속 조직 전부에 `dm` 복원 |
| 롤업 | 조상 체인 전부 복구 |

**S5 에서 멤버십을 안 지웠기 때문에 복원이 가능하다** — 이 두 시나리오는 짝이다.

#### S7. 직원 삭제

`DELETE /Users/kim` (겸직 직원).

| 검증 | |
|---|---|
| DynamoDB | 직원 레코드 삭제 + **모든 조직 멤버 목록에서 제거** |
| OpenFGA | 모든 `dm` 삭제 |
| 음성 검증 | 잔여 튜플 없음 |

#### S8. 직원 속성만 변경

`PUT /Users/kim` 에서 `displayName` 만 다르게.

| 검증 | **OpenFGA 델타 0건** |

#### S9. userName 중복 거부

이미 있는 `userName` 으로 다른 `id` 를 POST.

| 검증 | 409 `uniqueness`. **상태·OpenFGA 변화 없음** |

### 4.3 조직 변경

#### S10. 조직 멤버 전체 교체 (PUT)

L5 팀의 멤버 12명 중 4명 빼고 3명 새로 넣는다.

| 검증 | |
|---|---|
| DynamoDB | 최종 멤버 11명 |
| OpenFGA | `dm` 4개 삭제 + 3개 추가. **나머지 8개는 안 건드림** |
| 델타 | 정확히 7건 |

**요청에 "빠진 4명" 이 안 적혀 있다** — 이전 멤버 목록을 읽어 계산하는 경로다(설계 §5.5).

#### S11. PATCH — add / remove / replace

세 연산이 서로 다르게 동작하므로 각각 본다.

| 연산 | 기대 |
|---|---|
| `add members[kim]` | 기존 멤버 유지 + kim 추가. 튜플 1개 증가 |
| `remove members[value eq "kim"]` | **필터가 있으면 kim 만** 제거. 튜플 1개 감소 |
| `remove` (필터 없음) | **멤버 전체 제거** — 그 조직의 `dm` 이 전부 사라진다 |
| `replace` | 목록 통째 교체 |

**필터 없는 `remove` 가 전체 삭제라는 것**을 명시적으로 확인한다. 12명짜리 팀에 걸면
튜플 12개가 한 번에 사라진다.

> `members` 필터는 `remove` 에만 지원된다 — `add`/`replace` 에 필터를 주면 거부되는지도 본다.

#### S12. 비활성 직원을 조직에 추가

`active: false` 인 직원을 조직 멤버로 넣는다.

| 검증 | |
|---|---|
| **DynamoDB** | **멤버십은 생김** |
| **OpenFGA** | **튜플은 안 생김** |

**"멤버지만 권한 없음" 상태를 정확히 표현하는지.** 이 상태가 §5.1 후보 집합의 존재 이유다.

#### S13. 조직 계층 변경

L5 팀을 다른 L4 실의 멤버로 옮긴다 (부모 쪽 PATCH 두 번: 옛 부모에서 remove, 새 부모에 add).

| 검증 | |
|---|---|
| OpenFGA | `child` 엣지 이동 |
| **롤업** | 그 팀 직원 전원의 권한 범위가 **통째로 바뀜** |
| `dm` | 변화 없음 |

#### S14. 조직 삭제

L5 팀 삭제 (직원 12명 소속, 상위 조직 있음).

| 검증 | |
|---|---|
| OpenFGA | 그 팀의 `dm` 12개 + 상위로의 `child` 1개 삭제 |
| 직원 레코드 | **유지** — 조직이 없어진 것이지 사람이 나간 게 아님 |
| 롤업 | 그 직원들이 어느 조직에도 `member` 아님 |

#### S15. 대형 조직 PUT — 500명

전사 공통 TF 의 멤버를 500명 → 480명으로 교체.

| 검증 | |
|---|---|
| 정합성 | 20명 삭제, 나머지 유지 |
| **측정** | **BatchCheck 10청크의 순차 왕복 시간, 락 보유 시간** |

**락을 쥔 채 BatchCheck 를 도는 구간이 얼마나 긴지** 재는 자리다. §4.3 과 짝이다.

#### S16. 순환 조직 참조

L4 실을 그 손자의 멤버로 넣는다.

| 검증 | |
|---|---|
| 응답 | 성공 |
| 로그 | 순환 경고 |
| OpenFGA | 순환을 닫는 간선만 빠짐 |

### 4.4 복구·한계

#### S17. 멤버십 없는 고아 튜플 — 잡히지 않음을 못박는다

OpenFGA 에 `dm(ghost, DEV001)` 을 직접 심는다. DynamoDB 에 `ghost` 는 없다.

| 검증 | |
|---|---|
| 어떤 SCIM 쓰기를 해도 | **그대로 남는다** |
| 아카이빙 후에도 | **그대로 남는다** |
| `mode=tuples` 재적재 후 | **사라진다** |

**설계 §5.4 의 한계를 명시적으로 고정한다.** 이 단언이 `false` 가 되면 한계가 해소된 것이니
문서를 고쳐야 한다.

#### S18. 재적재 `mode=tuples`

5,541 튜플 전체를 재적재한다.

| 검증 | |
|---|---|
| 소요 | 몇 분. **하트비트가 리스를 유지하는가** |
| 그동안 | SCIM 쓰기가 **503** |
| 완료 후 | 상태와 OpenFGA 완전 일치, 쓰기 재개 |

**중간에 인스턴스를 죽여** 리스 상실 → `FAILED` 기록 → 재실행 복구까지 확인한다.

#### S19. 아카이빙 at 5,000

일일 아카이빙을 돌린다.

| 검증 | |
|---|---|
| 스냅샷 | **관찰한 실제 튜플**이 저장되는가 (의도한 것이 아니라) |
| S17 의 고아 튜플 | 후보에 없으므로 **스냅샷에도 없음** |
| **측정** | `loadAll` + BatchCheck 111청크 소요 |

어긋남을 심어두고(예: 튜플 하나 직접 삭제) **어긋남 로그가 남는지**도 본다.

## 5. 실행 구성

### 5.1 스위트 분리

| | 내용 | 예상 |
|---|---|---|
| **빠른** | L2~L17, S4~S17 (증분 변경) | 각 수초 |
| **느린** | L1, S1, S2, S18, S19 (전량) | LDAP 30~60초 / SCIM **2~5분** |

SCIM 대량(S1·S2)은 5,347건이 전부 락 직렬이라 길다. 일반 스위트에서는 **200건 부분집합**으로
순서·정합성만 보고, 전량은 느린 스위트로 뺀다.

### 5.2 시간 의존 결함 — 설정으로 재현

**데이터를 키워도 로컬에선 안 난다.** 로컬 OpenFGA 응답이 밀리초라 30초 TTL 근처에 못 간다.

| | 재현 방법 |
|---|---|
| **쓰기 경로 리스 만료** | `dynamodb.lock-ttl: 200ms` 프로파일 |
| 재적재 리스 상실 | 같은 프로파일 + 하트비트 주기를 TTL 보다 길게 |

> **여기서 확인할 구멍:** 쓰기 경로는 락을 쥔 채 BatchCheck 를 도는데 **그 사이 리스를
> 갱신하지 않는다.** `renew()` 는 `writer.apply` 직전 한 번뿐이다. 재적재는 하트비트가 있는데
> 쓰기 경로엔 없다. 대형 조직 PUT 이 TTL 을 넘기면 몇 번을 재시도해도 같은 지점에서 실패한다.

### 5.3 픽스처 생성

| | |
|---|---|
| **LDAP** | LDIF 생성기. UnboundID 인메모리가 5,000 엔트리를 감당하는지 먼저 확인 — 안 되면 docker-compose 의 OpenLDAP |
| **SCIM** | 요청 시퀀스 생성기. 조직 먼저 / 직원 먼저 두 순서 모두 |

두 앱이 서로 다른 테이블·store 를 쓰므로 독립 실행된다.

### 5.4 교차 검증 — 선택

같은 조직도를 양쪽에 넣고 **결과 튜플 집합이 동일한지** 대조한다. 두 커넥터가 같은 진실에
도달하는지 보는 것이며, 어느 한쪽의 매핑 버그를 드러낸다.

## 6. 측정 항목

시나리오마다 아래를 기록해야 의미가 있다.

```
OpenFGA 왕복 수 / 총 시간
DynamoDB 읽기·쓰기 건수
락 보유 시간, scim.lock.wait / contended / lease_lost
scim.drift.detected
응답 p50 / p99 / 최대
```

**특히 `scim.drift.detected`** — 이 값이 계속 0 이면 Check 기준선이 값을 못 하고 있다는
증거이고, 걷어낼 근거가 된다(설계 §5.6).

## 7. 이 시나리오로도 못 보는 것

| | 왜 |
|---|---|
| **운영 처리량** | 로컬 지연은 운영과 무관. 건당 비용을 재서 외삽할 뿐 |
| **멤버십 없는 고아 튜플의 탐지** | 열거 금지. S17 이 그 한계를 고정할 뿐 해소하지 않는다 |
| **DynamoDB 스로틀링 거동** | 로컬 DynamoDB 는 용량 제한이 없다 |
| **실제 IdP 의 재시도 정책** | Okta·Entra 가 503·409 를 실제로 어떻게 다루는지는 실환경 확인 필요 |
