# 규모 E2E 테스트 시나리오 — LDAP / SCIM

**작성일:** 2026-09-06
**목적:** 약 5,000명 규모의 실제 조직도로 두 커넥터를 각각 독립 검증한다.
**관련 설계:** `docs/superpowers/specs/2026-08-14-organization-sync-design.md`,
`docs/superpowers/specs/2026-09-01-scim-concurrency-design.md`

---

## 0. 이 문서가 전제하는 것

**로컬 E2E 의 목표는 운영 처리량 측정이 아니다.** 코드에 박힌 임계값(페이징, 배치, 청크)을
넘겨서 **구조적 동작**을 검증하는 것이다. 처리량은 건당 비용을 재서 외삽한다.

**시간에 의존하는 결함은 데이터가 아니라 설정으로 재현한다.** 로컬 OpenFGA 는 응답이
밀리초라 데이터를 아무리 키워도 락 TTL 근처에 못 간다(§4.3).

## 1. 공통 — 검증 하네스

**모든 시나리오가 매 단계 끝에 같은 검증을 돈다.** 이것이 없으면 "모든 케이스" 를 감당할 수 없다.

구현: `SyncVerifier` (core testFixtures). 포트(`DirectoryStateRepository`,
`RelationTupleChecker`)에만 의존하므로 LDAP·SCIM 양쪽 E2E 가 **같은 것**을 쓴다 — 두 커넥터를
서로 다른 잣대로 재면 "같은 조직도로 같은 결과에 도달하는가" 를 물을 수 없다.

```
검증(기대조직도):
  ① DynamoDB   state.loadAll() 이 기대조직도와 같은가
  ② OpenFGA 양성   기대 튜플이 전부 Check = true 인가
  ③ OpenFGA 음성   후보 − 기대 튜플이 전부 Check = false 인가
  ④ 롤업        각 직원의 조상 체인이 전부 member = true 이고
                형제 가지는 false 인가
```

### ③ 이 가장 중요하다

**"있어야 할 것이 있다" 만 보면 잘못 남은 튜플을 영원히 못 잡는다.** 이 프로젝트가 처음부터
위험하다고 본 것(퇴사자 권한 생존)이 정확히 그 모양이다.

음성 검증의 후보 집합은 `TupleMapper.candidateTuples(기대조직도)` 로 뽑는다 — `active`·순환
필터를 적용하기 전의 멤버십 전체다. 비활성 직원의 잘못 남은 튜플이 여기 들어온다.

> **한계를 알고 쓴다.** 후보가 멤버십에서 나오므로, **멤버십이 아예 사라진 튜플**은 이
> 검증으로도 안 잡힌다(설계 §5.4). 그것을 잡으려면 열거가 필요한데 금지돼 있다.
> 시나리오 L12·S17 이 그 한계 자체를 못박는다.
>
> `SyncVerifierTest` 에 이 사각지대를 통과 케이스로 고정해 뒀다 — 하네스가 잡는 것과
> 못 잡는 것의 경계가 코드에 남아 있어야, 나중에 "왜 이건 안 잡혔지" 를 다시 묻지 않는다.

### ④ 롤업 검증이 별도인 이유

인가 모델은 `member(P) = direct_member(P) ∪ member(자식들)` 이다 — **멤버십은 위로만 흐른다.**
②③ 은 `direct_member`/`child` 튜플의 존재만 보므로, 롤업이 실제로 성립하는지는 `member`
관계로 따로 물어야 한다.

```
L5 팀 직속 김씨   member(L5) = member(L4) = ... = member(L1) = true
L2 부문 직속 박씨 member(L2) = member(L1) = true
                  member(L3) = member(L5) = false      ← 아래로 안 샘
```

### 실측 비용

실제 컨테이너(OpenFGA + DynamoDB Local) 위에서 잰 한 회차 비용이다.

| | 싱크 | 하네스 검증 |
|---|---|---|
| LDAP 전체 동기화 | **7.3초** | 3.1초 |
| SCIM 최초 싱크 — 직원 먼저 (6,476건) | **47.9초** (건당 7.4ms) | 1.8초 |
| SCIM 최초 싱크 — **조직 먼저** (S1, 6,476건) | **57.9초** (건당 8.9ms) | — |

> 2026-09-10 갱신. 직원 6,124명·조직 352개 픽스처, `docs/superpowers/specs/2026-09-10-single-user-snapshot-design.md`
> 적용 후 값이다. 이전 값(직원 먼저 46.5초, 조직 먼저 835.4초)은 아래 절에 그대로 남겨
> 뒀다 — 그 절이 그 값으로 진단을 설명하기 때문이다.

#### 같은 데이터인데 순서만 바꾸면 18배였다 — 고쳤다 (2026-09-10)

**순서가 느린 게 아니라 조직 크기가 느렸다.**

`IncrementalSyncUseCase` 는 직원 하나가 바뀌면 델타를 내려고 before/after 스냅샷을 만들었고,
`snapshotOf` 는 그 직원이 속한 조직의 <b>멤버 유저를 전부 읽었다</b> — `TupleMapper` 가 각
멤버의 `active` 를 알아야 그 멤버의 튜플을 낼지 판정하기 때문이다. 그래서 **직원 한 명을
바꾸는 비용이 그가 속한 조직의 크기에 비례했다.** 1,600명 조직이면 한 명당 3,200번
(before + after).

- **직원 먼저** — 직원이 도착할 때는 아직 아무 조직에도 안 속해 스냅샷이 비어 있었다. 조직이
  나중에 한 번씩 도착하며 자기 멤버를 읽으므로 전체가 멤버십 수에 선형이었다.
- **조직 먼저** — 제1공장이 먼저 자리를 잡고, 그 1,600명이 하나씩 도착하며 매번 1,600명을
  두 번 읽었다. 1,600 × 3,200 ≈ **512만 번**. 그것이 835초의 정체였다.

**순서만의 문제도 아니었다.** 운영에서도 대형 조직 소속 직원 한 명을 비활성화하면 그 조직
전원을 읽고, <b>그동안 전역 락을 쥐었다.</b> 조직이 클수록 락 보유 시간이 길어지고 503 이
늘었다 — S3 의 실측(`{200=71, 503=129}`)이 그 모양이었다.

픽스처 최대 조직을 500명 → 1,600명으로 키우면서 드러났다. 500명에서는 눈에 안 띄었다.

**고쳤다 (2026-09-10).** 위 진단(낭비가 조직 크기에 비례해서 났다는 것)은 맞았다. 그런데
그 다음에 이 절이 적어 뒀던 예측은 틀렸다: *"고치려면 `active` 만 담은 투영을 따로 두거나
멤버 목록을 캐시해야 하고, 그건 별도 설계다."* **투영도 캐시도 필요 없었다.** `upsertUser`
가 델타를 내려고 만드는 before/after 그림에서, 조직의 멤버 목록을 바뀐 사람 한 명으로
좁히기만 하면 됐다 — 그 아래 `TupleMapper` → `mentioning(focus)` 필터가 어차피 동료의
튜플을 전부 버리고 있었으므로, 그림을 좁혀도 결과는 그대로다. 설계와 "왜 결과가 같은가"의
증명은 `docs/superpowers/specs/2026-09-10-single-user-snapshot-design.md` §4.2·§4.3.

실측: 조직 먼저(S1) **835.4초 → 57.9초 (14.4배)**. 직원 먼저는 **46.5 → 47.9초로
그대로다** — 그 순서에서는 직원이 도착하는 시점에 애초에 그림이 비어 있었으니 좁힐 게
없었다(개선 아님, 회차 잡음). S3(동시 16스레드 × 200건)의 503 은 `{200=71, 503=129}` →
**`{200=200}`** 로 전부 사라졌다 — 다만 이것은 관측이다. 락 보유 시간이 줄어든 것은
사실이지만, 그것이 503 소멸의 유일한 원인이라는 것까지는 이 측정이 증명하지 않는다
(설계 §5.7).

**`removeUser` 는 그림은 좁혔지만 조직 읽기는 남았다(설계 §4.4, 제목 그대로 "그림만
좁힌다").** 이 경로도 before 그림은 그 직원 한 명으로 좁혀져, 동료를 읽던 ~3,200회의
`findUser` 왕복이 사라졌다(`IncrementalSyncReadScopeTest.삭제에_동료를_읽지_않는다` 가
고정). 남는 것은 **조직 파티션 읽기**(`affectedGroupsOf` → `findGroup`)다 — 그림이 아니라
**커밋**(`reconcileRemovedMember` → `saveGroup`)이 최종 멤버 목록 전체를 요구하기 때문이다.
대형 조직 소속 직원을 **퇴사** 처리할 때는 이 조직 읽기가 그대로 남는다 — 온전한 승리가
아니라 정직한 경계다.

> 그림과 커밋이 요구하는 것을 섞어서 "그림을 좁힐 수 없다" 로 읽으면 안 된다 — `groups`
> (커밋용 전체 목록)와 `without`(그림이 아니라 커밋 재료)을 좁히면 §4.1 이 경고하는
> 1,599명 멤버 줄 전체 삭제로 이어진다. 좁혀지는 것은 diff 재료(before/after 그림)뿐이고,
> 커밋에 넘기는 `groups`/`without` 은 항상 전체 목록이어야 한다.

**그래서 시나리오는 최초 싱크를 한 번만 만들고 그 위에 순차로 쌓는다.** 시나리오마다 처음부터
채우면 SCIM 쪽만 19 × 47초 = 15분이다. 이어 붙이면 최초 47초 + 검증 2초 × 19 ≈ 1분 25초다.
실제 운영도 최초 싱크는 한 번뿐이므로, 이어 붙이는 쪽이 더 실제에 가깝기도 하다.

`ScimScaleSyncCostTest` / `LdapScaleSyncCostTest` 가 이 수치를 계속 재고, 동시에 두 커넥터가
**같은 조직도에서 같은 검증을 통과하는지**를 확인한다.

## 2. 픽스처 — 6,124명 / 352개 조직

**부문마다 깊이가 다르다.** 균일 깊이면 롤업 체인이 전부 같은 길이라 짧은 체인이 제대로
끝나는지를 검증하지 못한다.

```
L1 회사                      1개   직속    8명
L2 부문                      5개   직속 각 10명 =    50

A. 개발부문      L6까지
   L3 본부                   4개   직속 각  8명 =    32
   L4 실                    12개   직속 각  6명 =    72
   L5 팀                    40개   직속 각 12명 =   480
   L6 파트                  80개   직속 각  8명 =   640

B. 제조부문      L6까지, 넓음
   L3 본부                   3개   직속 각  5명 =    15
   L4 실                     9개   직속 각  5명 =    45
   L5 팀                    30개   직속 각 20명 =   600
   L6 파트                  90개   직속 각 18명 = 1,620

C. 사업부문      L5까지
   L3 본부                   3개   직속 각  8명 =    24
   L4 실                    10개   직속 각  7명 =    70
   L5 팀                    35개   직속 각 14명 =   490

D. 신사업부문    L4까지
   L3 본부                   2개   직속 각  6명 =    12
   L4 팀                    12개   직속 각 18명 =   216

E. 경영지원부문  L3까지
   L3 팀                    10개   직속 각 15명 =   150

제1공장          L2 직속      1개   직속  1,600명
빈 조직          L2 직속      5개   직속      0명
                ────                        ─────
조직 352개                                  6,124명
```

> 이 표의 숫자는 손으로 센 것이 아니라 `OrgChartFixture` 가 실제로 만드는 값이다.
> `OrgChartFixtureTest` 가 형상을, `LdifRendererTest`/`ScimRequestRendererTest` 가
> 그 조직도의 왕복을 검증한다. 표와 코드가 갈라지면 테스트가 먼저 깨진다.

**제1공장은 하위 조직 없이 직속만 1,600명이다.** 공장·콜센터가 현실의 이 모양이고,
`member` 속성 하나에 값이 몰려 **AD 범위 검색**을 밟는 자리다. 모두가 멤버인 "전 임직원"
같은 평평한 명단은 이 픽스처에 없다 — 그것은 수천 명을 겸직으로 만들어 랜드마크의 "소속이
하나" 전제를 흔든다. AD 범위 검색은 두 모양 다 때리므로 결함 재현에는 이것으로 충분하다.

**모든 중간 조직이 직속 직원과 하위 조직을 동시에 갖는다.** L4 실에 직속 6명 + 하위 팀 3개가
같이 있으면 그 조직의 `member` 에 `direct_member` 와 자식 롤업이 둘 다 기여한다 — 한쪽만
있는 조직에선 나오지 않는 경우다.

**이상치**

| | 노리는 것 |
|---|---|
| 제1공장 **1,600명** 직속 | BatchCheck 32청크 (상한 50). 그리고 **AD 범위 검색**(한계선 1,000/1,500)을 넘긴다 |
| 겸직 166명 — 깊이가 다른 두 부문에 걸침 | 다중 경로, 후보 확대 |
| 빈 조직 5개 (L2 직속) | 빈 델타 경로 |

**튜플: `direct_member` 6,290 + `child` 351 = 6,641**

`direct_member` 는 직원 6,124 + 겸직 166. `child` 는 조직 352 − 루트 1.

## 3. LDAP 시나리오

**구현 상태:** L1~L16 구현 완료. L17 은 단위 테스트 중복이라 쓰지 않기로 했다(아래 참조).
문서에 없던 두 가지를 더했다 — admin 조회와 DIT 전략.

| 시나리오 | 테스트 클래스 |
|---|---|
| L1~L11, L16 | `LdapScaleScenarioTest` — 하나의 컨텍스트에서 순차로 이어진다 |
| L12, L13 | `LdapDeletionGuardScaleTest` — 삭제 가드 경계 양쪽 |
| L14 | `LdapPagingScaleTest` — 서버측 상한 + 페이징 해제 |
| L15 | `LdapInterruptedSyncScaleTest` — 상태 저장 직전 중단과 수렴 |
| **A. admin 조회** | `AdminQueryScaleTest` — 운영자가 보는 화면 |
| **D. DIT 전략** | `DitScaleSyncTest` — 계층을 dn 경로로 표현한 디렉터리 |

### A. admin 조회 — 하네스가 못 보는 자리

하네스 ①은 `state.loadAll()` 로 DynamoDB 를 직접 읽는다. **그것과 admin 조회가 같은 답을
주는가는 다른 질문이다** — 사이에 커서 페이징, 상위 계층 조립, 디버깅용 Check 컬럼이 끼어
있고 전부 규모에 민감하다. 1,600명 조직을 100개씩 끊어 읽을 때 한 명이 두 페이지에 걸치거나
경계에서 빠지는 결함은 20명짜리 테스트로는 절대 안 보인다.

보는 것: 대형조직 1,600명 커서 완주(중복·누락 0) / 표시명 접두사로 6,124명 전원 커서 완주 /
Check 컬럼이 전부 true / 가장 깊은 직원의 경로가 조상 체인과 일치 / 겸직 직원의 직속 경로가
둘 / 조직 상세의 계층 / 없는 것 404.

### D. DIT 전략 — 같은 조직도, 다른 형식

매핑 전략이 둘인데 규모에서는 `groupOfNames` 만 돌고 있었다. 두 전략은 <b>전혀 다른 방식으로
읽어 같은 스냅샷을 만들기로</b> 돼 있으므로, 한쪽만 규모에서 확인하면 다른 쪽은 6단 깊이
5,000명에서 dn 경로 되짚기가 맞는지 아무도 모르는 채가 된다.

`DitLdifRenderer` 가 같은 `OrgChart` 를 ou 트리로 렌더링하고, `strategy: dit` 으로 읽어
**같은 하네스**로 잰다. 다른 잣대로 재면 비교가 성립하지 않는다.

> **겸직은 빠진다.** DIT 은 직원 엔트리를 ou 하나 아래에만 놓을 수 있어 형식 자체가 겸직을
> 표현하지 못한다. 렌더러는 겸직이 남은 조직도를 받으면 조용히 한쪽을 버리는 대신 즉시
> 깨진다 — 그렇게 버리면 검증이 형식의 한계를 구현의 결함으로 보고한다. 두 형식이 담을 수
> 있는 범위가 다르다는 것 자체가 결과다.

**모델:** pull 기반, 하루 1회 전체 재계산. 기준선은 **스냅샷**(우리가 썼다고 기록한 장부),
목표는 LDAP 읽기 결과다.

**시나리오 형식:** LDIF 를 바꾸고 → `POST /admin/sync/full` → §1 검증 하네스.

각 시나리오는 **직전 시나리오의 결과 위에서 이어진다** — 실제 운영이 그렇기 때문이다.

### L12. 삭제 가드 발동

LDAP 필터를 망가뜨려 70%만 반환하게 한다.

```
삭제 대상 1,992 / 기준선 6,641 = 29.995%  → 통과   (ratio <= 0.3)
삭제 대상 1,993 / 기준선 6,641 = 30.011%  → ABORTED
```

| 검증 | |
|---|---|
| 이력 | `ABORTED`, 사유 메시지 |
| **OpenFGA** | **아무것도 안 지워짐** |
| **DynamoDB** | **상태도 안 바뀜** |
| 다음 회차 | 필터 복구 후 정상 동기화되는가 |

**경계값을 둘 다 돌린다.** 가드는 `ratio <= thresholdRatio` 로 판정하므로 정확히 30%는
통과해야 하는데, 기준선 6,641 에서 정확히 30%가 되는 정수 삭제 건수는 없다. 그래서 30%를
사이에 두고 붙어 있는 두 값으로 경계를 집는다 — 한 건 차이로 판정이 갈리는 것까지 본다.

### L17. 정규화 충돌 — 같은 코드로 뭉개지는 두 조직

**규모 E2E 로 쓰지 않기로 했다.** 세 검증이 모두 단위 테스트에 이미 있다 —
`GroupOfNamesDuplicateIdTest`(직원 아이디 충돌: 하나만 생존, 경고에 두 dn, 생존한 쪽이
경고가 "유지" 라고 말한 dn)와 `DitStrategyDuplicateCodeTest`(조직코드 충돌).

충돌 판정은 `DuplicateIdGuard` 한 곳에서 두 엔트리만 보고 내려지므로 **디렉터리 크기와
무관하다.** 5,000명 판을 다시 깔아도 새로 얻는 정보가 없고, 통과하는 E2E 한 건이 늘면
"이것도 검증하고 있다" 는 착시만 커진다.

**다시 열어야 할 때:** 충돌 판정이 전역 정보(예: 전체 엔트리를 훑어 정하는 우선순위)에
의존하도록 바뀌면 규모가 변수가 된다. 그때 이 자리로 돌아온다.

## 4. SCIM 시나리오

**구현 상태:** S1~S19 <b>전부 구현 완료.</b>

| 시나리오 | 테스트 클래스 |
|---|---|
| S2~S16 | `ScimScaleScenarioTest` — 최초 싱크 한 번 위에 순차로 쌓는다 |
| S1 | `ScimProvisioningOrderScaleTest` — 조직 먼저 순서, 늦게 온 직원 |
| S17, S18, S19, S20 | `ScimLimitsAndRecoveryScaleTest` — 한계·아카이빙·재적재·순서 |
| S18-b | `ScimRebuildLockScaleTest` — 재적재가 락을 쥔 동안 |

#### S18-b. 재적재가 락을 쥔 동안 (문서에 없던 것)

S18 은 재적재의 <b>결과</b>를 봤다. 이것은 그 <b>도중</b>을 본다 — 리스가 유지되는가,
그동안 들어오는 SCIM 쓰기가 어떻게 거절되는가.

**리스 TTL 을 2초로 줄인다.** 기본값 30초로는 재적재가 그보다 빨리 끝나 하트비트가 한 번도
필요하지 않다 — 갱신이 통째로 망가져 있어도 테스트가 통과한다. 실측에서 재적재가 2.8초
걸렸으므로 갱신이 실제로 일했다.

실측: 재적재 2.8초 / 그동안 쓰기 5건 시도 → `{200=1, 503=4}`. 503 이외의 거절은 없다.

#### S20. push 순서 뒤집힘 (문서에 없던 것)

`add` → `remove` 를 IdP 가 의도했는데 `add` 가 재시도로 밀려 `remove` 뒤에 도착하면,
최종 상태가 <b>의도와 반대</b>가 된다. 그리고 <b>하네스가 그것을 못 잡는다</b> — 두 저장소가
서로 일치하기 때문이다. S17 처럼 통과 케이스로 고정한다.

근거와 완화 수단은 동시성 설계 §1.5 에 있다.

**모든 단계가 두 경로로 확인된다.** 하네스는 `RelationTupleChecker` 포트를 타고, `OpenFgaProbe`
는 OpenFGA SDK 를 그대로 쓴다. 어댑터에 결함이 있으면 하네스는 그 결함에 <b>같이 속으므로</b>,
같은 사실을 서로 다른 경로로 물어야 갈림을 볼 수 있다. LDAP 시나리오도 같다.

**모델:** push 기반, 증분. 전역 락이 쓰기를 직렬화하고, 기준선은 **OpenFGA BatchCheck** 다.

**시나리오 형식:** SCIM 요청을 보내고 → 응답 검증 → §1 검증 하네스.

| 음성 검증 | 잔여 튜플 없음 |

`PUT /Users/kim` 에서 `displayName` 만 다르게.

| 검증 | **OpenFGA 델타 0건** |

#### S9. userName 중복 거부

이미 있는 `userName` 으로 다른 `id` 를 POST.

| 검증 | 409 `uniqueness`. **상태·OpenFGA 변화 없음** |

### 4.3 조직 변경

#### S10. 조직 멤버 전체 교체 (PUT)

L5 팀의 멤버 12명 중 4명 빼고 3명 새로 넣는다.

| 검증 | |
|---|---|
| DynamoDB | 최종 멤버 11명 |
| OpenFGA | `dm` 4개 삭제 + 3개 추가. **나머지 8개는 안 건드림** |
| 델타 | 정확히 7건 |

**요청에 "빠진 4명" 이 안 적혀 있다** — 이전 멤버 목록을 읽어 계산하는 경로다(설계 §5.5).

#### S11. PATCH — add / remove / replace

세 연산이 서로 다르게 동작하므로 각각 본다.

| 연산 | 기대 |
|---|---|
| `add members[kim]` | 기존 멤버 유지 + kim 추가. 튜플 1개 증가 |
| `remove members[value eq "kim"]` | **필터가 있으면 kim 만** 제거. 튜플 1개 감소 |
| `remove` (필터 없음) | **멤버 전체 제거** — 그 조직의 `dm` 이 전부 사라진다 |
| `replace` | 목록 통째 교체 |

**필터 없는 `remove` 가 전체 삭제라는 것**을 명시적으로 확인한다. 12명짜리 팀에 걸면
튜플 12개가 한 번에 사라진다.

> `members` 필터는 `remove` 에만 지원된다 — `add`/`replace` 에 필터를 주면 거부되는지도 본다.

#### S12. 비활성 직원을 조직에 추가

`active: false` 인 직원을 조직 멤버로 넣는다.

| 검증 | |
|---|---|
| **DynamoDB** | **멤버십은 생김** |
| **OpenFGA** | **튜플은 안 생김** |

**"멤버지만 권한 없음" 상태를 정확히 표현하는지.** 이 상태가 §5.1 후보 집합의 존재 이유다.

#### S13. 조직 계층 변경

L5 팀을 다른 L4 실의 멤버로 옮긴다 (부모 쪽 PATCH 두 번: 옛 부모에서 remove, 새 부모에 add).

| 검증 | |
|---|---|
| OpenFGA | `child` 엣지 이동 |
| **롤업** | 그 팀 직원 전원의 권한 범위가 **통째로 바뀜** |
| `dm` | 변화 없음 |

#### S14. 조직 삭제

L5 팀 삭제 (직원 12명 소속, 상위 조직 있음).

| 검증 | |
|---|---|
| OpenFGA | 그 팀의 `dm` 12개 + 상위로의 `child` 1개 삭제 |
| 직원 레코드 | **유지** — 조직이 없어진 것이지 사람이 나간 게 아님 |
| 롤업 | 그 직원들이 어느 조직에도 `member` 아님 |

#### S15. 대형 조직 PUT — 1,600명

제1공장 의 멤버를 1,600명 → 1,580명으로 교체.

| 검증 | |
|---|---|
| 정합성 | 20명 삭제, 나머지 유지 |
| **측정** | **BatchCheck 32청크의 순차 왕복 시간, 락 보유 시간** |

**락을 쥔 채 BatchCheck 를 도는 구간이 얼마나 긴지** 재는 자리다. §4.3 과 짝이다.

#### S16. 순환 조직 참조

L4 실을 그 손자의 멤버로 넣는다.

| 검증 | |
|---|---|
| 응답 | 성공 |
| 로그 | 순환 경고 |
| OpenFGA | 순환을 닫는 간선만 빠짐 |

### 4.4 복구·한계

#### S17. 멤버십 없는 고아 튜플 — 잡히지 않음을 못박는다

OpenFGA 에 `dm(ghost, DEV001)` 을 직접 심는다. DynamoDB 에 `ghost` 는 없다.

| 검증 | |
|---|---|
| 어떤 SCIM 쓰기를 해도 | **그대로 남는다** |
| 아카이빙 후에도 | **그대로 남는다** |
| `mode=tuples` 재적재 후 | **사라진다** |

**설계 §5.4 의 한계를 명시적으로 고정한다.** 이 단언이 `false` 가 되면 한계가 해소된 것이니
문서를 고쳐야 한다.

#### S18. 재적재 `mode=tuples`

6,641 튜플 전체를 재적재한다.

| 검증 | |
|---|---|
| 소요 | 몇 분. **하트비트가 리스를 유지하는가** |
| 그동안 | SCIM 쓰기가 **503** |
| 완료 후 | 상태와 OpenFGA 완전 일치, 쓰기 재개 |

**중간에 인스턴스를 죽여** 리스 상실 → `FAILED` 기록 → 재실행 복구까지 확인한다.

#### S19. 아카이빙 at 5,000

일일 아카이빙을 돌린다.

| 검증 | |
|---|---|
| 스냅샷 | **관찰한 실제 튜플**이 저장되는가 (의도한 것이 아니라) |
| S17 의 고아 튜플 | 후보에 없으므로 **스냅샷에도 없음** |
| **측정** | `loadAll` + BatchCheck 133청크 소요 |

어긋남을 심어두고(예: 튜플 하나 직접 삭제) **어긋남 로그가 남는지**도 본다.

## 4.5 SCIM 실측 (2026-09-07, 로컬 macOS)

자동화 테스트와 별개로, 실제 앱을 독립 프로세스로 띄우고 <b>IdP 역할로 밖에서</b> 요청을
쐈다. LDAP 은 원천 디렉터리를 띄우면 앱이 알아서 읽어 가지만 SCIM 은 받는 쪽이라, 실측하려면
쏘는 쪽이 따로 있어야 한다 — `generateScimSeed` 가 요청 시퀀스를 NDJSON 으로 떨구고
`docker/scim/replay.py` 가 순차로 보낸다.

```bash
./gradlew :connector-scim:generateScimSeed
docker compose up -d openfga dynamodb-local
./gradlew :app-scim:bootRun
python3 docker/scim/replay.py
```

### 결과

> **이 절의 수치는 픽스처를 키우기 전(직원 5,024 / 최대 조직 500명)에 잰 것이다.**
> `bootRun` + curl 로 손으로 잰 회차라 픽스처 변경 후 다시 돌리지 않았다. 자동화 측정
> (위의 실측 비용 표)은 새 픽스처 기준으로 갱신돼 있다.

| | |
|---|---|
| 최초 싱크 5,376건 | **48.0초** (건당 8.9ms), 실패 0건 |
| 직원 상세 조회 (겸직, 두 갈래 경로) | 23ms |
| 500명 조직 멤버 100건 | 61ms |
| JVM 힙 | 138MB |

순차 적재 중 락 대기는 건당 평균 1.1ms, 최대 25.9ms 였다 (`scim_lock_wait_seconds`).

### 동시 쓰기 실측 — 설계의 503 이 실제로 성립한다

동시 32스레드로 500건을 쐈다.

```
200: 216건
503: 284건
500:   0건        ← 여기가 핵심이다
scim_lock_contended_total      334
scim_lock_wait_seconds_max     3.15초   ← 설계한 3초 획득 타임아웃
```

**500 이 하나도 없다.** IdP 는 503 을 재시도 신호로 보므로 프로비저닝이 유실되지 않는다.
500 이나 400 으로 뭉갰다면 IdP 가 영구 실패로 판단해 포기하거나 무한히 재시도했을 것이다
(설계 §4.4). 최대 대기가 3.15초로 설계값과 맞는 것도 여기서 확인됐다.

`ScimScaleScenarioTest` 의 S3 가 이 동작을 자동화로 고정한다 — 이미 활성인 직원에게
`active:true` 를 보내 <b>어느 요청이 성공하든 최종 상태가 안 바뀌게</b> 해 두고, 응답이
200/503 뿐인지만 본다.

### 이 과정에서 확인한 것 하나

`/actuator/prometheus` 가 테스트 컨텍스트에서 404 였다. 제품 결함이 아니라 <b>Spring Boot 가
테스트에서 메트릭 익스포트를 기본으로 끄기</b> 때문이고, 실제 앱은 200 을 준다.
`@AutoConfigureObservability` 를 붙여 테스트에서도 메트릭을 보게 했다 — 안 그러면 메트릭
회귀를 테스트로 못 잡는다.

## 5. 실행 구성

### 5.1 스위트 분리

| | 내용 | 예상 |
|---|---|---|
| **빠른** | L2~L17, S4~S17 (증분 변경) | 각 수초 |
| **느린** | L1, S1, S2, S18, S19 (전량) | LDAP 30~60초 / SCIM **2~5분** |

SCIM 대량(S1·S2)은 5,347건이 전부 락 직렬이라 길다. 일반 스위트에서는 **200건 부분집합**으로
순서·정합성만 보고, 전량은 느린 스위트로 뺀다.

### 5.2 시간 의존 결함 — 설정으로 재현

**데이터를 키워도 로컬에선 안 난다.** 로컬 OpenFGA 응답이 밀리초라 30초 TTL 근처에 못 간다.

| | 재현 방법 |
|---|---|
| **쓰기 경로 리스 만료** | `dynamodb.lock-ttl: 200ms` 프로파일 |
| 재적재 리스 상실 | 같은 프로파일 + 하트비트 주기를 TTL 보다 길게 |

> **여기서 확인할 구멍:** 쓰기 경로는 락을 쥔 채 BatchCheck 를 도는데 **그 사이 리스를
> 갱신하지 않는다.** `renew()` 는 `writer.apply` 직전 한 번뿐이다. 재적재는 하트비트가 있는데
> 쓰기 경로엔 없다. 대형 조직 PUT 이 TTL 을 넘기면 몇 번을 재시도해도 같은 지점에서 실패한다.

### 5.3 픽스처 생성

| | |
|---|---|
| **LDAP** | LDIF 생성기. UnboundID 인메모리가 5,000 엔트리를 감당하는지 먼저 확인 — 안 되면 docker-compose 의 OpenLDAP |
| **SCIM** | 요청 시퀀스 생성기. 조직 먼저 / 직원 먼저 두 순서 모두 |

두 앱이 서로 다른 테이블·store 를 쓰므로 독립 실행된다.

### 5.4 교차 검증 — 선택

같은 조직도를 양쪽에 넣고 **결과 튜플 집합이 동일한지** 대조한다. 두 커넥터가 같은 진실에
도달하는지 보는 것이며, 어느 한쪽의 매핑 버그를 드러낸다.

시나리오마다 아래를 기록해야 의미가 있다.

```

DynamoDB 읽기·쓰기 건수
```
